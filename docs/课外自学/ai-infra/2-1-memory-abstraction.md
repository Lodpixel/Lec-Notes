## 开场：主题与目标

大家好啊。今天我们这个主题叫 Memory Abstraction & Hierarchy，但其实这个名字可能并不是特别准确——实际上大概就是：怎样优化一个没有用到 tensor 库的 kernel。

要优化一个 kernel，我们首先就要想：这个 kernel 最快能优化到多少呢？

## 一、Roofline 模型与算存比（arithmetic intensity）

先看 NVIDIA GPU 的结构：这些绿色的东西就是 SM，它的计算单元；旁边就是 HBM，也就是它的内存。一个 kernel 的大概流程可以概括成：从 HBM 取一些数据到 SM 里面，让 SM 进行一些计算，然后再写回到 HBM。

所以这个过程涉及两件事情：一是内存的移动，二是计算。一个 kernel 的最高性能，由这两件事中比较慢的那一个来决定。这就是 roofline model：

- 从内存的角度看：最高性能 = 内存带宽 × 每移动 1 字节内存你要进行的计算次数。这里的最高性能是用 FLOPs 来衡量的。如果被内存限制住，性能就是带宽乘上算存比。
- 从计算的角度看：计算本身也有一个速度上限。
- 最终性能取这两者中比较小的那一个。

画成图的话：左边是一条斜线，右边在内存带宽打满之后就是平的，中间这个点叫 ridge point（拐点），它对应的就是计算性能与内存带宽的比值。

这里有一些典型 GPU 的峰值算力和带宽数据。可以看到 CUDA Core 和 Tensor Core 的峰值算力差别很大。如果大家不知道 Tensor Core 是什么：因为后来很多高性能计算的 workload 都是矩阵乘，所以 NVIDIA 在 Volta 架构之后加入了 Tensor Core，它是一个脉动阵列（systolic array），专门用来算矩阵乘。

所以，如果只看 CUDA Core，一般算存比在 10～20 之间就可以打满内存带宽了；如果要用到 Tensor Core，算存比就要高很多。

### 典型例子的算存比

**1. SAXPY（Y = a·X + Y）**

S 表示 single precision，也就是 FP32。它一共的计算量：每个元素要做一次乘法、一次加法，所以是 $2N$。它一共要搬运的内存：读 X、读 Y，再把 Y 写回去，每个元素都是 FP32、4 字节，所以一共是 $12N$ 字节。算存比就是

$$\frac{2N}{12N} = \frac{1}{6}$$

远小于 1，所以这是一个非常 memory-bound 的 kernel。

**2. 其他 O(N) 的规约/归一化类 kernel（如 softmax 等）**

字幕里这里记为 ZERNOM，听辨不清，结合"做一个 reduce、再除以一个东西"的上下文，应该是指 LayerNorm 一类的规约后归一化的 kernel。这类 kernel 的计算量是 $O(N)$，内存搬运也是 $O(N)$（读一遍写一遍），所以算存比一般也是个位数，同样是 memory-bound 的 kernel。

**3. GEMM（$M\times K$ 乘 $K\times N$）**

计算量：输出矩阵里的每个元素相当于左边一行与右边一列的点乘，长度是 K；一共有 $M\times N$ 个元素，点乘是一次乘法加一次加法，所以总计算量是 $2MNK$。

内存搬运：A 要读 $MK$，B 要读 $KN$，C 要写 $MN$，所以一共是

$$MK + KN + MN$$

除一下就会发现：分子是三个数的乘积，分母是两个数乘积的量级，所以算存比是一个非常大的数字。在 M、N、K 都比较大的情况下，GEMM 一般是一个 compute-bound 的 kernel。

**4. 推理 decode（KV cache）**

比如在 Transformer 里，如果从头开始、序列全都一样，我们可以把之前算出来的 K 和 V 缓存下来；之后做 decode 的时候，query 的长度只有 1，就只需要算一个矩阵向量乘。这种情况下计算量相当于是做 N 个点乘，大约是 $2MK$（字幕里写的 MMN 可能不太对，但量级就是 2MK 差不多）。内存搬运是读输入和权重、写输出。这样除一下，算存比大概在 1 左右，所以它也是一个 memory-bound 的 kernel。

所以现在推理优化有一些手段，比如 speculative decoding：先拿一个小模型生成一些草稿，然后大模型只需要去验证这些草稿。这样做的目的，就是在验证草稿的时候相当于一次推理了好多个 token，相当于把 M（batch）的大小增大，提高算存比，在 roofline model 上往右移，从而更好地利用 GPU 的性能。

## 二、为什么简单的 kernel 也打不满内存带宽

roofline model 讲的只是一个 kernel 的性能上限，但实际上我们大部分时候都达不到这个上限。那么怎么让一个 kernel 尽量用满内存带宽呢？

以最简单的 SAXPY 为例：它的内存访问完全是连续的，几乎没有任何 warp divergence（没有分支），也没有同步，可以达到 100% occupancy，并且没有任何数据依赖。但实际上很多时候这样的 kernel 并不能用完内存带宽。

下面这张图是在三张不同卡上的实测性能：

- 同一个 kernel 用不同的数据类型，性能会有比较大的差距。
- 在 A100 上，用 FP32 已经几乎可以达到最优性能（最右边的 STREAM 表表示这张卡的大致带宽上限）。
- 但在 B200 上，FP32 或 FP64 都离最优性能还有比较大的差距。

### 为什么：Little's Law

先用一个扶梯做类比：假设每一个台阶可以站一个人，扶梯每两秒到达一个台阶，那么带宽就是每秒 0.5 个人。如果一共有 20 个台阶，一个人从最上面下到最下面，延迟就是 40 秒。

但如果台阶上只有一个人，第一个人上去之后要过 40 秒才会下来，扶梯大部分时候其实是空的，实际只能达到"40 秒一个人"，达不到每秒 0.5 个人的带宽。要用满这个带宽，需要扶梯上同时有带宽 × 延迟 = 20 个人。这就是排队论里的 Little's Law。

把这个理论用到 GPU 上：如果想要打满内存带宽，就需要同时有"带宽 × 延迟"这么多字节 in-flight，也就是同时待在请求队列里。

左边那张表列了几个常见 GPU 的内存带宽和延迟数据（延迟数据不太准确，可以当成粗略估计）。用带宽 × 延迟算出同一时刻需要的 in-flight 字节数，除以 SM 的数量，再除以每个 SM 的线程数（假设 occupancy 是 100%、每个 SM 上 warp 数是最大的），就能算出每个线程需要发出多少个字节的请求才能把内存带宽打满。

A100 上每线程只需要 4.7 字节。因为 SAXPY 要读两个数组：如果用 FP8，每个元素 1 字节，读两个数组就是 2 字节，大约是 4.7 的一半——实测性能确实只有峰值的一半左右；如果换成 FP16，in-flight 字节就会翻倍（约 4 字节），实际达到的内存带宽也基本翻倍。右边那张图呈现的就是这个规律。

## 三、提高 in-flight 数量的方法

要提高同时在执行的指令数量，一般有两种方法：

- 一种是指令级并行（ILP）：同时发射更多相互无关的指令；
- 另一种是线程级并行（TLP）：让更多线程同时执行。

这对提高内存带宽是同样的道理。每个 SM 的 in-flight 字节数就是：

$$\text{warp 数量} \times 32\ (\text{每 warp 线程数}) \times \text{每条指令取的字节数} \times \text{每个 thread 发出的指令数}$$

其中"每个 thread 发出的指令数"就是 MLP（memory-level parallelism）。所以提高这三项中的任何一项，都可以提高 in-flight 字节数。下面依次解释这三项。

### 3.1 循环展开（unrolling，提高每线程发射的指令数）

例子：从数组 A、B 里各读一个元素相乘，加上 C 里原本的数字，再存回 C。所以每个 cycle 首先需要 load A、load B、load C。假设 load/store 指令的延迟是 1000 个 cycle，每个周期能发射一条 load 或 store 指令。

未展开时：这个 warp 前三个 cycle 每个周期都会发射一条 LDG（load global，从 global memory 加载）指令。之后因为算术操作依赖 load 的结果，warp 会停住，等 1000 个 cycle、三个 load 全部返回之后，才能执行 FMA；再等 FMA 执行完成，发射 store 指令。总共需要约 1006 个 cycle。这里所有指令发射完就算结束了，不需要等它写回 global memory。

如果进行展开，写成 for 循环，index 由每个 block 的线程数乘上 grid 的 block 数（运行时确定）计算。这样有一个问题：即使加了 restrict（上节课解释过，restrict 是假设不同指针之间没有重叠），编译器仍然不能知道两次取的 index 是不是同一个。它虽然可以把第二次的 load A、load B 重排到 FMA 前面，但在 load C 的时候，因为它不知道 I1 和 I2 这两个下标是不是一样的，必须先把 C store 回去再 load C，不能把 load C 也重排到 FMA 的前面。结果前五个周期都在发射 load 指令，然后 FMA、store、load……虽然展开了，但总周期数也翻倍了，实际上并没有什么收益。

改进方法：把展开的下标改成编译器能确定的固定数字。这样编译器就知道 I1 和 I2 一定不一样、两者没有依赖，可以把 load C 也重排到前面，一次性把所有的 load 全都发射出去，等 load 完成之后再执行 FMA，之后再 store。虽然工作量翻倍了，但周期数基本不变，吞吐量就翻倍了。

为什么每个 thread 发出更多指令就能提高 in-flight 数量？因为指令发射出去之后，在中间等待结果返回（stall）的阶段，它们全都是 in-flight 的；每个周期能发射的指令越多，前面总共发射的指令数就越多，同时就有更多的数据在途。

### 3.2 提高 occupancy

这里是 H100 一个 SM 的内部结构图。一个 SM 内部有 4 个 sub-partition，每一个都有自己独立的算术单元、寄存器文件和 warp scheduler。

warp scheduler 的规则：每个 sub-partition 上最多驻留 16 个 warp；每个 cycle，scheduler 会从所有 ready 的 warp 里选一个来发射。ready 的意思是没有依赖、需要的数据都已经算出来了。

GPU 和 CPU 不同：CPU 上切换线程要做上下文切换，把一些东西存到内存里再读出来；GPU 上不需要，因为所有 warp 的寄存器都存在寄存器文件里，所以上下文"切换"不需要任何操作，每个周期都可以发射一个新的 warp。

这样看的话，提高 occupancy 和提高每个 thread 发射的指令数是同样的道理：都是让更多连续的周期都在发射 load 指令。

提高 occupancy 也有一些限制因素：

- 每个 SM 不能超过 64 个 warp（4×16）；
- 每个 warp 都要用一定的 shared memory 和一定数量的寄存器，所以最大的 warp 数量不能超过 min(SM 寄存器数量 / 每个 warp 用的寄存器数，SM shared memory 大小 / 每个 warp 用的 shared memory 大小)。

不过，occupancy 并不是越大越好。真正起作用的是 occupancy 乘上每个 warp 发射的指令数量；只要这个乘积足够大，即使 occupancy 很小，也仍然可以打满内存带宽。下面这张 A100 上的实测图显示，一条斜线上的带宽差不多是同样高的——实验证明了确实是乘积更重要，而不是一味提高 occupancy。

### 3.3 向量化访存（vectorized memory access）

第三个提高内存带宽的方法就是向量化访存。比如用 float4：把 4 个 float 打包成 128 位（16 字节），这样每条指令直接 load 128 位，而不是 32 位（4 字节），每条指令访问的数据量就是原来的 4 倍。

这三个就是提高内存带宽的方法。

## 四、访存合并（coalescing）与缓存层次

前面讲过，虽然 NVIDIA 的 GPU 编程模型是 SIMT，表面上你是在控制每一个 thread，但实际上调度的时候是 32 个线程作为一个 warp 在 SM 上调度。所以一个 SM 同时发出的 32 条 load 指令，并不是分别执行的，而是由 LSU（load-store unit）把它们合并，再把合并后的请求发给 L2，L2 再从 global memory 取数据。

L2 的访问以 sector 为单位，每个 sector 是 32 字节。L2 里一个 cache line 是 128 字节，但那是管理缓存（做缓存驱逐）的单位；实际读取时是以 sector 为单位的。比如一个请求可以要一整条 cache line 上的 4 个 sector，但实际读取时会在连续的周期里、每个周期只发出一个 sector。所以读写 L2 的单位是一个 sector；L2 再从 global memory 读取的单位字幕记为"两个三角形"，听辨不清（这个细节不是特别重要）。

既然缓存规律是这样，我们在写 kernel 的时候就应该做 coalescing：让一个 warp 发出的请求尽量落在连续的 sector 上，这样才能用满连续的 sector。

举例：

- 每个 thread 访问相邻的 4 字节，整个 warp 就访问连续的 4 个 sector，这很好；
- 即使 warp 的访问不是随 thread index 单调的、是交叉的，只要这 32 个线程整体访问的仍然是连续的 sector，性能也不会有任何区别；
- 如果访问连续但没有按 32 字节对齐，请求就需要取 5 个 sector，利用率变成 4/5；
- 如果所有线程取的都是同一个 sector 上的数据，也非常好，只需要取一个 sector，相当于做广播；
- 如果相邻线程取的数据离得非常远，分散到完全不同的 sector 上，那就非常坏：32 个线程各取一个不同的 sector，相当于需要 32 次访问，非常慢。

### 实际例子：AoS 与 SoA

经典的区别是 array of structures（结构体数组）和 structure of arrays（数组结构体）。

假设有一个结构体，里面有很多 float 字段。如果是结构体数组：每个结构体本身连续存放，数组就是不同结构体排在一起；同时相邻的 thread 访问不同结构体的同一个字段（比如都访问 u）时，内存里相邻结构体的 u 实际上隔得很远（中间隔了其他字段，本例中约 80 字节）。这样的话，一个 sector 里只有大约 4/32 的数据被用到，访问效率非常低。

如果是结构体数组（SoA）：结构体里装的是数组，每个数组内部连续。访问 u 时，相邻线程的 u 就是连续的；访问 y0 时，相邻线程的 y0 也是连续的。这样每个 sector 的数据全部都能用到。

实测也是这样：SoA 的效率比 AoS 高 8 倍。这就是用 coalescing 做优化的一个具体例子。

## 五、Reduce 的优化过程

最后简单讲一下 reduce 应该怎么优化。问题很简单：求一个数组的和。

**朴素实现：原子变量。** 最简单的方法是用一个原子变量，每个线程直接拿原子变量与从 global memory 读出的数相加。这样非常慢，内存带宽只有 1.4 GB/s（和正常情况差了几千倍）。

为什么会这么慢？因为 GPU 上做原子操作时，这个操作本身并不是在 SM 内部完成的：请求会发给 L2 slice，L2 slice 内部有自己的 ALU，由它自己在内部完成加法和修改。如果所有线程加的都是同一个原子变量，所有请求都会串行地发给同一个 L2 slice，在那里串行执行，所以非常慢。

**优化 1：shared memory + 树形 reduce。** 首先把输入数组 copy 到 shared memory 里，防止重复访问 global memory；然后每个 block 在内部做树形 reduce：先把相邻两个元素加起来，再把加完后的相邻两个结果加起来。这样比原子变量快 118 倍。

但有一个问题：右图圆圈里的数字（每次执行时的线程 id）并不连续。也就是说 warp 的 32 个线程里，每次是第 0、第 2、第 4 个……这样的线程在执行，一半线程被浪费了，之后的轮次用得越来越少、浪费更多。

**优化 2：让连续的线程操作。** 优化方法就是每次都由连续的 thread 来操作，减少总的 warp 数量。之前的写法是每个 thread 操作的位置固定；现在改成线程根据自己的 id 计算出要操作的位置 id，再判断这个位置是否在范围内。这样就是从低 id 开始连续的一些线程在操作，相比之前有 2 倍加速。

但这样又带来新问题：bank conflict。shared memory 分成很多 bank，以 4 字节为单位，连续 4 字节在相邻的 bank，但过了 128 字节就循环：128～132 字节和 0～4 字节是同一个 bank。warp 里的不同线程如果访问同一个 bank，就无法在一个周期内把数据同时给两个线程，对 bank 的请求会被串行化，这就是 bank conflict，所以我们要尽量避免同一个 warp 里的线程访问同一个 bank。

示意图：最左边是没有 bank conflict 的访问（每个 thread 访问连续的 4 字节，落在不同的 bank）；如果每个 thread 都隔 4 字节访问一个，那么第 0 个和第 16 个 thread 就会访问同一个 bank，产生 bank conflict，总访问时间乘以 2；如果所有线程访问的是同一个 bank 的同一数据，就没有问题，可以进行广播操作，单位时间内完成。

回到 reduce kernel：后面的轮次里，相邻 thread 实际上是隔了几个 4 字节在访问的，这就会导致 bank conflict。用 NCU（Nsight Compute）看的话，summary 会直接提示有严重的 bank conflict；如果想自己用指标算，可以用 wavefront 数量除以请求数量，这个比值高就说明 bank conflict 很严重。

**优化 3：让相邻线程访问相邻数据。** 改成每个 thread 加自己的 index 和 warp index 之后的下一个数据，这样每个 thread 访问的数据就是连续的，同时也能避免 bank conflict。速度从 308 GB/s 提升到 344 GB/s（图上写的 1.6× 是笔误），有一些微弱的提升。

但这时出现新问题：计算吞吐已经达到 62%，DRAM 吞吐只有 18%。reduce 本来应该是一个 memory-bound 的 kernel，现在却变成了 compute-bound，说明肯定有问题。

原因：block 数量是随数据长度变化的，而不是固定数量。block 数量特别多，同时 reduce 操作的数量与 block 数量成正比，所以我们做了非常多次不必要的 reduce 操作。

**优化 4：减少 block 数量，让每个 block 做更多操作。** 一开始讲过，算存比在 10～20 以下的时候打满带宽是"免费"的，所以可以让每个 thread 做更多的读取和加法操作，减少因为 reduce 引入的额外加法；如果是在 shared memory 内部操作，串行加法不会引入任何不必要的算术。这样整个指令数下降，从 0.78 ms 降到 0.25 ms，大约 3 倍提升。

**优化 5：warp shuffle。** 实际上 thread 之间有直接交换数据的路径，不需要经过 shared memory，可以直接在寄存器之间用 warp shuffle 交换。指令大概有几种：

- broadcast（shfl）：所有 thread 接收一个指定的 source 发来的数据；
- up / down：每个 thread 把自己的数据传给自己后面/前面固定 offset 的 thread（offset 固定）；
- xor：每个 thread 把自己的线程 id 与传入的 mask 取异或，接收异或结果那个 index 的线程的数据。

实现 warp 内 reduce 有两种常见写法：左边用 xor 实现；右边用 shuffle down，每次把 down 的 offset 减半（第一次 4，第二次 2，然后 1）。两种实现速度上差不多。

实测：用 warp shuffle 实现之后，速度跟之前没有统计学上显著的差别。看 NCU profile 的结果：这个 kernel 的 compute throughput 已经非常低了，但内存带宽只达到了一半——这就是一开始讲的 in-flight 字节不够多的原因。此时 kernel 已经完全变成 memory-bound，要做的就是提高它的 in-flight 字节数。

现在 occupancy 已经是 100%，展开数量也很难再增加了，能做的就是向量化访存：最后用 float4 来实现向量化访存，之后内存带宽基本占满，达到 A100 的上限。

## 六、总结

大概整个优化过程就是这样的。实际上我们会发现，即使给第五个版本——也就是用 warp shuffle 之前、已经使用了向量化访存的 kernel——我们实际上也能打满 A100 的带宽。所以这里的 warp shuffle 其实没有任何用处，就只是为了提一下我们可以进行这个操作。

今天主要讲了 memory hierarchy，以及如何利用这个硬件结构来做一些简单的 kernel 优化。因为准备的时间实在有点不充裕，可能讲得不是特别好，这里给大家道个歉。这就是今天的内容，谢谢大家。
