## 开场：目标与直觉

这边由我来给大家介绍一下：如何用刚才学到的 memory hierarchy 的知识，来优化一个 FP32 GEMM。

由于时间准备的原因，这节课里大部分后续的优化我都无法讲到，但我希望给大家建立起一个直觉——怎么用 memory hierarchy 的思维来解决问题。

## 一、为什么选 FP32 GEMM

先讲 GEMM 是什么。传统说法是 General Matrix Multiplication（通用矩阵乘法），算的就是两个矩阵相乘。我比较喜欢右边这张图：左边是 A，右上方是 B，相乘得到 A×B；每个输出元素对应它在 A 中向左找的那一行、在 B 中向上找的那一列，把 A 和 B 对应位置的元素乘积求和。这是深度学习和科学计算里非常常见的例子，所以非常值得做。

优化目标是什么？我们算的基本上都是浮点数的乘加。这里以 FP32 的乘加为例：把一次乘法、一次加法叫做一次 FMA，乘和加统一记为 1 个 FLOP（floating point operation）。我们的优化目标，就是在相同时间内算出最多的 FLOPs。

为什么选 FP32 GEMM：

- 它足够简单。
- 因为矩阵乘法实在太常见，现代专用加速器上为了优化各种 GEMM，都会引入类似 tensor core 的计算单元来专门特化乘法计算——不是让你用简单的浮点 ALU 手动把规律抽出来，而是硬件原生就有计算矩阵乘的能力。
- 但 FP32 这里大家一般不会特意去用 tensor core：在深度学习这类应用中，不一定每一处都要用 FP32 计算，输入数据可能是 16 位甚至更低位就够用了，所以一般不会期望 FP32 走 tensor core。
- 一张 GPU 上 FP32 的裸算力，基本上就是 CUDA core 能够提供的算力。所以它很适合我们从纯手动的角度出发去写计算。

## 二、最简单的并行实现

终于可以来看怎么进行这个计算了。矩阵乘法要算很多独立的输出元素：每个输出元素涉及读 A 的一行、B 的一列，把它们乘起来、做点乘、加起来。并行化本身，就是把计算数据拆到硬件上很多可以同时执行的单元上面。

具体怎么拆、拆到哪，要回顾之前提到的 SIMT 模型。CUDA 提供了一套编程抽象，从 grid 到 block 再到 thread：一堆 thread 组成一个 block，block 会共享 shared memory 之类的资源；blocks 之间又组成一个 grid。这个层次正好可以映射到我们的 GPU 上面。

虽然 CUDA 给每个层级的索引都提供了 3 个维度（可能是为了适配一些图形学的计算），但在这里，输出 C 是一个 M×N 矩阵，我们用两维就足够了：假如让一个 thread 负责一个输出元素（就是图中中间的那些小块），就可以用这两维的抽象把整个 GEMM 切分开。这是最简单的实现方式。

具体做法：先把 C 这个大矩阵整个切成一堆大的 tile。用 block index 让每个 CTA 索引到 C 的一个输出 tile；在这个输出 tile 内，block 里的每个 thread 负责一个小的元素，用二维的 threadIdx 索引到具体元素。

代码思路（右边就是把想法写进 CUDA 的方式）：

- 先用 block index 找到这个 block 第一个元素所在的位置。每一行的话，就是"它在第几块 × 每块负责多大"（图中这个位置画得稍微有点问题），再加上它在 block 内的偏移，就可以定位到一个输出元素。
- 每个 thread 在寄存器里维护一个累加器，直接去读 A 的一行、B 的一列，挨个读、挨个乘，累加到一起。
- 调用方法很简单：定义 block 的大小，比如这里随机选了 16；整个 grid 需要启动 $N/16$ 向上取整、$M/16$ 向上取整这么多个 block，用 `<<< >>>` 三个尖括号的语法启动。

## 三、朴素实现的问题：没有数据复用

观察一下刚才这个 GEMM 的问题。它看起来比较美好，因为理解非常简单——把一个编程模型映射到一堆 thread 上就行了。但是这些 thread 相互独立，没有做任何数据复用。

比如这里：位置上相邻的 4 个 thread 要算 C 的 4 个输出，它们用到的 A 的行和 B 的列是可以复用的——每两个 thread 会用到 A 的一行，所以实际上只需要两行 A 和两列 B。但朴素实现里，每个 thread 都自己读了一遍。

回顾一下 roofline 的概念。我们想要达到的理论算存比（FLOP/byte）是：

$$\text{AI} = \frac{2MNK}{4(MK + KN + MN)}$$

解释一下：上面是计算量——我们有 $M\times N$ 个输出，每个线程要算 $K$ 次乘加，每次乘加算 2 次操作，所以是 $2MNK$；底下是访问 A、B、C 三个矩阵的字节数（FP32 每个元素 4 字节）。如果都是方阵（$M=N=K$），这个值就是

$$\frac{2N^3}{4\times 3N^2} = \frac{N}{6}$$

也就是说，在算很大的 GEMM 时，计算相对于缓存来说非常多，数据被非常激进地复用。这就是我们想要的理想状态：compute-bound，受限于计算单元的能力，而不是受限于内存带宽。

但我们实际上看到的情况不太一样：这个朴素实现只做了 $K$ 次乘加，每个线程访问了 $2K$ 个输入和 1 个输出，最后整个东西变成了一个近似常数的算存比——因为这里复用非常少，几乎每个线程都要自己亲自去把外面所有数据读一遍。这显然很不理想。

## 四、Shared memory tile 版本：显式复用数据

如何去复用这些数据？GPU 体系结构给程序员提供的编程模型是：每个 block 会有一个 scratch pad 来复用数据，block 内的线程可以共享它、往里面写和读，这就是 shared memory。

在讲 shared memory 版本之前，需要提一下：熟悉其他体系结构的同学可能会想到 cache。也就是说，我们希望硬件自动捕获一些时间或空间上的局部性。但 GEMM 实在太规整了——即使开始会捕获一部分复用，我们也很容易提前知道哪些数据是可以复用的，不需要在运行时根据一些无法预测的规则去做这件事。所以不如把这块 scratch pad 拿过来给自己用，也就是把整个 local memory 层次的东西拿来当 shared memory，显式地组织 thread 之间的协作。

利用刚才说的 CTA/grid 层次：每个 CTA 内部共享一片 shared memory，它们一起组成了一个中间 tile（图中灰色那块），大小是 block_M × block_N。所有线程不用各自重复读自己对应的那一行一列，而是先把计算需要的所有行和列取出来、写进 shared memory，然后每个线程再从 shared memory 读自己需要的部分。shared memory 在内存层次里更贴近寄存器，所以延迟会小很多，也会减少很多到 global memory 的带宽。

具体写法（右边）：

- 用 `__shared__` 语法开两个 A 和 B 的 scratch pad。
- 对规约的 K 维度也进行切分（这里为了简单，都写成 tile 大小）。
- 循环主体里：先让每个 thread 分到一部分数据，加载到 A、B 的 scratch pad 中。这部分加载和后面的计算是相对独立的——只需要把这一片数据搬进来就行，不像之前每个线程都要做有重复的读取。
- 搬完之后要同步一次：因为在 warp scheduler 下，没有任何关于 shared memory 版本可见性的立即保证，所以必须加一个 barrier（`__syncthreads()`），等数据写完之后才能进行下一步计算。
- 之后算 FMA，和刚才一样，只是把读的位置换成 shared memory：累加器每次加上 shared memory 里对应的位置，遍历 K。
- 在循环末尾当然也要再同步一次。因为如果不 sync，跑得快的 warp 可能会进入下一次循环、提前 load 下一块 A 和 B；而这里只有一片 shared memory 空间，下一次数据可能会把还没被计算的那部分数据提前覆盖掉，导致问题。所以这里需要两个同步点。

通过这种方法复用数据，就可以继续优化 GEMM。

### 分析这个版本的算存比

这种情况下的算存比其实和大 GEMM 没什么太大区别，只是把外面的 M、N、K 换成了 block 级的 tile 大小。可以发现：如果 tile 取 32，可以得到约 8 FLOP/byte，这比刚才那个好很多，起到了非常多的复用；并且这个式子渐近意义上与 tile 大小成正比。所以取更大的 tile，理论上可以让数据被更好地复用，让算力成为瓶颈。

## 五、Coalescing：如何把数据搬进 shared memory

怎么让那些 thread 把数据合并地搬进 shared memory？这里用到刚才学的知识：不是 global 缓存的 coalescing 版本——一个 warp 最好访问的是能够打包起来的、连续的、对齐的一片地址。

比如左边：每个 thread 访问 4 字节（一个 float），整个 warp 访问的东西就是 128 字节对齐的、连续的 4 个 sector，这对把所有请求打包起来很有好处。

另一种情况：每个访问 8 字节，整个 warp 访问 8 个 sector，仍然是连续并且对齐的。

但如果我们设计的访问方式不好，比如下面这种情况：每个 thread 希望拿到一段连续的访问，但实际做法是每次访问一个 4 字节、却带有一个步长——thread 第一次搬第一个，第二次搬相邻的那个，对每个 thread 自己来说看起来挺近的——这种情况下硬件几乎无法 coalesce，因为我们要看的是同一个 warp 内所有 thread 一次发出的所有请求到底落在哪里。所以我们要避免这种情况，让访问产生最连续的请求。

### 主序与 thread 映射的约定

怎么知道哪些访问是连续的？如果不讲其他事情，可能会认为 warp 就是 32 个 thread；但 thread 有 threadIdx.x 和 threadIdx.y，它们是怎么打到同一个 warp 上去的呢？

这里很多时候遵循某种主序。比如 C 风格的数组一般是行主序：行是最外层那一维，列是连续的那一维。对 A[i][j]，变动 j 这个维度是连续的——比如第 2 行第 1 列和第 2 行第 2 列是挨着的；索引计算里 j 这一维的 stride 是 1，它就是连续变动的维度。

CUDA 对 thread 的规定是：thread 在映射到原始的线性化 index 时，threadIdx.x 是最连续的方向。所以我们要把这两个维度对齐：让 threadIdx.x 作为连续方向的索引，尽量让它做数组下标里"列"的那一位，这样写会产生更好的效果。

如果反过来，让每个 lane 对应一行、用 threadIdx.x 去索引行的方向，就会导致刚才说的无法 coalesce。

## 六、向量化访存（float4）

除了 coalescing，刚才还提到一个向量化。我们知道 in-flight bytes 是我们追求的目标：有尽可能多的字节在飞，就能让它们互相掩盖延迟。提高 in-flight 的方法之一，就是让每个 thread 负责向量化的一块区域：比如让每个 thread 负责一个 float4 的搬运。float4 就是把 4 个连续的 float 打包到一起。

这里用显式 float4 可能有个好处：有时候虽然你的写法让编译器很好向量化，但具体执行时编译器可能不知道你的一些对齐保证，无法自动做，所以这里可能需要手动打包成 float4。

右边就是一种可以打包成 float4 的做法：行的维度和刚才一样；在列方向——因为列是最连续的一维——四个一组去打包，这样每个 thread 负责的就是连续的 4 个 float。

## 七、NCU 分析：为什么还会有 stall

看一下这个版本的一些问题。虽然我们做了 shared memory tile，但所有东西并不是持续发射的。这里需要提一下 NCU 的 warp 分类：

- active warps：资源足够，可以驻留到一个 SM 上的 warp。不管它们状态如何，只要拥有执行上下文（分到了寄存器、shared memory 等对应资源），就被认为是 active。
- eligible：active，并且当前下一条指令可以发射。可以发射的意思是：没有数据依赖、没有在等任何其他数据的完成，而且对应的 pipe 也空出来能给我们用。比如访问 global 或 shared memory 时打了太多请求、请求堆积起来、带宽跟不上，攒下来的请求排不上队，新的请求就无法发射到这些 pipe 上，这时它们就不再是 eligible。

我们遇到的问题就是这样。实测（A100 上）每个 scheduler 有 15.94 个 active warp。理论上一个 SM 最多驻留 64 个 warp，有 4 个 scheduler，所以其实打得非常满——约 16×4=64，occupancy 没有什么问题。但是这里面大约 60% 都不是 eligible。

看 NCU 底下的解释，它提到了 MIO（memory input/output）的概念：MIO 是 warp 往 shared memory、special function 等发送东西的指令队列。这里它显示这个 MIO 队列非常满：

- FP32 指令平均花了约 12.2 个周期（数值听辨存疑，可能是 12.19% 或 12.19 周期）在等待 MIO；
- 总的 warp stall 约为 39.4%，其中 MIO store 占 48.8%——也就是说我们大部分的 stall 都是在等 MIO。

在我们的例子里很容易看出来：shared memory 指令太多、堆积起来了。看底下的指令统计，LDS（load shared memory）相关的那一行是最多的。每个 warp 都想继续发 shared memory 指令，但相关的 instruction queue 已经满了。所以 shared memory 也要更好地复用。

## 八、更细的工作分配：tile 内 thread 负责多个输出

shared memory 版本更好之后，我们可以考虑在 tile 内部再做工作分配：tile 内的 thread 也可以分一个更小的分工去解决整个问题。这样算 TM 和 TN 是结构相似的——thread 为了计算这几个结果，不需要重复读那么多遍 TM 和 TN 的数据。

进行这样的二维切分会带来更好的事情：

- 每个 K 位置读两个 A、两个 B，做四次 FMA；如果按正常做法，需要读四个 A 和四个 B。
- 每个 thread 负责更多输出，也解放了线程数。比如 4096 的 GEMM 画成 32×32 的 tile，32×32=1024 个 thread，这差不多是 A100 能驻留线程数上限的一半了。如果我们有更多空闲线程，就可以允许更大的 CTA 出现。
- 根据刚才的算存比，能达到的 AI 随 tile 增大而变好，数据复用变得更好。让 thread 负责更多的计算，我们可以用剩下的 thread 把 AI 往更高的方向再推一些。

但要用好更大更好的 CTA tile，还需要做 autotuning 或者说细致调参，这里由于时间关系不详细展开了。具体来说，work assignment 可能导致一些更多的问题：比如 shared memory 有各种 bank，一起访问时会产生一些冲突的访问，强制让它们被服务的 wavefront 数量增多。我们可以调节 tile 大小、改变 work assignment，在 occupancy 允许的范围内搜索更大的 CTA tile。

## 九、结果与展望

刚才讲到这几个简单的优化，大概可以看到：相对于原始版本，能拿到 5～6 倍的加速；并且即使只做了这些 tile 优化，我们就已经能达到 FP32 相当于 cuBLAS 80% 左右的水平。这其实是一个还不错的结果——虽然说也不是特别好，因为 80% 听起来也没有那么好。

思考一下未来的问题：如果后面再去做一些 kernel tuning，其实我们能达到 80% 再往上一点；FP32 的 PyTorch 版本可能达到 87% 的样子，都是可以的。但是再往上的话，shared memory 版本的 bank 什么的怎么调，其实都不会太影响整个 performance 了。

## 十、串行流水与多缓冲（pipelining）

再回去思考之前的写法，会发现刚才写的整个流水是串行的：所有 thread 先搬运（copy），搬运完以后同步一次，然后做搬运上来的这部分数据的计算，然后再同步一次，就这样循环。整条计算路径几乎就是 load → compute 的循环，load 占据关键路径上的时间。

我们最终希望整个东西变得非常 compute-bound——compute 应该是唯一一个能解释整个运行时间的指标。而 load 卡在关键路径上，会导致计算单元并不是一直满的，load 的时候会有空转。

解决方法就是多缓冲（multi-buffering）。回顾一下，如果了解流水线，会知道这是一种指令级的并行：把多个可以同时做的事情并起来。如果有中间 buffer，可以开两个版本：让一个版本先接受一次 copy，然后在这份 copy 的数据上做计算；在这份计算进行的同时，另一份 copy 的数据可以直接进入另一个没在被计算的 buffer 上；接下来算刚 copy 完的那份 buffer 的计算，同时再进行下一次 copy。这样把 copy 和 compute 流水起来，就可以掩盖掉这部分开销，达到更好的效果。

## 十一、后续内容预告

这种方法如此普遍、并且硬件提供了更好的支持，这是以后讲到 tensor core 时你不得不去做的一些事情：

- 引入 cp.async：它是一种异步拷贝。warp 直接提交这个异步拷贝，拷贝可以不阻塞，直接去进行计算，而不是依靠 warp scheduler 去调度来掩盖开销。
- 再往后，为了减少地址计算之类的问题，还会有专门加速拷贝的硬件单元（TMA，tensor memory accelerator 一类的异步拷贝），它更自动化，并且伴随着 bulk 的异步拷贝内存语义（字幕记为"EBERRY"，听辨存疑，应为 bulk/cp.async.bulk 一类的语义），允许我们有更多的写法。

这些会在 tensor core 和 pipelining 那两节讲到。这部分就简单给大家介绍到这里，谢谢大家。
