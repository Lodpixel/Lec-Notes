### SMT 求解器

**09:30**

SMT 里的 S 就是 SAT 的 S，指 SAT；T 是 theory，也就是理论。离散数学里的 theory，叫公理也好、叫什么也好，在程序里对应的其实就是各种类型：例如用 array 求解时可能有不同的 array 类型，用 string 求解时也有不同的类型。M 是 modulo，就是“模”的意思。简单来说，SAT 和不同的 theory 组合在一起，就叫 SMT solver——在 SAT 的基础上，它可以求解不同的类型。

SMT solver 的原理并不神秘：先把问题建成布尔公式，交给 SAT 求解；得到解以后，再把解代入各个 theory 中检查是否成立。例如有一个 theory 专门处理全是等号和不等号的约束。检查后如果发现解不成立，就反馈一个类似冲突信息的东西，让 SAT 继续求解；如果成立，就得到解。图里先讲 SAT，再讲 EUF。EUF 中 E 是 equality，UF 是 uninterpreted function；两者合在一起可以求解带等号、但函数没有具体解释的约束，例如 \(f\)、\(g\) 这样的函数。

今天的课会比较灵活，会介绍一个很简单的问题，希望大家讨论。后面还要介绍一个引擎，涉及如何把程序转换成逻辑语言；这部分之前没有学过。今天先讲模板程序如何以 basic block 的形式变成形式化的语言。之后会有大量非考试的课程，展示逻辑在系统中的真实应用，我也会做一个简单的代码展示。

### 量词消去

**13:01**

上节课最后没有讲量词。现在问：能不能提出一个最简单的算法，以最小程度解决量词问题？例如有一个带任意量词的式子，一看就是 false、不可满足。目前我们讲的 SMT solver 能不能直接支持这样的量词？现在的设定里没有；如果有，要求解它是 false 该怎么办？怎么把量词去掉？

一个非常简单的办法是把量词中的变量直接换成一个常数 \(a\)。对任意量词来说，如果换成 \(a\) 后式子是 false，就可以反过来推出原式是 false。所有去掉量词的规则——无论基于存在量词还是任意量词——本质上都是用非常简单的一些规则来做的；真实工具里用的规则会比这里难很多。

还可以先把式子变成 Skolem 范式，把所有存在量词去掉。这里关键的知识点是：Skolem 化前后的两个式子，可满足性保持不变。有了这一点，要判断一个同时含有 \(f(a)\) 和 \(\forall x\,f(x)\) 的式子是否可满足，就可以把 \(x\) 换成 \(a\)；如果替换后两边对 \(f(a)\) 的要求发生冲突，就推出原式不可满足。

但这样做有一个问题：如果替换后的式子可满足，能不能说明原式可满足？不能。因为它牺牲了语义。

### 回顾：异或交换与状态机

**18:40**

这个函数做的是 swap：输入 \(a\)、\(b\)，做三次异或，把 \(a\) 和 \(b\) 交换。要证明它，可以写成相应的式子。前面每一个都表示一个异或运算，最后证明 \(a_3=b_0\) 和 \(a_0=b_3\)。这里有一个非常重要的概念：状态机。实际上是把程序每一步执行之前的状态和执行之后的状态，都看成整个程序的一个 state，所以这是一个 state machine。

### 用谓词逻辑简化位级公式

### 符号执行引擎

**20:21**

因此需要写一套新的软件，称为符号执行引擎。这个软件的输入是程序代码，输出是能够表示一个程序所有执行路径的谓词逻辑表达式。

顾名思义，符号执行引擎的基本技术叫符号执行（symbolic execution）。它的基本思想是：把函数的两个输入，比如输入 \(a\) 和 \(b\)，都看成一个 symbol（符号），假设它有符号，然后去执行；根据这种执行，可以把整个程序的每一个 path 都写出来。

### 与具体值执行的区别

**21:12**

它和 concrete value（具体值）的区别是什么？具体值执行遇到 if-else 时，会根据 \(a\) 的值去走 \(a=-b\) 或者 \(b=2\) 这条分支；而符号执行引擎会把所有路径都执行。比如 \(a=-b\) 这一条路径，假设 \(b\) 是一个 symbol，最后就会推出 \(a\) 等于 \(-b\) 这样的 symbol。\(b\) 这个 symbol 如何表示是另一个问题。

目前来看，符号执行引擎整个的基本思想是什么？

### 三个状态

**22:45**

符号执行引擎会维护三个状态：第一，有哪些变量，也就是每个变量用哪些符号来表示；第二，当前的分支条件，也就是 if-else 这种控制条件的约束；第三，下一步要执行的代码，也就是下一行代码。

举个例子：

```c
int f(int a, int b) {
    if (a > 0)
        a = -b;
    else
        b = 2;
    assert(a + b < 1);
}
```

### 初始状态

**23:26**

刚开始进入这个函数时，有两个输入 \(a\) 和 \(b\)。\(a\) 应该用符号表示，所以写成 \(a_{\text{symbol}}\)；\(b\) 也用符号表示，写成 \(b_{\text{symbol}}\)。当前的路径条件（path constraint）是 true，也就是说刚进入函数时不需要有任何条件。接下来要执行的第一行代码是 `if (a > 0)`，然后它会分别查看。

### 进入 a>0 分支

**24:20**

如果 \(a>0\)，要执行什么代码；如果 \(a\le 0\)，又要执行什么代码。对于 \(a>0\) 这一边，执行 `a = -b`，同时路径条件就变成 \(a>0\)。执行完这个分支后，路径条件就是 \(a>0\)，要执行的代码是 `a = -b`。执行到 `a = -b` 后，下一个状态是：\(a\) 等于 symbol 形式的 \(-b\)，\(b\) 等于 \(b_{\text{symbol}}\)；路径条件不变，没有增加新的路径条件。

### assert 与待求解的表达式

**25:08**

路径条件仍然是 \(a>0\)。下一个要执行的代码是 `assert(a + b < 1)`。对这样一个 block，我们就得到了一个谓词逻辑表达式。接下来要求解什么？这个式子要求满足什么？

### 取反后的路径条件不可满足

**25:37**

检查 `if (a > 0)` 这一分支。该分支执行 `a = -b`；在路径条件 \(a>0\) 下，断言 \(a+b<1\) 成立，因此 \(a>0\to a+b<1\) 在这条路径上是永真的。要检查断言是否可能失败，就取反，得到：

\[
a>0 \land a+b\ge1.
\]

把 \(a=-b\) 代入，得到

\[
-b>0 \land (-b)+b\ge1,
\]

其中第二个合取项化简为 \(0\ge1\)，为假。用 SMT solver 求解时，这个条件返回 unsat，所以这条路径不会产生反例。

### 第二条路径与反例

**26:42**

再看 `else` 分支。该分支的路径条件是 \(a\le0\)，执行代码 `b = 2`。执行后状态为 \(a=\alpha_a, b=2\)，路径条件仍为 \(a\le0\)。要检查断言 \(a+b<1\) 是否可能失败，取反得到 \(a+b\ge1\)，代入 \(b=2\)：

\[
a\le0 \land a+2\ge1,
\]

即 \(a\le0 \land a\ge-1\)。这个式子是 satisfiable 的，例如 \(a=-1\) 就满足。此时 \(b=2\)，\(a+b=-1+2=1\)，不满足 \(a+b<1\)，所以 \(a=-1\) 就是这段代码中的一个 bug。于是得到一个反例（counterexample）。给大家一点时间，看一下用符号执行走这样一条路径时，整个流程是什么样子。

### 论文中的符号执行记法

**28:29**

下面直接采用论文中的写法走一遍符号执行流程，因为这种写法简单一些。图中的符号实际指 symbolic；例如 \(\alpha_a,\alpha_b\) 分别表示 symbolic a、symbolic b，\(\pi\) 表示 path condition。我直接把论文里的图贴过来，下面是要执行的代码。

### 逐步执行：状态与路径条件

**31:38**

代码首先执行 `x = 1; y = 0;`。此时还没有任何路径约束；同时把两个输入赋成 symbolic 值 a、b。执行完这两句后，状态为

\[
x=1,\quad y=0,\quad a=\alpha_a,\quad b=\alpha_b,\quad \pi=\mathrm{true}.
\]

下一条语句是 `if (a != 0)`。它产生两个分支：一个满足 \(\alpha_a\ne0\)，另一个满足 \(\alpha_a=0\)。如果选择 \(\alpha_a\ne0\) 的分支，就进入下面的代码。

在该分支中先执行 `y = 3 + x`。因为此时 \(x=1\)，所以 \(y=4\)。于是下一个状态为

\[
a=\alpha_a,\quad b=\alpha_b,\quad x=1,\quad y=4,\quad \pi:\alpha_a\ne0.
\]

紧接着执行 `if (b == 0)`，这又产生一个新的分支。对于 \(b=0\) 这一支，状态仍为 \(a=\alpha_a,b=\alpha_b,x=1,y=4\)，而路径条件要取合取：

\[
\pi:\alpha_a\ne0 \land \alpha_b=0.
\]

在嵌套分支或嵌套循环中必须做这种 and 操作：走到下面这段代码，既要满足前面的 \(\alpha_a\ne0\)，也要满足新分支的条件 \(\alpha_b=0\)。

### 检查 b=0 分支

**33:56**

接着检查路径条件为 \(a\ne 0\) 且进入 `if (b == 0)` 的分支。若 \(b=0\)，执行的代码是

\[ x=2a+b. \]

执行后，\(a\) 仍取符号值 \(a\)，\(b\) 仍取符号值 \(b\)。该分支还要检查断言

\[ x-y\ne 0. \]

要判断断言是否可能失败，就取它的否定 \(x-y=0\)，并与路径条件合取。由于 \(y=4\)，代入 \(x=2a+b\)，得到

\[ 2a+b-4=0,\quad a\ne0,\quad b=0. \]

这个谓词逻辑表达式是可满足的：例如 \(a=2,\ b=0\) 时，\(2a+b-4=0\)。因此该路径上断言可能失败，程序可能出错。

### 其余分支

**35:29**

再看 \(b\ne0\) 的分支。此时路径条件为 \(a\ne0\land b\ne0\)。把断言取反后要求 \(x-y=0\)。在该分支中 \(x=1\)、\(y=4\)，于是条件变成

\[ 1-4=0, \]

即 \(-3=0\)，显然不可满足，因此这一分支不会使断言失败。其他分支类似，例如 \(a=0\) 的分支也没有错误。只有 \(a\ne0\) 且 \(b=0\) 这一条路径会出错。下面用一个完整例子，把符号执行、谓词逻辑表达式和求解过程串起来。

### 完整例子：先做符号执行

**36:39**

先看一个完整例子。程序里有若干赋值、一个 `if (a == b)` 分支以及最终的 `assert(a == c)`。第一步是用符号执行引擎把程序转换成谓词逻辑表达式。写状态时按课堂上的记法，不必照论文里的写法。初始时令 \(a,b,c\) 分别取符号值，路径条件为 true。执行第一条赋值后，得到 \(a=f(\text{symbolic}\ b)\)，而 \(b,c\) 仍保持原来的符号值，路径条件仍为 true。

这里把函数写得简单，是因为本课程用到的 SMT 求解器主要处理等号、不等号，以及 \(f\) 这种按输入方式处理的未解释函数。

### 生成路径条件

**38:12**

接下来程序产生两个分支：\(a=b\) 和 \(a\ne b\)。正常做符号执行时，两个分支都要走。先走 \(a=b\) 这一支，路径条件中增加 \(a=b\)。执行赋值后，\(a\) 变为相应的函数项，\(b,c\) 保持当前符号值；后面还会执行 `d = f(c)`，再遇到 `if (a != d)` 这样的分支，路径条件继续增加新的等式或不等式。

程序最后要检查 `assert(a == c)`。要证明该分支上断言成立，就取断言的否定 \(a\ne c\)，与路径条件和变量之间的关系合在一起，检查

\[ \text{path condition}\land a\ne c \]

是否不可满足。把 \(a,d\) 等用对应的 \(f\) 项代换后，得到一个含 \(f\) 的谓词逻辑公式；这个公式是不可满足的，所以该分支上断言不会失败。其他分支可以按同样方式写出各自的谓词逻辑表达式。

### 合并各分支

**40:25**

对整个程序而言，每个分支都会生成一个“路径条件 ∧ 断言否定”的公式。正确的程序要求所有这些公式都不可满足。合并时用析取（or）把所有分支的公式连在一起，再检查整个公式是否不可满足。

实际调试时，为了区分到底哪一行、哪个分支出现 bug，通常还是一个分支一个分支地检查，保证每个分支对应的公式都不可满足。

### 惰性 SMT 求解

**41:07**

对其中一个分支，也就是第一个分支，使用惰性 SMT 求解。先把公式中的原子命题抽象成 \(p_1,p_2,p_3\)，该分支公式可以写成

\[ p_1\land \neg p_2\land \neg p_3. \]

用 DPLL 求解命题逻辑部分，很容易得到一个赋值：

\[ p_1=\text{true},\quad p_2=\text{false},\quad p_3=\text{false}. \]

把该赋值代回，就得到一组等式和不等式，例如 \(f(b)=b\)、\(f(b)\ne f(c)\) 等。接下来把这些条件交给 EUF 求解器处理：把 \(b\) 记为 \(v_1\)，加入 \(v_1\ne v_2\)、\(v_1=f(b)\) 等约束，再检查这些等式和不等式是否可满足；若不可满足，就说明该分支对应的断言失败条件不成立。

### EUF 中的不可满足约束

**42:06**

在 EUF 部分，已知 \(v_1=b\)，由等价关系可推出 \(f(v_1)=f(b)\)；同时有 \(v_1=f(b)\)、\(v_2=f(b)\)。因为 \(v_1\)、\(v_2\) 都等于 \(f(b)\)，所以它们被并入同一个等价类，可推出 \(v_1=v_2\)。但约束中又有 \(v_1\ne v_2\)，因此这组条件不可满足。

### 阻塞子句

**42:46**

既然 SMT solver 判定这组约束不可满足，就把当前这个不可满足的赋值取反，作为阻塞子句加入约束，告诉求解器下次不要再返回 \(p_1=\text{true}\)、\(p_2=\text{false}\)、\(p_3=\text{false}\) 这一组取值。于是把被排除的赋值写成 \(p_1\land\neg p_2\land\neg p_3\) 这样的形式，再对它取反；后续求解中这个具体组合不会再被返回。对这样的公式继续判断可满足性，可以直接用单元传播和分支来完成。

### 用分支和单元传播验证不可满足

**43:18**

例如先猜 \(p_1=\text{true}\)，做单元传播；再猜 \(p_2=\text{false}\)，由已有条件推出 \(p_3=\text{true}\)。但 \(p_3=\text{true}\) 会使公式出现矛盾子句，于是回溯。改试 \(p_2=\text{true}\)，仍然出现矛盾子句；再回溯到 \(p_1\)，令 \(p_1=\text{false}\)，仍然不成立。因此所有分支都失败，整个公式不可满足。

### 转到 SMT 应用

**44:04**

这样就把一个从 C 语言程序（或具体式子）出发的问题，转换成 SMT 表达式，交给 SMT solver 求解。接下来讲 SMT 的应用，相关的代码和材料会放在课程材料中，可以对照查看。

### 数独问题

**44:47**

### 程序合成的含义

**27:17**

程序合成不是一阶逻辑，而是二阶逻辑。大意是：要找到一个 program，即存在一个 program \(p\)，使得对所有输入 \(x\)，都满足规格 \(P\)，即 \(\exists p\,\forall x\,P(x,p(x))\)。也就是说，输入和输出要一致，这就是程序合成。这里 \(p\) 就是一个程序，或者一般的伪代码；输入、输出都已经给出，我要找到一个程序。程序合成的基本思路其实很简单：两个模块，一个模块是合成器，一个模块是验证器。

### 合成器与验证器

**28:12**

合成器把代码合成出来，合成完之后扔到验证器里。验证器同时输入一些 test case，去验证这个程序是否满足规约；这里的规约其实就是 test。如果它不满足，就会生成 counterexample，合成器再根据 counterexample，按照一些基本规则去修改代码。当然有个问题：如何实现合成器和 verifier？对合成器来讲，现在有了大模型，其实变得非常简单。所以模型加形式验证，就可以真正合成想要的代码。

### 传统枚举与程序逆向

**28:57**

以前没有大模型，方法比较土：传统 enumerative 方法暴力枚举所有可能的代码片段，这导致程序合成一直没有办法做到特别大规模；直到最近大模型出来，情况才发生变化。程序逆向也可以认为是程序合成的一种，只不过它的 test case 是原始逆向之前的软件，输入和输出要与原软件一致，verify 可以用之前的 KLEE 来做。暴力枚举所有可能性肯定不合理，所以这里并不是去枚举所有程序，而是有一些基本的 constraints 和基本规则来做这件事。具体不讲，有一篇 2016 年的 paper，基本奠定了现在程序合成的基本思路。下面举一个例子。

### 第二个例子与 oracle

**34:06**

如果程序不满足要求，它就会重新生成补丁。例如完成获取测试用例、寻找 bug、定位 bug、最后修复 bug 这样的过程。它会打印出 UNSAT；对每个测试用例，它都会用 SMT solver 做一次 SMT 求解。由于采用纯枚举、暴力的求解方式，没有大模型，所以会比较慢。要满足这些测试用例，需要把 \(c = a + b\) 换成 \(c = a - b\)，才能打印出正确结果。

### 从合成到优化

**37:22**

大家想一下下一步是什么？我们已经能够合成正确代码，下一步就是优化。基于形式化验证、自主去优化程序，这样的代码优化称为超优化。

很多同学可能会问：GCC 开 -O2 不就已经可以优化了吗？不是这样。因为 GCC 很多时候是基于规则，这些规则没有办法涵盖非常大的优化情况。具体方式是：首先基于之前的合成。

### 性能评估器

**38:30**

左边是之前的代码合成。合成之后，可能得到多种不同的代码片段，它们都可以满足测试用例。这种情况下，会有一个 performance estimator（性能评估器）来评估。注意是 estimator，可以用不同标准来估算，比如指令数，比如运行时间，来判断哪一个既满足规约——或者说满足测试用例——性能又最优。

### 等价性验证

**39:17**

但目标是：给定 function 1，假设已经有了 function 1，然后去找 function 2。

### 超优化的概念

**39:50**

这个 function 2 既要满足 assertion，同时又要使性能更好，也就是 better than function 1。这就是 2013 年提出的超优化概念：如何在没有任何规则的情况下进行优化。现在所有的编译器基本都是基于规则：如果这样写能符合某个模式，就可以优化成另一个模式；超优化实际上没有这样的规则。

用 `-O3` 进行编译，然后根据之前那个过程生成测试用例，重新做 synthesis，重新做代码合成，最后发现它把代码变成了两行：先做一个 `bswap`，然后再 `movq`，这两条就结束了，非常好。

这就是做这件事情所需要的知识，之前其实你们都学到了，区别只是你们能不能想象得到怎样去做这件事情。

### 形式化验证与自动合成

**45:45**

这就是我们现在展示的形式化验证能力。形式化验证本质上解决的是验证问题，这个验证不仅仅是可靠性；有了验证、有了这一套东西之后，你可以做很多事情，从代码验证到代码自动合成，甚至到代码性能优化。

有了大模型之后，当然可以做更多事情。比如验证搞不定的事情，它可以做程序合成，可以做超优化。所以有了大模型之后，其实它能做的是后面两件事情。对于程序设计、程序语言（PL）来讲，它只是把后面两件事做得更好了，并没有解决验证问题。

### 大模型能做什么、不能做什么

**46:34**

也就是说，我可以把之前的枚举合成器（enumerative synthesizer）变成大模型。你们去年做这件事情时，就很容易写出一个性能更好的程序。但这样的程序怎样保证是对的呢？一定要用验证的方式来保证。还有性能最优的问题，大模型有一些领域知识的时候，知道怎样去写。

比如刚才那些基于汇编的例子，它可能没有办法在 C 语言里写；但大模型去看汇编的时候，会发现这个汇编语义可能等于某一条指令，那它可能去改。不过像第二个 `popcount` 那种汇编，对大部分模型来讲太复杂了，所以它不一定搞得定。之前试过的一些简单例子还是可以的，比如这种简单的方式：本来是把 `i + i`，它就直接 `return 2 * i`。所以大模型本质上能做的事情，是更好地做 synthesis，更好地做性能超优化。但难的地方在于，它仍然没有办法做程序验证。

### Coding agent 的一般流程

**48:02**

这也是我们第一节课讲的。在这里我们第一次扣回这个主题。下面以 coding agent 为例，大概讲一下它一般是怎么做的。

现在 coding agent 是怎么做的？第一步，因为大模型本身有 context window size 的限制，所以它会把整个仓库的代码切分，切成一块一块的，然后用一个数据结构对每一块进行索引。索引之后，把每一块代码转换成向量表达式，也就是 embedding，再对 embedding 这个向量表达式进一步索引。索引完之后放到一个 buffer 里面。每一次 coding agent 想重写整个大项目里的某一块代码时，它就会反过来，根据这个 vector 去索引，说这段代码到底在哪里，然后再去改哪一块代码。

所以整个流程中，它实际上牺牲了非常多语义正确性。基本上可以认为，它是对代码进行切分、压缩，然后进行索引。整个流程是这样子的，这是一个 ReAct，前一段时间比较火。

### ReAct agent 与验证

**49:20**

ReAct agent 是一种架构。用户发出一个请求后，它会先进行推理（reasoning），判断应该怎么做，然后执行动作（act）。在执行动作的过程中，它会搜索需要修改哪一段代码：根据前面的索引定位到相应代码，再进行 edit、add，修改代码并 push。这里所缺的，正是我们现在学习的验证问题：如何验证它所得到结果的正确性。
