### 分离逻辑的用途

**08:12**

好，我们来看分离逻辑。我不要求别的，只要求大家知道分离逻辑是干什么的。我先问一下，大家知不知道分离逻辑是干什么的？上节课总共讲了十页 PPT。它处理的是堆变量，是在动态分配内存的时候要用的。为什么动态分配的时候要用？因为在编译之前，程序并不知道堆的状态，传统方法没法直接处理。分离逻辑引入了一个新的符号，用来表示两个对象之间的关系。那么，分离逻辑本身要解决什么问题？

**09:23**

分离逻辑解决的是这样一个问题：我在代码里调用 allocate，分配一块新的内存。但在 allocate 之前，你不知道内存状态到底是什么，因此没有办法在它之前就把它的前置条件和后置条件精确写出来。那怎么办？做法就是提出分离逻辑。为什么叫分离逻辑？为什么分离逻辑能做这件事？大家谁记得？因为它可以分开指向两个对象。为什么可以这样做？上节课没有讲。原因在于，分离逻辑允许我们递归地定义谓词。今天这节课就讲这件事。没事，你今天预习了是吧？对，可以递归地做这件事情。我举一个上节课举过的例子。

### 链表删除操作

**11:06**

这是一个 delete 操作：有一个链表，我要把 x 节点删掉，删完之后 free，把该节点后面的所有节点全部删掉。这件事情没有办法直接写规约，因为它本身是一个递归调用，很难写出它的规约是什么。如果要写这个调用，就要说明：在调用函数之前，需要有一个链表 \(x \to next \to \cdots \to \mathrm{nil}\)，或者 \(x=\mathrm{nil}\)。当 \(x\neq \mathrm{nil}\) 时，后面的前提条件可以推出来。执行完 delete 之后，next 指向空；free 之后把 x free 掉，整个链表就空了。

### 分离逻辑的基本记法

**12:16**

再回顾一下上节课讲的分离逻辑。其实分离逻辑非常简单：它引入了星号 \(*\)，\(f*g\) 表示两个谓词。它不是传统霍尔逻辑中本体的一部分。假设有一个堆，也就是计算机系统状态，左边有一部分、右边有一部分；\(f\) 是描述左边部分的谓词，\(g\) 是描述右边部分的谓词。\(f*g\) 表示这两个谓词所描述的状态没有交集，而且这个状态是在堆上的。其中有两个基本记法：一个是 \(\mathrm{emp}\)，表示整个状态是空的；另一个是 \(\mathrm{acc}(x)\)，表示 \(x\) 已经在内存上被分配过，可以被访问。

### 星号与合取式的区别

**13:36**

举个例子：\(x\) 可以被访问，同时 \(x.next=y\)，\(y\) 这块状态也可以被访问。因为 \(x\) 被分配了一块内存，\(y\) 也被分配了一块内存，并且 \(x.next=y\)。若用星号，\(x\) 和 \(y\) 描述的是两块不重叠的内存；若把星号换成合取式 \(\land\)，它的意思就变成 \(x\) 被访问、\(y\) 被访问，也就是 \(x\) 和 \(y\) 各被分配了一块内存。此时并不要求两块内存不重叠，甚至可能指向同一块地址；再加上 \(x.next=y\)，就可能出现自己指向自己，next 指向自己。

### 链表的递归定义

**14:33**

接下来看怎样形式化链表（linked list）。上节课定义链表时，用谓词来描述链表当前的状态。可以把这个谓词记作 \(\operatorname{list}\)，输入是链表的头 \(x\)。它的定义是：\(x=\mathrm{nil}\)，或者 \(x\neq \mathrm{nil}\)，并且 \(x\) 一定被分配了一块内存；同时，next 指向的那部分也可以用 \(\operatorname{list}\) 来表示，说明后面这段也是合法的链表。这样的定义就是合法的。这就是对链表的分离逻辑定义。它可以递归地做，这是非常强的一点。

### 用分离逻辑检查内存错误

**16:26**

这样的定义能用来检查越界访问、释放后使用和重复释放等内存错误。上节课讲到这里：这些错误可以通过分离逻辑和霍尔三元组来描述相应的规约，并判断规约是否被满足。

例如，有一段程序在运行时一定会报错：\(x\) 之前已经被 free，不再指向任何内存，随后却又对它执行 free，于是出现 double free。又如，对一个已经分配、随后又被 free 的节点继续访问，也会出错；free 之后，这块堆对应的后置条件应写成 \(\mathrm{emp}\)。

### Frame rule

**17:14**

分离逻辑中最重要的推理规则之一是 frame rule。假设一段代码只改变堆状态中 \(P\) 对应的部分，把它变成 \(Q\)，而不触碰堆的其余部分；那么其余部分可以记为 \(F\)，并把前后条件分别扩展为 \(P * F\) 与 \(Q * F\)。也就是说，如果前置条件为 \(P\)、程序为 \(c\)、后置条件为 \(Q\) 的 Hoare 三元组成立，那么以 \(P * F\) 为前置条件执行同一程序后，后置条件为 \(Q * F\)。

这里的 \(F\) 表示没有被触碰的那部分堆。如果代码没有触碰这部分堆状态，那么推理时只需要修改被触碰部分的谓词，未触碰部分可以原样保留。

### 把 frame rule 用到整个堆

**18:13**

有了 frame rule，就可以这样推理：假设整个堆可以分成两部分，一部分的谓词是 \(P'\)，另一部分的谓词是 \(F\)，即整个堆的谓词为 \(P' * F\)。如果某个函数的前置条件是 \(P'\)，执行后能推出 \(Q'\)，那么把整个堆 \(P' * F\) 作为前置条件时，函数执行后得到 \(Q' * F\)。原因是这个函数只把 \(P'\) 改成了 \(Q'\)，\(F\) 对应的部分没有动。

### 验证 delete 函数

**19:14**

下面用这个规则来推导 delete 函数。首先要定义这个函数的前置条件。\(x\) 是一个合法链表，就写成 \(lseg(x)\)。\(lseg(x)\) 的定义是：\(x = \mathrm{nil}\)，或者 \(x \ne \mathrm{nil}\)、\(x\) 已经被成功分配，并且 \(x.next\) 也是一个合法链表。

执行到 \(x \ne \mathrm{nil}\) 的分支时，由 \(lseg(x)\) 可以推出：\(x \ne \mathrm{nil}\)，并且 \(x\) 已经分配；同时 \(x.next\) 是一个合法链表。这个条件既是该分支的后置条件，也是接下来调用 delete(x.next) 的前置条件。

调用 delete(x.next) 后，被删除的那部分链表对应的堆变为 \(\mathrm{emp}\)。因为这个调用只触碰了 \(x.next\) 这一部分，\(x\) 所在的这一部分没有动，所以根据 frame rule，\(x \ne \mathrm{nil}\) 且 \(x\) 已分配这个条件保留下来，同时 \(x.next\) 对应的部分变为 \(\mathrm{emp}\)。接着调用 free(x)，释放 \(x\) 的内存，使 \(x\) 对应的堆部分也变为 \(\mathrm{emp}\)。把这两部分合起来，就得到整个堆为 \(\mathrm{emp}\)，从而完成 delete 的验证。

### 用谓词逻辑定义合法链表

**25:04**

先看如何用谓词逻辑定义一个合法的链表。基本情形是：如果 `x` 等于 `null`，那么它是一个合法的链表；否则，`x` 不等于 0，并且 `x` 已经被分配了内存。对于非空节点，还要求 `x->data` 位于 `min` 和 `max` 之间，并且 `x->next` 也是一个合法链表，其所有节点的 `data` 同样都在 `min` 和 `max` 之间。这个定义只限制节点值的范围，不要求链表有序。

### 从谓词描述到程序验证

### VeriFast 中的分离逻辑记号

**30:44**

在分离逻辑中，分离合取写成 `f * g`；到了 VeriFast 中，编程记号写成 `f &*& g`，也就是星号左右各加一个 `&`。断言还可以表示 `x` 是可访问的，即 `x` 实际上已经被分配了一块 `malloc` 出来的内存。C 代码里会写 `x->next == y`，而在 VeriFast 的断言中，用 `x->next |-> y` 表示 `x` 的 `next` 字段指向 `y` 这个地址。霍尔逻辑中的前置条件 `P` 和后置条件 `Q`，在 VeriFast 中分别写成 `requires P` 和 `ensures Q`。

### VeriFast 的注释与标注

**32:02**

`requires P` 是前置条件，`ensures Q` 是后置条件。用 VeriFast 验证代码时，前置条件、后置条件以及证明都要写在注释里。注释中要加两个 `@` 符号，左右各一个，例如 `/*@ ... @*/`，表示这是一段证明代码；也可以写成双斜杠加 `@`，即 `//@`，同样表示这是 VeriFast 的标注。

### 链表谓词与分离逻辑

**33:15**

这里的条件表达式是：如果 `x` 为空，这个链表就认为是空，返回空谓词 `emp`；否则返回另一支。这里写的是 `x->next |-> ?next`，也就是 `x->next` 指向 `?next`。问号 `?next` 表示存在一个个体变量，它的值就是 `x->next`，可以把它看成对 `x->next` 的一个引用。这个存在量词同时说明 `x` 实际上是 allocated（已分配）的，也就是它实际上是 `malloc` 出来的一块内存；并且这个 `next` 本身也必须是一个合法链表，也就是 `list(next)`。这里的 `*` 就是分离逻辑的分离合取符号。

### 同学解释 partition 的思路

**42:42**

同学的大意是：partition 一开始要选 pivot 最终插入的位置，使得它左边的元素都比它小，右边的元素都比它大。先取一个基准数，默认取最后一个元素，也就是把 \(A[n-1]\) 拿出来，再从数组中找一个位置放进去；这样设计可以节省空间，因为取走基准后原来的位置就空出来了。接着从左往右遍历：如果 \(A_0\) 小于 \(A[n-1]\)，就不动它；如果某个元素大于基准，就说明它应该放在基准右边。实现时通过交换把基准位置腾出来，继续扫描；遇到大的元素先留在原处，遇到小的元素就把它移到前面，留下的空位再继续处理。

### 教师讲解 partition 的两个指针

**45:03**

刚才说过，为了节省空间，代码的做法是：首先令 pivot 为最后一个元素。代码里有两个指针 \(i\) 和 \(j\)，其中 \(j\) 从前往后遍历。若 \(A[j] < pivot\)，就交换 \(A[i]\) 和 \(A[j]\)，并让 \(i\) 加一。这样能保证小于 pivot 的元素都堆到前面，也就是都放到 \(A[0..i-1]\) 中。扫描结束后，\(A[0..i-1]\) 全都小于 pivot。此时只需把 \(A[i]\) 与末尾的 pivot 交换，pivot 就放到正确位置：左边都小于它，右边都大于它；等于 pivot 的元素放在哪一边没有关系。

**46:17**

### quicksort 的 Hoare 规格

**47:20**

接着看用 Hoare 逻辑描述 quicksort 的 specification。它的前置条件可以写成：存在一个个体变元 \(V\)，使得 \(A[0..n-1]=V\)。后置条件则是：排完序后 \(A[0..n-1]\) 变成 \(W\)，并且 \(\operatorname{perm}(V,W)\) 成立。这里的 \(\operatorname{perm}\) 表示 permutation，即 \(V\) 和 \(W\) 的元素完全相同；同时 \(W\) 必须是已经排好序的。也就是说，排序前数组是 \(V\)，排序后得到 \(W\)，\(W\) 与 \(V\) 含有相同的元素，并且 \(W\) 有序。

### 自动代码 review 的局限：一个编译器案例

**27:54**

Anthropic 最开始做了一个叫 auto review 的功能，就是 Claude 来做代码 review。它希望帮助大家 review 写出的代码，也就是大模型自己生成代码、自己 review。但效果并不好。我们之前测了一下，Claude 的 review 和 Cursor 的 review 都有。我找了一个有 76 个 bug 的模块，确定有 76 个，它只找到 6 个，甚至只找到 3 个。为什么效果不好？我给大家举一个很简单的例子。

这是编译器里的一段代码。它做什么？假设有一个 string，这个 string 是一行代码，这行代码里有一个 keyword；也就是说，要把这行 C 语言代码里的 keyword 拿出来。比如 null pointer 是一个 keyword，bool 也是一个 keyword。这段代码首先做的事情是有一个 fast-path reject，先去看：如果这个 keyword 的前面是 A、B、C、D、E、F、G 之类的，那就直接 return，表示如果不 match，它就不是 keyword。所以它有一个假设：keyword 必须以 A 到 G 开头。这是它自己生成的代码，这肯定是错的，因为它并没有涵盖所有 keyword 的情况。所以这就是一个 bug。但是大模型找不出来。为什么找不出来？

原因有三个。第一，注释本身也是错的；而且注释的错误和下面代码的错误是一致的。第二，这个叫 fast path：代码来了之后快速 check 一下，不行就直接返回。所以它发现 fast path 和 slow path 也是一致的，它们之间没有矛盾。第三，整个代码太长了，大模型不会非常认真地每一行都扫。所以，大模型跟人类一样，自己写代码、自己 debug，是一个逻辑；大模型自己写代码、自己 debug 是一件很难的事情。

### 两个挑战：写规约与写证明

**34:03**

他们的做法首先面临写 specification 的困难。像刚才的 quicksort specification 就要写很长，第一个挑战就是如何解决写规约的问题。第二个挑战是如何写证明。对此有两个基本答案。

第一，不证明软件中的所有性质，只证明最关心的性质；这些性质往往有 test case，可以把 test case 作为规约。例如一个 safety 规约，证明完成之后就能保证软件中不存在违反该规约的 bug，功能一定正确，例如 safety、memory safety，或者没有隐私泄漏。

第二，不再手写证明：只要从 test case 生成规约，把关心的性质写成 test case，再让大模型生成证明，然后运行证明验证器，比如 Coq、Verus，来验证生成的证明是否正确。如果证明不对，可能说明有 bug，也可能说明证明写错了；于是让大模型重写，或者让它判断到底是证明写错还是代码有 bug。

### 从 fuzz testing 到形式化规约

**36:33**

它的 testing 复用了 fuzz testing。形式化以前是比较小众的领域，就像用 Lean 写数学证明一样，非常小众；大模型出现之后，形式化突然变得大众，因为门槛被降低了。相比之下，软件测试一直很大众。所有软件之前都需要测试，其中最主要的是 fuzz testing。所谓 fuzz，就是有一个 fuzzer 随机生成一堆程序输入，输入有覆盖率引导，尽量覆盖各种 corner case，再用这些输入生成 test case，去跑 fuzz test。

比如要验证压缩算法没有问题，像 bzip2，Linux 或 Mac 上都会用到；其中就有 fuzz test。做法是：先拿任意数据做压缩，fuzzer 会放入各种随机 data；压缩完之后再解压缩，然后 assert：第一，压缩前和解压缩后的数据长度是否一样；第二，内容是否一样。这是一个非常经典的 fuzz test，它的 input data 通过不同的随机函数生成。以前是生成数据后直接跑；现在有了这样的设置之后，就知道这就是规约。以前规约是随机生成数据，保证压缩前和解压后的数据一致；现在这件事变成规约之后，要证明的就是对于任意的 data，压缩前和解压缩后的数据完全一致。同一个 fuzz test，在形式化验证和测试场景下，语义完全不一样。

### 为什么在汇编层做验证

**39:17**

这里有一个 fuzzing 的 library。有了这样的发展之后，就可以把程序编译成汇编。为什么要在汇编上做？首先，compiler 本身可能有 bug。即使证明的是 C 程序，也可能出问题；比如之前发现 GCC 在开启优化的情况下有 bug，会引入恶意输入，让编译器生成错误代码。其次，不同语言各自有一套建模方式：Dafny 有自己的一套语言，C 有一套；Rust 现在也有 Verus。对不同语言分别建模很费事，所以干脆直接在汇编上建模，因为汇编指令有限。

### 可验证的性质

**40:31**

对于 Claude 来讲，它能证明几件事情。第一类是功能性质，也就是 functional testing、fuzz testing 这些东西，检查与功能相关的 fuzz test 是否被违反。第二类是 undefined behavior。C 和 C++ 里有很多 undefined behavior。什么叫 undefined behavior？举个例子，访问一个 null pointer。

### 未定义行为与内存安全

**41:02**

对于未定义行为，C 语言并没有一个跨硬件的标准定义。例如在 macOS 或 Windows 上访问空指针，出错后的具体信息与行为并不要求一致，因此称为 undefined behavior。第三类问题是内存访问是否安全：是否会发生越界访问、use-after-free 等，这些都会引发安全漏洞。

**41:32**

举一个 undefined behavior 的例子：整数溢出。发生溢出后，ARM 芯片、Intel 芯片或不同操作系统上的行为可能不同。另一个例子是内存访问越界，包括数组越界和空指针解引用。比如要证明一个程序中的左移或右移位数一定小于 64；如果大于等于 64，移位就会超出范围。这类检查就是简单的规则断言（assertion），此外还有 memory safety 断言。

**42:19**

Memory safety 包括 use-after-free、double free、out-of-bounds access 等。以一个函数为例，specification 的生成其实很直接：对所有合法输入，程序都不应触发这些断言。也就是说，在正常规约下，代码中不存在任何可以触发这些错误的 bug。这就是验证系统要证明的事情。

### 对 RISC-V 汇编和系统调用建模

**43:27**

这里的“每个 input”包括输入文件、系统调用等。例如，Linux 系统调用出错，或目标程序执行不成功，都会导致错误。证明是在汇编层面进行的，针对 RISC-V 汇编，因为这种汇编相对简单。需要对每一条汇编指令建模。前面学过公理系统，这里的建模就是用数学方式构建模型：既要对每条指令建模，也要对整个操作系统的 system call 建模，还要建立进程行为（process behavior）的模型。这个模型称为 LPS（Linux 进程模型），用来描述 Linux 进程语义。

**44:12**

在做这件事之前，验证工程师专门负责把 Linux 操作系统、进程等建成模型。模型建好之后，它实际对应代码：通过工具生成规约，并给出一个二进制文件；需要证明这个 RISC-V 二进制中的规约成立，而它的执行模型就是 Linux process。

### 用大模型生成证明

**45:07**

生成证明的方式是：有一个代码和公理。公理就是前面说的规约（specification），系统自动生成 assertion，然后由 Claude 大模型负责写定理和证明。之前学过的快速排序等证明和定理，会生成对应的 proof；这些证明代码与 Lean、Rocq 这类定理证明器处于同一层面。

如果出错，系统会把 error information 返回给 Claude，判断是证明本身的问题、代码里有 bug，还是资源受限。如果是证明问题，就重写证明；如果有 bug，就修改 bug 后重新证明，直到全部证完。Claude 现在声称正在做的一件事，是把 GitHub 上能看到的开源代码全部整理。

### 示例：从 C 程序到 RISC-V 汇编

**46:20**

举一个非常简单的程序：

```c
a = 2;
b = a + 3;
c = a * b;
assert(c > 0);
```

证明时，首先把它编译成 RISC-V 汇编代码。刚考完 ICS，应该对汇编比较熟悉。不同颜色分别对应源码、汇编等不同层级；这些对应关系你们应该比我熟，这里不展开解释。

**47:08**

接下来要把规约塞进汇编代码。比如黑色的汇编代码表示一条规约：对于 \(b=a+3\)，正常情况下 \(b\) 应大于 \(a\)；如果 \(b<a\)，就说明发生了溢出。这里 \(a_1\) 和 \(a_0\) 是寄存器，\(a_1\) 存 \(b\)，\(a_0\) 存 \(a\)；发生溢出后 \(b\) 会小于 \(a\)，所以检查 \(a_1<a_0\) 就能发现溢出。规约要以 assertion 的形式嵌入汇编。类似地，也可以检查 \(a\times b\)，并把相应规约嵌入进去。

**48:05**

嵌入之后，系统会生成一个需要证明的性质。简单说，如果程序满足这些规约——例如功能上的 assertion 和 memory safety assertion——那么它的返回值一定是成功状态（exit OK）。

**48:41**

然后系统直接写一个 prompt：已经给出带有规约的汇编代码，让 agent 拼命写 proof 来证明它；同时提醒 agent 不要作弊，不要做没有真正证明的假证明。这是一个非常简单的任务。以前证明十行代码可能要写两百行证明；现在证明十行代码，只需要写一个 comment 就可以了。接下来整个大模型就开始证明这件事情。

### 大模型生成证明的过程

**49:16**

在讲证明系统时，证明过程中会引入规则。这里给大家看一下大模型自己写的 proof，它会先做规则引入，然后做定义引入，再做等价替换。等价替换的意思是：有些定理和另外一些定理等价，于是用等价的定理进行替换；这就是我们当时做证明时用的方法。

紧接着它会做 generalize。generalize 就是把表达式中的量词去掉，或者再引入量词，把它泛化成一个范式，然后再引入一些规则。这里有一个规则是 reflection，它实际上是一个引理；引入这个规则之后，证明就可以继续证出来。

这就是大模型自己写的证明。最后一步它唯一要做的，是检查整个证明有没有通过；如果没有通过，就报错，让它重新跑。

### 代码验证与 spec-first

**52:04**

用 VeriFast 来证明已经写好的 C 代码，是一种做法：代码已经用 C 写了，再对它做验证。也可以把它用于找 bug。还有一种做法是直接用验证语言来写代码。这两种做法有什么区别？区别在于，直接用这类语言写时，验证是内建在写法里的；而拿工具去证已有语言的代码时，有些特性它其实处理不了。

我觉得这一点在未来很重要。我们整个团队就在做这样的事情：把对过去已有代码的验证和对未来代码的生成放在一起。现在有一种叫 spec-first 的开发方式：我只写规约，生成的代码 by construction 就带有证明，从而是自动验证的。这就叫 spec-first。

### 验证工具链与最终答案

**53:24**

因为会有验证器去 check 我写出来的东西。下面跑的不是大模型，而是 VeriFast 和 Z3 solver。也就是我讲过的那一套：符号执行（symbolic execution）加 Z3 solver。它会一步步去推，检查前置条件加上代码是否能推出后置条件，最后推出规约。

如果推不出来，大模型会去检查：到底是代码有问题，还是证明有问题。然后它会 fix。在 fix 的过程中可能会走很多弯路，比如本来是证明有问题，结果把代码改了；但这都不重要。最后它交给人类的答案是一套证明：我们写了一个规约，它交的答案是这套证明可以证明它生成的代码满足规约。只要代码符合规约，就可以保证代码是对的。

最后的验证实际上是用验证器证的，不是大模型证的。
