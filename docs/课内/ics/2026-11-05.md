### 缓存结构的组成与开销

**05:56**

它被分成若干个组（set），每个组里面有若干 cache line，按相联方式组织，这里会有一个相联度（associativity）。这里给出了一个 cache 大小的计算：整个 cache 会占这么大的地方，但从 cache 的角度来说，我们就是用 cache 来缓存数据的，所以真正有用的部分其实是后面放数据的部分。valid、tag 这些都属于额外的 overhead，它们没有直接贡献数据容量，但是必需的，没有它们就做不了这个 cache。从 cache 设计的角度来说，第一条肯定是让放数据的面积足够大：花了钱买 cache，当然是里面能放数据的有用部分越大越好。在这个基础上，再去综合考虑访问它的速度等各方面的因素。

### 从地址查找数据：最朴素的设计

**07:02**

cache 使用时，我们手里只有地址：程序手里有的是地址，所以 cache 的使用就是“我给地址，它返回结果给我”。要到 cache 里面找数据，就必须从自己的地址出发。那么最简单、最朴素的设计，或者在没有专门设计的情况下，大家会怎么设计 cache 呢？就用一个 C++ 中的 set，或者一对一的 mapping：我给一个地址，对应一个数据。这样也可以做到一个 cache。但你会发现，这个时候 cache 的有用部分只有多少？我用地址，在 map 里面要把地址全存下来，进行一一比对，然后才能把数据取出来。如果一个地址对应到，比如说 8 bytes，那么地址也是 8 bytes，这样有用的部分就只有 50%。

### 从 map 到地址划分

**08:12**

这种用 map 一一对应的 cache，查找时要逐项比对，速度也比较慢，可以认为它是一个最差但还能工作的 cache。接下来的 cache 设计，就是在这个基础上提高利用率、降低查询开销。

虽然这节课和上节课开始时已经给出了一个答案，我们不必自己去重新发明，但看到答案时仍要理解它为什么这样设计。先看地址：书上或课堂上会把地址分成三个部分——tag、set 和 block，也就是 b 这部分。

### 块内偏移为什么放在低位

**08:51**

古老师上课前还叮嘱我，上节课最后留下来提问的是小戴同学。他留了一个问题，让你想 block index 为什么放在低位。我记得上课时应该会讲 tag 和 s 的位置：为什么 tag 在高位、s 在中间。还有一个更基础的问题：为什么块内偏移 b 放在低位？小戴，当时他让你想一想，你有想过吗？其他人也可以想想：b 为什么放在低位？它是用来在块内定位的。

比如一个块有 8 个字节，其实很小，就要用 3 个 bit 来编号。这 3 个 bit 决定一次访问中取到的是块内哪一个字节。因为在这个模拟场景里，输入一个地址，取回来的单位是一个 block。拿到地址后，用后三位决定块内偏移，前面的位用来匹配、找到某一行，再把这一行里的 block 取出来。

现在问：b 放在低位，能不能放在高位，或者放在其他位置？如果能，为什么放在低位更好？

### 块内偏移与程序局部性

**10:52**

对。如果 b 不放在低位，那么放进去的这 8 个字节在 memory 里就不是一块连续的，地址不连续。并不是说不能做：我可以去 memory 里找这 8 个东西，再把它们放到 cache 里；用地址去索引也仍然找得到。但显然这不是正常的设计思路，大家不会这么设计。因为第一，memory 和 cache 之间交换的代价会很大。

第二，它不符合程序局部性。上节课的 slide 里提到过空间局部性：程序很可能会连续、按顺序访问。cache 如果设计成连续取，那么第一次 miss 之后，后面的访问就会变成 hit。空间局部性最典型的例子是数据有空间连续性，比如访问数组、矩阵，写一个 for 循环。

代码里其实也存在空间局部性。如果没有 jump、branch 这样的操作，指令也是一条一条下来的。

### 指令 cache 与数据 cache 为什么要分开

**12:25**

在冯·诺依曼架构里，代码也作为数据被加载；CPU 执行时一条一条取指令，所以指令也有 cache。L1 这一层最接近 CPU 的 cache，实际上分成指令 cache 和数据 cache，二者要分家。分家的思路很简单：取指执行时用指令，中间发生数据访问时再去访问数据。

如果把它们混在一起会怎样？这两件事本身都有 locality，但它们是独立的 locality。放在一起时，我取指令取得好好的，要去访问数据，就跑到另一个地方了。大家看过反汇编出来的代码就知道，code 和 data 也不在一块儿。所以各自看有 locality，但只是局部的 locality；如果混在一块儿，整体就没有 locality 了，交错的过程中没有 locality。

### 时间局部性与软硬件的相互塑造

**13:29**

但很重要的一点是，locality 不只有空间局部性，还有时间局部性（temporal locality）。时间局部性现在比较简单：会对同一个数据重复访问。比如对全局变量、局部变量会重复访问；for 循环里的 i 在做累加时反复访问，这就是时间局部性。原来位置的指令也会存在时间局部性：一个 for 循环会在一段指令里重复执行。所以它们合在一块儿称为 locality，locality 其实是两个维度。

有了 locality，硬件设计会去匹配它。但这也是一个相互影响的过程：因为程序是这样，我们提出了缓存思路，有了 cache；反过来，因为硬件设计成了这个样子，程序也会更有意识地把代码写成有 locality。前面举的例子是程序天生、自然写出来就会有的 locality。但在更多情况下，应该让程序更偏向 locality。原来什么都不做、按逻辑写出来的程序，locality 可能也有百分之七八十；今天这节课会介绍，大家应该尽量把程序写成百分之九十、百分之一百有 locality，提升它的 locality。这样在硬件上跑才能跑得更好。

这是性能优化里很重要的一点，其实是一个相互交互的过程。硬件设计会考虑上面的负载；反过来，实际的编程也会考虑程序跑在什么样的硬件上。这有点像先有鸡还是先有蛋的问题，不能说谁先开始，但软件和硬件肯定会越滚越匹配。

### e 为什么没有编码进地址

**15:26**

刚才讨论的是 b。现在问一个问题：这里有 s、有 t，但结构里有 b、有 t、也有 s，那 e 去哪儿了？e 为什么没有在地址里体现出来？为什么不需要把 e 也编码进去？

其实我们在检查和查找的时候，已经把这个结构体现出来了；这个地址，或者说按照这个结构去放置数据。你们有没有想过这个问题？当然我现在每个问题听上去都很简单，好像是专门找出来的问题。e 不编码进地址，好像也可以，那 e 代表的是什么部分？

### e、s、b 与 cache 地址的灵活性

**16:22**

从结构上看，e 表示一个组里面的行数。e 没有编码到地址中，是因为在组内进行匹配时，这 e 行都有可能出现，都需要去比较。地址并不用来区分数据到底放在组内的哪一行：放在这一行或那一行都可以，这体现了放置时的灵活性。

在整个 cache 设计中，e 代表灵活的部分；b 是固定的，而且是为了利用局部性而固定；s 也是固定的设置。把 s 编码到地址中，就意味着这个地址只能进入确定的一个 set，没有挑选的余地。

### 直接映射

**17:27**

如果把 e 变成 1，也就是每个 set 只有一行，这也是一种 cache 设计。上节课介绍过这种设计，当时可能叫 direct mapping，也就是一对一映射：一个地址只能放到固定的位置，没有任何灵活性，只能去那个 set。这是上节课很重要的一点。

### 直接映射的查找开销

**18:08**

这种设计有什么优点？有人会说没有延迟，但这太夸张了；世界上不可能没有延迟。需要看延迟主要落在哪一部分，也就是查找开销。

访问 cache 的时间可以分成两部分：先查找，再把数据读出来并加载。直接映射下，一个地址只能去一个确定的位置，因此查找开销相对较低；但也不是没有开销，仍然要到这个确定的位置比较 tag。

### 全相联：另一个极端

**18:51**

另一个极端是 e 很大，而 s 没有固定的部分，只剩下灵活的部分，相当于只有一个 set。也就是说，整个 cache 中的位置都可以放数据，这就是全相联映射。

这样看，直接映射和全相联像是两个极端的设计：一个只有固定位置，没有灵活性；另一个只有灵活性。不过，在我的理解中并不存在三种模型的对比，从来只有一种 cache 模型，区别只是配置。这里先介绍的是 design space 的两端，它们的优缺点非常明确。

### 两种极端的取舍

**20:18**

直接映射的查询非常快，但因为限制了数据能放的位置，会出现 conflict miss。简单说，cache 里明明还有位置，数据却只能放在这里，或者有另一个数据来抢同一个位置，cache 的利用率就会特别低。

全相联则是有位置就可以坐。可以把它类比为电影院的票：直接映射像固定座位票，缓存又存在超售，一个位置可能卖给多个数据，大家来抢同一个位置；而全相联像不指定座位的票，只卖票，哪个位置都可以坐。

两者的优缺点正好相反：直接映射查得快，但容易出现冲突、利用率低；全相联的缺点是查找慢，因为所有可能的位置都要查一遍，找不到时还会比找得到时慢很多。

### 组相联与存储层次

**21:35**

因此又引入了折中方案：把 s 和 e 结合起来进行配比、进行设置，让两边可以权衡。这个说法没有错，但还需要回答一个问题：在什么情况下用哪一种配置。不能简单说某一种最好，因为折中的方案本身也需要设置。

这时要看到，整个 cache 处在所谓存储金字塔中。虽然这次 PPT 没有专门强调金字塔，但存储是一层一层的。

### 寄存器与系统 cache

**22:16**

存储层次最上面是寄存器。寄存器其实可以看成直接映射，例如 RAX 就是直接对应的寄存器。它下面是缓存。这里要区分“缓存”这个词的两种用法：cache 既是一种技术、一种优化方法，也常被用来指 CPU 里的硬件 cache。为区分，后者有时称为系统 cache。整个存储层次都使用了缓存技术，而寄存器和 memory 之间这一部分也叫 cache，它是物理上的 system cache。

### 内存的全相联特性

**23:06**

现在知道 cache 会有多层，L1、L2，现在基本上采用 L1 到 L3 的三层结构。再往下是 memory。内存管理还没有上，后面谷老师可能会讲。内存管理中存在这样的操作：把磁盘上的内容读进内存，返回一个地址，也可以 malloc 一块空间。因此内存其实非常灵活，属于全相联。

虽然我们会人为固定区间，例如把代码放在 code 区、数据放在 data 区，但理论上 memory 没有任何限制，数据放在任何一个地方都可以正常工作，所以它是全相联。

### L1 的相联度如何选择

**23:57**

中间的 cache 有三层，L1、L2、L3，它们的设计都采用组相联。设计上也会分大小，例如两路、四路、八路、十六路。那么 L1 应该取哪一个？是往大了取，还是往小了取？

### L1 与 L3 的路数选择

**24:33**

L1 应该往大了取还是往小了取？有做题和考试经验的同学很容易判断：往小了取。因为前面已经给出了层次关系，从设计趋势看，越靠近 CPU 和寄存器，L1 的路数相对小，L3 的路数相对大，这符合 cache 的设计方向。现在要倒推：为什么靠近寄存器的 L1 通常采用二路或四路组相联，而不采用八路、十六路或更大的路数？为什么 design space 中的灵活性在靠近寄存器的一端要收窄？

### 设计空间中的灵活性

**25:25**

design space 本身有一个变化趋势。答案容易得到，但更重要的是倒推：什么因素决定路数设计，为什么 L1 要倾向于较小的路数？可能有很多因素，先看最主要的因素，再看其他因素。以后大部分人不会去设计 CPU 的 cache，但课程介绍 cache 技术，是因为它会出现在各个场景中，例如大模型的 KV cache，也会遇到同样的 design space 问题。这里的“路”代表灵活性：越靠近寄存器，灵活性越要收窄；越往 memory 一端，灵活性越可以放宽。为什么？有同学愿意回答吗？

### 命中率与冲突缺失

**26:39**

有同学从灵活性会导致 conflict miss 的角度分析：越灵活，利用率相对越高，conflict miss 越少或越低；路数越高，利用率越高，cache 命中率也越高。但这是优点，放在哪一层都成立：L1 需要命中率，L3 需要命中率，memory 也需要命中率。因此，提高命中率至少不是最重要的区分指标。也可以反问：L1 的命中率不是更重要吗？如果在 L1 miss，就要访问后面的层次；反过来，后面作为兜底也需要更高命中率。总的来说，命中率可能是需要考虑的因素，但不是最明显的因素。

### 从 working set 比例看冲突

**28:34**

所谓明显的因素，应当是它对 L1 很重要，对 L3 却不重要。讨论到比值时，需要先分清是 tag 大小还是 cache 总大小。若保持 cache 总大小不变，只调整组织方式，cache 的有效存储部分不变。这里比较的不是 cache 与 memory 的比值，而是 cache 容量与程序数据的比值。L1 较小、L3 较大，比例可能是一比八或一比十六；比例越大，越容易发生冲突。更具体地看程序的一个 working set：L1 可能只能放下整个数据的百分之五，而 L3 可能放下百分之五十甚至更多，这样 L1 中重复冲突的情况可能更严重。沿着这个角度会推出 L1 应把路数设得高一些，这可以做比较深入的推理。但它并不是最重要的决定性因素；决定性因素应当是那种一听就知道必须这么做、不这么做会有坏处的因素。

### 查找时间与访存时间

**30:45**

cache 的优势是查找速度，但一次 cache 访存，无论 hit 还是 miss，速度都由查找速度和访问速度两部分组成。降低组相联的路数时，查找所需的时间会减少。不过，查找时间对不同的 cache 意义不同。匹配查找的时间基本上恒定：在 L1 中查找和在 L3 中查找没有本质区别，它主要取决于 tag 的数量和设计的灵活性；但 L1 和 L3 的访存速度不同。举例来说，L1 访存可能是 10 个 cycle，L3 访存一般是五十到一百个 clock。再假设查找匹配需要 5 个或 10 个 clock；组相联路数较高时，例如十六路以上，可能需要 20 个 clock。从 10 到 20 是否重要，并不只是看它变成了两倍。

### 优化查找延迟的收益取决于占比

**32:40**

能否从优化中获益，取决于被优化部分在端到端时间中的占比。对 L1 来说，把查找时间从 20 个 cycle 降到 10 个 cycle 很重要：原先 20 个 cycle 的查找加上 10 个 cycle 的访存，共 30 个 cycle；优化后变成 20 个 cycle。若再把查找时间降到 5 个 cycle，总时间会进一步明显下降。对 L3 而言，同样从 20 降到 10，感觉就不大：一次访存取数据约需 100 个 cycle，总时间只是从 120 变成 110。最大的因素是你想优化的查找在整个时间里的占比。因此优化一定要针对占比大的部分。在 L1 上，匹配、查找时间和读数据时间非常接近，所以查找很重要；到了内存这一层，从内存取数据要约 200 个 cycle，多花 10 个 cycle 做匹配影响不大。实际匹配可能在一个 clock 内完成，甚至更快。这也说明为什么越靠近上层越需要优化查找速度。

### 为什么常见二路、四路相联

**34:22**

最后一个问题是：缓存设计通常采用四路、二路相联，为什么不用一路？在命中路径上，一般除了直接映射这种受限情形，不会只设计一路；常见的是二路、四路。一个重要原因是，一路和四路在速度上可以一样。做软件时不容易理解：只和一个 tag 比较，为什么和四个 tag 比较速度一样？硬件中广泛采用并行方式：四路有四个比较电路同时比较，比较结果再用一个门电路汇总，就能知道是哪一路命中。相联度也不会无限增加，一般到 16 路、32 路左右就差不多了。再往上电路太复杂，复杂度会限制路数。

### 缓存结构与替换策略回顾

**35:31**

回顾上节课介绍的 cache 结构。通过 cache 设计，主要想了解一个缓存设计最重要的几个部分；其中缓存的结构最重要。接下来是缓存上的策略：放置策略受结构限制，没有太多设计空间；替换策略则决定把谁踢出去，例如采用 LRU 还是 LFU。策略相关的研究这里先过。

### 存储金字塔与逐层缓存

**36:23**

最后看存储金字塔。现在这张图已经画得不太像金字塔；如果看书，金字塔的形状会更明显：从寄存器到内存，再往下，中间是缓存。这里有一个问题：寄存器和内存之间是缓存，缓存本身是一种方法、一种技术。硬件的 cache 是内存的缓存，内存又是磁盘、外存的缓存；每一层既充当下一层的缓存，也被上一层缓存。这样一层层往下，构成 hierarchy 金字塔，往下还可以到磁带；现在最新的研究甚至可能用到 DNA。最下面这一层如果直接放到 DNA，可以把全世界的数据都塞进去。总的来说就是一层一层往下缓存，这种技术到处都有。但是什么时候需要增加一层？

### 什么时候需要增加一层缓存

**37:45**

这个大的概念大家都懂：缓存很好，设计需要灵活性，需要 trade-off。真正要问的是：什么因素决定要增加一层，什么时候又还不到时候。最早计算机没有 cache，CPU 直接面向 memory；后来不够，加了 cache；L1 不够，又加 L2；大约 2000 年出现 L3，现在没有再继续增加。为什么当时要增加，为什么现在又不增加？这决定了 cache 主要用来解决什么问题。最初的问题是内存太慢：CPU 很快，memory 太慢，读一个数据太慢。碰到速度问题，优先想到缓存。学完这门课，当一个程序、整个系统跑起来，算法等都确定后仍然觉得慢，第一反应也应该是用缓存思路：缓存提供了一条更快的路径。

### 成本、局部性与速度差距的估算

**39:11**

在存储这边，缓存主要来自硬件特征：可以把硬件设计得很快，但很贵，成本最终是问题。因此要在速度和容量之间做 trade-off：利用 locality，把快的部分做小一点，把便宜的部分做大一点。缓存用来解决速度问题，增不增加缓存取决于速度——发现太慢，就增加缓存。但“太慢”不好衡量：多慢算慢？有人觉得一秒可以忍，有人觉得一百毫秒都不能忍。所以关键问题是：两层之间的速度差距达到多少时，我们会尝试往中间插一层；或者按现在存储的角度，两层之间的速度应控制在多大。这个大概怎么估算？做计算机设计需要很强的估算能力，不需要很精确，但要大致知道。

### 缓存层次的估算依据与命中率

**40:44**

增加一层缓存，或者说把两层之间的速度差控制在什么范围内，需要有一个道理和依据来估算，这个范围是怎么得出来的。也可以从合理、能够自圆其说的角度来估计，例如看两层之间的流量是否大致相当，或者下层比上层更大，再借用上面的计算方式；这只是其中一种估算方式。从流量角度看，就是访问数据时有多少能在上面一层拿到、多少要到下一层拿到，并希望找到一个平衡。比如一半数据从 L1 拿到、一半从 L2 拿到，这种设计本身合理，但比例不一定合适。实际上，L1 缓存的命中率大约在 95%；L2 这边，CPU 上程序的缓存命中率应该达到 97%，L3 可能更大。可以看到命中率一开始就要到百分之九十几。为什么要大于百分之九十几？这其实就是要控制缓存，而且要做到这样的程度。

### 平均访存时间与层间速度差

**42:19**

这个百分之九十几的缓存命中率也决定了层与层之间的速度差。可以这样算一笔账：程序整体的访存速度，是把每一次访存的时间加起来求平均。每次访存只关心它从哪一层来，简单起见先设计两层。如果第一层命中率达到刚才说的 95%，那么整体性能就是第一层的访问速度，加上 5% 需要从第二层拿数据的部分。假设第一层访问速度为 \(x\)，第二层为 \(y\)，平均访存时间大致为
\[
0.95x+0.05y.
\]
如果第二层比第一层慢 10 倍，那么 0.05 × 10 = 0.5，平均时间约为原来的 1.5 倍；原来为 1，现在因为缓存不命中，整体响应时间变成约原来的 150%。这时就要考虑它会不会拖慢整个 CPU 的执行。可以认为访问寄存器不会拖慢执行，在指令集中寄存器访问和计算指令基本在同一数量级；到了 L1 会慢一些，大约慢几倍。当然不希望整个程序因为这部分未命中惩罚被拖慢很多。因此，两层之间的性能差通常控制在一个数量级。若原来相差两个数量级，中间就要插一层，把它分成一个数量级。

### 多级缓存与 CPU、内存的速度差距

**44:46**

对于内存访问，现在的延迟大概在 200 个时钟周期左右，大部分是 200 个时钟周期。因为 CPU 和内存之间存在两个数量级、数百倍的差距，所以中间被插入了三层缓存来缓解这种情况。插入多层缓存并不只是缓存这一个原因；L2 和 L3 之间的差距其实没有那么大。总的来说，两层之间会控制在 10 倍以内。当前未命中率大约控制在 2% 到 3%，所以当性能差达到 10 倍时，算下来的平均速度约为上一层 L1 性能的 1.2 到 1.3 倍，仍在 1.5 倍以内。这也就解释了为什么现在不再插 L4。而之前插 L1、L2，是因为 CPU 当时有一段时间快速变快，内存速度却上不去，频率上不去。最初机器刚造出来时，内存速度和 CPU 速度是一样的，因为它们的工艺没有太大差别，都是门；二者最初大致在同一数量级，甚至内存可能略快一点，因为它更简单。但随着工艺发展，二者的差距迅速拉开，现在已经达到数百倍。所以中间经历了几次增加缓存，差一层不够就再加一层，目的是保证 CPU 变快时不会被内存访问拖慢，否则 CPU 变快就没有意义。

### 写操作与缓存一致性

**46:43**

这是对之前课程的简单回顾。今天的内容其实不是很多，也比较简单。前面考虑的都是读操作，即读缓存；这里要引入写操作。课件给了一个例子，我觉得这个例子关系不是很大。它说明存在一种攻击：数据被读入内存之后，另一个人可以把它改掉，然后利用被改掉的权限去做一些事。但它更想说明的是，缓存这项技术看起来很好用：速度不行就加缓存。远程下载电影太慢，就在本地放缓存服务器；十年前全校转播世界杯时，一栋楼里有一个人看了之后，大家再看就会比较快，因为数据和信号已经拿过来了，可以共享。缓存好像非常好，但缓存会带来一个非常重要的问题，需要记住：在计算机里提出一个好方法，把之前解决不了的问题解决了，往往会带来新问题。缓存带来的非常重要的问题，是它会让同一份数据出现在两个地方，或者出现在多个地方，于是存在一致性问题。前面那个攻击的背景，其实就是同一份数据出现在两个地方，到底以谁为准。或者说，在什么情况下保证它们一致，在什么情况下保证不一致。最简单的情况是内存会掉电：内存修改之后，如果不写回磁盘，系统崩溃就会丢失。所以以前机器崩溃之后，会出现之前的 PPT 没保存、Word 没保存的情况。原因就是增加了缓存，而磁盘太慢；每次在 Word 里修改、敲一个字母或删掉一个字母，重新写之后都不会落盘，因为落盘太慢，受不了。它们之间差几百倍，差距非常大，所以后来才会有 SSD。

### 缓存的写回与一致性

**48:51**

缓存必须写回。如果每次写都立刻写回，缓存就基本失去作用；但如果一直不写回，又会出现不一致的风险。因此第一个要讨论的策略就是写。此前只考虑读时，缓存确实能提高读取速度；一旦碰到写，我把某个数据改成 2，同一份数据就同时出现在缓存和内存两个地方，二者可能不一致。如果此时发生崩溃，就会带来可靠性问题：结果是否仍然正确？

好消息是，在 cache 和 memory 之间，暂时不必过于担心一致性问题：断电或崩溃时，CPU 和内存会一起失效；磁盘则不会一起失效。但缓存仍然必须写回，因为计算结果最终要更新到内存。

### 缓存层级与平均访问时间

**50:20**

访问一个数据的时间由查找时间和读出时间共同决定。L1 和 L3 的读出时间差别很大：L1 的设计和工艺使其更快，通常只有三四个 cycle，L2 则要几十个 cycle。查找匹配是比较电路，与具体层级关系不大，L1 和 L3 的匹配性能可以认为相同。

问题在于路数：路数越大，查询时间越大。如果从一路变成两路，查询时间可能相应增加。原本访问 L1 可能只需三个 cycle；如果 L2 的速度比 L1 慢一百倍，那么一次访存中，假设 L1 命中率为 99%，100 次访问里有 99 次命中 L1，1 次访问 L2；访问 L2 后再把数据装入 L1，并从 L1 读出。把 L1 的访问时间归一化为 1，平均访问时间可以写成 \(0.99 \times 1 + 0.01 \times 100\)，接近 2。也就是说，平均访问时间大约翻倍。

为了不让整体性能被 memory 缓存拖累，需要再插一层缓存，把性能下降控制在百分之几十。至于这个百分之几十与两倍是否可接受，是当前设计要权衡的问题。

### TLB 与页表

**52:50**

有同学提到高通的 TLB 设计问题，以及 TLB 缓存如何工作。教师表示没有太看清它是如何协作的，并确认问题是在问 TLB 怎么工作。页表这件事虽然还没讲，它属于 MMU；查找时会牵涉到虚拟地址。要在很大的地址空间里找到对应项并不容易。页表用来帮助查找，完成虚拟地址到物理地址的映射。

查找时要查页表，而页表本身很大，也存放在内存中。为了找数据 a，拿到 a 的地址后，页表还要被加载到 cache 中，再逐级查找，因此非常慢。思路就是“凡是慢就加缓存”。TLB 就是页表项的一个 cache，就像指令有 instruction cache、数据有 data cache 一样，TLB 缓存的是页表中的映射关系。查找时先从 TLB 找；TLB 命中就直接知道数据在哪里，然后直接访问 memory；TLB 未命中再去走页表。因此 TLB 也是一种缓存，只是缓存的内容不同：有的缓存地址，有的缓存指令，有的缓存数据，而 TLB 缓存的是映射关系。

有同学又提到“TLB 合并”。教师说不知道这具体指什么；如果指的是能否用一条 TLB 项存好几条映射，那也是一个问题。

## 计算机系统基础（1）｜第 10 节（16:50）

### Cache 中 tag 的压缩

**00:00**

这种技术可以看 tag 的例子：一个 block 连续存放了多个地址，不必为每个地址都存一份 tag。因为块内偏移对应的地址低三位没有用，tag 也不必保存完整地址，只保存地址中的一部分即可。这实际上是在缩减 tag 所占的存储，降低 overhead。原来一个位置只能放下一个映射；经过压缩、合并之后，在没有增加硬件的情况下一个位置就能存三个，那当然很好。

### 写操作与写回的必要性

**04:30**

继续看写操作。如果数据已经在 cache 里，又被更新了，那么 cache 中的内容就和后面的内存不一致了，怎么办？如果不写回，一旦数据丢失就会成为问题。前面也说过，在这个层面，cache 与内存一致性的问题不需要过多考虑；但它至少告诉我们：数据总是要写回的，否则这个操作就没有意义。如果只在 cache 里面做修改，最终一定要写回去。

### 写直达与写回

**05:33**

现在的问题是：什么时候写回？这是一个策略问题。一种策略是写直达（write-through）：每次写的时候马上更新到内存。这看上去不像一个好设计，因为写内存的开销很大，cache 在写操作上就没什么帮助了。另一个策略是写回（write-back）：每次写的时候不写回，等到这个块要从 cache 中被 evict 掉，或者程序结束时才写回。它可以吸收写回的次数：可以写一百次，只往下层写一次。这是它最大的优点。因此写回是尽量要使用的策略，效果更好，也能解决前面提到的问题。

### 写回在替换时的代价

**06:43**

那么写回在什么情况下会带来问题，或者说写直达在什么情况下有优势？写回的问题不出现在写操作上，而出现在替换的时候：如果要替换一个被修改过的块，就必须触发一次写回。从 L1 到 L2 的访问性能可能差十倍，会比较慢，所以这是一个问题。写直达的好处是：每次更新都会同步到下层，因此要把块踢出去时不用写回，直接踢掉即可。什么时候会踢它？在访问读的时候，如果没有读到，就要把数据拿上来，同时踢一个块出去。如果用的是写回，这次 miss 的时间很可能更长，因为 evict 时还要处理写回。不过大部分情况下我们仍然会选择写回策略，因为它显然性能更好，吸收了写操作。

### 脏位（dirty bit）

**07:59**

但是要实现写回，原来的结构就不够了，需要增加一个 bit，叫做 dirty bit。必须知道这个块要不要写回。如果没有这个 bit，就无法判断它是否被修改过、驱逐时是否需要写回。

### 脏位与写回

**08:12**

因此，默认情况下都要写回。但很多时候一个数据是只读的，或者这次并没有修改，所以需要用一个 dirty 位来区分要不要写回。有了这个位之后，把缓存行踢出时就可以先判断：要写回就写回，不要写回就直接剔除。因为内存里本来就有这份数据，不需要再复制回去，也不会担心数据丢失。

### 替换策略与 valid、dirty 位

**08:37**

dirty 位还会影响替换策略。同样是踢出一行，LRU 会选择最近最久未使用的那一个，LFU 会选择最近使用频率最低的那一个。但这些策略都是在没有更好选择的情况下才考虑。更优先的是空行：先判断 valid 位是否为零，优先把数据放到 valid 为零的缓存行；其次判断 dirty 位是否为零，因为替换这样的行不需要写回。只有这些情况都不存在时，才讨论到底踢谁。可见写策略不只影响写操作，也会影响读和替换。

### 写命中与写缺失：写分配与写不分配

**09:47**

上面讨论的是写命中：数据已经在缓存里，只需考虑写完缓存之后要不要写到下一层。如果写的时候发生 miss，缓存里还没有这个数据，一种做法是先把数据加载上来，修改后再放回去。这种策略叫写分配（write allocate）：写的时候数据必须出现在缓存中，没有就先读上来再写。还有另一种选择，叫写不分配（no-write-allocate），也就是绕过缓存，直接写内存。选择策略时不能只看这个操作本身，还要考虑它对其他操作的影响。

### 写分配的好处

**10:58**

写分配的好处与程序访问特征有关。通常写完一个数据后，还可能继续写或读它。如果写 miss 时先把缓存行读上来，后续的写就能命中，后续的读也能命中，相当于做了一次预取。因此写分配使用得比较多，并且常和写回（write-back）结合使用，尽量让数据在缓存中发挥作用。这是写 miss 时的写分配。写分配看上去很好，那么什么情况下会采用写不分配，它又有什么好处？

### 写不分配的适用场景

**11:55**

先看写不分配。如果之后还要写，仍然是 miss；如果要读，也是 miss。因此，重复写同一数据的程序用它没有好处。它适合写一次的情况：写操作不会污染缓存。这里的污染是指，如果写完以后这个数据再也不用了，而采用写分配，缓存行会被它占一个位置，甚至可能把别的行踢出去；这个预取就没有取到将来要用的数据，反而有坏处。所以对于只写一次的日志、最终输出等写完后不再读的操作，写不分配可能好一些。但这种情况相对较少。

### 写穿、volatile 与缓存一致性

**13:12**

而且这种只写一次的情况很难判断，程序员也很少自行控制。更常见的需要使用写不分配的场景，是必须写穿（write-through）的时候。程序中可以指定这种语义。以前可能认为它只影响寄存器，实际上有 volatile 这样的修饰：结果不能只留在寄存器，也不能只留在缓存里，必须写回内存。这样做是为了解决一致性问题，让写操作能被别人看到。

这也与硬件结构有关：缓存位于不同 CPU 上，L1 和 L2 是 private 的。一个线程写在缓存里的结果，另一个运行在其他 CPU 上的线程看不到，于是出现不一致。这时就要强制把缓存刷回去。各种策略都有存在的意义，只是适用范围大小不同。一般情况下，通用方案是写回（write-back）加写分配（write-allocate），因为性能相对较好，也适合程序中一个数据会被多次读写的常见假设。

### 平均访存时间与命中率

**14:51**

下面看性能指标。平均访存时间可以写成命中时间加上不命中带来的额外开销：

\[ \text{AMAT} = \text{hit time} + \text{miss rate} \times \text{miss penalty} \]

其中 m 就是未命中率，也就是未命中的百分比。miss 之所以比 hit 长很多，是因为两者性能差得很大。一次操作经过平均之后，如果命中率是 95%，就有 5% 的操作去乘 miss penalty。如果 miss penalty 已经达到两个数量级，最后的平均结果可能差六倍。

原本 L1 可能可以满足 CPU 的速度，但实际平均访存速度变成 L1 的六倍。不是每一次都单独变慢，而是单次不命中可能慢一百倍，平均到整体上程序就慢了好几倍，这是难以接受的。所以一般要把这个倍数控制在一个数量级以内。前面的命中率也解释了为什么缓存命中率要做到 97%、98%、99%：95% 都无法接受，整个系统会慢一倍、两倍。

### 缓存命中率与不命中率

**16:23**

缓存不命中会让程序跑慢六倍，这是无法接受的，因此缓存设计一定要提高命中率。这也解释了为什么大家更关注不命中率而不是命中率：如果说命中率从 95% 优化到 97%，听上去像是在开玩笑，这个工作似乎没有意义；但实际性能可能从慢六倍降到慢三倍，仍然是很大的改进。反过来，把不命中率从 3% 降到 1%，听上去就非常重要。

### 缓存设计的权衡

**17:17**

缓存有很多设计参数。它是一个典型的系统设计问题：单独看每一个指标或策略都不难理解，但写策略会影响读和替换，一个设计必须和其他设计放在一起整体考虑，因此整个设计会变得非常困难。基础是先知道每个策略或配置的影响，再做综合权衡。

**18:02**

例如容量：把 cache 做大当然能提升性能，似乎没有代价；其实最大的代价是成本变高。手机 256 GB 和 512 GB 的存储价格差得很远，笔记本增加内存或存储也会贵很多。容量受成本限制，而成本不简单，因为预算要花在整个存储层次上：L1 花多少、L2 花多少、L3 花多少，需要统一考虑。

**18:49**

再如块大小。一次访存 miss 时，cache 会把整个 cache line 取上来，相当于做一次预取。那为什么不把块做得更大，甚至一次 miss 就把整个内存都取上来？因为取上来的数据如果不用，就会占住 cache，影响命中率，并在这里造成 miss 惩罚。所以块要大，但不能太大。块大小定义了一次 miss 取多少数据。

**19:41**

块大小在不同存储层次之间通常不同，越往上越小，越往下越大。cache 从下一层取数据通常按一个 cache line，约 64 字节；磁盘往内存取时，过去是 512 字节，现在更大，例如 4 KB。从远端取数据时，一部电影甚至可能整个被取到本地，所以越往下块越大。再加上组相联大小、写回策略和替换策略，这些一起决定 cache 设计的最终效果。

**20:34**

因此 cache 设计是很复杂的系统工程，不指望把所有细节都想明白，但需要了解 cache 技术很重要，以及如何设计 cache。接下来进入另一个主题：如何写缓存友好的代码。前面讨论的是如何设计 cache 让程序跑快；程序本身不是死的，也可以写得更适合在 cache 上运行。缓存友好与不友好可能差别很大，否则随便写即可；是否优化取决于优化带来的效果。

### 缓存友好代码与访问步长

**21:26**

例如按 i、j 的顺序依次访问，一开始会不断命中。这里还有一个步长的概念：如果逐个访问，局部性很好；如果跳着访问，也有局部性，但效率会降低。这种跳着访问的间隔称为 stride（步长）。按顺序 sequential 访问最理想，能完美衔接程序的访存，CPU 甚至感觉不到访存带来的影响。

**22:10**

因为顺序访问时数据都已被取上来，甚至第一次 miss 都可能不存在。CPU 硬件并不笨，会做预取，而且预取得很好；如果按字节逐个访问，甚至可能一次 miss 都不出现，因为它会提前把后面的 cache line 取下来。但如果一次取上的 cache line 只用一点点，利用率就会降低；如果访问跨越多个 cache line，甚至每次都可能 miss，没有命中。

### 矩阵乘法与循环顺序

**22:49**

前面那个例子在现实中似乎不太会出现。下面看一个经典例子：矩阵乘法。二十年前讲这个例子时，大家可能觉得太 toy，认为自己不会写矩阵乘法；但现在不一样，大家要写的代码很多都是矩阵操作。

**23:28**

对同样的矩阵操作，在算法上不做任何优化，矩阵乘法按行乘列得到结果中的一个点，代码写法仍可能差别很大。计算一个点时就有三层循环；把整个结果算完，复杂度是 n×n×n，即 O(n³)，循环变量为 I、J、K。

**24:00**

IJK 其实有六种排列，都能完成矩阵乘法；只是所有操作的先后顺序不同，算法上没有差别，最终结果完全一样。下面比较这些写法在性能上的区别。IJK 是逻辑上最直观的写法：取一行的所有元素和对应一列的所有元素，计算出一个点。那么每计算一个点会出现多少次 miss？

### 矩阵乘法的访存顺序与 miss

**24:36**

在 IJK 这种最直观的写法中，访问 A 时局部性较好：一次 miss 之后，整条 cache line 中的数据大量命中。但访问 B 时情况就不好，B 的访问跨度很大。计算时会先取得整条 cache line，因此 A 的访问在一次 miss 后可以连续命中；而 B 在这个过程里则不断出现 miss。矩阵足够大时，取完一个元素后，下一次访问仍然会 miss。

粗略按每 8 个元素发生一次 miss 计算，A 的 miss 约为八分之一；B 基本每次访问都会 miss；如果把 C 的累加放在局部变量中，不产生额外的 cache miss。这样平均算下来约为 1.125 次 miss。另一种写法的访存情况与它相近。下面换一种访问方式来看。

**26:06**

这种访问方式是让 A 不动，先把 A 这个元素参与到的计算全部算出来。矩阵乘法的累加是可交换的，因此可以调整计算顺序。固定 A 的一个元素后，让它与 B 中对应的元素相乘，并把结果累加到 C 的相应位置；也就是先把这些操作提前完成。这样 cache 的效果非常好：A 放在局部变量中，B 和 C 的访问都是顺序的，具有空间局部性。得到的结果约为 0.2，性能非常好。虽然这种写法可能不符合通常的矩阵计算逻辑，但效果要好很多。

**26:58**

还有另一种更极端的写法：固定 B 的元素，让 A 不断移动，同时 C 的更新位置也在移动。这种实现的性能非常差。一般不会这样写，但确实存在这种很差的实现。

这说明同一个算法在实现上进行调整，可以得到不同的性能结果，差别可能有几倍，并且与 miss 的情况大体匹配。多数人按直观逻辑写出的代码，往往就是前面那种普通写法；但在不改变算法逻辑的情况下调整访存顺序，可以带来数倍的性能差异。因此，编写 cache 友好的代码非常重要。优化的基本思路就是提高局部性，具体问题还需要结合具体情况处理。

### 存储器山与硬件性能测量

**28:19**

下面用另一种方式来作分析，即存储器山（memory mountain）。这就是教材封面上那张很有名的图，但这套 PPT 里没有把它放出来。

相关测试想测的是硬件性能，同时也能测出一些硬件指标。例如，一台机器上的 cache 有多大，厂商可能会标出容量，但未必会说明带宽、几路组相联等更具体的行为和参数。问题是有没有办法自己把这些指标测出来。测出来有什么用处先不论，这里主要分析和解释它的行为：为什么可以通过测试把它测出来，以及测试结果可以用来分析硬件的实际行为。

### 数据集大小与步长的影响

**29:26**

这里的测试使用一个很大的一维数组，访问它时有两个影响因素：一是访问的数据集大小，也就是整个 memory footprint；二是访问时的 stride，即跳跃步长——是连续访问整个数据集，还是跳着访问。如果访问次数不同，性能当然会不同，因此实验中会控制比较的口径，最后看的是吞吐量（throughput），也就是单位时间内能够访问多少次，而不是单次访问的快慢。这样看的是单位时间访问次数，而不是总数据量本身。

需要观察的就是这两个因素——要访问的数据集大小和访问步长——会怎样影响性能。可以先考虑它们会造成什么样的趋势，例如 size 越大会怎么样。

**30:58**

当 size 从很小开始逐渐变大时，关键在于数据能放进哪一级 cache。如果数据足够小，能够放进 L1，程序会运行多次；第一次先 warm up，然后再正式运行。经过第一次 warm up 之后，后面的访问就都会是 L1 hit。随着数据变大并超过 L1，就会进入 L2 的情况：第一次 warm up 完成后，留在 L1 里的数据其实只是尾部的一部分，因此再运行时就会出现 miss，性能会比全部放在 L1 时差一些。数据再大，超过 L2，就会出现 L3 的性能。因此性能会下降，但需要考虑这种下降是线性的，还是阶梯式的。

**32:02**

第二个因素是 stride，也就是跳跃。连续访问当然很好，局部性能够体现出来。如果隔 4 个、8 个、16 个、32 个元素跳着访问，跳得越来越远，miss 率就会提高，命中率会逐渐下降。此时性能会呈现什么形状？它不是线性的，那又会是什么样？如果大家手上有教材，可以看看封面上的那张图：它是一座山，但并不是一座光滑的山。

### 内存山与工作集

**32:41**

这个结果并不是画成一座山，而是给出一组数据，用颜色深浅表示性能或缺失率的高低。横轴是 stride 步长，另一个轴是工作集大小；工作集很小、步长为 1 的位置就是“山顶”。它不是一个圆顶的山，而是半坡面；8K 附近还有几条像等高线一样的线，用来划分工作集大小。实测机器的 L1 是 48K，L2 是一点几兆，L3 是 24M。落在 L1 内、步长为 1 的区域性能最高，往其他方向走，整体颜色也逐渐变化。可以沿图切剖面：固定 stride，看不同工作集大小的影响；或者固定工作集大小，看 stride 的影响，这就是控制变量。

### 台阶效应与缺失率饱和

**34:27**

取步长为 1 和步长为 8 的剖面，可以看到明显的台阶效应。L1 和 L2 之间有差别；L2 内部未必有明显差别，后面接近边界时也不会刚好在某个点整齐地下降，而是超过一点后逐渐下降。原因是数据放不下时会引入更底层的开销，也就是 cache miss。步长为 1 时本身性能更好，所以这个台阶比较明显。

再看固定工作集大小、改变 stride 的情况：取 256K 和 128M 两个工作集，性能都会下降；256K 这边不明显，128M 这边分成两个区域。前一个区域随 stride 增大近似线性下降，因为跳得越远，miss 越多；后一个区域不再变化，因为 miss 已经差到一定程度，跳得足够远时大家基本都 miss，最差也就是 100% miss，不可能再差，所以性能稳定下来。这里有一个有意思的现象。

### 预取带来的平台

**35:57**

8K 这组数据性能不是最好，但和最好差不多；它的 cache 相对较大，8K 的访问次数不够多，性能会波动，没有完全稳定，重测一次可能不完全一样。更值得注意的是：工作集明明已经超过 L1、进入 L2，性能却和 L1 差不多，没有想象中“L2 比 L1 慢十倍”那么大的差距。按平均访问来算，本来应该慢一倍；即使差距没这么大、命中率比较高，也应该慢百分之二三十到五十。为什么这里没有明显变化？书上专门解释这里有平台：为什么前面有平台，后面同样的曲线又没有平台？

### 硬件预取

**37:01**

原因是硬件本身经过大量研究，越来越聪明。如果你一步一步、以很小步长访问，硬件很快就能学习到这种访存特征，并主动做预取。因此虽然工作集超过了 L1，它在访问之前就把数据取到 L1 里，性能上感觉不到差距。后面步长比较远时，预取上来的数据你并不怎么用，预取效果就降低。所以好的 locality 不仅可能接近软件上估算的结果，甚至会更好。

前面讲的 read、write 都是硬件按程序执行，没有主动预取；而预取是主动提前把数据拿上来。硬件既然知道你有 locality、有 for 循环，就会帮你取。这个现象说明性能还反映了硬件预取：好的代码，硬件还能帮你预取。

### 矩阵乘法与 miss 率练习

**38:24**

这是一个关于代码访存友好的练习，不用特别去做，感觉比较简单。第一题给一个很大的数组和三段代码，问哪段好；上过课就能看出来，一个是 i-j 顺序，一个是 j-i 顺序，这里再挑错不太合理。后面还问带 stride 的情况，算 stride 的 miss；只要大概知道原因——stride 会差一点——就可以了。miss 率算得准不准影响不大，因为实际上很难算准，硬件会影响你判断的大致方向。

第二题是矩阵乘法，前面讨论过两种策略；现在元素是 4 字节，原来是 8 字节，也就是一个 cache line 里能放下的数据原来只能放 8 个，现在能放 16 个。让你算 cache 的 miss 率，这其实对应着原来约 \(1/8\) 的缺失率变成约 \(1/16\)。稍微看看就可以，不再花时间练习。剩下十五分钟讲一个大家可能觉得更有意思的 topic：大模型里的缓存。

### 从硬件缓存到大模型缓存

**39:57**

大模型里的缓存，从我的角度看和前面讲的缓存是一样的，只是用大模型的例子大家可能觉得更有意思。前面讲的是硬件下如何设计层次化缓存；这是一个通用的策略：当速度不够时，首先想到用缓存提供一条快速路径。大模型要访问很多数据，GPU 算得很快，但 GPU 的显存有限，数据放不下时怎么办？有什么策略？这是大模型的基本问题。我们不需要了解模型内部具体怎么做，只要知道它要做大量矩阵计算即可。

### 大模型的自回归生成

**40:51**

我们知道它的行为：输入之后每次吐出一个词。先是 prefill，之后由 decoder 每次再取一个词。当前 transformer 大模型根据之前给它的 prompt，预测下一个最可能的词是什么。然后不断预测，直到预测出句号结束。所以它的本质是用前面的内容预测后面的回答，是一个用之前的输出来预测后续回答的过程。这里只需要知道这一点即可。

### KV cache 的切入点

**41:31**

它内部的计算有一个大家很容易想到的、和上课内容有关的技术，叫 KV cache，也叫 KV 缓存。名字里有 cache，容易联想到我们讲过的缓存技术。下面看所谓 KV cache 到底缓存谁、为什么要缓存；它的设计可以用之前介绍的哪些技术，应该怎么用。

### 注意力计算中要保留的部分

**42:03**

要介绍为什么要缓存 KV，这里有 Q、K、V 三个量；为什么不把 Q 也缓存？整个计算可以看成这样一个过程。首先这边是刚才输进去的 token，例如“今天天气很好”。切成 token 后，先不管模型内部为什么这样做；它为每个 token 找到一个向量来表示其信息。于是得到一个 n×d 的矩阵 X，d 是向量的宽度。内部计算可以分成三个步骤，这里图上先画两个步骤。第一步由 X 得到 Q；得到 Q 后，与转置后的 K 做矩阵乘法，得到另一个矩阵。这个矩阵只有下三角部分有用，因为后面的 token 只关注前面的单词，不关注后面的 token。有了这个结果，再和 V 做一次乘积，就得到最后的输出。

### KV cache 存什么

**43:30**

为什么这样设计先不管。从性能优化角度看这个过程即可。它是一个迭代过程：每预测出一个结果，就把它追加到输入后面，再把刚才的过程做一遍。其中肯定有很多东西不需要重新计算。因为只需要预测一个输出，不关心前面这部分计算；例如这一块其实不关心。只要这里已经有了结果，再和这边相乘就能得到最后的输出，前面的东西都不用。因此容易看出，真正需要的是已经算出的 K 及其转置；用它去乘，可以得到这部分；再和 V 相乘，就得到最后结果。前面的不需要重复计算。于是就有了 KV cache：这一部分要留在那里，因为下次计算还要用它们，不应重新算出来，否则开销太浪费。所谓 KV cache，存的就是 K 和 V，也就是图中蓝色的部分。执行过程中 KV cache 会慢慢变大，不断追加这部分，这是基本逻辑。

### 读写特点与规模

**45:13**

KV cache 的操作大部分是读：把数据读出来避免重复计算，读出来后就可以用；少数情况是写。写会让 KV cache 不停变大。图中可以看到它不断上涨。有和没有 KV cache 的差别非常大，否则就不需要用这个技术。图中没有 KV cache 时要这么多；而且随着上下文越来越长，也就是刚才的 token 数增加。这边是 6，现在可能要做超长的、几百万 token 的上下文，那么 cache 就会有几百万那么大，变得非常大。所以上下文越大，性能优化效果越明显，也越需要做缓存；但缓存的东西越来越多，因此需要考虑怎么组织这件事。

### GPU 内存与会话

**46:19**

这是一个典型系统。GPU 内存一般放模型，然后放中间结果；中间结果很小，接着放 KV cache。然后会有不同会话。每次聊天，上下文会积累，每个会话都有自己独立的一份 KV cache。这里还没有替你算。这里其实可以算出来：当上下文达到一兆时，一个会话的 KV cache 就和模型差不多大了。所以它变得非常重要。如果只有几 K，甚至不用缓存，或者缓存也没有问题，非常简单就能做到。

### 放不下时的替换

**47:03**

现在来看系统上的问题：放不下怎么办？模型要计算，模型权重总是要用的，每次计算都要用。但某个会话不一定一直会用。最简单的是新会话来了，希望替换掉一些旧的。这其实就是 cache 中的 LRU 替换策略。LRU 说的是最长时间不用的。一般情况下我们不会主动跟大模型说“我下面不讲了，我们结束了，再见”，不会这样说。所以一般情况下，长时间不用的会话会被干掉，应首先替换它。这里其实就是 cache 替换策略的设计：新会话来了，而某个会话一直在讲，就要进行替换。一般使用 LRU，也可以用 LFU。通常会话有一段时间不交流、闲置了，比如一个小时，就认为它可以被替换。

### 替换出去后是否保存

**48:19**

会话被替换出去时，这里要注意：刚才介绍的 KV cache 被替换出去时，需不需要保存它？因为之前讲系统 cache 时，替换出去都是往下层放：cache 踢到 memory。而这里 KV cache 肯定也可以存到 CPU memory、存到磁盘上；但 KV cache 有一个自己的特殊点。

### KV cache 的替换与丢弃

**48:51**

KV cache 与传统 cache 设计相比，会多一个选择：除了在 cache、内存、磁盘、CPU 内存和 GPU 显存之间决定放在哪里，还可以直接不要。因为 KV cache 中保存的内容本来就是计算出来的，它用存储换计算，目的是减少重复计算。空间不够、需要替换时，可以把它额外写到磁盘，也可以把旧内容直接扔掉，下次需要时重新计算，再把新内容放进来。所以过期或替换时可以采用 LRU、LFU 等策略，也可以设计其他策略。

### 缓存与内存、磁盘的一致性

**50:06**

有同学接着问：如果直接丢弃，之后怎么办？回答是重新计算即可；prompt 还在，相关内容可以再算出来，大不了重做一遍。随后讨论写操作中内存与缓存的一致性。CPU 和内存通常是一起失效的，所以它们之间不需要像内存和磁盘那样保证一致性；真正需要保证一致性的是内存和磁盘。上层的 CPU、内存一起丢失并不可怕，更可怕的是上层数据丢了、下层磁盘却没有丢，或者留下的是错误的数据，这才会造成问题。

### 写直达与写回

**51:26**

写直达（write-through）是写入 cache 后马上写内存；写回（write-back）则先写到 cache，等该 cache 行被替换出去时才写回内存，因此同一数据的多次写最后只写一次。写回的优势是写内存次数少；写直达的优势是 cache 与内存始终一致，不会留下需要写回的脏数据，替换时可以直接丢弃该行。写回在替换时必须先把脏数据写回，替换过程更慢，也会影响替换；写直达虽然每次写都要访问内存，但替换更快。实际系统大部分采用写回。

### 注意力计算中的 Q、K、V

**52:38**

接着看注意力计算中 Q、K、V 的依赖关系。实际计算时不需要把所有 Q 都保留下来；对某一行输出来说，需要当前 Q 与相应 K 算出的分数，再对这些分数做 softmax，得到权重后与 V 相乘。因此，分块计算时只需要保留参与当前计算的 Q、K、V 块，其他块可以不要。

### 矩阵乘法的循环顺序

**53:33**

这也对应矩阵乘法中的循环顺序。可以固定 B 的某一列，把 A 的每一行与这一列相乘，并反复更新 C 中对应的位置：先算一个位置，更新完后再算下一个。也可以一次把一个 C 元素算完，再把各项累加进去。不同写法的最终效果相同，但实际实现中一般不会采用某些写法。
