## 计算机系统基础（1）｜第 3 节（09:55）

### 从 jump 到 function call

**07:20**

好，我们开始上课。接着上一节课的内容，这里讲到 function call。上一节课已经讲完通过 jump 这样一条指令，我们可以改变 CPU 执行指令的顺序。CPU 默认会去取下一条指令执行：它根据当前指令知道当前指令的长度，然后把 PC 更新到下一条指令的位置，取出这条指令并开始执行下一条。中间的 jump 可以改变 PC，这样就不用去取下一条指令，而是跳转到我们指定的位置继续执行，从而可以实现分支、循环等控制结构。今天要讲的一件事情是 function call。我们看到，在自己的代码里面不仅仅有一个函数；目前解决的其实是单个函数内部的问题。

### 从函数调用引入 caller 与 callee

**08:43**

如果函数不去调用别的函数，我们已经能理解它在 CPU 上是怎么运行的。现在的问题是一个函数还会调用另一个函数。为了软件工程上的可维护性，通常会让每个函数的代码尽可能短；例如谷歌以前的 C++ 代码规范建议一个函数的代码行数不超过五十行，这样在 code review 时更友好。这大概是“古法编程”时代的软件工程约定；到了 vibe coding 时代，代码甚至可能没人仔细看。

以 main 函数调用 dot_product 为例。执行到 main 的 return 之前，CPU 如何跳转到 dot_product？dot_product 执行完之后，如何把结果作为 main 的返回值传回去？也就是说，它跳过去之后还得跳回来，这一点和之前的 jump 不太一样。我们把发起调用的函数称为 caller，被调用的函数称为 callee。

### 函数调用与 jump 的区别

**10:24**

下面比较函数调用和之前的跳转的异同。首先两者都会改变 PC：如果用 jump dot_product，PC 也会跳到 dot_product 的第一条指令开始执行。区别在于，dot_product 执行完之后要返回到 main 中调用点的下一条指令，而 jump 只管跳过去，不管回来。函数调用还需要一些约定：caller 要给 callee 设置好参数，例如第一个参数是什么、第二个参数是什么，callee 才能正确执行；callee 执行完之后还要把返回值传回给 caller。这些也都是简单 jump 不具备的。

### 局部变量的存放问题

**11:46**

此外，每个函数内部可以定义局部变量。以 main 为例，它有自己的局部变量：两个数组，每个数组由四个 int 组成，一个叫 w，一个叫 x。一个数组初始化成 1、2、3、4，另一个初始化成 5、6、7、8。由此产生的问题是：这些局部变量放在哪里？如何存储、如何分配、如何初始化？运行时它们位于计算机的哪个部分？

### 寄存器数量与跨函数复用

**12:26**

另一个问题是寄存器。现在的代码里大量出现对寄存器的操作，例如 `mov RAX, RBX`，以及 `mov RBX, ...`、涉及 `RCX`、`RDX + RCX` 等指令。每个函数编译出来的代码都要通过操作各种寄存器来表达自己的语义、执行各种指令。可是 x86-64 上的通用寄存器（general purpose register，例如 RAX、RBX 等）一共只有 16 个。

而一个程序里可能有一百六十个甚至更多函数。如果给每个函数分配一个寄存器，根本不够分。实际做法是所有函数共用同一组寄存器，但这样就会出现一个问题：一个函数改写了某个寄存器，可能会影响另一个函数。寄存器是 CPU 内部的硬件资源，CPU 制造出来时就只有 16 个，数量无法改变。程序里可能存在 A 调 B、B 调 C、C 调 D 这样的调用链，每个函数都需要使用这些寄存器；这些寄存器如何跨函数复用，就是函数调用要解决的问题。

### 函数调用实现的第一部分：控制流转移

**14:21**

所以今天就来讲函数调用的实现：函数调用在 CPU 上到底是怎么完成的，或者说程序究竟是如何实现这个过程调用的。这个主题分为五个部分。第一部分是控制流的转移：怎样把 CPU 的 PC——PC 也称为控制流（control flow）——转移到 callee 的入口，也就是被调用函数的入口；而且还要能回来，控制流要能回到调用点的下一条指令。

### 返回地址与调用点

**15:12**

先看什么叫返回，或者说返回地址到底返回到哪里。在 main 函数里有一条指令会调用 dot_product，这条指令后面还会跟着一条指令；在这个例子中，后面大概率就是直接 return，所以它的下一条指令就在这个位置。当从这条调用指令调用 dot_product 时，控制流跳到 dot_product 去执行；dot_product 执行完最后一条指令后，必须回到这个位置，继续执行调用点后面的那条指令，这就是所谓的“返回到调用点的下一条指令”。

但还要考虑另一件事：dot_product 作为 callee，可能在程序中被很多地方调用。A 函数可以调用它，main 可以调用它，C 函数也可以调用它；一个 callee 可以被多个 caller 调用，也可以被同一个 caller 在多个地方调用。这些都是允许的。因此，每次 dot_product 执行完要返回时，返回位置其实是不确定的：这一次是哪个 caller 调用了它，它返回时就应该回到那个调用点对应的位置。

### 返回地址与间接跳转

**16:57**

如果在这里直接使用 jump，就无法实现“返回到调用点”的语义，因为 jump 只能确定地跳到某个固定位置。除非我们能有一种方式记住要回到哪里，再通过间接跳转跳回去：把要返回的地址存到寄存器里，然后跳到该寄存器所保存的地址。这就是两者的区别。接下来的问题是：需要返回的地址到底存在哪里？这个地址叫做 return address，它放在一个我们其实相当熟悉的地方——栈（stack）中。

### 栈溢出

**17:46**

什么是栈？大家之前应该知道栈，也听说过 stack overflow，也就是栈溢出。知名网站 Stack Overflow 的名字就来自程序员常说的“栈被撑爆了”。例如一个递归函数如果没有终止条件，一直递归下去，栈就会不断增长，随后可能报出 segmentation fault（段错误）或 stack smashing 之类的错误。问题就在于栈被撑爆了。下面先大致看一看栈到底是什么。

### 程序视角下的内存与 CPU 假象

**18:49**

从应用程序自身的视角看，它以为自己的内存长成某种样子。程序运行时，必须把代码和数据加载到内存中；CPU 则到内存中取指令、取数据。现代 CPU 加上现代操作系统构建出一种假象：让每个程序都以为自己独占整台计算机。实际上同一台计算机上同时运行着很多程序，比如腾讯会议、后台的守护进程、PPT、Edge 浏览器等。如果每个程序都必须感知其他程序的存在、关心旁边还有多少程序在运行，程序就没法开发了。因此操作系统和 CPU 提供了一种保证：每个应用程序的运行完全独立，互不干扰。

### 独占内存与独占 CPU

**20:42**

具体来说，每个应用程序在运行时都认为自己独占全部内存，可以使用从 0 地址到最高地址（如果是 64 位地址空间，就是 \(2^{64}\) 个地址）的全部地址，而且不必考虑其他程序是否也在使用这些地址。多个程序甚至可以同时使用 0x1000、0x5000 这样的地址而没有任何问题，它们互相看不到对方的内容，也不会冲突。这件事后面课程会介绍如何实现。除了内存，系统也会让程序认为自己独占 CPU：它可以使用任何寄存器，它的 PC 与其他程序的 PC 不会打架。两个程序都在运行，但实际上只有一个 PC，这些都不需要程序员或程序自己操心，操作系统会处理。因此每个程序运行时都认为自己独占了全部 CPU 资源和全部内存资源。

### 内存布局：text、data 与 BSS

**22:08**

从应用程序自己的视角看，运行时的内存会有一个布局，一般来说都类似一个模板，实际通常更复杂，但简单来看就是这样。较低地址处（不会到 0）有 text 段，程序从 ELF 文件加载出来的 code section 会放在这里，所以也叫 text section。编译出的程序中的 data 段和 BSS 段会放到数据段中。全局变量通常放在数据段，局部变量不会被编译到可执行文件里。data 和 BSS 的区别在于：data 是已初始化的值（initialized），BSS 是未初始化的值（uninitialized）。

### 为什么区分 data 与 BSS

**23:31**

例如 `int a = 1;` 和 `int b = 0;` 都是全局变量，最终都要放到数据段。它们唯一的区别是初始化时有没有初值。区分 data 和 BSS 的好处是节省磁盘空间。全局变量在运行时都可能被修改，所以运行时必须为它们真正分配内存。b 一开始是 0，但运行时可以赋值为 100、200。它们都得占一个 int，各占 4 个字节，必须存在，最终都在数据段中。但初值的来源是 ELF 文件，也就是磁盘上的文件。如果 BSS 中这些未初始化的值也都在文件里写成 0，文件就会变大；为了让文件短一点、节省磁盘空间，文件里就不写这些零，只记录 BSS 一共有多少、有多长。不过加载到 memory 中时，这些零仍然要填。

### 内存布局：BSS、堆与未使用空间

**25:08**

BSS 段中那些零最后可能都会被写成别的值，这是 BSS 段。再上面是堆。大家以前写 C++ 时可能用过 `new`/`delete`；`new` 一个对象，这块空间来自整个内存地址空间中的堆（heap）。所有 `new`/`delete` 以及 `malloc`/`free` 操作的都是堆。动态创建的变量、非局部变量都可以放在这里。

堆和栈之间会有很多未使用（unused）的空间。因为一个程序认为自己拥有的内存有 \(2^{64}\) 字节，这是一个巨大的空间，不可能有一个程序把它用完，所以中间会留下很多空着的区域。再往上有一段叫运行时栈（runtime stack）。

### 栈与栈帧

**26:20**

运行时栈就是 stack，用来存储函数调用的栈帧。每个函数调用通常会开辟自己的栈帧；所谓压栈，就是这个栈从高地址向低地址增长。因为函数调用中 A 调 B、B 调 C，栈就要增长：A 要在栈空间上分配一段，B 也要再分配一段，B 调 C 时再分配一段。所以栈是一个从高地址向低地址生长的过程。

通用寄存器中有一个 RSP。它并不是特殊的硬件规定，而是软件约定：大家都遵守这个约定，让 RSP 指向栈顶位置，表示当前栈涨到了哪里。运行时栈中的函数栈帧，也就是图中黄色部分，可以用来存临时变量和局部变量。栈只在当前栈帧还活着的时候有效；比如 caller 调用 callee 时，callee 会分配一段新的栈帧。当 callee return 时，所有局部变量都没有用了，这个栈帧也会被释放，RSP 再加回去。所以栈是动态增减的，同时也可以用来存东西。

### push 与 pop

**28:29**

栈上可以存临时变量，其实 return address 也会存到栈上。先看两条操作栈的指令：`push` 和 `pop`，后缀 `q` 表示操作 8 个字节的数据。

`push` 的意思是把数据压入现有栈：比如当前 RSP 在某个位置，`push` 会把 RSP 减 8，再把数据压到新的 RSP 位置。

`pop` 则反过来：当前 RSP 指向栈顶，`pop` 把栈顶的 8 个字节数据取出来，送到 destination，一般是一个寄存器，然后把 RSP 加 8，向上还原到之前的位置。

这相当于在栈里做压栈和出栈操作。把这样的指令和之前学过的 `jump` 指令结合起来，就可以实现 function call 和 function return。

### 用 lea、push、jump 实现函数调用与返回

**29:58**

核心的一点是要记录当前的 return address。在 caller 里，调用者调用一个函数之前，要做的事情是 `lea` 加 `pushq`。`lea` 通常是去计算一个地址；这里做的事情是把 next instruction 的 label 计算出来。这一行指令的意思就是把 next instruction 的地址，也就是 return address，先放到 RAX 里，然后再对 RAX 做 `push` 操作，把之后要回来的 return address 先存到栈里。

接着再 `jump` 到目标函数 `dot_product`，跳到目标函数开始执行。`dot_product` 执行完之后要 return 回来，回到返回地址处继续执行。它怎么知道返回地址在哪里？因为之前已经把返回地址存在栈上，所以要做的事情就是 `pop`，把返回地址从栈上再 `pop` 出来，`pop` 到 RCX 里，然后用 indirect jump 跳回 RCX 指向的地址。

这样就用 `jump` 加 `push` 实现了 function call 和 function return。整体看起来，一共要用五条指令：跳到一个函数的入口并且从一个函数回来，过去是三条指令过去、两条指令回来。

### x86-64 的 call 与 ret

**31:45**

为了更加高效，x86-64 做了改进，提供了两个新的指令，对应实现 call 和 return 的功能。一个就是 `call`（function call），名字很直观：调用一个函数，直接用一条 `call` 指令就完成了对 `dot_product` 的调用；最后要返回时执行一个 `ret` 就可以了，和 C 里面的 `return` 也很像。这样就用两条指令搞定了。

它一共只需要缩减到两条指令，并且每条指令的字节数也变少了，总的字节数也变少了。它还有另外一个好处：不需要占用额外的寄存器。前面还要使用 RAX、RCX 等额外寄存器，而这两条指令不需要，直接 `call`/`ret` 就结束了。

### call/return 的效果示例

**32:44**

下面看 `call`/`return` 的效果。在一个代码示例中，这是程序认为自己拥有的地址空间：代码段在下面，上面是它的栈。程序先执行 main 函数，函数入口在 main 这个位置。执行到 main 中间的一堆代码后，程序计数器 PC 执行到 0x401156 时，执行了一条 `call`，去调用 `dot_product`。

### call 指令：跳转与压入返回地址

**33:19**

这时 PC——也就是 CPU 的控制流——会跳转到 dot product 的入口，即地址 0x401160。在调用发生的时刻，也就是执行 call 指令之前，main 函数的栈帧长成前面图中的样子，上面黄色部分由 RSP 指向。执行完 call 之后，栈帧发生了变化：RSP 向下减了 8，RSP 的值变小，栈相应地变大了。这时栈里被压入了一个新的返回地址 0x40115b，它正是 call 下面那条指令的地址，也就是这次调用之后要返回的位置。压入返回地址这件事是 call 指令自己完成的，实际上由 CPU 硬件直接完成；同时它还把 PC 设到 dot product 的入口，接下来就从那里开始执行。

### return 指令：弹出返回地址并恢复 PC

**34:43**

从 dot product 的入口往下执行，一直执行到最后一行 0x401199，这条指令是 return。return 之后栈的形态变成什么样？return 会先做一次 pop，把当前 RSP 位置上的返回地址弹出来，并把 PC 设回去。于是它把 0x40115b 从栈上取出来，RSP 也还原回去；同时 PC 被设为 0x40115b，控制流回到下一条指令继续执行。这就是 call 和 return 所做的事情。

### 栈帧的分配与销毁

**35:31**

它正好把我们前面说的需要实现的功能实现了。刚才的运行过程中已经看到了一个栈帧，它其实做了一件事：存放返回地址。以 main 函数为例，程序的栈如果要增长就向低地址增长，如果要销毁就往高地址加回去。main 调用 f，或者调用另一个函数，栈就增长一段；f 再去调 g，又增长一段；如果 g return 了，g 的这段 stack frame 就没用了。回去之后 f 还可以再调 h，所以栈是一个动态变化的结构，stack frame 的分配和销毁都随之发生。

它的动态分配和销毁也很简单，就是更新 RSP 的位置：把 RSP 减一个数，就是分配了一段，因为 RSP 变小、栈变大，新的一段被分配出来；把 RSP 再减一个数，又分配了新的一段。当 g 的 frame 不再需要时，就把 RSP 加回去。所以通过加减 RSP 的值，就能实现 stack frame 的 allocate 和 deallocate。当然，除了返回地址——目前只看到返回地址——马上还会看到栈里可以存放参数，可以存放局部变量，还可以做寄存器保存（register saving）。

### 参数与返回值放在哪里

**37:22**

第二件事是传递数据。caller 需要把参数传递给 callee，callee 需要把真正的结果 return value 返回给 caller。具体怎么做？回顾刚才的代码：代码里有 main 函数，main 调用 dot product 时传递了三个参数，第一个是 w，第二个是 x，第三个是 4，其中 4 是一个立即数。w 和 x 分别是两个局部变量、两个 int 数组，传进去的时候被当成两个 int*。那么问题就是：w、x、4 这些参数放在哪里？又是怎样传给 dot product 的？dot product 的结果怎么返回给 main？这要看它的约定。

### 调用约定与参数寄存器

**39:08**

这里有一个约定，它是一个软件约定，是程序员、所有编译器、所有程序形成的共识，也可以说是一份协议，叫做 calling convention，也就是调用约定。它约定函数的参数怎么传。先考虑只有六个参数的情形，通常一个函数有六个参数已经很多了；软件工程里对一个函数的长度有约定，对参数的数量同样有约定，一般来说不应该超过六个，甚至应该保持更短。假设有六个参数，那么这六个参数分别通过 RDI、RSI、RDX、RCX、R8、R9 这六个寄存器传递；假设只有两个参数，就是 RDI、RSI。有几个参数，就按这个顺序把参数传下去。caller 应该把自己的参数设置到相应的寄存器里，这样 callee 的入口开始执行时就知道：我需要的参数都已经按约定设置到这些寄存器里了。

### 返回值约定与 ABI

**40:38**

返回值也一样，也有约定，也是 calling convention 的一部分：callee 要把 return value 放到 RAX 寄存器里，如果位宽更小，用 EAX 也可以。这样 caller 的下一条指令开始执行时，就知道自己想要的 return value 已经在 RAX 寄存器里了。这套约定也叫应用二进制接口（application binary interface，ABI），它规定了这些内容。我们所有的编译器、所有编译出来的结果都要满足这样的接口和约定。

### 调用约定与 ABI

**41:34**

假设 A 同学写了一个程序，去调用另一位开发者十年前开发的三方库，或者调用昨天刚开发的三方库，都能调用成功。你自己编译出来的程序在链接别人已经编译好的程序时也能正常工作，前提是大家都遵守同一套规定。否则，如果别人认为参数应该放在 RAX 里，而你却把参数放到 RDX、RDI 里，那肯定不行。

所以，所有程序编译出来之后，都遵循这一套规范。这是软件层面的约定。如果一开始大家约定的第一个参数不是 RDI，而是 RSI，也完全可以，只要所有人都遵循这个约定。

### 调用 dot_product 时的参数设置

**42:40**

具体看刚才的 main 函数调用 dot_product 的过程。main 调用 dot_product 时会用 call 指令。调用这个函数之前，需要设置好参数寄存器。之前的代码设置的是 RDX/EDX，它直接把一个立即数 4 设置到 EDX；根据约定，RDX 存的是第三个参数。前面还会分别设置两个参数：第一个设置 RSI，第二个设置 RDI，也就是把这三个参数都设置好。

那为什么设置成这两个值？RDI 和 RSI 里存的应该是两个局部变量，也就是两个数组的起始地址，即 w 和 x 的地址。代码把 RSP 写进 RSI；RSP 是当前栈顶的位置，是一个栈上的内存地址。写到 RSI 里，意味着 x 这个数组大概率在栈底的位置。接着把 RSP 加 16 写到 RDI；RSP 本身是一个地址，加 16 也是一个内存地址。为什么大概是 16？因为中间反正要放四个 int，所以大概率是这么回事。局部变量也是存在栈上，所以这些局部变量的地址确实和 RSP 相关，很合理。

### 超过六个参数：通过栈传递

**44:50**

可能也有一些情况：程序本身不太规范，或者程序确实非常复杂，参数要超过六个。这时候怎么办？放内存，放到栈上。

约定是：如果真的要超过六个参数，从第七个开始，就把它压到栈上，通过栈传递额外的参数。看一个例子：有一个函数叫 last_two，它接受八个参数。我们去看看它如何获取第七、第八个参数，以及调用者 use8 如何传递第七、第八个参数。

use8 在调用 last_two 之前，做了很长一段事情，因为它的参数是一到八。前六个参数都按照约定放到寄存器里；第七、第八个参数则 push 到栈上。它先 push 8，再 push 7，也就是把第 8 个参数和第 7 个参数压栈，放到当前 use8 的栈顶位置。

last_two 做的事情，是从栈上取出自己的第七、第八个参数，然后做减法。所以，超过六个参数之后，额外的参数会被压到栈上。压栈之后，call 还会再压入一个返回地址。因此当 last_two 开始执行时，栈大概是这个样子：当前 RSP 指向返回地址，返回地址里存的是 call 之后下一条指令的地址；返回地址上面是两个被压栈的参数。

这涉及调用者（caller）和被调用者（callee）。在调用一条 call 指令之前，我可能已经执行了很长一段代码，并且已经把 RAX、RBX、RCX 这些寄存器的值设置好了。而被调用者也可能去用这些寄存器，这样就会破坏我原来的值。我们当然希望，调用返回之后这些寄存器的值保持不变，不应该改变。那这件事怎么做？怎么保证？

### dot_bias 的参数寄存器

**49:46**

**51:38**

但这里有问题：b 没了。为什么 b 会没了？代码本身写得很简洁，看起来没有任何问题，但执行 call 时，PC 会转到被调用函数那里。等到从 dot_product 返回时，ECX 中保存的已经不是原来的 b，b 被破坏了。执行到 call 时 ECX 确实还是 b，但 call 执行完、再执行后面的指令时，ECX 已经不知道被写成什么了。再回来时，仍然以为 ECX 里是 b，实际上已经不是。

### 跨函数调用与寄存器保存

**52:39**

不同的函数、不同的函数体，大概率都会用到相同的寄存器。这些寄存器没有任何备份，大家共享同一组寄存器。因此跨函数调用时，必须保证这些寄存器的值不要被改变，或者至少需要保存的值不能被改变。问题是怎么实现？我们还要加 b，所以 b 的值必须保留下来。最直观的办法就是把它保存到内存里。考虑这类问题时，要从第一性原理出发：目标是什么？需要做什么？自己先想办法，然后再去看实现，而不是死记硬背。我们也能想到办法，实际实现大概率也就是这些方法。

### 一种简单的寄存器保存方案

**53:43**

这里要做的是寄存器保存（register saving）。最简单的一种做法是：在每个函数开头、进入函数入口时，把所有寄存器都压到栈上；在函数 return 之前再恢复。当然，RAX 要用来存放返回值，留给 return；RSP 是栈指针，也不用保存。于是把其他十四个寄存器全部 push 一遍，保存到栈上，然后在 return 之前把这十四个全部恢复。这样是不是就可以了？其实可以。相当于每个函数都保证了一件事：调用者交给它的寄存器不会被破坏。总共十六个寄存器，其中 RAX 用来存放返回值，本身就会被破坏；RSP 则是栈的位置，这一点大家通常知道，栈是向下生长的。

### 全部保存的代价

**00:00**

这样可以保证对每一个 caller，我都可以拍着胸脯说：你给我的寄存器，我一个都没改，你是什么值，你继续执行。这肯定没问题，但显然有不好的地方：push 十四次，再 pop 十四次，一个函数莫名其妙就多了二十八条指令。这个函数本来可能只需要执行很短的几条指令，结果却要执行这二十八条指令，而且这二十八条指令非常昂贵。

为什么昂贵？因为 push、pop 操作的是栈，而栈在内存里；操作内存比操作寄存器慢很多。

### caller-saved 与 callee-saved 的划分

**00:47**

这是一个方法。基于这样的方法，我们要想一想怎样进一步优化：功能已经实现了，现在要优化性能。于是调用约定里又开始做约定。约定什么呢？之前十四个寄存器全部保存，着实有点浪费；一个函数不一定真的会用到十四个寄存器。

所以先做一个划分：caller 和 callee 各保存一部分。一部分寄存器称为 caller-saved register（调用者保存），另一部分称为 callee-saved register（被调用者保存）。大家不用知道具体哪些寄存器属于哪一类，只要知道有一部分是 caller 保存、有一部分是 callee 保存就可以了。

### callee-saved 的按需保存

**01:44**

划分之后，再做一件事，或者说再做一个优化：对于一个 callee-saved register，你的函数作为 callee 时要想一想，如果我要使用其中一个寄存器，那我就得负责把它保存起来，按需去做 save 和 restore。

比如现在有这六个寄存器，但我的 callee 函数里压根儿不去用，或者压根儿不去破坏 RBX，那我也不用去 save。所以这又是一个按需保存：第一个是划分，第二个是按需保存。callee 要去保存：如果它破坏了某一个 callee-saved register，它要先把原值保存到栈上，在 return 的时候再把它恢复出去。这样对于 caller 来说，它就知道：在 call 之前和 call 之后，这个 callee-saved register 的值一定不会变；因为即便 callee 自己改了，它也会帮我还原。

### caller-saved 的按需保存

**02:52**

那对于 caller-saved register 来说，也是一样，也是按需保存。如果这个 caller 发现，或者说他知道自己在 call 执行完之后还要去用这个 caller-saved register 的值，那他自己在 call 之前就得保存一下这个值，或者把它移到一个 callee-saved register 上，交给 callee 去处理。这是 caller 要做的事。

当然对于 RSP，因为 call 之前和之后它的值相同，不用变，所以我们也不会把它放到 saving register 里面来。RAX 是 caller-saved，RCX 也是 caller-saved。因为 RAX 大概率会被破坏，用来放返回值；所以如果 caller 自己需要 RAX 的值，就需要自己把它存起来。

### 例子：dot_bias 中 b 的保存

**03:51**

好，这是这样一个 case。所以有了 caller-saved 和 callee-saved 的划分之后，我们的 dot_bias 这个函数，它里面的第四个参数 b 其实被分配在了 caller-saved 的 ECX 里。

又由于它在调用另外一个函数之后还要使用这个 b——dot_bias 会去 call dot_product，调用之后它还要把 return value 加上 b——所以它需要自己去做 saving。这个 caller dot_bias 自己作为 caller，要去做对 b、也就是 ECX 的 saving。

saving 的方式其实也简单，有两种：一种是把 b 保存到栈上，在调用完 call 之后，再把它 pop 出来，作为加法的一项；另一种方法是先把 b 移到一个 callee-saved register 里面去。这样按照约定，dot_product 执行前后这个 callee-saved register 的值是不变的，所以也可以这么干。

**24:15**

被切出的程序期望下次回来时所有东西都不变：RAX、RBX 这些寄存器里的值还在，自己还能接着往下执行。对程序 a1 来说，它根本不知道自己被打断过，以为一直在那里跑，实际上中间已经被延迟了很长时间。之所以能给它这样的假象，是因为操作系统在任意时刻打断它、将来恢复它时，都从它的 next instruction 开始执行，并且恢复它全部寄存器的状态。

但寄存器是硬件资源，每一个 CPU 核只有一份；当切到 a2 的时候，a2 也要用这些寄存器。所以操作系统做的一件事情，跟我们在函数里面做的事情一模一样、或者非常类似：把这些寄存器的状态存到内存里去，这部分内容就是 a1 的上下文，也就是 a1 的 context。a2 也会专门分配一个区间存放 a2 的 context，操作系统在切换的时候帮它存进去；将来 restore、恢复 a1 执行的时候，就类似于函数 return 之前，需要把这个状态恢复回去。

这样，很多很多程序才能够 share 同一份硬件资源，就跟很多函数能够 share 同一份寄存器是一个道理。它本质的思路都是分时复用：某一个时刻给谁用，下一个时刻还回去，restore 的时候把状态还原，给程序构成一种假象。

### 局部变量的存放位置

**26:11**

这种假象就是好像所有的寄存器都只有我一个人在用一样。关于 register 的部分就讲到这里，接下来看局部变量：main 函数里面还有最后一个东西没有讲，就是 w 和 x 在哪里。局部变量实际上有两个地方可以放，第一个是寄存器，第二个是栈，通常就这两个地方。放到寄存器里当然好，寄存器在 CPU 内部；放到栈上就相当于放到内存里，就变慢了。

**26:50**

但你肯定不可能永远都放得下寄存器，所以局部变量放到内存里，可能有以下几种情况。

第一，寄存器不够用了。

第二，局部变量比较复杂：一个寄存器只能表达一个 64 位的数，也就是 8 个字节；如果局部变量是一个数组或者一个结构体，你想放寄存器也没法放，只能放到内存、放到栈上。

第三，如果我们的程序对这个局部变量做了取地址操作，编译器看到这种情况，如果还把它分配到寄存器里，后面那个取地址你就不知道怎么操作了，而寄存器本身并没有地址。所以这时候编译器也会把它放到栈上面去。

所以局部变量到底分配到哪，其实就是编译器决定的：编译器看一看，当前这个寄存器还有富余，你要放的又是一个 int，就会给你扔到寄存器里；而如果发现当前要分配的是一个 array，那就只能分配到栈上。

### 局部变量在栈上的分配

**27:55**

那怎么在栈上分配呢？无非就是在函数开始的时候把 RSP 减一下，这样我们就分配出了一个栈的空间出来；后面的局部变量，只要相对 RSP 进行偏移访问就可以了。

看刚才的例子，也就是我们的 main 函数，它需要去初始化 w 和 x 这两个数组。你会发现局部变量是在这个函数执行的时候去做初始化的，局部变量不存在我们的 ELF 文件里，编译的时候没有，它只是在我们的代码里面去做动态的初始化。你会发现这个函数在调用 code_product 之前，那三行是在设置它的三个参数。

**29:04**

第一个参数放在 RDI，第二个参数放在 RSI，第三个参数在 RSP，一共三个参数。而前面的一二三四五六七八，就是在初始化它的两个数组：做法就是把这些数都按照 RSP 的偏移去放。

当前 RSP 的位置、RSP 加 4 往上再放一个——每个元素都是一个 int，都是四个字节——往下是加 8、加 12，于是 RSP+0、RSP+4、RSP+8、RSP+12 放的是 5、6、7、8，这就是 x 这个数组。另外一个数组是 w，是一二三四，放在 RSP 加 16 的位置，一二三四这样去放。这样一共放了 8 个 int。

### 栈帧大小与 16 字节对齐

**30:05**

8 个 int 占 32 个字节，而这里有一个要求：栈要做 16 字节的对齐，所以这边又加了一个 8，一共是 40 个字节。因为它前面还会有一个 call，call 的时候会压入一个 return address；这样加起来是 48，是 16 对齐的。它要求在执行 call 之前、在函数入口（function entry）的时候，RSP 的值是 16 对齐的，这也是我们的一个软件约定。所以它这里空出了 8 个字节。它一开始分配这个栈帧的时候，就是 RSP 减 40。

**31:11**

减 40 就意味着 RSP 从原来的位置一下减到这里，这一段就都是它自己能用的。最后在 main 函数 return 之前，得把这 40 个字节销毁掉，也就是把当前的栈帧销毁掉。怎么销毁？一行指令就可以：分配的时候是一行指令减一下，销毁就是加一下、加回去，加回去之后再 return，这时候就结束了，栈帧也就销毁掉了。这就是这样一个例子。

### 两条新指令与软件约定

**31:44**

总结下来看，函数调用总的来说也不复杂，它提供了两条新的指令：一条是 call，一条是 return。call 使得我们可以把 PC 上的控制流转移到 callee，然后在 callee 执行一条 return，就可以回到 next instruction。中间的 return address 存在了栈上，call 的时候会直接 push 到栈上去。此外我们还会有一个软件约定，这个软件约定就是怎么样去传递我们的 argument。

### 函数调用约定与运行时栈

**32:17**

caller-save register 和 callee-save register 如何划分，这些都是编译器自己会遵守的约定。与函数相关的是运行时的栈：栈帧通过 `sub` 向下减小、向下生长，返回时再通过 `add` 加回去，从而动态增长。栈帧里可以保存返回地址、保存寄存器；放不下的参数、需要保存的 register，以及 local variable 都可以放在其中。

总的来看，完整的流程是：对于一个 caller，它在调用之前要做的一件事是保存自己之后还要用的寄存器，也就是 caller-save register；然后第七个及之后的参数需要压栈，因为超过六个参数时寄存器放不下。其他参数放在寄存器里，执行 `call` 的时候会把返回地址保存起来。

### 调用与返回的完整流程

**33:36**

把返回地址保存起来，这是硬件自己会干的。类似的，callee 也得保存自己的 callee-save register。所以一般来说，会在一个函数的 entry point 处保存一些 callee-save register。然后 `subq` 给自己分配栈帧：每个 callee 会给自己分配栈，减小 `rsp`，后面把自己的局部变量放进去。

最后执行完函数体之后，把 return value 放到 `RAX` 里，然后通过 `addq` 把栈还原回去；再执行 `pop`，把 callee-save register 恢复回去，最后执行 `return`。这就是整个过程。

### ISA 与 ABI 软件约定

**34:29**

指令的行为是由 ISA 决定的。例如 `call` 会做压栈，`return` 会做出栈，并把它当作 return address；这些都是 ISA 决定的，软件改不了，是 CPU 实现层面的约定。而 ABI 是我们说的软件约定。

软件约定就是到底哪个寄存器放哪一个参数。如果所有人都有一个共识，那么改成一个新的约定也没问题。可以看到，Linux 和 Windows 上的 software ABI 约定完全不一样。比如参数传递，Linux 上用六个寄存器传六个参数；Windows 上是另一种情况。但它们是同一个 CPU：装的系统不同，软件约定就不同。

### 缓冲区溢出与 ROP 攻击

**35:36**

最后还有一点时间，可能不一定来得及讲完，大概讲一下缓冲区溢出和 ROP 攻击。这和刚才讲的 `return` 很相关。

为什么会讲这个？第一，它和栈相关；缓冲区溢出很多时候就是栈上的溢出，如果有这样的漏洞，就可以被攻击者利用，然后再利用 `return`。刚才说的 `return` 指令可以发起一些比较有意思的攻击。

看一个例子。这个例子用一个非常常见的库函数，不过它现在可能也被弃用了，因为它存在问题；但它代表了一类缓冲区溢出的问题。它是从键盘输入中获取一个字符串。

### `gets` 的行为

**36:47**

它的做法是：每次获取一个 `getchar`，如果它不等于 EOF、也不等于回车，说明还没输完，就把这个字符串后面追加一个新的 character。每次把输入的东西放到这个字符串里面来。最后在目标 s 的结束加一个 `\0`。

`\0` 代表一个字符串的结束，加一个终止符，最后把这个字符串返回。这个函数就是去获取键盘输入，你可以输入一行、获取一行。

问题在于，它没有检查到底输入了多少个 character。

### 缓冲区溢出的栈布局

**37:42**

假设现在的 buffer 是一个有限长度。比如说 buffer 只有八个字节，你去调用这个 `gets` 函数，其实最多只允许用户输入七个 character，因为最后还会加一个 `\0`。但是 `gets` 里面没有任何检查，所以用户实际上可以输入任意多的数量；甚至可以输入一千个，只要不打回车，一直往下按，它会一直给你存下来。

于是就有个问题：输入的一行超过七个字符的时候，多的字符存到哪去了？存到 buffer 后面了。buffer 在哪？在内存的哪个区域？栈上。所以它其实就会把栈上的区域覆盖掉。

我们看一看当前的情况，比如当前执行到 `echo` 的时候，栈的情况是什么样子。

### 覆盖保存寄存器和返回地址

**38:48**

main 函数调用了 `echo`。调用 `echo` 的时候，main 函数的 return address 也会被压到栈上。然后 `echo` 做了一件事：它减小了这么多，减了 24，也就是 3×8。

这边有一个地方是去存它的 buffer；buffer 是一个八个字节的 character 数组，所以它占了八个字节。这是它的 buffer。当然它还有自己保存的内容，这里先不管。

现在去执行 `gets`。执行 `gets` 的时候，会把用户输入往这边填，依次往后填。所以当填完前面七个的时候没有问题，现在还能正常工作，其实还没有越界。最后填 `\0` 的时候，当然也会越界了。然后当你再往后填的时候，它其实就把 saved register 给干掉了。再往上填，你可以继续往上输，其实就把 return address 都覆盖掉了。

这个时候就比较危险。为什么？你把一个 saved register 破坏了，程序大概率就跑飞了。

### 缓冲区溢出与代码注入攻击

**40:19**

如果只是破坏了 saved register，程序可能运行一段时间后崩溃；但如果覆盖了 return address，下一条 return 的目标就可能被攻击者控制。攻击者把 return address 写成某个值，就可以跳转到指定位置执行。

攻击者可以在 buffer 中直接输入一段代码。输入的内容虽然是一串字符，也就是 0 和 1，但如果把这段 0/1 解释成指令，它就可以成为可执行代码。攻击者可以在 buffer 的起始位置写入一段代码，再继续向后覆盖，最终覆盖到 return address，并把 return address 的值填成 buffer 的起始地址。这样，下一次函数返回时，程序不会回到原来的返回位置，而是跳到攻击者植入的代码处执行。这就是 code injection（代码注入）攻击：通过 buffer overflow 把自己的 payload 放入 buffer，再把 return address 改成 payload 的地址，然后执行。

下节课会继续讨论相关问题。一个问题是：return address 需要填写，payload 可以自己设置，但攻击者怎么知道要跳转到的位置？另外，针对这类攻击有什么防御方法？

### 课后答疑：寄存器保存与编译器优化

**46:13**

课后交流中还讨论了调用者保存寄存器和被调用者保存寄存器。不同做法可能影响汇编代码的长度，但底层操作和需要实现的功能是一样的，编译器会做一些优化。

问题大致是：如果被调用函数使用了某个被调用者保存寄存器，是否一定要保存？看起来编译器会做优化，只在某个寄存器于某段代码中确实要被使用时才处理，这个识别是在编译时完成的。编译器会查看全局代码，知道自己要用哪些寄存器；CPU 只是逐条执行指令，并不知道程序后面还要用到什么。编译器在编译时已经知道某个值后面还会用，于是可以决定把它放到合适的寄存器中。
