## 计算机系统基础（1）｜第 9 节（15:55）

### 回顾：指令执行的五个阶段

**06:50**

先回顾上节课的内容。上节课最重要的是把 CPU 打开，观察每条指令执行时被划分成五个 stage。这里先讨论一种简单的参考设计；曾经也有真正的商用 CPU 采用这样的设计，现代 CPU 会设计得更复杂。五个阶段分别是 instruction fetch、decode、execute、memory 和 write back。问大家一个问题：为什么要把一条指令的整个执行过程分成这五个阶段？这样做有什么好处？

### 流水线的阶段划分与硬件复用

**08:06**

有好处。我先请一位同学回答，同时回顾上节课的内容：一条指令的执行被分成五个 stage，每条指令都沿着这五个阶段走。相比之下，有些指令其实很简单，不一定需要完整经过五个阶段，其中某些阶段可能什么都不用做；如果把流水线设计成两个 stage，或者把指令分成若干类、为每类专门设计阶段，理论上简单指令可以执行得更快。这个因素可能相关。

**09:48**

另一个优势类似软件开发中的代码复用：五块代码通过不同组合可以组成不同程序，从而降低开发复杂度和工作量。CPU 中也是把硬件部件设计成五个 stage；设计好之后，这五部分已经能够表达所有 hardware instruction，使整体设计更简单、更高效。

### 流水线与并发指令数

**10:37**

接着看：一条 CPU 指令可以分成多个 stage 执行。当某条指令执行到某一个 stage 时，其他 stage 的硬件部件可能都空着、没有干活。自然会想：怎样提高硬件资源利用率？办法是采用流水线。采用流水线后，CPU 中同时执行的指令数可以变多。最多是多少？最多等于流水线的级数，因为每个 stage 最多有一条指令在执行。五级流水线最多五条；如果 PC 笔记本是十八级流水线，最多就是十八条。并不一定总有十八条指令同时执行，具体取决于流水线是否会出现空闲。

### 数据冒险与控制冒险

**12:17**

流水线中出现空闲的一个原因是依赖：data dependency 或 control dependency。英文教材中称为 data hazard 和 control hazard，中文教材通常译作“数据冒险”和“控制冒险”。前面的指令和后面的指令之间存在数据依赖或控制依赖时，流水线可能需要 stall，停下来等待前面的结果；stall 之后要在流水线中插入 bubble，让相应部件空转、不干活。请坐。以上是对上节课的回顾。

### 吞吐量与时延

**13:33**

上节课的核心之一，是怎样增大一个系统的吞吐量。流水线是提高系统吞吐量的一种方式，但它不能降低系统的时延。从单条指令的执行时间看，流水线并没有缩短时间：一条 instruction 仍然要经过五个 stage，而且由于流水线中间还需要存储中间结果，instruction 的 execution latency 甚至会变长。但这是对单条指令而言；从整个系统看，throughput 提升了。流水线设计在真实世界和软件系统中都很常见。上节课还补充了一些 modern CPU 中听起来比较厉害的内容。

### 多核与线程

**14:37**

包括 superscalar、hyper-threading。Multicore 大家可能相对熟悉，之前也讲过。老师问：什么是多核 CPU？同学回答：可以同时执行很多个线程。接着问：什么是一个线程？大家之前学编程时有没有用过并发编程的接口？同学们回答没有。所以大家写的都是单线程、没有并发的程序。

### 多任务与资源共享

**16:07**

线程是什么并不重要，不用管它。我们考虑什么是应用程序：写一个 main 函数，编译出 a.out；也可以编译出 b.out、c.out。可以开多个终端窗口，让这些程序同时运行。那么在 CPU 里，它们到底怎么同时运行？这又回到一个经典问题：对于有限资源，比如只有一块 CPU——买来的电脑就是这样——怎样在一台机器上同时运行 n 个程序？怎样在有限资源下运行很多程序，如何共享资源？之前介绍过两个思路。

举个例子：现在只有一块 CPU、一台笔记本电脑，某个时刻同时跑十个程序，打开 Word、Chrome、腾讯会议，开了一大堆；明天可能开二十个，有时开五个，有时开一百个。程序数量可以很多，但硬件资源是固定的。这些程序怎样共享有限、固定的硬件资源？

### 分时复用

**17:58**

分时没问题，还有多核。所以核心只有两个思路，没有什么花哨的东西：分时和空分。分时的意思就是大家都要做共享，也就是做分享或划分；分享只有两种方式。第一种，以这间教室为例，现在这间教室在上 ICS 课，我们在四点到六点上 ICS；之前两点到四点还有别的课。这就是分时复用：在一个时间段做一件事情。

也就是说有 APP1、APP2、APP3，无论有多少个 APP，只要约定一个时间。谁来帮它们做约定？操作系统可以做协调：决定第一个时刻、第一分钟或第一秒让 APP1 执行，第二秒让 APP2 执行。通过分时复用，让这些程序共享固定的硬件。软件数量任意多都没关系，都可以通过分时复用共享；只是程序真的特别多的时候，电脑会显得很卡。比如一个程序排队，要排一千个程序才轮到它执行，自然很卡。

### 空分复用与多核

**19:41**

另一个叫空分。空分是什么意思？比如这间教室很大，考试的时候把两场考试排到一个考场，因为考试人数很少，大家各做一块，另一门做另一块。这样两个程序或两个任务可以同时共享同一份资源。它们在真正的同一时刻一起执行，这叫空分复用。

CPU 里怎么做到空分复用？因为有多核 CPU，multi-core 表示一个大 CPU 里有多少个核心；每个核心可以认为能跑一个 APP。所以在同一时刻，它是真正可以同时运行的。如果是分时复用，比如应用 a5、a6，它们都在同一块 CPU 上排队执行。从用户视角看，可能感觉它们也是同时运行，但这种同时实际上是一种假象：因为切换得很快，给人的感觉好像背景音乐没有停、前面的电影还在放、Word 也没有被关闭。这是分时复用给人的感觉，但它并不真正在同一时刻一起跑。

这是对硬件资源最基本的使用方式。其实不只 CPU 这样，GPU 也这样，现在的大模型也这样。本质上没有更多方式；所有多路复用（multiplexing）的方式最终都可以归类为这两种。

### 超线程与超标量

**22:00**

这是多核，硬件上是这么设计的。超线程（hyper-threading）做什么事情？现在有四个核心，但 CPU 还支持一个功能：把一个核心再变成两份，让两份任务在上面同时运行。比如可以同时运行应用 a1 和 a5，在同一个物理核（physical core）上同时运行两个，这就叫超线程。它到底怎么做？它和物理多核有什么区别？它给上层程序看到的状态，就好像四个核一下变成八个核；实际上硬件做法比真正增加物理核心的成本小很多，所以叫超线程。

具体是因为之前说过的超标量。超标量大概做的事情是：之前说五级流水线，我们是一个流水线 CPU，每一个流水级（stage）可以设置多个硬件。比如取指这个流水级（stage），就可以设置多个硬件。传统最简单的流水线每个 stage 只有一个部件，这样每个时钟周期最多完成一条指令；最后写回（write back）这边只有一个，因为进来也只有一个，每个 stage 最多只有一条指令在执行。所以它的做法就是所谓的超标量。

### 超标量与乱序执行

**24:15**

超标量的做法是把流水线中间的部件复制多份：取指可以有多个，执行阶段也可以有多个计算单元，例如多个 ALU，可以同时完成多条加法。这样的设计称为超标量。超标量可以结合乱序执行（out-of-order execution，OOO）。程序中的指令不一定存在前后依赖，后面的指令可以提前执行，从而更好地利用流水线、利用空闲部件。为了让乱序程度更高，可以把更远的、没有依赖的指令提前运行；硬件也可以设置更多部件、支持更强的乱序，让指令执行得更快，提高 IPC（每周期完成的指令数）。

### 按序提交的限制

**25:35**

但有了超标量之后，并不能保证一个程序真的能把所有超标量部件用满。虽然可以乱序执行，最后仍必须按序提交（in-order commit），也就是按序退休（in-order instruction retirement）：写回之后对外可见的结果以及存在依赖关系的部分，最终仍要按程序顺序生效。整体来看，指令还是要按照从前到后的顺序完成，因此中间会出现一些由于硬件冗余而产生的重复和空闲情况。

### 超线程

**26:21**

能否利用这些空闲部件再执行一个程序？这就是超线程（hyper-threading）的思路：超标量会产生很多空闲硬件，因此可以在同一个核心上再运行一个线程或程序，共享 ALU 等中间部件。比如本来有多个加法单元，一个程序用不完，另一个线程可以一起使用。这样就能同时运行多个程序。

代价是每个程序都需要自己的一份“程序员可见状态”（programmer-visible state）。其中很重要的一部分是通用寄存器，还包括 PC、标志寄存器等。因此超线程在硬件上的主要开销是复制一份寄存器：两个应用程序各自使用各自的寄存器，互不冲突。但如果是多核，中间这些流水线部件都要各复制一份；超线程则可以共享这些部件，这就是超线程和多核的区别。

所以超线程的性能比不上真正的物理核：超线程的八核和真正的八核性能并不一样。但它更省硬件，同时能提高部件利用率，给应用程序带来更好的性能。

### 几种技术的区别

**28:34**

总结这几项技术的区别：超标量增加硬件，把流水线每一级的部件做成多份；超线程复制的是寄存器，让寄存器完整地多出一份，但五级流水线中的计算单元、取指单元等可以共享，不会随之增加；真正的多核则把寄存器、流水线等东西都完整复制一份。

### 分支预测与性能监控

**29:22**

上节课还提到硬件预测器（hardware predictor）或分支预测器（branch predictor）。CPU 遇到分支或跳转指令时，需要决定是否跳转。流水线此时不能一直等，因为还不知道究竟跳不跳。传统最简单的做法是停顿（stall），等到跳转条件真正判断出来，知道是相等还是不相等之后，再决定跳或不跳，但这样会产生流水线气泡（bubble）。

为了避免这种气泡，CPU 增加了猜测当前跳或不跳的功能。上节课也让同学们用 prompt 去尝试这件事，并可以通过操作系统提供的 perf 工具查看 CPU 的分支预测准确率。CPU 中有专门的功能单元——性能监控单元（PMU），其中设置了一些特殊寄存器。这些寄存器与通用寄存器无关，可以暴露 CPU 内部状态，例如分支预测的 miss rate、缓存的命中率等。perf 这样的系统工具可以帮助查看这些信息。

### 基于查表的分支预测

**31:11**

对于分支预测，上节课讲过一个非常简单的实现，这里给出的是现代 CPU 中具体的实现，基本原理差不多，也很简单。不会在 CPU 内部设计一个神经网络来判断跳或不跳：分支预测对延迟要求非常严格，必须非常快。假设原本只是为了减少两个 cycle 的流水线气泡，结果放一个神经网络要耗两毫秒，那肯定受不了。因此这里的设计会非常简单：它变成一张表，变成查表操作。CPU 硬件最擅长查表，查表可以很快。具体做法是用当前 PC 的地址去查这张表。

### 分支预测表与两位计数器

**32:22**

这张预测表的大小是固定的。如果某个分支在表中还没有对应项，就在表中添加一条表项；查找时可以通过某种哈希映射或其他映射方式，找到相应的 entry（表项）。

例如当前 PC 是 0x34 这样的地址，就会对应到某个表项。这个表项不会记录具体的指令，它记录的是一个两位计数器。计数器初值为 0：如果这次分支的实际结果是跳转，就加一，最多加到 3；之后再遇到跳转也保持在 3。如果下一次实际结果是不跳转，就减一，从而形成一个很小的状态机。

预测规则是：当前计数器为 0 或 1 时，预测这次不跳转；当前计数器为 2 或 3 时，预测这次跳转。CPU 内部的分支预测可以就是这样一个简单逻辑。

### 一个分支预测的例子

**34:03**

接下来看一个简单的例子。这个例子本身没有实际意义，只是为了观察在一个大循环里，当分支容易预测或不容易预测时，程序表现会有什么不同。这个程序就是一个 for 循环，循环中判断当前数组元素是否为零。如果数组元素不为零，就做一次乘法并加到累加和中；如果为零，就跳过这次乘加。因为元素为零时乘出来的结果一定是零，再加也没有意义。

从程序员视角看，这似乎是一段经过优化的代码：零元素不做乘法，而乘法又比较昂贵，所以性能应该更好。但实际运行结果不一定如此。它取决于 workload，也就是当前实际跑的数据具有什么特征。

### 全非零数据

**35:31**

先看数组 w 的元素全都不为零的情况。此时每次 if 判断都成立，程序都会进入分支，执行乘法并累加。最后用总时间除以 65536 个元素，可以得到处理每个元素的平均时间约为 0.55 纳秒。

### 不同数据分布下的性能

**36:24**

第二种情况是数组前半部分为零、后半部分不为零。这个数据分布很有规律。此时处理每个元素只需要约 0.40 纳秒。

第三种情况同样是一半为零、一半不为零，但零的位置没有任何规律，是随机出现的。此时平均处理每个元素需要约 2.9 纳秒。三个程序处理同样多的元素，性能差距达到六倍以上。

### 分支预测失效导致的性能差异

**37:09**

同一个程序、同样多的元素，为什么会有这样的差异？前半部分为零的情况比全非零情况快，是因为程序中的人工判断起了作用，很多乘加操作没有做。那为什么随机一半为零反而比全非零还慢？按操作数量看，随机情况下也应该有一半的乘加被跳过，只做一半的乘加，似乎应该更快。

原因在分支。如果不从分支预测的角度分析，很难看出性能缺陷在哪里。用 perf 查看 branch prediction 的 miss rate，会发现随机情况下的未命中率很糟糕。因为这种随机数据没有任何可把握的特征，分支预测器失效了。分支预测能够生效的前提是，跳转结果具有历史规律。从大的统计规律或一般程序行为看，分支通常是有规律的。上节课举过一般的 for 循环，例如外层 for 循环的跳转就肯定有规律。

### 流水线案例：大模型的词元生成

**38:42**

上节课的内容告一段落，还剩一个小的 case study：看 pipeline。流水线技术在大模型推理基础设施中也很常用。大模型的基本原理可以看成一个单词接龙游戏：它每次根据当前给定的句子或 prompt，生成下一个单词、下一个 token。token 可以理解成一个字，也可以理解成一个词。

具体来说，模型先接收一个前缀句子，把它全部送入模型计算，算出一个概率分布：下一个词是“吞吐”的概率有多高，是“速度”的概率有多高，是“效率”的概率有多高。然后它可以选择概率最高的词，比如“吞吐”，把它加回原来的前缀，形成新的 prompt。接着再把整句送入模型，重新计算下一步的分布。

### 自回归生成与前向计算

**40:24**

模型在上一步得到“吞吐率”之后，会把“率”继续追加到已有前缀后面，形成一句更完整的话：“流水线提高的是吞吐率”。然后把这整句话再次送入模型。这一次模型给出的最高概率词元可能是终止符；一旦生成终止符，就表示这句话讲完了，模型返回并结束本次生成。这个过程称为自回归。

模型内部是一层一层的神经网络，每一层都要用大量权重与输入向量相乘，这称为前向计算。这里不展开模型本身，只需要大致了解这个过程；接下来关心的是它与流水线的关系。

**41:25**

这张图看起来像流水线：大模型有第一层、第二层、第三层、第四层……很多层，好像流水线的每一个 stage。数据每经过一层都要先做乘法，再进入下一层继续乘，这样一层层往下走，看起来就像流水线。

**41:49**

但这里有一个问题：模型体量太大了。现在常举的例子是 405B 的模型；两年前这已经算很大。到 2025 年初 DeepSeek 671B 出现时，六七十 B 已经算是还不错的尺寸；而现在模型参数规模已经到几个 TB，甚至更大。假设有一个 405B 的模型，405B 指参数规模。若每个参数用 16 位、即 2 个字节表示，那么模型权重一共占 \(405\times10^9\times2\) 字节，约 810 GB 内存。一张显卡才多大？例如 4090/5090 这类显卡，显存大概十几到二十几 GB，约 24 GB，连模型的二十分之一都不到，显然放不下。即便用一张 H200，这类卡很贵，也只有 140 GB 显存，仍然放不下 405B 模型，更不用说现在更大尺寸的模型。仅按显存容量相除，至少需要六块 H200。

### 模型划分与流水线并行

**43:41**

而且上面只算了模型参数。计算过程中还会产生大量中间结果：一个矩阵、一个 prompt 传进去，中间会产生很多中间计算结果，对内存和显存的压力很大。因此现在的做法之一是把模型拆分。假设模型一共 126 层，可以把第 1 到第 21 层放在一张 GPU 上，把第 22 到第 42 层放在下一张 GPU 上，用六张 GPU 均匀分摊模型参数。这样实际上就是设计了一条流水线，并且每个 stage 的计算时间相对均匀。流水线设计如果不均匀，整体会被最慢的环节拖住，所以要让各段尽量均匀。好处是每张卡只需要放六分之一的权重，显存需求一下减少到六分之一，模型就能放得下。

**45:18**

六块 GPU 工作时，一个 token 在第一个时间片先到 GPU 1 上计算。前向传播要经过网络的每一层；GPU 1 算完后，因为下一段参数在 GPU 2 上，就把中间结果传到 GPU 2，让 GPU 2 接着算。算完再传到 GPU 3，让第 43 到第 63 层在第三张 GPU 上计算，如此一直往下。通过这种 partition 方式，六块 GPU 确实能协同支撑模型推理，让模型跑起来。但问题是，这条流水线里会充满大量 bubble。

**46:24**

这就像一条指令经过六级流水线：在同一个时刻、同一个时间片里，只有一个部件在工作。对模型并行来说，某个时刻只有一个 GPU 在算当前请求，其他 GPU 都在空闲、打酱油，整个 GPU 利用率很低。GPU 本身又很贵，肯定不希望它空转。于是可以用更多请求来填满 GPU：这就像从顺序 CPU 的设计转向流水线 CPU 的设计。流水线 CPU 在每个时钟周期都启动一条指令；这里也是类似，只是周期不是 CPU 时钟周期，而是粒度更大的一个周期。

**47:24**

具体来说，当请求 1 在 GPU 1 上执行完、进入 GPU 2 时，就让请求 2 开始在 GPU 1 上工作，计算第 1 到第 21 层。通过这种方式，可以让不同请求在不同 GPU 上重叠执行，把 GPU 利用率提上去。假设请求很多、一直有请求到来，那么所有 GPU 都会工作，各自负责不同层的计算。这样通过请求重叠，就能提高整个 GPU 集群的利用率。

### 流水线并行与请求重叠

**48:31**

把模型划分到多个 GPU 上，是不得不做的一件事。后面的 token 依赖前面的 token。请求一在某一层的计算结束后，又得被放回去，请求一还得回到这里继续执行。到第七个使用周期时，这一侧又空出来了，就可以再回去。此时可以把它看成一个新的请求，重新和其他请求一起送进去。

### Pipeline 与预测执行

**49:34**

这就是 pipeline 思想在推理系统中的使用。这里并不是只想讲 CPU 有流水线；pipeline 是一种在很多时候都可以使用的思想。Prediction，也就是投机执行或预测执行的方式，也不是只在 CPU 的 branch 里才有用，在很多系统里也有用。仍以大模型为例。它是 auto-regressive 的，采用单词接龙的方式，每次只吐出一个 token。每次只吐一个 token 的问题是，一个 token 都要把整个大模型，比如刚才说的一百二十六层，全部经过一遍才吐出来，效率很低。如果要生成的 output 很长，就得经过很多很多轮，才能把最后的内容生成出来。

### 大模型中的投机推理

**50:35**

于是有一个想法：能不能做投机推理？先猜一猜下一个词是什么，再下一个词是什么，再下面一个词是什么。通过猜测，让大模型一次走完推理。把这些 prompt 批量放在一起给它，让它一次性把后面的词都填出来，这就是投机推理的基本思路。怎么猜下一个词？用一个草稿模型：用一个很小的模型，就像 branch predictor 一样，有一个小部件专门去猜下一个词是什么。

**51:37**

这个小模型本身猜得不一定准，但运行速度很快。例如给它 prompt“流水线提高的是”，它可以直接猜出接下来的三个、四个 token 可能是什么；后面可能是“吞吐量”和逗号。它一下可以帮你猜出后面四个 token 是什么。因为是小模型，猜得很快，但不一定对。于是让大模型核对：把这样的 prompt 同时送进去。具体会变成什么 prompt 呢？把“流水线提高的是”作为第一个 prompt，第二个是“流水线提高的是吞”，第三个是“流水线提高的是吞吐”，依次组成几个 prompt。原来的 prompt 加上逐个拼接猜测 token 得到的 prompt，一共组成五个 prompt，把这五个 prompt 变成一个矩阵。

**52:47**

把这五个 prompt 送进去，依次推理，把每个 prompt 的下一个结果都推出来。推出来之后就可以检查：例如第一个 prompt 的下一个结果确实是“吞”，那就说明刚才草稿模型猜的“吞”是对的。通过让大模型做一次推理、一次前向传播，就把这些结果做了一次验证；如果验证结果一致，就接受。若发现不一致，比如草稿模型猜的是“量”，但大模型在“流水线提高的是吞吐”之后吐出来的是“率”，那就不一致；后面的猜测就没用了，需要从这里重新猜。这样，大模型推理一次就可以得到三个词，而原来推理一次只能得到一个词。这就是投机推理，和预测执行的思想比较像：你确实不能提前知道，但可以想办法提前猜一猜。

### 视频播放中的流水线

**54:00**

类似地，大家每天刷手机、刷 B 站、刷小红书，看视频时其实就有一个非常经典的流水线。你们经常遇到卡顿，B 站会提示降低清晰度以保持流畅。为什么会卡？因为看视频本身是边下载、边解码、边播放的过程，并不是一次性下载好再播放。一次性下载好再播放，用户体验不好：要等很长时间才能看一个视频，虽然看的时候一定不会卡。所以视频网站的做法是让用户点开视频立刻就能看：先下载一点点，下载到缓冲区里，然后开始解码。

### 需要优化的矩阵乘算子

这些算子会被赋值到这个结构体中，再进入运算。本次主要实现的是 matmul，也就是矩阵乘法。它输入的数据是 Q4_0 格式，前面已经多次提到过这种量化格式。

一次推理需要经过非常多神经网络层，每一层都要计算很多次注意力和前馈中的矩阵计算。在一次推理中，也就是一次前向传播之后，我们实际测了一下：在这么多算子里面，单看这一个算子，并测量了它在 CPU 上运行的情况。

### 性能瓶颈与矩阵乘函数接口

**08:12**

这一个算子在 CPU 上的时间占用在 99% 以上。因此，发现这个瓶颈之后，优化程序效率就要重点关注这个算子，想办法把它实现得更快。它一旦变快，占运行时间 99% 以上的部分就能加速，整体推理效率也会提高。

先看这个矩阵乘积函数做了一件什么事。它一共传入五个参数：第一个 `float *y` 是输出，指向结果向量；第二个 `uint8_t *w` 是权重指针，权重经过 q4_0 量化，因此以 `uint8_t` 指针的方式传输；第三个 `float *x` 是输入。需要把 \(w\) 和 \(x\) 相乘才能得到 \(y\)。后面两个参数分别是行数 `rows` 和列数 `columns`。

这个函数要做的事情很简单：把 \(w\) 的每一行与 \(x\) 相乘，结果放到 \(y\) 中。输出 \(y\) 的长度为 `rows`：每一行 \(w\) 与 \(x\) 的点积对应 \(y\) 的一个元素。

### 行字节数与 q4_0 块布局

**09:56**

先看标量版本。第一行计算 `row_bytes`，也就是每一行占多少个字节。一行有 `columns` 个元素，而一个 q4_0 量化块包含 32 个权重，所以先算出一行有多少个块，再乘以每个块的字节数。

一个 q4_0 块占 18 个字节：前 2 个字节是 FP16 的 scale \(d\)，后面 16 个字节包含 32 个权重。每个权重用 4 bit 表示，32 个权重正好占 16 个字节。这样第一行就算出了每一行占多少字节。接下来用一个循环遍历每一行，因为每一行都需要算出一个乘积，并赋到 \(y\) 里。

### 标量实现的行指针与块遍历

**11:08**

循环体第一行先算出当前行第一个块的指针：用权重指针 \(w\) 加上行偏移，也就是当前行号乘以 `row_bytes`，得到当前行第一个元素的地址。然后定义一个 `sum` 用于求和。

接下来针对这一行中的每一个块做反量化。循环变量 \(c\) 每次加 32，直到 `columns`，相当于依次遍历每个量化块；每处理完一个块，就把 `block` 指针加 18，让它指向下一个块。

在这个循环里，先取块的头两个字节。`q4_0_scale` 函数可以直接把 FP16 的 scale 值转换成 `float`；这个逻辑前面的代码中已经写过，不需要大家再写。

### 反量化 32 个权重

**12:34**

接下来要把剩下的 32 个权重反量化，所以最里层循环让 \(j\) 从 0 到 15。对一个字节来说，低 4 位对应 \(q_0\) 到 \(q_{15}\)，高 4 位对应 \(q_{16}\) 到 \(q_{31}\)。反量化时先把 int4 的值减去 8，再乘以块开头的 FP16 scale。

### 点积累加与结果写回

**13:22**

设当前块从输入的第 \(c\) 列开始。低 4 位对应的权重与 \(x_{c+j}\) 相乘，高 4 位对应的权重与 \(x_{c+j+16}\) 相乘，因为高 4 位在块内多了一个 16 的偏移。把这一组的乘积累加，并乘以 scale \(d\)，就得到该块对点积的贡献：

\[
\sum_{j=0}^{15}\left((q_j-8)x_{c+j}+(q_{j+16}-8)x_{c+j+16}\right)d
\]

把一行中所有块的结果累加，就得到该行 \(w\) 与 \(x\) 的乘积和，再把它放到 \(y_i\) 中，其中 \(i\) 是当前行号。标量版本基本上就是实现前面那张图：每一行 \(w\) 与 \(x\) 相乘，结果放到 \(y\) 里，只是这里多了一步反量化。如果还不太理解，可以回看前面反量化部分的代码。

### AVX2 向量化思路

**14:43**

接下来讲 AVX2 中怎样实现这个算子。AVX2 的做法是使用更大的寄存器，做多通道求和、多通道加法和多通道运算。AVX2 使用 YMM 寄存器，YMM 是 256 位的寄存器。如果要在其中做 32 位浮点运算，256 位一共可以存放 8 个 32 位浮点数，所以 AVX2 中的基本想法就是做 8 路累加或 8 路乘法。

在一行里面可以把它分成很多块。例如这个模型一行一共有 2048 列；因为采用 8 路累加，而每个 q4_0 块有 32 个参数，所以 2048 列一共可以分成 64 个块。

### 分块与反量化公式

**16:21**

每个块包含 32 个参数。由于 AVX2 做的是八路累加、八路乘法，32 个参数需要拆成 4 组、每组 8 路来处理。具体来说，一个块中的 32 个 int4 权重占 16 个字节；把这 32 个编码拆出来后，分成 4 组，每组 8 个，分别与输入相乘，并把每次乘法的结果累加到临时和 `b_sum` 中。随后把 `b_sum` 乘以缩放系数 \(d\)，再累加到最终结果中。对应的反量化公式是：读出的 int4 值 \(q\) 先减去 8，再乘以缩放系数 \(d\)，得到还原后的权重，然后与输入 \(x\) 相乘。

### 提取公因子 \(d\)

**17:33**

对一个块内的 32 个权重求和，内层是 \(\sum_{i=0}^{31}\)；一行有 64 个块，因此外层还要从第 0 个块求和到第 63 个块。注意，同一个块内的 \(d\) 是不变的，所以可以把 \(d\) 提到内层求和之外：

\[
\sum_{b=0}^{63}\sum_{i=0}^{31}(q_{b,i}-8)\,d_b\,x_{b,i}
=
\sum_{b=0}^{63} d_b \sum_{i=0}^{31}(q_{b,i}-8)\,x_{b,i}.
\]

### 先累加再乘 \(d\)

**18:21**

提取 \(d\) 的目的是减少乘法次数。做法是先把 32 个 \(q\) 与对应的 \(x\) 相乘并求和：把 32 个权重分成 4 组、每组 8 路，四组的结果都累加到同一个 `b_sum` 中，最后只需要把 `b_sum` 乘以一次 \(d\)。如果先让每组分别乘 \(d\)，由于有 4 组，就要做 4 次乘法；先做内层乘加、最后再乘一次 \(d\)，效率更高。一个块处理完后，再把这个块的结果累加到最终总和中。

### 八个 float 的水平求和

**19:31**

一个块最后得到 8 个 float32 数，需要把这 8 个数相加。AVX2 提供了相应的归约函数：第一步把高 128 位加到低 128 位上，使高半部分的 4 个通道分别加到低半部分的 4 个通道；第二步做相邻两个数相加。由于相邻相加函数会分别对高、低 128 位各做一次，所以不能一开始就用它，必须先把高 128 位加到低 128 位。之后再做两次相邻相加，最低位就是 8 个数的总和。最后把这个结果输出到最终结果寄存器中。

### 从 16 个字节中拆出 32 个 int4 权重

**21:06**

具体到字节级，一个块有 16 个权重字节；每个字节包含两个 int4 权重，所以 16 个字节正好对应 32 个权重。首先用 load 类函数把这 16 个字节加载到一个 XMM 寄存器中：16 字节 × 8 位 = 128 位，正好与一个 XMM 等宽，便于在 XMM 内继续处理。然后取每个字节的低 4 位：把每个字节与 `0x0F` 做按位与，得到 \(q_0\) 到 \(q_{15}\) 这 16 个权重。接着把整个 16 字节向量右移 4 位，使原来的高 4 位移动到低 4 位；再与 `0x0F` 做按位与，得到 \(q_{16}\) 到 \(q_{31}\) 这 16 个权重。

### 扩展到 32 位并做向量乘法

**22:46**

拆出各个权重后，需要把它们转换成浮点数。可以使用 `cvtepu8` 这类指令，把单字节的值扩展成 32 位整数并放入 YMM 寄存器；每次取 8 个，例如 \(q_0\) 到 \(q_7\)，再分别处理其余各组。之后把每个权重转换成 32 位 float，因为输入 \(x\) 也是 32 位 float，只有通道数和字节宽度匹配后才能做乘法。整个流程是：先把 32 个权重全部剥离出来并放入 YMM，再把 YMM 中的权重向量与输入 \(x\) 向量逐通道相乘；在这之前，需要先把 \(x\) 加载到一个 YMM 寄存器中。

**24:23**

把输入 x 的对应通道与权重逐项相乘，得到结果后累加到 YMM 临时寄存器 bsum 中，这个寄存器保存一个临时加和。一个块中有 32 个权重，按上述方法分成四组，做四次乘加，就得到该块的部分和；此时还没有乘以 d，是图中右侧的 bsum，也就是一个块的八路部分和。然后把这个部分和乘以 d，再累加到总的部分和 ACC 中，一个块就处理完成。对每个块执行相同操作，就能得到一行中所有块的总结果，最后输出即可。

### 标量版与 AVX2 版的性能对比

**25:40**

把这个算子写出来后，编译并执行。这里没有重新跑编译，展示的是之前跑过一次的结果。左边是前面列出的很多矩阵，包括注意力矩阵以及后面一些前馈矩阵。以第一行为例，标量方式一次运算约需 3 毫秒；换成 AVX2 向量化方式后，一次运算只需 0.479 毫秒，速度提升接近 6 倍。

### AVX2 代码结构

**26:39**

前面标量的代码如果理解了，这段 AVX2 代码也不难理解。代码里有很多不熟悉的函数，但不需要逐一了解，只要知道每一步在做什么。第一步是掩码操作：用一个 128 位的 XMM 寄存器把每个字节都设为 15，即 0x0F，从而得到掩码。第二步计算这一行的字节数，和前面的标量循环一样，然后进入循环，按行处理；循环内的第一行也与标量版本相同，同样是计算行字节数。

**27:59**

进入块循环前，先计算当前行的起始地址。ACC 是当前行求和的总结果，所以先把它置零；这与标量代码中的 `float sum = 0` 对应。接下来进入每一块的循环，对每个块执行同样的操作。

**28:33**

对每个块，先取 block+2 的位置，跳过开头两个字节的 float 值（缩放因子），把 128 位加载到 XMM 寄存器。然后与 0x0F 掩码做与操作，得到每个字节的低 4 位，即 q0 到 q15。再把寄存器右移 4 位，并再次与 0x0F 做与操作，得到高 4 位，即 q16 到 q31 这 16 个权重。

**29:37**

接下来把每个权重转换成 float。转换函数接收 low 或 high 部分，输出对应的 float 值。然后从 x+c 开始取 256 位（当前处理到哪一列，就取对应的 x 值）加载到 YMM 寄存器，与第一组 8 个权重 q0 到 q7 相乘，把部分和放到 s 中。接着继续在 s 上累加：用 q8 到 q15 的权重与 x+c+8 相乘；用 q16 到 q23 的权重与 x+c+16 相乘；用 q24 到 q31 的权重与 x+c+24 相乘。这里没有写循环，而是一次处理 32 个数，最终得到 s。四个乘加组分别对应 8 个通道，所以 s 是 8 路部分和。

**31:24**

这时 s 还没有乘以 d，只是部分和。从 BLK 中取出 scaling 值 d，与 s 相乘，再把结果加到 ACC 上，就得到当前块的结果。然后遍历这一行中所有的块，每块都这样处理，最终得到整行的 ACC。

**32:00**

最后对 ACC 中的 8 个 float 做水平求和，使用 `hsum_8` 函数，原理与前面相同；感兴趣可以在代码中找到这个函数看实现。具体做法是先把高 128 位加到低 128 位，再调用两次相邻两个数求和，最后取出最低 32 位，得到标量结果。这就是这个向量化实现的基本做法；向量化部分涉及很多新指令，不熟悉是正常的。

### 向量函数的实现与模拟执行

### 栈帧与 buffer 地址

**50:05**

接着看汇编。`RBP-8` 处存放的是当前写入位置的指针；程序把它取到 `RAX`，把字符写到 `RAX` 指向的位置，再处理 `RAX+1` 的位置。要进一步确认，就要看 `RBP-8` 对应栈上的哪个位置。函数开头先保存 RBP，并把 RSP 的值移到 RBP，使 RBP 成为当前栈帧的基准。`RDI` 是第一个参数，也就是缓冲区 `buffer` 的地址，因此接下来要重点看 `buffer` 在哪里。

### 覆盖返回地址

**52:14**
