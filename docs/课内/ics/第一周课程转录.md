## 2026 年 9 月 15 日｜第 1 周周二第 3 节回放

### 课程定位与课程背景

**03:00**

现在开始 ICS 课程的第一次课。

**05:28**

ICS 是 Introduction to Computer Systems，通常译作“计算机系统导论”。这门课由陈榕老师和古金宇老师共同授课。按照原本的安排，古老师负责第一学期的课程，但他临时去北京出差，因此第一节课由我来讲。

第一节课通常和后续的具体内容不完全相同，主要任务是介绍课程，希望大家愿意继续学习这门课。现在让学生对一门课产生兴趣比过去更困难一些。这次课堂上大约有接近一百名同学，之后人数可能会有所变化。

**06:43**

ICS 不是一门有特别悠久历史的课程，但它非常重要。大约在 2001 年，这门课第一次被引入国内。那时我正好是软件学院第一批学生，也是最早接触这门课的学生之一。

在传统的计算机教学中，计算机组成、操作系统、网络等内容通常被分成一门门独立的课程，但缺少一门课程从整体上介绍计算机系统。ICS 最初的目标，就是让学生对整个计算机系统建立一个初步而完整的理解。

最开始这门课曾经在一个学期内讲完，之后逐渐变成两个学期，学分也随着培养方案有所调整。仅从课程持续的时间和学分安排，就可以看出它在整个计算机教育中的重要性。

### 教材与课程的学习方式

**08:54**

课程对应的教材是 Computer Systems: A Programmer’s Perspective，也就是大家熟悉的 CSAPP。这本书最初获得了很高的评价，但现在距离它出版已经有一段时间，很多同学可能会担心它是否还能跟上今天的技术变化。

在计算机教学中，十年并不一定意味着内容已经失效。过去我们使用的很多教材甚至比当时的课程早几十年。虽然现在技术变化更快，但系统中的很多基本概念并不会因为大模型出现就立刻失去价值。

以前课程还会配合一本 C Programming 相关的教材。现在这部分被删去了，换成了一些在线课程材料。C 语言仍然会在课程中使用，但本课程并不是为了重新讲授 C 语言编程。

**10:55**

这门课和很多传统课程的区别，在于它不是孤立地介绍一个个知识点，而是从全局、从编程者的角度介绍整个系统：程序运行在什么环境中，系统如何支持程序，以及各个概念在整个系统中的位置。

课程还会鼓励主动学习。CSAPP 配套的实验曾经包括拆弹等很有趣的任务，学生可以在本地运行程序、验证自己的理解。二十年前，这些实验对学生来说非常新鲜；现在大家可能会觉得它们相对简单，甚至不如自己训练大模型或做 AI 项目“时髦”，一些实验的具体形式也可能已经发生了变化。

但实验背后的目标没有变化：学生不仅要听懂概念，还要通过实践验证它们，理解程序在真实系统中如何运行。

这门课过去的口号，是培养稀缺而强大的程序员。很多毕业生在工作后反馈，课程和教材中的内容确实帮助他们解决了实际问题。

### AI 时代还要不要学习系统

**13:19**

在大模型出现之后，大家会自然地产生新的问题。现在有了 AI 辅助编程，很多代码可以直接由模型生成，为什么还要学习这门课？过去第一节课常用 Hello World 作为例子，讨论一段文本是如何最终在机器上运行并输出字符串的。现在这个例子可能显得太简单，因此课程会把它换成一次 AI 推理请求，让大家观察一次大模型应用如何运行在系统上。

更根本的问题是：在 vibe coding 和大模型普遍存在的时代，我们还需要把自己训练成一个强大的程序员吗？如果模型已经知道教材中的内容，自己学习这些内容还有什么价值？

**18:19**

第一个问题是：代码越来越不完全属于编写者本人。

过去，程序员会亲自写每一行代码，完成实验，并进一步阅读代码编译后生成的汇编，借此发现问题、调试程序、优化性能，甚至分析和防御攻击。

现在，很多代码由大模型生成。我们可能不再完全理解代码，也不能完全掌控和修改它，出现问题时甚至会把责任推给模型。对于制作 Demo、展示想法或验证研究方法来说，AI 生成代码确实能够极大提高效率；但真正需要长期运行的代码，仍然必须保证性能、正确性和安全性。

不能只测试几个正常输入就认为程序正确。还要考虑没有测试过的边界条件、不同工作负载下的性能，以及代码可能暴露出的安全问题。传统的程序设计通常有一个自顶向下或自底向上的整体构建过程，而 AI 生成代码往往是局部生成、快速迭代，未必形成完整的系统设计。

因此，问题不是要不要回到完全手写代码的时代，而是要思考：在代码不完全由自己编写和掌控的情况下，如何保证它的性能、正确性和安全性。

**22:11**

这也是为什么仍然需要训练自己成为一个强大的程序员。不过这里的 programmer 和单纯的 coder 不完全相同。coder 可能只是按照要求写出代码，而 programmer 应该能够掌控整个应用和系统。

未来的目标可能不是亲自写出所有代码，而是在不直接写出全部代码的情况下，仍然能够理解、监督和控制代码。AI 时代程序员的体力负担可能变轻了，但思考、理解和运用知识的负担反而更重。

第二个问题是：vibe coding 改变的是写代码的成本，而不是整个系统的约束。

例如，数据局部性、存储层次结构、并行性、数据之间的依赖以及一致性等约束不会因为模型更强而消失。离处理器更近的数据通常访问代价更低；一个操作写入的数据必须先完成，后续操作才能读取；存在依赖的任务不能被随意并行。这些都是系统本身的约束。

**25:00**

ICS 或 CSAPP 从来不是为了教大家如何编程。编程语言课程负责教会大家写程序，而本课程默认大家已经具备编程能力。这里要学习的是：程序如何在整个系统中执行，以及如何基于对系统的理解改善程序。

大模型改变了编程方式之后，课程研究的对象就变成了你自己写的代码，或者 AI 帮助你生成的代码。你需要能够在程序中定位问题，设计合适的解决方案，并判断模型给出的多个方案中哪一个真正适合当前系统。

如果你知道问题的答案，可能会发现答案已经出现在模型给出的很多选项中；但如果没有相应的系统知识，你就不知道应该如何选择，也无法验证方案是否真的解决了问题。

### 课程强调的几个核心特征

**27:57**

课程的几个特征需要重新理解。

第一，Enduring Concepts，也就是能够长期发挥作用的概念，在今天反而更重要。

计算机更接近工程，而不是单纯的科学。科学研究的是世界本来是什么样子；工程则是在特定环境中构建系统。今天解决的问题，明天可能还会在不同的硬件、软件和工作负载下重新出现。因此，不能只记住某个固定答案，而要理解一个解决方案为什么适合当前环境，以及当环境变化后应该如何调整。

过去课程通常给出一个相对固定的默认环境：Linux 操作系统、CPU、内存层次结构、网络和其他外设，并说明程序在这个环境下会如何运行、遇到什么问题。现在的环境变化更快，规模也更广：可能是数据中心中几千台甚至上万台机器，也可能是手机、穿戴设备或机器人。

所以，课程更希望大家掌握可迁移的系统思想，而不只是记住某个环境下的具体做法。

第二，课程仍然强调从程序员的角度理解系统，但会更加重视应用。学习和应用不是互相替代的关系。没有基本的学习和训练，就无法真正做到有效应用。因此课程仍然会从比特、数据表示和程序执行等基础内容开始，同时尽量压缩机械性的学习过程，把更多时间用于理解这些知识如何被使用。

第三，目标仍然是成为强大的 programmer，但要在 programmer 前面加上 system：成为一个理解系统的 programmer。

现在很多人认为 AI 会替代大量应用程序员，但 AI 仍然必须运行在系统之上。AI 需要系统来训练和推理，也需要系统与物理世界交互。对于希望从事 AI 应用的人来说，系统知识可以帮助其理解底层；如果不局限于 AI 应用，系统方向本身就会成为非常重要的能力。

### AI Infrastructure 中的系统思想

**33:55**

为了说明这些知识为什么仍然有用，可以观察近几年快速发展起来的 AI Infrastructure。它虽然换了应用场景，但其中大量思想都可以在 ICS 中找到对应内容。

首先是优化和并行。Transformer 的一个重要优势，是非常适合在 GPU 这样的并行硬件上运行和训练。训练基础设施中会使用数据并行、张量并行和流水线并行：

- 数据并行（Data Parallelism，DP）：有大量数据需要执行相同的程序，可以让不同设备分别处理不同的数据；
- 张量并行（Tensor Parallelism，TP）：模型或程序过大，一份模型需要跨越多张卡执行；
- 流水线并行（Pipeline Parallelism，PP）：把执行过程拆成多个阶段，让不同阶段形成流水线。

流水线最早会在 CPU 设计中接触到。在 AI Infrastructure 中，流水线同样要处理资源利用率、流水线气泡、数据依赖和执行顺序等问题。

其次是缓存。推理阶段会缓存 Key 和 Value，也就是 KV Cache，以减少后续解码时的重复计算。缓存是整个系统中反复出现的思想，CPU 中有缓存，AI 推理系统中也有 KV Cache。vLLM 中的 PagedAttention，则把操作系统和内存管理中的分页思想用于管理 KV Cache。

再次是浮点数和量化。过去很多计算以整数为主，浮点数的编码似乎不那么重要；现在大模型计算大量使用浮点数，并且经常涉及 8 位、4 位计算和量化。本质上，这些问题都在讨论如何用有限的二进制位表示数值。

最后是安全。课程中会学习缓冲区溢出；在大模型应用中，提示词注入也可以看作一种注入式攻击。虽然攻击对象不同，但背后的思路仍然是利用系统或程序对输入的解释方式。

课程会尝试更广泛地介绍这些知识，不仅说明知识本身，还会关注它们在实际应用中如何被使用，以及使用时依赖哪些条件。

### 从 Hello World 到一次 AI 请求

**40:30**

过去课程常用 Hello World 说明程序如何运行在系统上。现在可以把它换成一次 AI 应用请求：用户在客户端输入问题，客户端可能是命令行，也可能是图形界面；请求通过网络发送给推理服务，最终由具体机器上的 CPU 和 GPU 完成计算，再把结果返回给用户。

从系统的角度看，这和传统应用并没有本质区别。AI 只是应用中的一部分，最终仍然要由硬件执行，由操作系统管理。输入经过处理得到输出，本质上仍然类似一次函数调用。

**42:59**

现在的 AI 应用通常仍然通过 HTTP 接口通信。HTTP 已经存在了很长时间，但它仍然被使用，是因为系统设计需要兼容已有的生态。一个应用不应该只追求在局部硬件上的最高效率，还要考虑与其他组件的兼容。

这种设计通常采用 Client-Server（C/S）架构。客户端和服务端被分离后，对用户来说，后端究竟是 OpenAI、其他云服务，还是本地推理引擎，并不重要。只要双方遵守相同的接口，前端就可以连接不同的后端，后端也可以服务不同的前端。

这种分离思想很早就出现在 Unix 图形系统中，用于支持本地登录和远程登录。今天，前端可以是浏览器、命令行或图形程序，后端可以是云上的大型模型，也可以是本地机器上的推理引擎。

系统设计的重点不在于某段代码具体写成什么样，而在于这种分离是否适合当前环境。当然，资源受限的嵌入式设备或机器人不一定适合直接采用复杂的 C/S 设计。环境变化后，设计也需要随之调整。

**47:03**

为了观察一次推理的完整生命周期，可以把后端换成本地运行的 Ollama。运行本地推理时，通常需要先启动服务，再加载模型文件，然后通过客户端输入请求。

模型可以作为文件保存在磁盘上。服务启动后加载模型，加载完成后才能处理请求。localhost，也就是 127.0.0.1，是一个指向本机的特殊地址，因此请求仍然可以按照网络通信的形式发出，最后回到本机执行。

如果只是使用应用，用户不需要知道模型运行在哪个平台，也不需要知道它如何读取内存、执行 CPU 指令并得到结果。系统在背后提供了抽象。

但如果完全不了解后面的系统，整个过程对你来说就是一个黑盒。你只能提问、等待结果，或者更换模型和问题；当程序变慢、卡住或出错时，就没有足够的手段去掌控它。下一节课将继续讨论系统如何支持这样一次推理。

**50:31**

本节结束。之后的课堂仍然会围绕两个学期展开，同时会根据现在的技术环境补充一些内容，例如操作系统、并行和 GPU 相关知识。

## 2026 年 9 月 15 日｜第 1 周周二第 4 节回放

### 从应用问题定位到系统问题

**04:57**

上一节课的例子中，客户端向 Ollama 或其他推理服务发送问题并得到反馈。从应用角度看，如果回答不满意，可以换问题或换模型；但如果出现系统问题，就需要另一套知识。

例如，请求执行很慢，十秒后才返回结果；程序运行到一半崩溃；请求卡住后永远没有结果。这些问题不一定能靠更换模型解决。不了解程序运行的环境，就很难定位问题；有了系统知识，至少能够建立排查问题的手段。

**06:40**

如果程序运行很慢，第一步是追踪整个执行过程，记录各个阶段花费的时间，找到最耗时的部分，再针对这一部分进行优化。

在一个本地推理系统中，可能至少包含几个不同的进程：前端的 CLI 客户端、负责接收请求和调度的服务进程，以及真正执行推理的 worker 进程。客户端把请求发给服务进程，服务进程管理请求队列并把任务交给推理进程，推理进程处理完后再逐层返回结果。

如果执行很慢，可能是客户端处理输入的方式有问题，也可能是服务进程中的队列拥塞，还可能是推理进程本身耗时过长。进一步追踪后，可能发现第一次调用很慢，是因为推理进程在第一次请求到来后才加载模型。模型加载本质上是从文件读取大量数据，通常会花费较长时间。

**09:48**

如果内存足够，可以把模型缓存到内存中。之后请求到来时，直接访问内存中的模型，而不必再次从磁盘读取。内存访问速度通常比磁盘快很多，因此可以显著减少延迟。

但如果需要使用多个模型，内存可能放不下全部模型，就必须设计缓存替换策略：哪些模型或数据应该保留，哪些应该被替换出去。需要根据访问特征识别热点数据，把经常访问的数据放在更靠近处理器的位置。

存储层次结构通常具有这样的特点：越靠近 CPU，存储越快、越小、越昂贵；越靠下层，存储越慢，但容量更大。因此，系统会尽量把热点数据放到离处理器更近的位置。

系统程序员的能力，就体现在能够使用工具定位问题、选择合适的解决方案，并通过再次运行验证优化是否有效。如果问题仍然存在，就继续沿着执行链路向下排查，直到找到真正的瓶颈。

### 系统的分层结构

**12:07**

刚才的例子说明，系统设计通常采用分层结构。整个系统太复杂，不可能作为一个整体一次性设计完成，因此每一层负责自己的问题，并向上层暴露接口。

可以从下到上粗略地看到这些层次：

1. 硬件层：提供计算、存储和输入输出能力；
2. 指令集与汇编层：对硬件进行抽象，规定机器能够执行什么操作；
3. 工具链、运行时、库和算子库：提供公共功能，解除应用与具体硬件实现之间的绑定；
4. 操作系统层：管理资源、支持多任务，并向程序提供更高层的抽象；
5. 应用层：使用下面的能力完成具体任务。

如果只停留在应用层，遇到性能、正确性、安全性或崩溃问题时，往往没有办法继续定位。学习 ICS，就是逐层了解这些抽象为什么出现、解决了什么问题，以及它们的边界在哪里。

### 硬件层与冯·诺依曼架构

**15:00**

硬件是能够买到、看到和摸到的部分，例如 CPU、主板、内存和 SSD。早期计算机往往是一台机器对应一个任务。如果要完成另一个任务，就需要重新制造一台机器。

计算机的出现，使计算过程软件化：不必为每个任务重新制造硬件，只要改变输入的指令，同一套硬件就可以完成不同任务。

课程不要求大家学习如何制造 CPU 或 GPU。门电路、存储电路和计算电路可以先作为黑盒，但需要理解这些硬件对上层程序提供了什么能力。

**17:04**

冯·诺依曼架构把计算抽象为不断取指令、解码并执行的过程。指令被编码成二进制，存放在内存中；CPU 取出一条指令，理解它代表的操作，执行完成后再取下一条指令。

计算机从开机开始，就不断执行这样的循环，直到关机。对硬件来说，运行的是 Hello World、游戏还是一次大模型推理，并没有本质区别，都是执行大量指令。

冯·诺依曼架构最基本的两个部分是 CPU 和内存：CPU 负责执行，内存负责保存指令和数据。显示器、键盘、磁盘等输入输出设备可以在此基础上加入，但不是计算机完成基本执行循环的必要部分。

### CPU、GPU 与存储

**18:54**

随着任务变复杂，系统中出现了更多计算单元和存储层次，例如 GPU、NPU、缓存以及 GPU 使用的 HBM。无论具体硬件如何变化，本质上都可以从“计算”和“存储”两个方面理解。

CPU 能够执行更复杂的控制流和更多种类的指令，因此指令集更丰富；GPU 能做的操作相对简单，但可以大规模并行执行，因此在合适的工作负载下速度更快。

在设计应用时，需要判断程序的时间究竟花在哪里。如果时间主要花在数据加载、复杂的逻辑判断或依赖关系上，单纯加入 GPU 未必有帮助。若时间主要花在大规模矩阵运算、重复的数据处理和相同指令的执行，并且这些操作之间没有依赖，就可以考虑把这部分负载放到 GPU 上。

**21:09**

如果把矩阵计算放到 GPU 上后只快了一倍，而按照硬件能力预期应该快五十倍甚至一百倍，就需要进一步调试。可能的问题是矩阵太大，超过了 GPU 的 HBM 容量，时间没有花在计算上，而是花在数据在不同存储之间的交换上。

这时，解决方案可能是使用更大的 HBM，或者重新设计数据组织方式。不了解硬件和存储层次，就无法判断性能问题究竟来自计算还是数据移动。

课程后续会在处理器、存储器层次结构等章节中介绍这些内容。最接近 CPU 的是缓存，最远的是磁盘。磁盘本身会简单介绍，更重要的是理解缓存、局部性以及不同存储之间的数据交换。

### 指令集与汇编

**23:16**

最早的计算机可能通过打孔纸带表示 0 和 1。随着任务增多，直接控制这些底层输入已经无法满足需求，因此需要指令集来简化和加快编程。

汇编是对底层硬件的一次抽象。它不再关心门电路是如何构造的，而是把存储抽象为寄存器和内存，并用指令集描述硬件能够执行的操作。

指令集和汇编使硬件与软件分离。不同硬件可以有不同的电路实现，但只要提供相同的指令集，上层程序就可以使用相同的抽象来运行。这样，分析程序时也不必直接分析 0 和 1 的电路，而可以在汇编层面定位问题和性能开销。

**25:43**

从底层门电路到更高层程序，可以理解为逐层构建：许多门电路组成更复杂的硬件，硬件提供指令，指令被组织成汇编代码，汇编代码再被组织成应用和服务。

指令集还需要考虑向后兼容。新硬件出现后，不能让过去编写的程序全部无法运行，因此通常会逐步扩展指令集，使新机器继续支持原有指令。课程会以 x86 系列为主要背景，但新旧处理器之间的基本思想并没有本质变化。

### 工具链、运行时与算子库

**27:37**

在汇编之上，还需要工具链和运行时来解除程序与硬件的绑定。只要底层支持的汇编接口保持一致，上层程序就不必随着硬件实现的变化而全部重写。

公共功能可以被提取为库。例如，程序调用 printf 打印 Hello World 时，表面上只需要一行代码，实际的打印功能可能由大量公共代码实现。把公共功能做成库后，不同程序可以重复使用，而不必各自重新实现。

这个思想在 AI 中也非常常见。模型开发者通常不需要自己实现每一个底层操作，而是调用算子库，把不同的层组合起来。一个算子可以抽象地表示乘法或卷积，具体实现可以在 GPU、NPU 或其他硬件上完成，并随着底层实现优化而变化。

工具层的作用是解耦：上层程序建立在库和算子之上，而不是直接建立在某种汇编实现之上。但抽象同时也会隐藏底层信息。如果程序出了问题，只停留在库的层面可能无法定位，因此仍然需要具备阅读底层代码和汇编的能力。

**30:07**

课程不要求大家大量手写汇编，但需要能够阅读一些汇编，理解程序为什么在某条指令上花费更多时间，以及源代码中很小的变化为什么会造成明显的性能差异。

课程会在相关章节中介绍高层语言如何编译成汇编，也会讨论动态性问题。例如，推理引擎如何在不重新编译整个系统的情况下加载不同模型；模型和推理引擎如何分开编译，再通过动态加载完成组合。

如果一份程序希望同时使用 CPU 和 GPU，编译器可以把同一份代码中的不同逻辑分开编译，生成分别运行在不同处理器上的代码，并通过约定好的接口协同工作。类似的思想也适用于同时使用 CPU、GPU 和 NPU 的 AI 设备。

### 操作系统与资源抽象

**36:09**

最初的计算机可能一次只运行一个任务。随着计算机能完成的任务越来越多，一台笔记本上可能同时运行上百个进程，用户可以一边打开 PDF，一边聊天、看视频或执行其他程序。

操作系统的出现，使单任务机器变成支持多任务的系统，让多个程序共享硬件资源。程序员写程序时通常不需要知道程序会和谁一起运行，也不需要知道它会被放在哪一台具体机器上。操作系统负责隐藏硬件细节，管理和分配资源，并提供保护和隔离。

例如，一个程序即使写成死循环，也通常只会让自己的进程卡住，而不会直接破坏整个系统中其他程序的执行。这是操作系统通过隔离机制提供的保护。

操作系统的重要价值，在于它对硬件提供了抽象，去掉上层程序不需要直接处理的细节，并基于这些抽象完成资源调度。这样的抽象在过去几十年中持续发挥作用，即使大模型出现，短期内也不会消失。

**40:12**

从硬件类别来看，操作系统可以看作提供三类重要抽象：

- 对处理器和计算的抽象：进程；
- 对内存的抽象：虚拟内存；
- 对外设和输入输出的抽象：文件或 I/O 接口。

存储设备和网络设备都可以被归入 I/O 的范围。文件是一个非常高层的统一抽象：通常可以对文件进行读和写。键盘和鼠标可以理解为主要向系统写入，显示器主要由系统向其写入或驱动显示；网络发送相当于写入，接收相当于读取；GPU 也可以通过向设备发送命令、读取结果的方式被使用。

这种高层抽象的优点是能够统一容纳大量不同设备，但缺点是不能充分利用每一种设备的特殊能力。网络与磁盘文件就存在明显区别：文件可以随机访问任意位置，而网络数据通常以流的形式到达，不能像普通文件一样自由定位。

因此，网络接口会在文件抽象之上提供更适合网络特性的接口。现在还有 RDMA 等技术，支持更接近远程读写的操作。

课程会分别介绍处理器、操作系统、虚拟内存和 I/O。外设种类太多，不会全部展开，而是帮助大家掌握作为用户使用 I/O 接口所需的基本知识。

### 进程、时分与空分

**45:12**

进程是操作系统中非常重要的抽象。它让程序员感觉整台机器都是自己的，同时又能与其他程序共享机器。

CPU 上实际任何时刻只有一条物理指令流，但每个进程都可以拥有自己的逻辑执行流。操作系统把不同进程的指令流交错组织起来：可以先执行一个进程，再切换到另一个进程，也可以交替执行不同进程的一部分指令。

对 CPU 或 GPU 来说，它们看到的始终是要执行的指令，并不知道这些指令属于多少个任务。操作系统把多个程序合并起来，在不同时间使用硬件，这就是时分。类似的思想也可以用于 AI Infrastructure：多个请求需要分时共享同一个模型。

内存则不适合简单地采用时分。把一个进程的内存内容拷贝出去，再把另一个进程的内容拷贝进来，代价通常很高。因此，内存更多采用空分：不同程序同时占据不同的空间。

这种设计基于一个观察：程序可能申请很多资源，但在有限时间内只会访问其中一小部分。只要不同程序在同一时间访问的区域不完全重叠，就可以让它们共享内存空间。

**48:45**

当环境变化后，原有的抽象和策略也需要调整。普通 CPU 程序可能申请一大块空间，但实际只使用其中一小部分，因此操作系统可以采用分页和按需分配：程序申请了空间，只有真正访问的部分才被加载到内存中。

GPU 程序可能有所不同。很多 GPU 工作负载申请多少资源，就会在执行过程中快速访问多少资源，可能很快遍历整个模型。因此，CPU 上常见的按需策略不一定适合直接套用到 GPU，需要根据硬件和工作负载灵活运用系统知识。

这门课的特点，就是把计算机中的多个经典方向融合起来，让大家先看到整头“大象”，避免只见局部而不了解整体。

### 课程考核与 AI 使用约定

对于 AI 的使用，课程不会专门检查大家具体使用了什么工具，但有一个“君子协定”：不要把 AI 当作端到端的替代品。无论 Lab 设计成什么样，只要直接把任务交给模型，模型都可能给出一个看起来能拿满分的答案；但这不代表学生真正掌握了内容。

过去常说程序员有“35 岁危机”，但在 AI 时代，可能会出现“22 岁危机”：如果一个人毕业时只会把任务交给 AI，那么雇主可能会选择用更少的模型服务，再由一个有经验的 senior 程序员负责管理。

更有经验的人之所以仍然重要，是因为他们有系统思维和行业经验，知道如何让 AI 工作。例如，大模型可以帮助组织语言、让论文更接近 native speaker 的表达，但论文的核心思路、逻辑、故事组织、第一性原理和研究判断，仍然需要人自己掌握。

对于代码也是一样。必须知道什么是好代码、如何设计测试、什么是好的测试，才能判断 AI 生成的代码质量，并指挥 AI 完成工作。可以让 AI 帮忙查询 API、参数和库，但代码结构、模块设计以及对系统的理解不能完全交给模型。

### 教学形式的调整

**35:14**

过去课程中会安排 Tutorial，带大家安装虚拟机、Linux、Docker 或其他开发环境。早期可能需要手动安装虚拟机，后来改成容器；现在，agent 已经能够通过自然语言帮助完成这些安装和启动工作，因此这些内容不再适合作为课程重点。

过去的 Tutorial 与 MIT 的 Missing Semester 有些相似，会讲虚拟机、SSH、终端、Vim、tmux 等程序员基本工具。但现在这些问题大多可以直接向模型询问，agent 甚至可以代为操作终端和浏览器，所以课程会把时间转向更有价值的讨论。

**38:44**

新的教学形式会围绕一些 topic、paper 或 system project 展开，允许大家结合 vibe coding 和 agent 阅读、理解并讨论系统。

例如，可以讨论模型量化：为什么能够把 FP16 模型量化到 INT8 或 INT4，量化过程中发生了什么。

也可以讨论 CPU 流水线。课程可能先用 CPU 的五级流水线作为具体案例，再抽象出 pipeline 这一系统设计思想，讨论它还会在哪些系统中出现，而不是只记住某一种五级流水线实现。

之后可以通过讨论课、阅读材料或小型 writing/project，让大家自己验证流水线是否真的提高了系统效率。周六预留的时间也可以用于完成这类实践。

### 从 Ollama 模型文件进入数据表示

**41:15**

接下来开始本节的数据表示内容。上节课提到可以在本地运行 Ollama。一个模型文件可能有大约 1.9 GB。使用 ls 可以查看文件，使用 file 可以查看文件类型。

file 可能只会告诉我们它是 data，也就是一段数据。对于操作系统而言，一个可执行文件、MP4 文件或模型文件，从最底层看都只是数据。问题在于：这一段数据究竟按照什么规则编码？Ollama 又是如何知道这一段数据是一个模型的？

这节课要回答的就是信息如何在计算机中表示。

**43:37**

计算机中最小的表示单位是 bit。一个 bit 只能是 0 或 1。多个 bit 组成向量后，需要按照某种约定来解释，才能得到数字、字符或其他信息。

课程使用了一个自行生成的 tiny GGUF 文件作为例子。GGUF 是一种模型参数文件格式，除此之外还会遇到 safetensors、ONNX、pickle、ZIP 等不同格式。模型发布时可以选择不同的文件格式。

可以使用 xxd 等工具查看文件的二进制或十六进制内容。一个 GGUF 文件的开头通常包含四个字节，对应 ASCII 字符串 GGUF。这个用于标识文件格式的固定开头叫 magic number。

如果把文件头部的 magic number 修改掉，Ollama 在读取文件时就会发现它不符合 GGUF 格式，从而拒绝解析。也就是说，文件类型并不是数据天然携带的，而是软件之间共同遵守的一种解释约定。

**46:23**

四个字节本质上仍然是 0 和 1。为什么这些 bit 可以被解释成字符 G？首先需要把 bit 向量解释成一个无符号数。

对于一个有 w 位的向量，最低位的权重是 2⁰，下一位的权重是 2¹，依次类推。把所有为 1 的位对应的权重相加，就得到这个 bit 向量对应的无符号整数。

ASCII 又规定了整数和字符之间的映射。例如，十进制数 71 对应字符 G。程序先把二进制解释成整数，再根据 ASCII 表把整数解释成字符，最终就能读出文件头中的 GGUF。

对于一个 8 位向量，例如只有第 3 位和第 1 位为 1，它对应的十进制数就是 2³ + 2¹。把十进制转换成二进制时，可以反复除以 2，记录每次的余数，最后将余数逆序排列。

十六进制每一位可以表示 0 到 15，因此一位十六进制数对应四个 bit；一个字节由八个 bit 组成，也就对应两位十六进制数。

在 C 或 C++ 中，常见的数值写法包括：十进制直接书写，十六进制使用 0x 前缀，八进制使用 0 前缀，二进制使用 0b 前缀。

### C/C++ 中的基本数据类型

**52:11**

不同模型文件的开头可能出现不同的 magic number。例如，ONNX 文件中会出现与模型和权重有关的可读信息，pickle 文件通常会出现 PK 等标识。文件格式的名字和描述信息，本质上都是对同一串 0 和 1 的不同解释。

在 C/C++ 平台上，常见数据类型有不同的大小。一个 byte 是 8 个 bit；char 通常占 1 个 byte；int 通常占 4 个 byte。long 的大小与平台有关，在 32 位平台上通常是 4 个 byte，在现代 64 位平台上通常是 8 个 byte。

现代手机、PC 和服务器大多是 64 位平台。指针的大小由平台的地址宽度决定，在 64 位平台上通常占 8 个 byte。指针保存的是对象在内存中的地址。

float 通常占 4 个 byte，double 通常占 8 个 byte。size_t 常用于表示容器长度、缓冲区大小等，它是无符号类型，在 64 位平台上通常占 8 个 byte。

### 地址、指针与 64 位机器

**00:00**

在 C/C++ 计算机中，内存地址通常是一个 64 位二进制数。64 位机器和 32 位机器的主要区别之一，是能够表示的地址范围不同。

32 位机器最多能够表示 2³² 个地址，也就是约 4 GB 的地址空间。早期 PC 的内存上限通常接近 4 GB。64 位机器可以表示 2⁶⁴ 个地址，地址空间大得多，因此可以支持更大的内存。

指针保存对象的地址，因此在 64 位平台上通常也是 64 位，也就是 8 个 byte。float 和 double 分别通常占 4 个和 8 个 byte；size_t 在 64 位平台上通常占 8 个 byte，并且是无符号类型。

布尔值在逻辑上只需要 1 个 bit，因为它只有 true 和 false 两种状态。但内存通常按 byte 寻址，不能直接寻址一个 bit，所以最小的数据类型通常至少占 1 个 byte。布尔值占用的这个 byte 中，只有一部分 bit 携带有效信息。

一个 int 通常占 4 个 byte，也就是 32 个 bit。计算机把这 32 个 bit 按照某种规则解释，才得到上层程序看到的整数。

### 内存的数组抽象

**04:45**

字节序要解决的问题是：一个多字节对象在内存中如何排列。

物理上的内存条可以有 DDR4、DDR5 等不同规格，但从抽象角度看，内存可以看成一个从 0 地址开始的大数组。假设有 16 GB 内存，就可以把它看成从 0 到 16 GB 范围的一组连续地址，每个地址对应一个 byte。

每个 byte 都有自己的地址。例如，地址 0x100 处可以存放一个 character。把数据放进内存，就是找到一段空间，把数据放在那里。

如果用取地址运算符取得一个字符的地址，再赋给一个 char 指针，那么指针保存的就是这个字符所在位置的地址。可以把它理解成“对象住在内存中的哪个地址”。

如果存放一个 int，它需要连续占据 4 个 byte。指针保存的通常是这段连续空间的最低地址，但这 4 个 byte 中每一部分的排列顺序还需要由字节序决定。

### 小端法与大端法

**08:24**

在大多数现代机器上，int 的地址是它所占连续空间的最低地址。具体的字节排列方式与机器的字节序有关。

小端法（little-endian）把一个数的低位有效字节放在低地址处。假设四个 byte 从高位到低位写成 12、34、56、78，那么在小端机器中，内存从低地址到高地址的排列是 78、56、34、12。

大端法（big-endian）则相反，内存中的排列与人们通常书写数字的顺序一致，即 12、34、56、78。

“小端”指低位放在低地址，“大端”指高位放在低地址。x86 机器通常使用小端法，常见 ARM 平台也通常采用小端法；网络传输中的网络字节序通常采用大端法。

**11:35**

如果地址宽度是 n 位，就可以表示 2ⁿ 个地址，也就是 2ⁿ 个可寻址的 byte。32 位地址空间能够覆盖约 4 GB，64 位地址空间则大得多。现代系统中，虚拟地址空间通常已经不是一个很紧张的资源。

任何多字节对象都会占据连续的 byte。对象的地址可以理解为它所占的最低地址。小端法规定最低有效字节放在最低地址处。

字节序在网络通信中非常重要。不同机器之间传输的通常只是一段没有类型信息的 buffer，接收方必须根据双方约定来解释它。例如，可以约定网络包的前 4 个 byte 使用大端法表示整个 buffer 的长度，后面的内容再按照字符串或其他数据格式解释。

**14:23**

网络传输为什么需要这样的约定？因为 A 机器发送给 B 机器的本质上只是一串字节，不会自动附带 C/C++ 中的 int、string 等类型信息。

发送方和接收方需要约定数据布局，例如前四个字节表示长度，后面的部分表示字符串。接收方先按照大端法解析长度，再根据长度读取后面的内容。这就是协议和数据格式的基本思想。

可以使用类似 show_bytes 的工具，给定一个指针和长度，逐字节打印内存中的内容。它能够帮助我们观察一个对象在内存中真实存储的字节。

### 同样的数值，不同的二进制表示

**16:32**

如果一个 int 和一个 float 都保存数值 12345，它们都可能占 4 个 byte，但内存中的字节内容并不相同。

int 和 float 采用不同的编码规则。show_bytes 看到的是内存中真正存放的 bit，而不是上层程序把这些 bit 解释后得到的数值。因此，同样大小的对象，即使表面上表示相同的数值，它们的二进制编码也可能完全不同。

把一段 bit 解释成什么，取决于程序使用的类型和双方约定。计算机硬件只保存 bit，具体含义由软件规则赋予。

### ASCII、UTF-8 与 Token

**20:04**

一个 byte 可以按照无符号数解释成一个整数，例如 47。ASCII 再对这个整数作一次约定，把它映射成字符。ASCII 主要使用 7 个 bit 表示英文字符。

在 Linux 或 macOS 的 shell 中，可以通过 locale 等环境变量看到字符编码相关的设置。ASCII 足以表示英文，但不能覆盖中文等大量字符，因此需要 Unicode 以及 UTF-8 等编码。

UTF-8 是一种变长编码，一个 Unicode 字符可以使用 1 到 4 个 byte 表示。程序先把这些 byte 按照规则组合成一个数，再通过 Unicode 的映射表得到最终字符。

因此，同一段信息在计算机中的表示要经过多层约定：底层是 0 和 1，内存中按 byte 存储；多字节对象需要考虑大端和小端；文件需要遵循自己的格式；字符还需要遵循 ASCII、UTF-8 等编码。

**23:03**

大模型中经常出现的 token，也是在对文本进行另一层编码。最简单的理解是，把一段文本切分成若干 token，再为每个 token 分配一个词表中的整数编号。

例如，可以把一个英文单词作为一个 token。tokenizer 按照预先规定的规则把文本切分，再把 token 映射成词表中的整数 ID。后续的 embedding 会把这些整数 ID 映射成向量，注意力等计算则在这些向量上进行。

tokenization 的规则和 UTF-8 类似，都是预先约定好的映射，只是它们处在不同的抽象层次，解决的问题也不同。

### 无符号整数与补码

**25:22**

如果把一个 w 位向量按照无符号方式解释，得到的是大于等于 0 的整数。这种解释可以称为 B2U（Binary to Unsigned）：每一位按照 2ⁱ 加权求和。

但整数还需要表示负数，因此同一段二进制可以按照另一种规则解释为有符号数。这种规则是二补码（two’s complement），也就是 B2T（Binary to Two’s-complement）。

对于 w 位二补码，最低 w−1 位仍然按照 2ⁱ 加权，但最高位的权重变成 −2⁽ʷ⁻¹⁾。因此最高位为 0 时，数是非负的；最高位为 1 时，数是负的。

以 4 位数为例，0111 按无符号数和二补码解释都是 7；1000 按无符号数解释是 8，按二补码解释则是 −8。最高位为 1 时，二补码解释与无符号解释的差异正好是 2ʷ。

无符号 w 位整数的范围是：

0 到 2ʷ − 1。

有符号 w 位二补码整数的范围是：

−2⁽ʷ⁻¹⁾ 到 2⁽ʷ⁻¹⁾ − 1。

负数的可表示范围比正数多一个值。

### 有符号数与无符号数的类型转换

**29:34**

代码中经常会出现显式或隐式类型转换。例如函数参数要求 long，而手里有一个 int，就需要发生类型转换。

当一个负的 short 被转换成 unsigned short 时，内存中的 bit 不会改变，改变的是解释这些 bit 的规则。因此，同一段二进制在有符号解释下可能是负数，在无符号解释下可能变成一个很大的正数。

这与 int 和 float 的情况不同：int 和 float 通常具有不同的编码规则，而有符号数和无符号数转换时，往往只是保留同一段 bit，改用另一种整数规则解释。

**33:01**

有符号数和无符号数混合参与表达式时，很容易出现反直觉的结果。例如：

- −1 < 0 的结果为 true；
- −1 < 0U 的结果却可能为 false。

原因是 0U 是 unsigned int。当有符号数和无符号数比较时，有符号数可能被转换成无符号数。−1 转换成无符号数后会变成一个很大的正数，自然不再小于 0。

另一个经典例子是比较两个字符串长度。假设字符串 AB 比字符串 ABCD 短，但代码通过两个 string length 的结果相减，再判断差值是否大于 0，就可能得到错误结论。

原因是 string length 返回 size_t，而 size_t 是无符号类型。两个无符号数相减时，即使数学结果应该为负数，实际也会按照无符号规则发生下溢，得到一个很大的正数。这个例子说明，类型和隐式转换会直接影响程序的正确性。

### 用户态、内核态与类型导致的安全问题

**36:54**

最后补充一个应用程序与操作系统交互的经典例子。

应用程序通常运行在用户态（user level），操作系统运行在内核态（kernel level）。内核拥有更高权限，用户态程序不能直接任意访问内核数据。用户态和内核态之间存在严格的边界。

Linux 中有 copy_from_user 和 copy_to_user 等接口，用于在用户态缓冲区和内核态缓冲区之间安全地复制数据。复制时需要指定源地址、目标地址和复制长度。

假设内核缓冲区只有 1024 个 byte，接口会限制复制长度不能超过缓冲区大小。问题在于，复制长度通常使用 size_t，也就是无符号类型。

如果上层函数接收的是一个有符号整数，调用者传入 −1，随后代码又把它与缓冲区大小比较或传给使用 size_t 的内存复制函数，就可能发生隐式类型转换。−1 会被转换成一个非常大的无符号数，最终导致复制范围异常扩大。

这样就可能从内核缓冲区之外继续读取数据，把本不应该暴露给用户态的内核数据泄露出去。这是过去经常出现的一类用户态读取内核数据的漏洞。

这个例子说明，类型系统、隐式转换和边界检查并不是细节问题。它们会同时影响程序的正确性、性能和安全性。
