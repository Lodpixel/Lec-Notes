## 计算机系统基础（1）｜第 3 节（09:55）

### 上节课内容回顾：控制流、数据流与寄存器约定

**05:41**

同学们，我们继续来讲上节课没有讲完的一些内容。上节课讲到 stack 这部分流程：在 CPU 上，两个函数一个作为 caller、一个作为 callee，它们之间的控制流是怎么传递的，数据流是怎么传递的。

参数的传递要通过寄存器来完成，而两个函数会用到同一套通用寄存器（GP register），所以软件上又做了一个约定：哪些是 caller-saved register，由 caller 负责保存；哪些是 callee-saved register。如果 callee 要破坏某个 callee-saved register 的值，它就必须负责保存和恢复，使 caller 之后还能正确地使用这些寄存器原来的内容。

**07:31**

当然还有栈（stack）。栈很重要的一个功能是保存 return address。我们在 CPU 执行 call 指令的时候，硬件会自动把下一条指令的地址，也就是 return address，压入栈中；将来执行 return 这条指令时，它又会自动从栈上把 return address 弹出，然后把 PC 的值设置过去。那么除了存放 return address 之外，栈还有一个很重要的作用是存放什么内容？

### 栈上的局部变量与 gets 的边界问题

**08:15**

局部变量放在栈上。还有一些不那么常见的情况：如果函数的参数特别多，超过六个，按照软件约定，更多的参数不再通过寄存器传递，而是通过压栈传递。

之前见过一个例子：函数 echo 中有一个局部变量 buffer，它只占 8 个字节，是一个由 8 个 char 组成的数组。echo 调用了 gets。gets 是一个缺少边界检查、带有 bug 的函数：它从键盘读取输入，把读到的字符填到目标位置。这个函数想达到的效果，就是把用户的键盘输入填到 buffer 中，然后用 puts 打印出来——puts 和 printf 的作用类似，就是把用户的输入再输出一遍。问题在于，gets 本身没有边界检查。如果输入超过 7 个字符，buffer 就放不下了，因为 buffer 的最后一个字符还要放 '\0'，作为字符串的终止符。

### 缓冲区溢出与返回地址覆盖

**10:02**

如果函数运行过程中执行 gets，用户一直输入：前面 8 个字符还能填进去，正好把 buffer 撑满；再往上写，就会写到栈上的其他内容。buffer 是局部变量，放在栈上，它上面还有 register saving 的寄存器，再上面还有 return address。继续向上填，就会发生 buffer overflow，覆盖上面的值，进一步覆盖 return address。将来执行 return 时，跳转的位置就完全不知道到哪里去了。

如果攻击者恶意构造 return address，把它填成 buffer 的起始地址，就可以跳回来。也就是说，在 return 指令执行、PC 被设置到该位置之后，CPU 不会再把这段内容当成简单的 buffer，而会把它当成指令来解释。同一段 0/1 数据，这时就变成了一段由攻击者构造的代码，可以在其中执行。

### 任意代码执行与 Heartbleed

**11:41**

这样就能执行 arbitrary code，即任意代码执行。这非常危险：一旦存在这样的 buffer overflow 漏洞，一个远程攻击者甚至不需要接触你的机器，只要输入一段内容，就可以劫持整个机器，在上面执行任何代码。

2014 年左右有一个非常著名的漏洞，叫心脏滴血漏洞（Heartbleed）。它的触发原因与 buffer overflow 类似，是在相关协议交互过程中存在 bug，导致任何远程攻击者都可以劫持机器。上次课留了一个问题。

### 攻击者如何知道地址：固定布局与 Morris 蠕虫

**12:55**

之前留下的问题是：buffer 可以被攻击者控制，这没问题，因为它本来就是面向用户的接口，用户当然可以往里面输入东西，也可以覆盖 return address。但攻击者怎么知道 return address 应该被改写成什么？可以把它改写成 buffer 的起始地址，可攻击者又怎么知道 buffer 的起始地址是什么？

原因其实非常简单：在早期的机器上，每一个程序在不同的机器上运行时，内存布局是完全一样的。你在本地跑一下，这个地址是多少，世界上别的机器跑起来也是同一个地址。

这也就是 1988 年互联网上非常著名的 Morris 蠕虫病毒。Morris 利用的就是 fingerd 程序中一个缓冲区溢出问题，也就是刚才说的 gets 这类问题。由于当时大家运行这个程序时地址都一样，同一个病毒可以感染全部计算机，或者打下很多很多计算机。Robert Morris 当时还很年轻；做这个蠕虫病毒之后，被判了三年缓刑，当然没有坐牢，所以没被抓进去——400 小时社区服务，罚了一点钱。后来他去了 MIT 当老师，2006 年成为 tenured professor。接下来这位大家认识吗？他可能一年以后会成为大家的老师，这是夏虞斌老师，也是 IPADS 的老师。

### 地址随机化与栈随机化

**15:27**

既然有这个问题，就要想一些方法。这个问题听起来很傻：本地跑一个程序和远端跑一个程序，地址都一样，那一个很自然的想法就是能不能让地址不一样。地址不一样，攻击者不就猜不到地址到底是什么了吗？所以最简单、也很直接的一种防御方式叫地址随机化（address randomization），其中一个特殊形式是栈随机化（stack randomization）。也就是说，每次程序执行时，操作系统为它分配一段栈，这段栈的起始地址是不确定的。这样，即便是同一个程序，其栈的起始地址也不再确定。

### 栈随机化

**16:18**

在不同的机器上，甚至在同一台机器上，每次运行时栈的位置都不一样。这样一来，攻击者就不知道 buffer 的起始地址到底是多少。这里有一个简单的 case：三行代码，打印自己局部变量的位置，你会发现在这台机器上运行三次，结果都不一样，并不是同一个地址。这就使得攻击者猜测的难度增大，他不知道该怎么猜。

### 地址空间布局随机化

**16:56**

除了栈随机化之外，栈位于地址空间中比较高的地方，所以它的地址相对来说比较大，每次的起始地址我们可以换。此外，code 和 data 相对来说位于比较低的地址，这个地址其实也可以做随机化。整个程序的地址空间——每个程序都看起来独占全部地址空间，认为自己占了全部内存——所以 data 段、指令 code 段、stack、heap 理论上都可以在里面任意选择一段地址来使用。这就叫地址空间布局随机化（address space layout randomization），我们可以把这些段随便放。这样攻击者去猜测的时候，就很难猜到地址空间布局是什么样子。

**18:09**

这里还有一个 case：把刚才我们自己写的这个小程序运行一万次，可以看到它的随机化范围。其实它也不能说是完全随便任意一个地址，一般来说会有一个可变化的 range。我们把最高和最低的地址都打印出来，可以看到：在 32 位平台上，这个变化范围大概是 \(2^{23}\)；在 64 位平台上则是 \(2^{34}\)，已经是一个比较大的地址范围了。

**18:39**

当然，这时攻击者也不是就不攻击了，他要想个办法。既然现在在本地跑起来跟你的值不一样了，buffer 的值不一样了，那还有没有别的方法去猜一猜 buffer 的位置？现在的问题是，攻击者每次做一次 buffer overflow 去覆盖 return address，只能写一个值：return address 填成 a 就跳到 a，填成 b 就跳到 b，很难精准控制到想跳的位置。最简单的方法就是暴力攻击：如果允许攻击者尝试 \(2^{34}\) 次，他也能成功，反正每次换一个地址去试。但试这么多次，别人也很容易发现你有问题。

### NOP sled

**19:34**

那么有没有办法，写一次就能尝试很多个地址？攻击者就想出一个方法，叫做 NOP sled，也就是 NOP 滑梯。在 x86-64 中有一条指令叫 nop，它只占一个字节。这条 nop 指令什么事情也不干，它就是一条指令，但没有任何用处。于是攻击者就可以做一件事：在他真正想填的这个 input buffer 前面填很多 nop，比如填 256 条 nop，也就是 256 个字节，真正的攻击代码放在后面。他填的 return address 只要落在中间即可——因为栈会随机化，buffer 可能被前移后移，但无论真正跳到哪个位置，前面都是一堆 nop，最后总会执行到攻击者代码。这样做的好处是：如果这一次 return address 猜的地址正好落在这个区间里面，就一定可以攻击成功，从而降低了攻击者需要尝试的次数。比如随机化范围是 \(2^{23}\) 时，这样一次就相当于猜了 \(2^{8}\) 个地址，可以让 retry 的次数降低。所以栈随机化增加了攻击的工作量，但它不能完全阻止攻击。

**21:44**

甚至可以用一个更大的 buffer，理论上用一个超大的 buffer，可以让这个次数下降得更夸张。但是我们能不能把 NOP sled 设得特别特别大，来减少尝试次数呢？通常不会设得特别大。一个原因是栈本身的大小：想一想，栈的用途是函数调用，a 调 b、b 调 c、c 调 e，栈会继续往下涨，栈的区间会变大。所以即便是一个非常复杂的程序，它通常用到的栈的大小也不会特别大。常见的 stack size 可能也就是十几 K、几十 K，大一点的可能是几兆、十几兆，一般情况下差不多就是这个上限。因此，如果一下把 NOP sled 设得特别大，那么在你复写的时候，可能就已经访问了一些非法地址，不用等 return，这个程序就 crash 了。攻击者就通过这样的方式来降低猜测的难度。

### 金丝雀（canary）

**23:20**

那么，除了栈随机化之外，我们还要增加一些防御的方法。增加的防御方法是什么呢？我们想一下：既然是 buffer overflow，你是从这个 buffer 往上覆盖，要覆盖掉返回地址。所以我们想一个方法：在返回地址的下面加一个金丝雀（canary）的 value。

为什么叫这个名字？我不是特别清楚，我有点印象，是说金丝雀可以去探测有没有毒。比如下井探险或者考古的时候，先放一只金丝雀下去，看它在下面能不能活；能活的话，就说明这个环境没问题。这里金丝雀的作用就是：我会先设置一个金丝雀在这里，如果有攻击者去复写……

### 栈金丝雀的检查逻辑

**24:33**

通过 buffer overflow 覆写返回地址时，也会把栈上的金丝雀（canary）破坏掉。所以只需要检查一件事：在进入函数之前设置好金丝雀的值；函数返回时检查这个金丝雀的值是否仍然是原来设置的值、是否还正常。这样就可以检测栈有没有被破坏。

看一段简单的代码：通常一个编译出来的函数，其入口（entry point）处的代码和 return 处的代码会包含类似的金丝雀检查。

### 编译器插入的检查代码与 FS 寄存器

**25:17**

会看到类似这样的代码：把 \(FS:0x40\) 的内容送到一个寄存器；最后再把 \(FS:0x40\) 的内容和栈上的值做比较。如果 not equal，就跳转到一个 label，这个 label 叫 stack check failed。这段代码和函数的逻辑没有任何关系，它是编译器插入的检查金丝雀值的代码。前面一段从 \(FS:0x40\) 把金丝雀取出来放到栈上；最后一段把栈上的值再拿出来和金丝雀真值比较，如果不等就报 stack check failed，说明栈内容已经被破坏。

\(FS:0x40\) 是什么意思？FS 是另一个比较特殊的寄存器，叫段寄存器。段寄存器里面会存一个基地址，\(FS:0x40\) 就表示基地址加 \(0x40\)，也就是一个地址。

### 金丝雀的初始化与攻击问题

**27:02**

程序初始化的时候，在 main 函数之前还会有一段代码在跑。程序的 entry point 其实不是 main；main 才是我们真正写的代码或程序核心逻辑的入口。所以在前面一段初始化里还有一些事情，比如设置金丝雀的内容。操作系统会在程序初始化、程序创建的时候随机生成一个值，作为栈的金丝雀值。一个 64 位的金丝雀，要猜中的概率基本为零，这就是这种防护的做法。

### 能否读取金丝雀

**28:02**

怎么攻破金丝雀的防御？大家讨论一两分钟。假设你是一个攻击者，现在告诉你这里有一个 buffer 漏洞，栈地址也告诉你，stack randomization（栈随机化）也关掉了，但栈上有一个 canary，你怎么办？

有同学说读 canary，非常好。怎么读 canary？就是搞一个指针放到 canary 的位置。问题是你怎么知道 canary 在哪里，相对位置是什么。这就是为什么我们会用 FS 这个寄存器去存一个基地址，把它作为 canary 存储的基地址。

### 金丝雀的地址与运行时检查

**29:13**

FS 这个寄存器是在运行时、程序初始化或程序创建的时候由操作系统设置的一个值，它当然也在程序的地址空间里面。地址空间本身很大。比如 FS 指向某个位置，指向一个机器地址；canary 存在里面的这个位置，也就是加 \(0x40\)。这是一个 8 字节的 canary。

它的假设是攻击者不知道这个 canary 到底在哪里。因为要猜到地址，也是在 \(2^{64}\) 的地址空间里精准猜到位置，这件事和直接猜到 \(2^{64}\) 中的一个数值一样困难。也就是说，你不知道它的地址在哪，也不知道它的值是什么。编译器插入代码，在运行的时候把 canary 的值搬到栈上；如果被 buffer overflow 了，就在 return 之前 check 这个值。它大概是这么一个逻辑。

### 绕过金丝雀的几种思路

**30:46**

如果有方法能够读到它的值，当然可以绕过它的防御，但这也确实比较困难。还有没有别的方法？直接越过去？这也是一种方法。

如果 buffer overflow 比较神奇，比如有一个奇怪的机制，它会跳 8 个字节去复写，那你在复写 buffer 的时候，就可能每次正好越过 canary，只复写这些，中间的被跳过。如果有这么奇怪的 buffer overflow，确实有可能做到。这是一种不去碰它的方法。通常 buffer overflow 还是会往后顺次写，所以还有一个方法是什么呢？

### 利用 server 的 fork 与并发

**31:46**

通常攻击金丝雀的一个做法是：我们的 server 程序一般是在攻击 remote machine（远程机器），这个 server 程序有一个特点——会有很多 concurrent client 访问它。对于每一个 client c1、c2、c3，server 为了更好的并发性，为了不让每个 client 排队。假设去买火车票，如果每次只能服务一个用户，你肯定受不了，不知道要排多长时间。所以它的做法是 fork，会分身：每来一个 client，就创建一个和自己 clone 出来的副本。

### 固定 canary 的逐字节爆破

**32:42**

克隆出来的新 server 每个都彼此相同，因此其中的 canary 值也相同。攻击者就可以利用这一点，用暴力方式去猜 canary。原本如果直接暴力猜一个 8 字节的 canary，需要猜 \(2^{64}\) 次，显然不可能。但 canary 值不变后，每次需要猜的范围就变得非常简单：第一次进行 buffer overflow 时，只改写 canary 的第 0 个字节，前面的字节都不动。只爆破第 0 个字节时，只需要猜 \(2^8\) 种可能。猜出第 0 个字节后，再按同样方式猜下一个字节。这样总共只需约 \(2^8 \times 8 = 2^{11} = 2048\) 次，就能猜出一个原本来自 \(2^{64}\) 随机空间的值。攻击者因此比较容易精确得到 canary。所谓按字节猜，是因为不必破坏整个 canary：如果覆盖第 0 个字节后程序仍能正常 return，就说明这个字节猜对了。

### 不可执行栈与内存权限

**34:46**

于是人们发现，光有 canary 还不够，这仍然没有彻底解决攻击，可以说是道高一尺、魔高一丈；当然我们更希望魔高一尺、道高一丈，所以还需要继续做更深层的防御。一个办法是设置内存权限。进程的地址空间在抽象上仍然像之前看到的那样：程序认为自己独占全部地址空间，其中有 code 段，也有位置较高的 stack。前面攻击者的假设是，通过 buffer overflow 改写栈上的局部变量——局部变量本身是数据——并覆盖 return address，让 return address 指向栈上的一段地址；这样把 PC 设置到那里后，CPU 会把原本应解释为 data 的内容当成 instruction 去执行。为此，体系结构/CPU 提供了一个新功能：可以设置内存属性，并不是所有内存都可读、可写、可执行。它把 stack 设为 non-executable，不允许执行；把 code 段设为 executable，可以执行。这里的 x 就表示 executable。

### 查看进程内存映射：/proc/self/maps

**36:52**

我们可以查看一个程序的 memory layout。可以自己写程序查看，也可以直接用命令查看，实际上就是查看 /proc：Linux 系统下有 /proc 目录。它里面是当前系统中运行的进程，构建出来的是一个虚拟目录，并不是磁盘上真正的文件。self 表示这个进程自己的 ID，maps 则是这个程序自己的 memory layout，也就是 memory mapping、内存映射情况。查看后会发现它打印出类似下面的内容；也可以直接 cat 这个文件，或者用 mmap、read 把它读出来。输出中会有一行行区间，表示某段从起始地址到结束地址的内存，并说明这段内存有什么权限。例如，有一段是 read、execute、non-writable；有一段是 heap。heap 是 malloc/free、new/delete 动态创建对象的地方。还有 data 段，它属于数据，应该是可读、可写、不可执行，因此权限写作 read/write/non-executable。输出还会告诉你每段区间的范围。例如 libc.so 这样的动态库，程序一般都会链接一些动态库，动态库自然是可执行的，因此权限是 read/executable。程序运行也需要 stack，stack 的权限是 read/write/non-executable，它的 range 位于比较高的地址区域。

### ROP 攻击的引入

**39:57**

这样一来，栈上的内容已经被设置为 non-executable，攻击者再用经典的 buffer overflow 方式就没有用了。随便猜、随便破坏 return address，并让它跳回栈上的位置，也不会再有效果。虽然仍然可以跳过去，但一旦跳过去，CPU 就会发现当前 PC 指向了一个 non-executable 的地址；它不会执行，而是报一个异常。攻击者因此又想别的办法。原来那种直接在程序里插入一段 payload 的方式已经行不通，他需要找新的方法。于是出现了更聪明的 ROP 攻击，也就是 return-oriented programming，即跳回到原来的程序。这是什么意思呢？

### ROP：不写指令，只写 return address

**40:52**

在 buffer overflow 之后，攻击者不再往里面写指令了，因为他知道写指令也没有用：把想执行的指令写到栈上，栈已经被设置成不可执行了。所以他做的一件事情是，在栈上写很多个 return address，也就是把 buffer overflow 写入的内容变成很多个 return address。

这些 return address 的特点是，它们指向程序原本里面的代码片段。程序很长，其中可以找到很多个片段，称为 gadget。一个 gadget 的特征是：可能就几行指令，然后以 return 结尾，而且是程序本身的代码。程序里面肯定能找到很多很多这样的片段，每一个函数结尾至少都有这样一个片段。

于是攻击者做的事情就是：本来这些小的片段在程序里面各自有自己的意义，现在把其中的一些片段挑出来，把这些片段拼起来去执行。

### gadget 链的执行过程

**42:01**

具体做法是：先跳到片段 A 的位置，而片段 A 原来不应该从这个位置开始执行，它是函数中间的一个位置。跳到这个中间位置后执行几条指令，最后是一个 return；return 的时候会把栈上的地址 pop 出来，回到我精心设置的地址。

我设置的是回到 b，也就是挑的第二个 gadget，于是它就跳到程序原本里面的另外一个片段 b。b 又执行了一段，执行完最后又是一个 return。这个 return 回到哪里？又是去 pop 栈上的 return address，而这个栈正是我自己控制的：栈上第三个 return address 指向 c，于是跳到 c 这个地址去执行。

通过这样的方式，攻击者不用在代码里面插任何一行指令，而是利用程序本身已有的这些指令，把它们拼起来拼成一个链。他找到很多很多小碎片，这些小碎片的特征都是以 return 为结尾。通过若干个以 return 结尾的 gadget 拼起来执行，就可以实现他想让它执行的功能，比如打开一个 root 的 shell，或者把一个文件发送出来，等等。

### gadget 和地址从哪里来

**43:49**

怎么找到这几个片段？举一个最简单的例子：libc。libc 是每一个 C/C++ 程序都得去 link 的一个 library，而 libc 的代码又是开源的、公开的，每个人都知道你链接的这个所谓 third party 库。这就是供应链安全的问题：三方库一定要安全，如果三方库不安全，会受影响的程序就特别多。当然，这种开源生态的库也非常非常重要，大家都要去用、能够去复用。

这就解决了第一个问题：攻击者怎么知道这些 gadget——他可以自己去挑。第二个问题是，libc 里面他怎么知道这些 return address 在哪？这要通过一些 hybrid 的方法，借助一些别的信息做 address leaking。比如通过前面 nop sled 的方式去知道 randomization 的情况是什么样子；或者通过 data address leak 反推出来 libc 被加载到了什么位置；或者我手上有一个 arbitrary read，可以读到一个位置，去猜 libc 被加载到哪里。因为 libc 内部的偏移是确定的，所以我只要猜到它的随机化在哪里就可以了。

### 防御：影子栈、控制流完整性与 execute-only code

**45:50**

接下来就变成了怎么去防御 ROP 攻击。前面的这些方法对它来说都已经不奏效了。现代或者说比较有效的做法有几种：影子栈、控制流完整性（CFI，control flow integrity），以及 execute-only code。

execute-only code 其实是要避免刚刚同学提到的那个问题：到底怎么知道 gadget 在哪个位置。要知道 gadget 在哪个位置，前提肯定是我得能读代码。比如我有一个 arbitrary read 的 bug，就可以去读这个代码；我扫描代码的时候发现这个片段在这个位置，就可以推测出整个位置在哪；或者对于一个 unknown 的代码，比如你没有链接 libc，我也可以在你的代码空间里面去扫，扫到我想找到的 gadget。所以 execute-only code 可以避免的问题就是：这个 code 段是不可以读的，你没有办法通过 detect 一个地址是不是在我预期的范围里面、是不是我预期的一些地址，来判断你的偏移是什么样子的，或者来找我的 gadget。

所以它把这一段设成 not readable、not writable、execute only 的情况。当然并不是每一个 CPU 都支持这样的 feature：前面两个可以通过软件去实现，而 execute only 要有硬件去支撑。

### 影子栈的基本思路

**47:45**

影子栈和控制流完整性，核心的思路是：既然这些攻击本质上都是要去复写我的 return address，通过 buffer overflow 把栈上的 return address 覆盖，从而劫持我的控制流，那么一个思路就应该是去检查这个 return address 到底对不对——在 return 之前，我要检查一下我 return 的地址，是不是我真正想回去的、之前设置的那个地址。

具体做法是：原来有一个正常的栈，然后我们再设置一个影子栈，这个影子栈攻击者也不知道在哪。我们每次去做 call 指令的时候，call 指令本身会去压一个栈，然后我们还要通过另外一个方法，把这个返回地址在影子栈上再保存一下。将来在 return 的时候，return 指令会从这个栈上去 pop 这个 return address，同时我们要去检查一下 pop 出来的 return address 和这个地址是不是相等的。通过这样的方式，就可以保证这个 return address 和 return 的位置。

### 影子栈的软件与硬件实现

**49:15**

返回地址一定是我们当时设置进去的那个位置。这种影子栈的方式可以有不同的实现，既可以通过软件实现，也可以通过硬件实现。

软件实现方面，像 LLVM 或 GCC 里面都有相应选项可以打开。LLVM 编译器里把这一功能称为 shadow stack，可以启用它；这样编译器会在函数入口和返回之前插入一些读取影子栈的指令。这个思路和刚才的 canary 有点类似，实现方法也类似。除此之外，还有硬件的实现。

在 Intel CPU 上有一个叫做 CET 的技术，也就是 control flow enforcement technology，用于增强控制流完整性保护。它实现的一个特性是：一旦启用，CPU 会改变 call 和 return 的硬件行为。call 指令会同时压两个栈，return 指令也增加了一个硬件行为，去比较这两处保存的值是否相等。攻击者最多只能写普通栈上的内容；影子栈软件根本不能读写，只有特殊指令可以直接操作。通过这样的方式，可以保证比较高的安全性。这是跟 call 相关的内容。

第四部分是数组和结构体。数组和结构体是我们理解一个基本的程序在 CPU 上运行需要掌握的最后一部分汇编；这部分讲完，基础汇编部分就结束了。

我们会发一些 lab 给大家。然后看一看矩阵，还是之前那个例子：矩阵和向量相乘，\( W \) 乘以 \( x \)，再放到 \( y \) 里面。现在看它的问题：我们已经知道，对于一个局部变量，它的存储位置是栈（stack）。因此对于 main 函数，在执行时、在 main 函数的 entry point 处，它会创建当前函数的栈帧。

### 结构体的对齐与填充

**16:25**

它会占多少个字节？有同学说是 32，对，非常好。这个肯定不可能是 24 加 1。

所以它其实会有一个对齐要求，有一个约定。这个约定是：对于基础类型的对象，它的地址通常需要满足 2 的幂次方对齐。具体取决于类型的大小。比如 `char` 类型可以放在任意地址；如果是 `short`，通常做法是让地址是 2 的倍数；如果是 `int`，就是四字节对齐，起始地址应该是四字节对齐；如果是八字节的对象，起始地址就应该八对齐。

结构体也是由这些基础类型组成的，所以在结构体里面，每一个字段的地址仍然要满足这样的要求。因此结构体里会有一些空隙来满足对齐要求。对于结构体来说，字段之间要加入空隙，末尾也可能要加入填充，为了让整个结构体也满足对齐要求，对齐到结构体里面最大的对齐要求。会有这样一个限制。我们看一个 case。

### 为什么需要对齐

**19:06**

我们可以直接去问：第 119 页这个对齐限制是什么？它会告诉你对齐大概的理由。这个是在我们的 CPU，我们之前画过 CPU 和 memory 的图。CPU 在这里，CPU 会从 memory 里面读数据。它们之间的传输会有一个要求。

举个例子：假设它们每次传输的大小是八个字节。如果我们遵从这样的对齐（alignment）要求，那么读任何一个 `long` 时，只要读一次，一定可以把整个 `long` 读到。因为要求都是八字节对齐，而这边每次确实取八个字节过来。假设软件分配的时候不给它八字节对齐，就意味着我得读两次，然后拼起来。这个可不可以？也可以。

其实 x86-64 比较强，也支持这样的功能，可以不对齐，读 `long` 时也能读到。但效率会低一些。所以我们的约定就是把它对齐。还有一些情况是硬件也不支持，硬件强制要求一定要对齐，如果不对齐就会报错。

所以形成了这样的约定，会有这样的对齐要求：一部分是因为效率更高，一部分是因为硬件也这么要求。

第二个字段 `int value` 数组的偏移是多少？偏移是相对于这个起始地址。刚才说 `name` 的偏移是零，所以 `value` 的偏移是多少？八个。因为它紧接着往后排，中间不需要有 padding。为什么不需要？因为 `int` 这个数组只要对齐到四就可以了。对齐到四，而这边对齐到八个肯定是满足的，所以中间不用动。所以这边怎么放？第一个是 `value[0]`，然后 `value[1]`，`value[2]` 接着放。

### 结构体 node 的布局

**24:35**

接下来看 next 指针。next 在哪里？它相对于 base address 的偏移是多少？能不能放在这里？它还是要放到后面，所以放到偏移 24 的位置。为什么放到偏移 24？不是因为它放不下，而是因为它必须 8 对齐。因为 node * 是 8 个字节，8 个字节就要求它的起始地址对齐到 8。所以 next 指针放在这里，就意味着中间这个地方空着浪费了，浪费了 4 个字节。

最后还有一个 character，character 怎么放？它的偏移是 32，只要紧接着放就可以了，因为 character 没有任何对齐要求，任何字节都能放，因为它只有一个字节。所以它只放到了这里。这是一个字段，剩下的我们的 node 一共有多大？后面有没有要浪费的？又浪费多少？全部浪费了，因为它要对齐到 8。

一个 node，一个 struct，它要对齐到自己内部最大的对齐要求，所以它要求对齐到 8；对齐到 8 之后，还要把它 padding 到最近的 40。所以整个 struct 长成这个样子。其他内容大家自己看就 OK 了，反正也没其他难度。这是这部分的内容。

### 调用约定与参数传递

**35:49**

快到这个位置时，大家想一想，进入 `phase_1` 时要注意函数的参数是怎么传的，也就是调用约定（calling convention）。参数依次通过 RDI、RSI、RDX、RCX、R8、R9 传递。来看 `phase_1` 的第一个参数：RDI 里的值是什么？它传的是 `read_line` 的返回值，因为 `read_line` 的返回值在 RAX 中。程序先做了一件很无聊的事情：把 RAX 先存到栈上，把返回值存到栈上，再把这个返回值取回来，最后把 RAX 放到 RDI 里。所以 `phase_1` 的参数就是我们 `read_line` 读到的内容。
