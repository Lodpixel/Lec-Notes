### 从矩阵乘法到点积

**08:00**

大家应该还是听说过，模型有各种参数，要做 FFN，做各种各样的乘法，其中有一个很重要的计算就是 \(W \times X\)：在矩阵里就是一行乘以一列，得到一个内积。这样的内积需要有推理程序来完成，比如 Ollama 这样的框架，它负责组织先计算什么算子、再计算什么算子，最后把结果输出出来。假设我们现在用 CPU 进行推理，就在 CPU 上做这个点积，它做这个内积也没有问题，也能算，只是可能没有 GPU 那么快。

简单来看代码的话，它可以就是一个简单的 for 循环，完成 \(W \times X\)。假设是 \(n\) 维，那就是 \(w_i \times x_i\)，然后累加到最后的 sum 里面去，一共一个 for 循环，把每一个位置对应的都相乘一下，这就是 dot product（点积）。这样的程序对 CPU 来说，CPU 根本不认识：这个程序是写给人看的，是我们 programmer 写的，CPU 也不认识里面的 for，也不知道你这个 dot product 是什么意思。那它到底在我们的 CPU 上是怎么执行的呢？这就是我们这节课要去回答的一个问题。

那 CPU 实际上在干的事情是什么呢？CPU 实际上要做的一件事情就是去执行指令，执行硬件规定好的一些指令。那这些指令从哪来呢？指令也是从 memory 里面去获取的，叫做取指令。CPU 得从主存里面把指令 fetch 过来，fetch instruction，取到 CPU 里面去执行。但指令长成什么样呢？

### 从可执行文件到汇编指令

**10:51**

指令在 memory 里的指令是哪来的呢？最开始也是从磁盘上存的 Ollama 可执行文件里面来的。我们看一看 Ollama 这个文件，如果用十六进制去查看它，用 objdump 这样的工具去看一看，它实际存的就是这些机器码，比如 f3 0f，当然它是用二进制表示的。如果改用 hexdump，用十六进制去查看，它会告诉你是 f3 0f 10。那这个一行代表什么意思呢？

如果我们把它翻译成汇编指令——也就是人能看懂的机器码形式——这就叫汇编指令，具有一定的可读性。比如这个就叫 movss。后面也不管它干嘛。mov 是什么意思呢？mov 就是做数据搬移，这个可以猜一猜。

后面又有一条很长的机器码，占了五个字节。这也对应一条指令，前后又有后缀 ss，我们也不管它是啥。前面这个就是 mul，multiply，乘法，明明它是个乘法指令。这边也类似，这个就比较短一点了，这条指令只需要四个字节就能翻译出来。这个指令是 add，就是加法；后面还有 inc，加一；dec，减一；jump；not equal，跳转。这些后面都会讲到。它们就是汇编指令，有可读性，根据名字大概就能猜到它可能是干嘛的。

**12:54**

这些东西其实就是 Ollama 的 binary file，里面存的这些 0 和 1。它有一个 code section，这些 code section 会被加载到内存里面。当 CPU 去取址的时候，CPU 就知道：第一条指令是 mov，是做搬运；第二条指令是乘法；第三条指令是加法，它就开始在这里执行。

### 操作数：寄存器与内存

**13:22**

这些指令被依次执行，这就是 CPU 要干的事情。CPU 在做这个事情的时候，你可能发现它还要干另一件事：比如你做 mov，或者做乘法、做加法，它得有操作数。加法总得加两个东西，a 加 b；乘法你得 a 乘 b。那 a 和 b 这两个操作数分别是什么呢？

有一种你发现它是百分号开头的。比如加一这条指令，它只要一个 single 的单个操作数就可以了，但总得有操作数，对这些算术指令来说也是如此。这些以百分号开头的操作数叫做寄存器。寄存器在哪呢？寄存器在 CPU 里面。那括号是什么意思呢？括号是另外一种操作数，代表内存里面的 data。

**14:35**

于是就发现，最开始比如我们要算 \(W \times X\)，W 是 weight，x 是你的 input，W 就是模型的权重。模型的权重在哪？我们之前讲过，模型的权重在磁盘上的模型权重文件里，就是我们的 GGUF 文件里。刚才看到的是 GGUF 的 header，是那个 magic number，它后面还有很多内容；这个文件很大，里面剩下来的很多都是参数，那这些参数也得被加载到 memory 里来。

当 CPU 要去乘一个参数的时候，它得指定一个地址，指定一个内存的地址，就用括号这样的方式去找一找模型的参数在哪儿，把它 load 回来，fetch 回来，加载进 CPU 里面去执行，加载到一个寄存器里，然后进行运算。大概是这么一个逻辑。

**15:39**

CPU 在执行的过程中，其实就是在执行一条一条指令。这些指令从哪来？从 memory 里面把这些指令取出来。然后在执行指令的过程中，你做加法也好，做乘法也好，都需要有操作数，这些操作数很多也来自内存中的数据。这就是 CPU 要从内存中获取指令和数据进行计算，它大概就是一直在干这么一件事。

### 编译、入口与 main

**18:40**

那么怎么编译它？用 GCC 去编它时，会遇到报错。原因之一是当前是一台 Mac 电脑；如果大家也用 Mac，直接对 PPT 上的代码编译也编不了。这里需要修正一下：GCC 加 -c 是可以编的，因为它只是单独编译成一个中间的 .o 文件，并不是编不了。

直接使用 GCC 编不了的原因，是它会直接编译出一个可以运行的文件；而可运行文件默认要求有一个 main function。写程序时我们通常有一个 main 函数，并声称 main 是程序入口，程序先执行 main，所以必须定义 main 才能编译。

但 main 真的就是程序入口吗？其实不是。举例来说，调用 main 时可以使用它的参数，例如 argc、argv、envp；main 可以有三个参数，也可能有很多参数。这些参数很多是在 main 执行之前，由一段 init 代码、程序初始化代码帮忙 set up 运行环境。大家也可以自己了解。此外，在写程序或编译时，可以加一个 init array，它可以在程序运行 main 之前运行，做一些其他初始化。这些都是现代系统支持的功能。

因此直接编译时，系统会提示找不到 main 函数、不知道入口在哪里，所以告诉你不行。

### 默认优化与关闭优化后的汇编

**22:45**

刚才的指令中有一条 mov，有一条 integer multiply，应该是整数乘法的意思，然后还应该有一条 add。我们看看能不能找到这三条指令。发现在默认编译结果中并没有找到这三条指令，编出来的代码一共就这么长。有没有 multiply？有，在其中的一行有一个 integer multiply，但它和上面看到的不太一样。

### 编译流程

**25:04**

经过这样的过程，就可以看到同一段程序的两端：既有 C 这种高级语言的表达，最后又编译成机器码这个样子，中间还可以去读它的汇编码。那么整个编译流程是什么呢？大概有四个步骤。也就是我们在输入 GCC、直接去编译一个程序的时候，它到底经过了哪几步。

### 预处理

**25:35**

第一步叫做预处理。我们也可以通过加上控制命令，让它只做其中的一步，比如第一步是预处理，可以加 -E。预处理做什么事情呢？比如我们的文件里面经常会写 include，包含头文件。为什么在 include 的头文件里面不能去定义一个全局变量？我们学的时候应该教过大家。如果你在一个头文件里面定义了一个全局变量，这个程序是不是一定不能编译？其实，如果这个头文件只被整个程序 include 一次，它是没问题的。

因为 include 的逻辑是：预处理的时候，编译器会把你 include 的这个头文件直接塞到你的程序源码里面来，把你的文件变得更大。它还会做一些宏替换，比如我们可以 define 一些 macro，这些宏也会在预处理这一步全部被替换成真正的内容。

那么，如果一个全局变量的 definition 只在我们的文件里出现一次，其实是没问题的。但头文件通常会被多个 source file 去 include，所以如果我们在头文件里面 define 了一个全局变量，被多个 source file 引用的时候，经过预处理之后你就会发现，这个全局变量的定义出现了不止一次，而是出现 n 次——被 include 多少次就出现多少次。所以这个时候它自然就会告诉你有一个 multiple definition 的问题。这就是预处理干的事情。

### 编译与汇编

**27:34**

第二步叫做 compile（编译），你可以加 -S 去看它，它可以生成一个 .s 文件，这时生成的其实就是一个刚才看到的人能读得懂的汇编代码。然后再通过汇编器，把这样的汇编码直接生成一个 .o，这已经是一个二进制文件了，是一个 object file。这个 object file 也是 ELF 格式的，但它并不是一个 executable，不能运行。

### 链接

**28:08**

它只是一个 .o。那这个 .o 需要怎么样才能运行呢？我们刚才看到里面起码连 main 函数都没有，它自然也不能运行，最后需要做一步 link（链接）。比如说我们还有一个 main.o，里面有一个 main 函数，这个时候把它们两个链接到一块儿，最后这一步链接到一块儿，生成最终的可执行文件。也就是说，把多个 object file、多个不可执行的 object file 最后做一个链接，把它们链接到一块儿，包括给它们加上一些东西。链接器其实会干一些超出我们刚才所见的事情。

### 链接示例：main.o 与 dot.o

**28:53**

我们先看一下 main.c，它的代码也非常简单，什么都没有，就是一个 main 函数去调用了一下 dot_product。你会发现，如果我们去编译 main.c 的话，main.o 的代码也很简单，非常符合我们的预期，它里面只有一个 function，就是这个 main function。

然后我们做最后一步，把 main.o 和 dot.o 去做链接，告诉它生成的文件叫做 dot_product——叫什么名字都行，比如生成 test 也行。

按我们的理解，link 这两个文件，里面一个只有 main function，一个只有 dot_product function，只有两个 function，链接出来的程序按理说也应该只有两个 function。但实际上我们去看，会发现里面出了一大堆你不知道是什么东西的东西，完全不止这些；不过 dot_product 确实存在，跟刚才看到的完全一样，是很复杂的 move、很复杂的 multiply 和这个 add；main function 也在。

### 真正的入口：start

**30:37**

但是你会发现它会多出一些东西，这边有一些 _init、_fini，还有一些其他的 section，还有这个 start。你会发现它其实有很多东西。仔细看一下 start，看这个名字猜一猜，它好像是我们的程序的入口。你再看它，会发现它有点像：在 0x1078 这个位置，它调用了我们的 main function，所以是从它去调用到我们的 main function。

我们说 main 函数是入口，实际上并不是，在 main 之前我们还会做一段初始化。通过 readelf 应该也可以看一个可执行程序的入口。readelf -h 是看它的 header，你可以看到里面的一些信息，有个 entry point，entry point address。它说是 0x1060 这样的一个地址，是它的入口函数 entry point。如果我再回来看这个汇编文件的话，0x1060——你会发现正好是这个 start。

所以说它的入口函数其实根本不是 main，而是这个 start。那这些代码从哪来的呢？这些代码是我们的 GCC 在做这样一条 link 命令的时候，编译器帮我们加了一些代码，包括依赖的一些东西，比如动态库。

### 编译链接的四个步骤

**32:29**

链接这一步，编译器并没有显式调用动态库的代码，但它还是会帮我们加入一些前后所需的 startup function。这就是第四步 linking。所以整个过程一共四步：预处理、编译、汇编，再加链接。

平时我们其实不会分别执行这四步，通常只干一件事——一步到位。例如 `gcc main.c`，并告诉它要生成的可执行文件，它也能编译。在这个过程中，它把刚才那四步自动全部做掉了。

这就是从 C 代码到机器码的完整过程。中间会用到一些小的工具：加上 -E、-S、-c 这些命令行选项后，就对应上面那些具体的小工具，最后一步由 ld 完成链接。

### 指令集架构：同一份程序为什么能在不同 CPU 上运行

**33:53**

前面大致讲了一遍整体流程。现在我们看到的是：编译器把 C 代码经过这样一些编译步骤，最后变成了机器码，而机器码要能被 CPU 认识，这中间就必须有一个约定。

想一想，同一个编译出来的可执行程序，为什么能够在不同的 CPU 上运行？比如大家买笔记本时，如果买英特尔的 PC、英特尔的 CPU，会看到 i7、i9，现在有十一代、十三代等等，同一份程序在不同代的 CPU 上都能装、都能跑。这些 CPU 肯定不一样，不可能说十三代的 CPU 和七代的 CPU 完全一样。

它们之间实际上做了一件事，就是有一个指令集架构：CPU 虽然在不同时间生产出来，性能等各方面也都不一样，但它们都遵循同一个指令集架构，比如 x86-64，也就是 ISA。

### ISA 与微架构的分层

**35:35**

指令集架构的规范里定义了哪些内容？如果一个 CPU 声称满足 x86-64 的 ISA，那它就必须实现规范中规定的寄存器——比如刚才看到的那些以百分号开头的操作数所对应的寄存器，都得实现出来；也必须支持规定的指令，能认识编码后的加法指令、乘法指令等等。这些都是 ISA 规范定义的。

对于不同的 CPU 来说，内部设计可能完全不一样：流水线到底怎么设计，有多少个加法器，同时能执行多少个加法；核心数也不一样，比如二十四核、十六核、大小核，有 performance core，也有 energy core；频率也不一样。但这些东西对软件来说都看不见，它们属于内部的微架构（microarchitecture）实现。

中间有一层是相同的：不管你是什么 CPU，只要声称支持 x86-64 的 ISA，这些东西就必须一样。所以上面编译出来的一个可执行文件，才能在我们所有人的 PC 上运行——只要大家都是 x86-64 的 CPU 就能用。这就是通过解耦的方式实现的，ISA 类似于一层 interface，只要满足这个接口的实现都可以，具体怎么实现随便。

### 执行一次计算：从内存取数到寄存器

**37:42**

前面这段大致是一个 overview。现在我们具体到执行一次计算：就是刚才 dot product 里的一次，例如第一次循环的 \(w_0 \times x_0\) 这一段代码。它要实现的功能是什么呢？

w 是模型的权重，我们要找到模型权重 \(w_0\) 在哪里——这是个数组，数组的第零个元素在哪里？它存在内存里：一开始在文件里，现在已经搬到内存了。从 CPU 的视角来看，现在要去做这个乘法，CPU 做乘法得先找到要乘的操作数在哪里，所以要先找到 \(w_0\) 在哪；同样也要找到 input x 的 \(x_0\) 在哪里。首先要拿到这两个地址，有了内存地址之后，把数据从 memory load 到寄存器里，再执行相应的乘法运算，最后再做一次加法，做一次加和。

**39:14**

这里面有一点：CPU 做这些运算操作、执行这些指令的时候，比如执行乘法、执行加法的时候，是没有办法直接操作内存的。它做的事情都是做一次数据搬运：真正在执行时，都得把数据从内存搬运到 CPU 内部来，然后再完成运算。

类似于这样：这一行代码实际上在内存里面有两个数组存好了，然后我们要找到 \(w_0\) 在哪、\(x_0\) 在哪，把它搬运到 CPU 里面，通过 ALU 单元——把 ALU 理解成能够做加减乘除的算术运算单元就可以了。CPU 在里面可以执行加法，前提是要先找到 \(w_0\) 在哪、\(x_0\) 在哪，并且把它搬到 CPU 里面来，才能执行相应的加法指令。

所以我们要解决的第一个问题是：把数据从内存里面搬到 CPU 里面。搬到哪儿？一开始我们说过，内存是一个按字节可以索引的大数组……

### 从内存到寄存器

**40:33**

内存按字节组织，每一个字节都可以存放数据，可以理解为每个字节都有自己的“小房子”。当 CPU 要执行运算时，需要把数据从内存搬到 CPU 中；搬到的目标位置叫作寄存器。寄存器属于指令集架构（ISA）规定的内容，也是程序员或程序视角下能够看到的处理器状态的一部分。

### 通用寄存器

**41:03**

程序员可见状态中最常见的是通用寄存器（general-purpose register）。在反汇编（objdump）输出中，经常能看到以百分号开头的寄存器名，这是一种书写约定。典型寄存器包括 RAX、RBX、RCX、RDX 等，一共有 16 个通用寄存器。把数据从内存搬到 CPU 时，可以搬到其中任意一个寄存器；每个通用寄存器的位宽是 64 位，也就是 8 个字节。除通用寄存器外，还有其他寄存器。

### RIP/PC 与取指执行循环

**41:55**

其中一个特殊寄存器叫作 RIP，也叫 PC（program counter，程序计数器）。它的重要性来自 CPU 的工作方式：CPU 是一个反复取指令、执行指令的机器，可以理解成一个循环，循环体中只有两件事——取指令（fetch instruction）和执行指令（execute instruction）。那么 CPU 到哪里取指令？内存中存放了很多指令，CPU 必须知道从哪个位置开始取。这个位置由 IP/RIP 寄存器记录：它保存下一条要执行指令的地址，因此也叫程序计数器。

### rflags 与溢出

**43:05**

另一个特殊寄存器是 rflags（RFLAGS），其中包含若干标志位，用来记录算术或逻辑运算结果的一些特殊状态。

整数表示是有有限位宽的：例如 int 只有 32 位，long 也只有 64 位。两个数相加时可能出现溢出。以无符号 int 为例，两个最大的无符号 int 相加一定会溢出，而加 0 不会溢出；加 1 也会溢出。溢出后得到的结果与直观理解不同。

例如最大的无符号 int 加 1：它的 32 位全为 1，加 1 后产生进位，但结果只能保留 32 位，于是低 32 位变为全 0，结果自然是 0。这类溢出状态需要记录下来。

记录的位置就是 rflags。例如其中的 carry flag 表示进位/溢出，此外还有 zero flag 等，每个标志位都有各自含义，用来表示一次算术或逻辑运算结果的特殊状态。这些寄存器都在 CPU 内部。

### 虚拟地址空间与内存控制器

**45:03**

在 CPU 内部，除了通用寄存器，还有两个比较特殊的寄存器：RIP 和 rflags。通用寄存器用来接收从内存搬来的数据。

此外还有虚拟地址空间。可以先把 main memory（主存）理解为存放程序运行所需内容的地方：我们看到的代码、数据、全局变量，以及执行过程中的栈，都放在主存中。为什么叫虚拟地址空间，后面的课程会讲，今天先不展开。函数调用会使用栈；如果代码有问题，可能出现栈溢出、栈被破坏或写坏等情况。这些问题都与栈相关。

代码和数据都存在主存中，CPU 需要从主存取指令、取数据。取指令和取数据的方式相同：CPU 发出一个地址给内存控制器（memory controller）。读操作时，内存控制器把对应数据返回；写操作时，CPU 给出地址和数据，内存控制器把数据写入，例如更新一个全局变量。

### 寄存器的别名

**46:35**

16 个通用寄存器各自还有一些别名。每个寄存器是 64 位宽，但我们经常只需要用到 32 位，例如表示一个 int 时不需要 64 位。在 32 位机器时代，寄存器有以前的名字，例如 RAX 以前叫 EAX，RBX 以前叫 EBX。这些历史名称现在仍然保留：引用 32 位寄存器时，使用原来的名字。寄存器还有更小的名字；历史上还经历过 16 位寄存器、甚至 8 位寄存器的年代。8 位寄存器可以表示一个字节（byte），16 位寄存器可以表示一个 short，它们都有各自的名称。

### 为什么需要寄存器

**47:26**

由此引出一个问题：为什么通用寄存器只有 16 个？在讨论这个问题之前，先问另一个问题：为什么需要有寄存器？为什么不直接在内存里做计算，而要把数据搬到 CPU 里来计算？

一个直接原因是内存慢、寄存器更快，寄存器可以更快地对数据进行操作。但还要考虑后续问题：数据在 CPU 内部计算完成后，最终仍然要把结果写回内存。这样，运算的代价就不仅是 CPU 内部的计算，还包括把数据搬入和写回的开销。

### 内存搬运开销与 PIM

**48:41**

这相当于加上了两次内存搬运的开销：先把数据搬进 CPU，计算完之后再搬出去。这种设计成立的前提是内存搬运也很快；但实际上内存很慢，这里面有很多原因。

为了避免内存搬运，过去三星等厂商做过一些设计。有一段时间有一个东西非常火，现在依然很火，叫做 PIM（processor in memory）。尤其是在大模型时代，用 PIM 设计加速器也非常火。PIM 做的事情就是在内存的存储器里也加上运算单元，好处是可以做原位计算。这样，内存数据不用再搬运到计算单元里，而是直接原地计算，从而省掉内存搬运的开销。上一节课讲过浮点数要做量化。

### 量化与 GPU 内部搬运

**50:08**

为什么要做量化？节约的是什么？一个很重要的原因是在 GPU 里面。比如如果使用的是 DRAM，在 GPU 里面，像 4090，它的内存架构也使用 DDR 这类情况，数据得从 GPU 的显存搬到运算单元里计算。因此，GPU 内部带宽对现在模型的计算是非常大的限制和挑战。

从量化视角看，它节约的是 GPU 内部的搬运开销：数据变小、变短了，在相同的带宽下，搬运的数据就可以更多。这样只需用一个更轻量的量化、反量化机制，就可以用计算开销换搬运开销。所以内存搬运在计算机体系结构中是一个很大的约束和瓶颈，因此会有 PIM 这种设计。但我们默认的、最早的、经典的以及现在比较主流的计算机没有这个设计。

### DRAM 与搬运开销的均摊

**51:35**

主流计算机里的 DRAM 没有运算能力，根本算不了，所以只能把数据搬进来进行计算。

另一点是，我们并不是每次把数据计算完之后都会把它写回内存。如果每次都做一次内存读取、做一次计算，再把计算结果写回去，那也受不了，这很浪费，因为内存搬运的开销还是免不了，而且非常大。每次执行一条计算都得搬两次，这肯定受不了。实际上，很大一段代码中，一个数据进来后可以计算很多次，可以在 CPU 内部一直计算，最终计算出一个结果之后，再把它写回内存。这样我们就可以均摊掉内存搬运的开销。

### 寄存器数量的硬件约束

**52:25**

那么，如果寄存器可以设计得非常多，性能自然会更好，因为可以把大量数据都搬进来，尽量不往外面写，一次性搬完之后一直在里面算，从而减少 CPU 和内存之间的搬运。但是通用寄存器（general purpose register）只有十六个，这其实有两个硬件约束。

其中一个约束更好理解：不可能把寄存器做到一个 GB，那得做多大？CPU 一共就那么大，里面能占的空间体积只能这么大。如果做得变大，最后就会变成内存那么大，又会变慢。所以这取决于硬件设计上的限制，寄存器容量最多也只能是非常有限的数据，但肯定不止十六个。比如做三十二个寄存器，是不是也能做到一样快？很可能也是可以的。

比如在 ARM 体系结构上，就不止十六个寄存器。但十六这个数字还有一个好处，或者说它受到编码字段的限制。

### 指令编码对寄存器数量的限制

**53:48**

比如一条指令，像刚才看到的 add 指令或者 multiply 指令，要去指定后面的操作数。整条信息都编码到指令里面。不管是五个字节也好，还是四个字节也好，都要把操作数信息编码到指令里。如果操作数要表示的寄存器有一千个，那就得有十位，因为 2 的 10 次方等于 1024，可以编码一个寄存器，表示操作数是 RAX 还是 R1000 之类的寄存器。这样，编码长度自然就会变得特别长，代码体积和整个指令编码的复杂度都会膨胀。

如果是十六个寄存器，只需要用四位就可以表示一个寄存器，就能比较有效地控制指令编码的长度。

### 数据搬入 CPU 后放在寄存器

**54:53**

这样我们就回答了一个问题：内存里的数据要被搬到 CPU 里参与计算，而在 CPU 里面放到哪里的问题解决了——放到寄存器里。

## 计算机系统基础（1）｜第 4 节（10:50）

### 取指令与数据的位置

**00:00**

这一步是取指令。下一条指令存放在哪里？下一条指令的地址来自 PC（在 64 位下是 RIP）寄存器，这个寄存器里存着一个地址，这个地址就是下一条指令所在的位置，CPU 据此去取下一条指令。

现在要做的是计算 \(w_0 \times x_0\)。问题在于：从哪里去取 w，从哪里去取 x？也就是说，CPU 怎么知道数据在内存中的哪个位置。

### 数组元素在内存中的布局

**00:30**

数据在内存中的什么位置？这就要回到刚才的 w0 和 x0。看任何一个高级语言里、也就是 C 语言里对数组元素的引用，比如 W[i]，它在内存中的布局是这样的：有一个起始地址，也就是数组 w 的基地址（base address），另外有一个下标，下标表示它对应第几项。

**01:09**

数组本身在高级语言里带有类型信息，它告诉我们是 int 类型。每个 int 占用 4 个字节，所以在内存布局上，从基地址开始，第一个元素占最前面的 4 个字节，第二个元素占接下来的 4 个字节，第三个元素再占 4 个字节，依次排布。

因此每个元素自身的起始地址算法很简单：基地址加上下标乘以 4。例如 w 加 0 就是基地址加 0，w 加 1 就是基地址加 4，w 加 3 就是 3 乘以 4，也就是基地址加 12。

用这样的方式就可以算出并索引到数组元素的地址。当然，寻址的方式有很多种。

### 指令中操作数的编码

**02:18**

一条指令要去操作内存中的某个数据时，必须先指明位置。在指令的编码里，要用一种 encoding 的方式来表示操作数在哪里，这也是一种信息表示，只不过现在表示的是这条指令要做什么、它的操作数在哪里。

之前已经知道，可以用 4 个比特表示一个寄存器操作数，它属于非内存操作数；也可以表示一个常量，比如要让一个寄存器加 5，这个 5 可以直接作为立即数编码在 instruction 里面。这些都是非内存操作数。

一条 add 指令既可以操作两个寄存器，也可以操作一个寄存器和一个立即数，还可以操作一个寄存器和一个内存中的值。

**03:32**

那么内存中的操作数怎么寻址？这里会有几种表示方式。

第一种对应 C 语言里取指针所指的内容，一般写成把寄存器用括号括起来，例如 (RAX)。它就是间接寻址模式：把 RAX 当作一个地址，去取这个地址对应的内存中的值。

### 比例变址寻址

**04:10**

再看更复杂的形式。比如先不看前面的 displacement，只看后面的 (RB, RI, s) 这个三元组，它对应刚才 C 代码里的 W[i]。

RBX 里存的是什么呢？存的是基地址，也就是 w 的 base address；RI 就是这个数组下标 i；最后是一个 scaling，表示要放缩多少，由于元素是 int，这个 s 其实就应该是 4。前面还可以加一个偏置量，有时候需要，也可以是 0，也就是空着。

它最终表达的地址是 RB 加上 RI 乘以 s，再加上前面的偏置量，这就对应了刚才那种寻址方式。

**05:32**

还有一种是基地址加偏移量的形式。比如在 C 或 C++ 代码里访问一个成员变量，写 p 箭头 field：真正表达它的地址时，寄存器里存的就是这个指针的值，也就是 base address，前面再加上这个 field 的偏移量。因为 struct 在定义的时候，偏移量就已经确定了——第几个成员在哪个位置是确定的，所以可以用这样一个方式去寻址。

所以，一条指令的操作数可以是三种类型：立即数、寄存器，以及内存操作数。既然是内存操作数，我们就得知道它在哪，也就需要通过刚才这些方式去编码它的内存地址。

### 地址生成单元与 LEA

**06:46**

地址的计算会有一个专门的单元，叫做 AGU，也就是 address generation unit（地址生成单元），专门用来生成地址。因为地址无论怎么算，最复杂的形式就是一次乘加操作。

所以最后是有一块独立电路，可以在一个周期里完成一次乘法再加上几个数相加；也可以通过一条专门的指令来完成这件事，算出一个地址。

**07:35**

这条指令叫 LEA。它的语法大致就是给出一条汇编指令 LEA，把这样一个地址算出来，写到 destination 指定的寄存器里面去。这个过程单周期就能完成，而且不会进行任何真正的内存访问，只是单纯把地址算出来。下面给一个例子。

### LEA 地址计算示例

**08:03**

例如指令 `lea 0x8(%rdx,%rcx,4), %rax`。已知 `%rcx` 的值为 3，`%rdx` 的值为 `0x2000`。执行这条 LEA 指令后，`%rax` 的值是多少？

计算时先做比例变址：\(3 \times 4 = 12\)，再加上位移 8，得到十进制 \(12 + 8 = 20\)。十进制 20 写成十六进制是 `0x14`。再加上 `0x2000`，结果是 `0x2014`。因此这条指令执行完后，`%rax` 的值是 `0x2014`。

考试时千万不要把十进制和十六进制搞混；建议写出计算过程，至少保留过程。

### 从地址计算到数据搬运

**09:32**

LEA 的这种寻址方式可以用一个非常简单的电路在单个周期内算完，而且它只计算地址，不会真正访问内存。

到这里，数据从内存搬到 CPU 的哪个地方已经解决了：搬到寄存器中；从内存的哪个位置开始搬也已经解决了：指令中需要对内存操作数进行编码，也就是要表示内存地址。

现在只缺最后一步：真正把数据搬过来。PPT 里还需要补一张图，我给大家画一下。

### add 指令的操作数：内存与寄存器

**10:29**

例如有一条 `add` 指令。它有两个操作数：第一个操作数是内存操作数，写成 `(%rax)` 这样的形式，表示要取内存中的数据；第二个操作数是一个寄存器。

对第一个操作数，需要根据给出的地址去内存中取出数据。假设现在给出 `%rax` 的值是 `0x1000`。我们把内存看成一个从 0 地址开始的大数组，每个字节都可以索引，`0x1000` 就对应其中一个位置。

问题是：从内存里取多少个字节回来？有同学回答 8 个字节。为什么是 8 个字节？

### 取数宽度由指令编码决定

**12:32**

如果改成另一个例子，第二个操作数只占 4 个字节，那么到底取 4 个字节还是 8 个字节？这时是取 4 个字节。

原因在于指令的 encoding（指令编码）。指令里会有 `addq` 或 `addl` 这样的后缀：`q` 表示做 8 个字节的加法，`l` 表示做 4 个字节的加法。这是具体编码层面的区分；有时汇编助记符中不显示这个后缀。

真正进行指令编码时，会根据后面寄存器的宽度决定取 4 个字节还是 8 个字节。例如刚才使用的是 `%rbx`，它确实会取 8 个字节回来；如果写成 `%ebx`，就会根据 32 位寄存器宽度取 4 个字节。

因此第一个问题是：我们给出的只是一个地址，但到底取多长的数据——取 4 个字节、2 个字节、1 个字节还是 8 个字节——是由指令本身编码时决定的，或者说由编码中寄存器的位宽决定。

### 寄存器操作数的编码位数

**14:20**

第二个问题是：表示第二个操作数中的寄存器，需要用多少位？答案是 4 位。因为一共只有 16 个通用寄存器（GP register），4 位就足够表示 16 种编号。

### 从人类可读指令到机器编码

**14:33**

整条指令是人能读得懂的，但真正机器读取时，指令会变成一堆 0 和 1。具体长什么样我现在是随手写的，不一定正确，但大致就是一堆二进制位。

一条指令可能占 3 个字节或 4 个字节，也不一定固定，一般在 3 个字节左右。机器拿到的是一个 bit vector，也就是一串 bit，它必须能够解释这串 bit。

解释的方式大概是先看前面的部分，比如用前面的位表示 OP code，表示这是一条 `add`。很多时候我们并不需要知道 `add` 一定被编码成某个固定的 0/1 串，但需要知道什么是编码，以及它可以怎么表示。

### 自定义一套 ICS ISA 的编码

**15:34**

例如可以假设我们新规定一套 ICS ISA，自己定义编码规则：用前面一段 0/1 表示 OP code，表示这是一条加法指令；后面再表示有两个操作数。世界上并没有这样的 CPU，但我们可以回头自己写一个。

两个操作数中，一个用一段编码表示它是内存操作数（memory），另一个用一段编码表示它是寄存器（register）。

### 操作数的编码与指令解码

**16:11**

寄存器只需要四位就够了，而内存这一段可能会相对比较长，因为内存的编码可以很复杂，可以有各种不同的编码方式。但无论编码写得多复杂，最后都映射成一堆 0 和 1。CPU 在执行指令的时候，先看到前面的 OP，就知道后面一共有多长，然后知道后面每一部分应该怎样解释。

前面已经说过，指令大概就是这个样子：可以有一个内存操作数，有自己的一种编码；也可以是寄存器操作数，有自己的编码。

### load/store 与 x86 的 mov 指令

**17:09**

接下来才是真正要去搬数据。在 x86 里面其实只有一条指令负责搬运，但内存的搬运有两个语义：从内存到 CPU 叫 load，也就是加载；从 CPU 写回内存叫 store。在 ARM 这边，在 RISC 指令集下，load 和 store 是两条指令。而在 CISC 指令集下，比如 x86 这样的复杂指令集，只用一条指令就可以表示一个复杂语义，也就是 mov。mov 的语义还不只是搬：它不仅能从内存里搬、搬到内存里去，还能在两个寄存器之间搬。这就是所谓的 CISC 指令集——一条指令可以比较复杂，可以表示的语义比较多。

mov 指令有两个操作数，这是硬件规定的：第一个叫 source，第二个叫 destination；它做的事情就是把 source 搬到 destination 里。

**18:27**

每个操作数可以是以下三类之一，和刚才说的操作数类似。第一类是 immediate，也就是立即数，比如想把 EAX 写成 5，就 mov 一个立即数 5 到 EAX 这个寄存器里。另外还可以是寄存器，也可以是一个内存操作数。比如这样一个例子：源操作数是一个内存地址，也就是内存操作数，目的 destination 是一个寄存器。

再问一个问题：这个东西搬多少个字节？四个字节。第一个可以通过后缀 l 确定，l 就是四个字节；后面这个 EAX 也是四个字节。RAX 是 64 位，EAX 是 32 位，是它的一半。这条指令干的事情就是把内存里的数加载到一个寄存器里，其实就是刚才说的 memory load：我们已经知道这个内存数据的地址，然后把它的内容取出来。比如要去读某个内存地址的时候，就可以用这么一条指令搞定。

**19:58**

它具体执行的过程，在之前的一页 PPT 里也有：CPU 真正执行这条指令的时候，把这个地址、把 RSI 的值交给内存控制器，然后内存控制器把数据取出来还给 CPU，CPU 再把这个 32 位数据写到 RAX 里面。中间还有一个操作：并没有一个单独的寄存器叫 EAX，它其实就是一个 64 位的大寄存器 RAX，EAX 无非是表示它的低 32 位。当我们写它的低 32 位的时候，高 32 位会被自动清零，这是 CPU 自己去做的。

### mov 指令的约束

**20:43**

mov 指令有一些约束。刚才说它的操作数可以是立即数、寄存器和内存，但有些写法是非法的。如果两个操作数都是内存，是不允许的，不能直接访问两个内存位置。立即数也不能作为目的操作数，这也很好理解：把立即数移动到某个位置里面，这算怎么回事，显然不行。

所以内存到内存的数据搬运必须拆开：先把内存的内容搬到一个寄存器，再从寄存器搬到另外一个内存，拆成两条指令来做。

### 写寄存器时的清零规则及其来源

**21:34**

还有一个比较微妙的地方。刚才说写 32 位寄存器的时候，CPU 会自动把高 32 位清零，这看起来挺自然、挺合理。假设原来的 RAX 是 64 位全 1，然后我们做一件事：mov 1 到 EAX，之后整个 RAX 的值还是 1，因为高 32 位都被清零了，最后就是前面全是 0，最后一位是 1，所以它还是 1，很合理。这类似于写 int a = 1，假设 a 现在被分配到寄存器里，我们最后读它整个 64 位寄存器，还是希望它是一；或者说把 int 扩展成 64 位的时候，确实希望它的值不变。

但另外，如果我们去写它的第八位或者第十六位，就比较奇怪，前面的内容不会被清掉。比如原来 EAX 还是全 1，如果我们只写它的 AL，AL 应该是它的第八位，写完之后只有最低的八位变成 1，前面的位还全是 1，就比较奇葩。这是为什么呢？大家可以回去自己搜一下。

我昨天问了一下，大概的理由是所谓“新人新办法，老人老办法”。因为从 32 位到 64 位的时候，其实是谁做得比较好呢？其实是 AMD 先做得比较好。一开始 CPU 肯定是英特尔做得比较牛，英特尔的体量比 AMD 大很多，但 AMD 后来凭什么能有技术领先？就是它先把 64 位的 CPU 做出来，所以在 64 位上走得比英特尔更早、更好。因此它在设计 64 位的时候就设计了这么一条规则：写低 32 位的时候，高位就清零了。而从 8 位到 16 位、再到 32 位演进过来的那些规则，就一直保留在这里。所以这实际上是两家厂商留下的不同规则，但最后大家都统一到 x86-64，这条规则就一直保留在这里。

### C 语义与编译器生成的扩展指令

**35:50**

所以这里会有一些算术指令。前面还有一个扩展操作。比如 int 和 long 比较时，要比较长度，就需要做扩展。之前说过：位宽小于 int 的，先提升到 int，也就是 32 位；然后看谁更长，再看有符号、无符号怎样转换。这些 C 语义 CPU 并不知道。CPU 不知道你是什么整数类型、是不是无符号，也不知道你要先提升到 32 位、再变到更宽的类型。CPU 只认指令：给它什么指令，它就执行什么。因此，C 中的这些语义由编译器在编译时生成相应指令。比如要让 short 和 long 比较，最后要把 short 转成 long，这件事就要编译器生成相应的指令，也就是零扩展或符号扩展、位宽扩展指令。

第一个是 zero extension，零扩展，通常适用于无符号数。要把无符号数变宽，可以通过 movz 系列指令，例如 byte to long、word to long，其中的 z 表示 zero。符号扩展则是 signed byte to long、signed word to long、long to quad 等。这里要特别注意：long 是 32 位，quad 是 64 位。这些指令都是通过编译器在编译时选择出来的，用来表示高层 C 的语义。CPU 看到指令后并不关心这些语义，只是老老实实执行；它不需要理解你为什么要做扩展，也不需要知道你原来是有符号数和有符号数比较。你生成什么指令，它就执行什么指令。

### CLTQ 指令

**38:34**

还有一个比较特殊的指令，我们经常会看到，叫 CLTQ，全称是 convert long to quad。它没有显式操作数，不看到汇编的话就只长成这个样子。它的语义是把 EAX 符号扩展到 64 位的 RAX，效果和 signed extension long to quad 类似，也就是 l to q，从 32 位扩展到 64 位。为什么会有这样一个特殊指令？因为这个指令长度更短，占用的空间更少；专门的实现也可以让它更快，性能更好。这也是 CISC 指令集的一些特殊特点。这里的零扩展和符号扩展的区别，和我们之前讲的比较类似。

### 零扩展与符号扩展的区别及后续整数运算

**39:45**

如果从一个字节扩展到四个字节，零扩展会在前面都填零，因为它不管最高位是什么。如果是符号扩展，最高位是 1，则前面扩展出来的位都是 1；最高位是 0，仍然补零。这样补码数值不会改变，依然不会变。后面还剩一些整数运算，比如 \(w_0 \times x_0\)，其实要做的事情就是一条整数乘法指令加上一条 add 指令。
