### 可执行文件中的代码与数据

**14:17**

因为断电之后程序还得在。总不能关机之后游戏就没了、APP 就没了，这肯定受不了。所以这个文件存在 disk 上，存在 SSD 上，这些非易失性的存储介质上。真正要运行一个 ELF 文件、运行一个程序时，是由操作系统——Android、Windows、macOS、鸿蒙等——把它从 SSD、从 disk 加载到内存里。只有发生了这个加载，才会出现所谓的内存地址。

**15:04**

### 回顾传送与扩展指令

**18:03**

我们讲到了传送，也讲到了扩展：怎样从一个 byte 做 zero extension 到比如说一个 long，或者扩展到双字，这样的一个情况。

当时有两条指令：一条是零扩展，叫 zero extension，从 byte 到 long；另一条是有符号扩展，long to quad（long to q），也就是从三十二位扩展到六十四位，而前一条是从一个字节、八位扩展到三十二位。它们的区别无非是：一条在前面全部填零，另一条按照最高位去复制。你会发现，在二补码下复制完之后它的数值是没有变的。

### 有符号与无符号的解释由编译器负责

**19:01**

我们看一个具体的 case。之前说过，CPU 就是你给它一个 RIP，它根据自己当前记录的 PC 值去取一条指令执行。它其实根本不知道上层这个到底是有符号数、是 int，还是 unsigned int，它根本不知道。

那么，对有符号数和无符号数的解释是谁干的呢？这件事自然只有一个人有这个角色可以干，就是编译器。我们在写代码的时候会写这是一个 signed char、那是一个 unsigned char；但是最后编译出来的指令，你到底是做 zero extension 还是做 sign extension，这件事是编译器选的。编译器选了什么指令，CPU 就老老实实执行什么指令。CPU 根本不会知道你用什么高级语言，也不知道你有什么语义信息，它只是去执行指令。所以，对这些数的类型作出解释、然后选择相应的指令去生成代码，这件事是编译器干的。

### 有符号数与无符号数比较的例子

**20:24**

我们看一看这个例子。代码非常简单，就是一个函数，它传了两个参数，一个参数是有符号的 char a，另一个参数是无符号的 char b，它要返回的结果是一个 true 或 false 的值。它虽然写的是 int，其实返回的就是一个布尔值；a == b 是一个判等的 condition。

大家记得我们之前说过的一个规则：如果两个参与比较的数的位宽小于 int，我们要做的第一件事是把它 extend 到 int，也就是扩展到三十二位的 int。这件事其实是 C 语言约定的规则，编译器会遵守这个规则，它来干这件事。它在干的时候，又会去看你当前是从一个 signed、也就是有符号数，还是无符号数去做扩展。

所以你会发现前两条指令就用了我们刚才说的扩展传送指令：一个是从 signed 的 byte 到 long，也就是从一个 char 到一个 int，这是它对 a 干的事情；另外一个是 zero extension，从 byte 到 long，这是它对 b 干的事情。EDI 和 ESI 是三十二位的寄存器，而 DIL、SIL 是它们这两个八位寄存器的别名。

它干的事情是：一开始 a 和 b 这两个参数，一个存在 DIL、一个存在 SIL 这两个寄存器里面；然后它做了一个 compare。做完 compare 之后，后面它会去做一个 set e。compare 的意思就是比较一下，其实就把 ESI 减 EDI；set e 的意思是说，如果减出来的结果等于零，也就是两个相等（equal），那这样的话就把 AL 设置成一，说明 a 等于 b。然后再去做一个 byte to long，因为 AL 是一个字节，要 extension 到这个三十二位，最后返回值就返回 EAX。后面我们会讲一下函数的一些约定，也就是我们的参数会放到约定好的一些寄存器，我们的返回值 return value 也会放到约定好的寄存器。

这就是对于这种符号扩展指令的选择。那如果我们假设这两个参数都是 0xF0，a 和 b 都是 0xF0，其实这里 return 出来的结果是不相等的，返回的应该是零，因为它们两个 extend 之后的结果也是不相等的。

### 整数乘法指令

**23:52**

接下来我们继续讲一些 CPU 会去执行的指令。下面这个是整数的乘法。整数乘法前面有一个 i，表示它是整数乘法，后面是 multiply；后面的 l 是指它操作的是三十二位。这就是这样一个乘法指令的名字。它的操作数也是两个，比较常见的是两个，一个是 s，一个是 d；这里 d 指的是 source，也就是 source register。

### 乘法指令

**24:38**

这里补充乘法指令。`s` 指 source，`d` 是 destination，指令把 d 乘以 s 的结果写回 d。其中 s 可以是寄存器、内存操作数或立即数；destination 只能是寄存器，因为最后结果要写到 d 里面去。乘法只保留乘积的低 32 位。两个 32 位数相乘，结果很可能超过 32 位，这时只保留低 32 位；如果两个数本身比较小，乘积不超过 32 位，结果就没有问题；一旦超过 32 位，数据会被截断，结果和预期不一致。有符号乘法和无符号乘法在低 32 位上是一样的，所以 CPU 不区分 int 和 unsigned 的乘法，这一点和加法类似。

### 单操作数乘法与有符号/无符号

**25:41**

加法在 CPU 中也不会区分 signed 和 unsigned。前面有些指令则需要区分，例如扩展传送指令会区分零扩展和符号扩展。乘法还有一些其他编码，这里不特别展开。它有一个单操作数格式，稍微特殊：只写一个 source 操作数，destination 是隐含的。这个格式保留完整的 64 位乘积。x86 中它对应单操作数乘法指令；在这样一条指令里，会默认用掉 EDX 和 EAX 这两个没有显式写出的寄存器：假设乘法的操作数已经放在 EAX 中，再乘上这个 source 操作数，乘好的结果可能是 64 位，会存到 EDX 和 EAX 中，EAX 存低 32 位，EDX 存高 32 位。对于完整 64 位乘积，有符号和无符号的结果在高位上不一样，所以这里会区分有符号和无符号。以上大致就是乘法指令，大家认识它即可。

### 加法指令

**27:24**

类似地看加法指令。`addl` 中的后缀 `l` 表示操作 32 位数，也就是 32 位加法；`addq` 表示 64 位加法。加法同样是把 d 加 s 的结果写回 d。s 可以是立即数、寄存器或内存操作数；d 可以是寄存器，也可以是内存，但两者不能同时是内存，这和 mov 一样，不能直接把一个内存操作数移动到另一个内存操作数。32 位二进制加法的结果写回 32 位目标；两个 32 位数相加也可能超过 32 位，也就是溢出，但这时同样只截断保留低 32 位。有符号和无符号相加得到的低 32 位一样，所以加法也不区分有符号和无符号。常见形式包括两个寄存器相加，结果写回寄存器；寄存器加立即数再写回寄存器，相当于把该寄存器的值增加一个立即数；以及把寄存器的值加回到内存中。

从汇编的视角来看，汇编是面向人阅读的，所以一般根据名字就能大致知道含义和语义，不需要把每条指令的前后操作数都记得非常清楚，先有一个印象即可。LEAQ 还记得是做什么的吗？它是一条计算地址的指令，不真正访存，通常用于计算地址。例如这里把 s 的地址算出来，放到 destination 寄存器中。所有 `l` 后缀都表示操作 32 位数，`q` 后缀表示操作 64 位数。`inc`、`dec`、`neg`、`not` 这些顾名思义，分别表示增加、减少、取负、取反，都是一元运算。

### 算术、按位和移位指令

**29:41**

加减乘除对应 `add`、`sub`、`mul`、`div` 这类指令。还有 `and`、`or`、`xor` 这几条按位与、按位或、按位异或指令；注意这里说的是按位运算，不是逻辑运算。然后是左移、右移：算术左移、算术右移和逻辑右移，包括 `shift right`、`shift left` 这类操作。前面提到的后缀 `w`、`l`、`q` 分别对应 16 位、32 位和 64 位版本。编译器看到一段 C 代码后，会根据 C 或 C++ 约定的语法规则，从 CPU 可以识别的指令中挑出合适的指令，编译出程序。

### 编译器选择与寄存器清零

**30:58**

编译出的 ELF 格式可执行文件最后可以被加载到内存中，由 CPU 执行。在选择 CPU 指令时，同一段 C 代码可能有很多种甚至无穷多种汇编指令组合，都能表达同一段 C 代码的含义。编译器肯定有一些原则和指导方针：例如希望代码越精简越好，如果一万行指令表示一段 C 程序，而十条指令就能表达同一段 C 程序，那肯定选择十条的，这样体积更小、执行效率也更高；另一方面，如果两种方式效果相同，但其中一种执行效率更高、性能更好，也会优先生成高性能版本。举个例子：对一个寄存器清零，如果后面去看 objdump 文件、看它的汇编，会发现经常有 xor 指令，让一个寄存器和自己异或，从而把寄存器清零，因为任何一个数异或自己结果都是 0。

### 用异或指令清零

**32:39**

这件事在 C 代码里很常见：经常要对一个值做初始化，把它的初值赋成 0，所以这条指令非常常用。更直观的做法是把立即数 0 用 mov 指令搬到一个寄存器里，这本身也是轻量操作，但为什么不这么做？因为 CPU 提供了专门用于这种优化的特殊指令；用异或实现清零，性能比 mov 0 更好。一方面，异或指令的编码长度更短：XOR 只要两个字节，而 mov 指令要五个字节。另一方面，硬件本身还有一些优化：当 CPU 发现你对两个相同的寄存器做异或，也就是两个操作数相同时，它会做特殊处理，甚至不花时间、不占用计算资源，直接完成结果，不必真正执行一次异或，因为它知道结果一定是 0。

### 用 lea 和移位实现乘法

**33:53**

刚才说的是选取更优的指令实现相同功能；另一个例子是用更多条指令实现相同功能，比如实现一个乘法。例如计算 \(x \times 12\) 时，如果你用编译器并加上优化选项，比如 -O2 或 -O3，让编译器优化生成的代码，你会发现里面找不到乘法指令，这看起来很奇怪：明明写的是乘法，为什么没有乘法指令？因为乘法和除法在 CPU 里执行相对较慢，相对加法和移位来说更慢。所以编译器在能用别的指令达到同样效果时，会选择生成更高效的代码，比如用 lea 指令和移位指令来实现乘法。

先看 \(x \times 5\)。编译器用了一条 lea 指令。之前说过，lea 通常用来计算地址；它的语义是把前面的地址计算好，放到后面的寄存器里。这里相当于计算 \(RAX \times 4 + RAX\)，把结果写到 EAX。老师指出这里目标寄存器最好写成 EAX，按 64 位 lea 写进去可能会截断；这里大家统一看成 EAX 即可。假设 EAX 里存的是 x，那么结果就是 \(x \times 4 + x\)，实现了 \(x \times 5\)。

再看 \(x \times 12\)。它先算 \(x \times 2\)，加上 x 得到 \(3x\)，再把 \(3x\) 左移两位，也就是乘以 4，所以 \(3x \times 4 = 12x\)。之所以这样处理，是因为 lea 指令执行起来很快，能达到相同的效果；虽然指令编码很长，但它只要一个 CPU 周期，而乘法可能要三个周期。我们刚才介绍了一大堆指令。

### 指令编码与 CISC 变长指令

**37:02**

有哪些呢？有一元操作指令，比如 not，也就是按位取反；有二元的加减乘除；还有位运算。上节课有同学问：CPU 怎么认识这些指令？这些指令最后都放到内存里，全都是 010101……CPU 怎么知道我一条指令有多长？怎么知道我这条指令是 mov，不是 add，也不是 not？CPU 怎么知道这件事？

所以，指令有一个 encoding。一般来说，CPU 执行的指令由操作码（OP code）和操作数（operand）两部分组成；操作数部分又可以有多个，比如两个操作数。看一些简单例子：在 CISC 指令下，x86 就是一个 CISC 指令集，CISC 的 C 代表 complex，也就是复杂。复杂一点的第一个特征就是指令是变长的，一条指令的长度不确定。

### 变长指令下 PC 如何前进

**38:33**

比如这里有一条 ret 指令，待会儿我们会知道它是干什么的，现在先不管，它占一个字节。后面这条 mov 指令占了五个字节，再后面还有一条异或指令，就是刚才说的清零，把这个寄存器自己清零，它只要占两个字节。可以看到，每条指令的长度都不一样。

那我问大家：CPU 执行完一条指令之后，要把 PC 指向下一条指令，要知道下一条指令在哪里，去取下一条指令执行。对于这种长度不一样的情况，CPU 怎么知道下一条指令在哪？怎么知道当前是把 PC 加一、加四、加五，甚至加六？第三排这位男生回答：确定。

### 用操作码确定指令长度

**39:49**

很好，这就是一种方法。如果让你去设计 CPU，也可以这样设计：假设我们规定每条指令的第一个字节代表这条指令是什么，代表这条指令的 OP code。如果这一点确定，通过第一个字节就可以知道这条指令是什么。CPU 能支持执行的合法指令数是有限的。

### 指令编码与 PC 更新

**40:42**

大家之前接触的是 x86-64。不同厂商设计的 CPU 可以不一样，但在同一 ISA 下，可执行的指令数和指令类别是一样的。因此可以约定，例如一个 x86-64 CPU 一共可以执行 500 条指令，每条指令有多长其实都是确定的。只要通过 opcode 就可以知道当前这条指令是多长；加上当前指令的长度，就可以知道下一条指令在哪里。

这就是 CPU 更新 PC 的方式：它一直处在一个大的循环中，根据当前 PC 去取指令、执行指令，同时在取指令时计算出下一条 PC 在哪里。

**41:35**

### 定长指令与 RISC

**42:33**

### 反编译的常见场景

**00:45**

什么时候会做反编译？通常是在一些不太好的事情中，比如假设你是一个黑客。

当然，如果是在攻击敌人，那做的就是好的事——打败敌人。这时候会有一些其他信息。比如你现在可以访问一个网站，网站上有个程序，通常你只知道怎么调用它，它会告诉你接口，但你并不知道它内部怎么实现。这时黑客可能想知道你的源代码长什么样。

又比如游戏被破解后，可以在里面修改、作弊。再比如别人写的一个 APP——大家可能知道外包应用程序开发，十年前开发一个安卓应用大概几万块钱。这是一个公司自己的资产，它写的程序要发布到安卓应用商店、Google Store，让大家去下载。

为了防止被别人复刻，一个做法是在里面做二进制混淆。为什么要做二进制混淆？因为给别人一个 APK 或者一个二进制程序，别人一定能知道你的字节码，或者如果是 ELF 文件，能知道你的汇编代码长什么样。二进制混淆要做的，就是增大从汇编代码到 C 代码、再到高级源代码的难度，从而在一定程度上保护知识产权和数字资产，这是一种技术。

现在要说的，是我们怎样做反编译。或者说，从一个简单视角来看，在有一些提示和信息之后，怎么知道一段汇编代码对应的 C 代码是什么。

### compare 指令与标志寄存器

**17:54**

compare 指令计算的是 EAX 减去 EDX 这样的值。它并不把这个结果真正写回到某个地方，而是把结果产生的特征记录下来，例如减出来正好是零。这些状态记录在标志位里面，而标志位本身是 CPU 里的一个寄存器。之前讲过，CPU 里的通用寄存器有十六个，64 位下比如 RAX、RBX、RDX；程序计数器 RIP 比较特殊；另一个比较特殊的就是 RFLAGS，它用来记录算术指令或比较指令的结果。JL 这类指令会读取标志位来判断“小于”是否成立：如果减出来是负数，就说明小于成立。RFLAGS 中有一位叫 sign flag，结果为负数时它被置为 1；后面的 JL 看到 sign flag 为 1，就知道小于成立，于是执行跳转。

**19:44**

此外还有 zero flag，结果为零时置位；carry flag 对应进位，也就是无符号数相加发生溢出；overflow flag 对应补码情况下的溢出，比如两个正数相加却加出一个负数。大致就是这四位在记录这些信息。下面用一个简单的例子看一下 carry flag 和 overflow flag 的区别。

### CF 与 OF 的区别：0xFF + 0x01

**20:26**

以两个 8 位二进制数相加为例。对 CPU 来说，它并不知道你把它当作无符号数还是有符号数，所以两种情况下它都会帮你把相应的标志位设置好，CF 和 OF 都会相应地被设上。假设做的是 0xFF + 0x01：如果解释成两个无符号数相减相加，255 加 1 得到 256，已经超出了 8 位无符号数能表示的范围（0 到 255），这时 carry flag 即 CF 会被置为 1；如果解释成有符号数，那就是 −1 加 1 等于 0，可以正常表示，没有任何问题，没有溢出，所以 overflow flag 即 OF 为 0。这就是加完之后这两个 flag 分别被设置成什么值。

**21:38**

当然，这些标志位具体如何更新，不必记得那么清楚，只需知道 CPU 会干这些事、会把这些状态记下来。理解代码时，往往可以顾名思义地猜一猜，不用记得特别清楚，这里只是带大家走马观花地看一遍。再说一下 compare 指令：一般来说，在一条条件跳转之前都会执行 compare，它计算的是 s1 减 s2，计算结果本身不会写到任何地方，而且两个操作数也不会被改变，它只是记录并更新这几个标志位。

### test 指令

**22:21**

另一个指令叫 test，它做的不是减法，而是按位与：把 s1 和 s2 按位与之后，再根据这个结果去设置标志位。它常见的用法是让一个寄存器与自己做 test，因为任何数 n 与自己按位与还是 n，这样就可以通过 zero flag 判断当前的数是不是零；也可以结合 sign flag 判断它是不是小于零。把一个寄存器传进去 test 一下，通常就是干这件事。

### 比较条件与直接跳转

**23:27**

### 直接跳转与间接跳转

**24:37**

直接跳转之所以是直接跳转，是因为跳转的位置是确定的：在生成代码的时候其实就已经确定了，label 在哪里我们都知道，是确定的。

还有一种特殊的跳转指令，或者说一种特殊的跳转编码，是跳到一个由寄存器指定的位置，这叫做间接跳转。

**24:56**

间接跳转的好处是，它可以在动态的时候决定要跳到哪：只要动态地修改这个寄存器的值，就可以决定跳转的目标。`jump *IX` 和 `jump *(IX)` 这两种写法难道不一样吗？我印象里是一样的，你可以 confirm 一下，也可以问一下大模型。不论它们是不是一样，反正它就是跳到一个可以动态决定的值。

### 为什么需要间接跳转：switch 的编译

**25:39**

为什么需要间接跳转？我们看这样一个例子。这是一段 switch 代码，其实本身没什么意义，但 switch 是我们写代码时经常会出现的一种结构，也就是 switch table 这样的情形。

你会发现，这样一段 C 代码如果要去编译成汇编，其实挺难编译的。因为 switch 在 C 语言中的语义，是由参数 OP 决定去哪个 case、去哪个分支；而在编译的时候，编译器当然不知道 OP 的值，也就是不知道它是几，因此不知道要跳到哪。

如果我们只有 direct jump，只能跳到一个固定的 label，那这个东西就非常复杂：我们得把 OP 和每一个 case 的 value 做一次 compare，比较之后再用 `je`，如果相等就跳。这样你可能要比较很多次，最差情况下得把每一个 case 都比较一遍，才能跳到目标的地方去。

### 跳转表的设计

**27:10**

这样代码显然不够高效。所以它做了一件事情：生成了一个叫做跳转表的东西，这个设计其实还挺有意思。

它做的事情是，把六段代码排成一张表，然后按照 OP 去取第 OP 个地址。这样说比较抽象，我们直接看它的实际情况。

**27:34**

我们把这段程序编译之后，用 objdump 去看，会发现有一个比较奇怪的东西，叫做 `.quad`，后面跟着 l9、l8、l3 之类的 label。这是我们的汇编文件，它实际对应到二进制文件中的什么呢？这里是一个 value，是一个 8 个字节的 value，是一个 64 位的 value，`.quad` 就是这个意思——q 表示 64 位。这里就是若干个 value，一共六个 value。

这六个 64 位的值、这八个字节是什么呢？其实是地址。是谁的地址呢？

**28:23**

这些地址就是分别对应我们这六个 case 的起始地址。每个 case 编译出来应该有一段代码，有一小段汇编、一小段二进制，而这段二级制开头会有一行指令，它的第一条指令的地址就是存到这张表里的这个地址。

所以如果我们要跳到任何一个 label，只需要把这个 label 对应的值取出来，跳进去，就跳到对应的 case 了。它做的事情就是这样。

**29:01**

这段汇编是跳转到 L4，再加上 RDI 乘 8。这段汇编是什么意思呢？它跟我们之前讲的 memory address 的表达是一样的：内存地址加括号，就是取内存里面的值。也就是说，把 RDI 先乘以 8，加上 L4，把它作为一个 memory location，再把这个 memory location 里面的值取出来，跳到那个位置去。

所以你会发现，到真正的汇编代码这里，我们 switch 这段代码的开头就是这样。它会把 RDI——也就是我们刚才的那个 OP——用上。第一个参数是 OP 的话，按照我们的约定，它就存在 RDI 寄存器里。

你会发现它会把 RDI 乘以 8 再加上 L4。label 4 是什么呢？label 4 就是刚才我们在 data section 里面存的那个 label，也就是这个小表格；把它看成一个数组的话，它就是数组的起始位置。第一行存的是 L9 这条指令的地址，这些其实都是指向一条指令的地址，也就是指向六个 case 的地址。所以它这边做的事情就是：根据 OP，你是第几个 OP，它就跳到这个表里面的第几项，

**30:51**

把其中的第几项的 instruction address 取出来，然后跳到相应的那个位置。

所以通过这样的方式你会发现，它已经不需要去做很多次 compare，而是用一条间接跳转（indirect jump），再配合设计这样一个 jump table，把各个 switch case 的起始地址都取出来，先排成一张表，然后第几项就跳到其中的第几项。通过这样的方式，这个设计就比较巧妙。

### 条件传送与条件设置

**32:58**

除了条件跳转，还可以用一些特殊指令实现特殊功能。它们不一定能完整表达 for 循环或分支结构，但有时有自己的用处。例如有两条带条件的指令：`cmov` 和 `setx`。

### 条件传送实现 int max

**34:21**

这个 case 是一个 `int max(a, b)`：最后返回 a 和 b 中较大的那个。实现上先把 v 赋成 a；如果 a 小于 b，就把 v 赋成 b；然后 return v。

如果用 `-O0` 编译，也就是不采用任何优化，它会用条件跳转实现 if/else 分支。如果加上优化选项，它就会用 `cmovge`（条件传送）之类的方式，让代码更简单。不加优化编译出来的版本和加了优化的版本相比，后者会少一条指令。

优化后的版本先 compare `ESI` 和 `EDI`，它们分别对应参数 a 和 b；然后把 `ESI` 也就是 a，先移动到返回值寄存器 `EAX`（也就是 v）中；接着再比较。如果条件成立、`EDI` 更大，就用条件传送把 `EDI`（b）传进去；如果没有更大，就不管。这就是通过条件传送实现分支效果。

### 侧信道攻击与条件传送

**35:48**

条件传送还有一个优势，与一种叫侧信道攻击（side channel attack）的攻击有关。侧信道攻击的意思不是正面攻破，而是从侧面获取信息。

举例来说，早期安卓手机上的 malware（病毒）比较多，曾经有一种攻击：攻击者通过越权或向用户申请陀螺仪权限，获取手机当前的姿态信息。获得陀螺仪传感器权限后，它没有办法直接记录键盘输入，却想窃取密码，比如锁屏密码。于是它利用侧面信息：在你输入密码时，手机的偏移。通过陀螺仪，它可以推断你按了哪个键，比如第一个按键、第二个按键，从而知道密码。这就是一种侧信道。

侧信道就是通过侧面信息获取本来拿不到的信息。还有很多更有趣的侧信道，甚至站在这里也可能被利用。例如用电磁波接收器观察 CPU 发出的热辐射和电磁辐射变化，甚至能知道你现在在做什么，比如有没有在看 PPT。这些通过物理或侧面信息推断程序行为的方式都叫 side channel。

它和条件传送的关系在于：CPU 在执行分支时，假设两个分支区别比较大，执行 branch A 时对 CPU 的影响——比如程序速度更快，执行 branch B 时速度更慢。攻击者就可以据此知道你正在执行哪个分支。这是攻击者可以获得的信息。如果用了 `cmov`，这个信息就被隐藏了，因为代码没有 branch 的概念，所有代码都顺序往下执行，攻击者不知道执行的是 if 还是 else，也就无法猜出 condition 是 true 还是 false。

这在加密算法中非常常见：现在通常的加密算法为了防御各种侧信道攻击，都会尽量去除分支（branch），采用类似条件传送的方式实现。
