### 量化模型的算术强度

**09:16**

谷老师已经介绍了这部分的主要内容，我们开始。先回顾上一次讨论课提到的量化。nano count 实验里可能有些同学已经做过：对一个 Qwen3-1.7B Instruct 模型做简单量化。如果是这样一个量化模型，它的计算强度到底有多少？上一次课介绍过，模型的计算强度由模型本身的参数量以及量化程度决定。我们上次拿到的量化模型一共有 17.2 亿个权重；它只有 2B，其实 2B 已经是很小的模型，现在的模型参数量要大得多，可能高很多个数量级。采用第二讲提到的 Q4_0 量化模式，也就是 nano count 实验的第一部分：每 32 个权重占 18 个字节。这里简单复习一下：32 个权重每个都是 int4 值，占 4 位；对整个权重做量化时，Q4_0 还额外存一个用于映射的 scale 值，这个值占 2 个字节，是 FP16。两个字节就是 16 位，摊到 32 个权重里，每个权重会多占 0.5 位，所以每个权重占 4.5 位。

**11:39**

生成一个 token 时，输入会和矩阵做乘法。对于这种简单模型，没有别的复杂结构，从第一层到最后一层一直做前向推理，每一个权重都必须参与运算。所以每生成一个 token，都需要把整个模型读一遍。于是乘加次数与参数量一致：生成一个 token 大约进行 \(1.72\times10^9\) 次乘加。至少数量级是这个数量级；由于里面的算子不太一样，实际运算数目可能有些偏差，但数量级不会错。从内存中读取权重时，读多少权重？\(1.72\times10^9\) 个权重，每个 4.5 位，算出来约 0.9 GB。根据上一次讨论课得到的公式计算算术强度：用生成一个 token 的总浮点运算次数，除以整个模型的大小。乘加一次相当于两次运算，所以把乘加次数乘以 2，再除以从内存读取的字节数，得到算术强度 \(I \approx 3.6\ \mathrm{FLOP/byte}\)。也就是说，每读一个字节需要进行约 3.6 次浮点运算。

### 程序执行与数据传输路径

**17:43**

运行 mini Ollama 或 Ollama 时，程序会经历若干步骤。首先程序被加载到内存；随后 CPU 开始取指执行，把程序中的指令一条一条从上往下运行。运行到加载模型时，模型也被加载进内存。接下来，模型中的每一个权重数据都要传输到 CPU 中参与运算。这条路径上的每个环节都可能限制程序的执行速度。

### 指令条数如何限制乘加吞吐

**18:34**

真正限制速度的地方在哪里？查看 Ollama 和 mini Ollama 的汇编可以发现：mini Ollama 使用 20 条汇编指令完成两次乘加，相当于每次乘加需要 10 条指令；Ollama 使用 22 条指令完成 32 次乘加，平均每次乘加只需要 0.69 条指令。CPU 执行指令也有速率限制，其中一个基本参数是主频。比如 1 GHz 的主频意味着每秒有 \(10^9\) 个时钟周期；简单指令通常一个周期执行一条，复杂指令可能占用更多周期。因此，如果把每条指令都按一个周期计算，mini Ollama 每完成一次乘加要等 10 个周期，中间会空转很多；而 Ollama 平均每次乘加只用 0.69 条指令，就没有这种明显空转。

### 用指令条数估算推理速度上限

**20:13**

以点积为例。点积需要做累加，内层循环每执行一次完成两次乘加，而这段循环体实际有 20 条指令。这里不逐条查看汇编，因为其中涉及哪些加法、乘法指令比较麻烦。我们可以根据指令条数估算 mini Ollama 的推理速度上限；前面则是根据 CPU 的运算速率进行估计。

每次乘加需要 10 条指令。对 x86 处理器来说，一个周期最多可以有 5 条指令开始执行，也就是可以并行启动 5 条指令；后续讲 CPU 流水线时会再说明，现在先接受这个结论。按平均吞吐计算，一个周期最多完成 \(5/10=0.5\) 次乘加。

这颗 CPU 的主频是 3.8 GHz，即每秒有 \(3.8\times 10^9\) 个时钟周期，所以每秒最多完成
\[
0.5\times 3.8\times 10^9 = 1.9\times 10^9
\]
次乘加。前面已经算过，生成一个 token 需要 \(1.72\times 10^9\) 次乘加，因此速度上限为
\[
\frac{1.9\times 10^9}{1.72\times 10^9}\approx 1.1\ \text{token/s}.
\]
也就是说，这颗 CPU 最多每秒吐出一个 token，这显然不可接受；使用 DeepSeek 时通常能看到每秒几十个 token 的速度。前面的实测约为 \(0.77\ \text{token/s}\)，实际值会低于速度上限，因为程序除了乘加指令还要处理其他事情，还有别的指令。

Ollama 平均每次乘加使用 0.69 条指令，与 mini Ollama 的 10 条指令相比相差约 \(10/0.69\approx 14.5\) 倍；速度上也确实相差约 14 倍。两者具有很多类似性质，因此可以相信当前推理速度之所以特别慢，主要是被指令条数限制了，而这个上限主要来自 CPU 的时钟频率，也就是前面提到的主频。如果对主频的作用感兴趣，可以自行和 AI 讨论。

### 降低指令条数与提升硬件吞吐

**23:36**

解决方案也能从这张表中得到。第一项是每次乘加需要的指令条数，它来自程序，也就是编译出来的二进制。二进制一旦确定，这个数就确定了；但可以优化二进制，让指令条数降低。因此第一个方案是降低每次乘加的指令条数。

第二项是每个周期最多完成多少次乘加。前面提到，每个周期最多执行 5 条指令，这由 CPU 的流水线决定。要提高这个上限，CPU 本身无法直接改，因此可能需要引入新的硬件来提高这一项。

### 可行方案：降低指令数与提高并行度

**24:19**

回到前面的表：第一项是每次乘加所需的指令条数，它来自程序，也就是编译出的二进制。二进制确定后这一项就确定了，但可以优化二进制，减少指令条数。第二项是每个周期最多完成多少次乘加，它由 CPU 的流水线决定；要提高这一项，需要更新 CPU，或者引入新的硬件。第三项是每秒能完成的乘加次数，它来自 CPU 主频。主频会随 CPU 技术发展而提高，但个人电脑常用 CPU 通常在 3 GHz 到 5 GHz 左右，不会出现数量级跃升，因此这一项基本带不来多大改变。最后，生成速度的上限还取决于每个 token 需要多少次乘加，这显然由模型决定；模型确定后，这一项也无法施加影响。

所以真正可用的解决方案是前两项：降低指令条数，以及提高每个周期完成的乘加次数。前者最简单的想法是让一条指令执行多次运算，这就是 SIMD（single instruction multiple data）。后者可以利用 CPU 的多个核，让每个核都执行乘加；如果有多个核，就可以把每个周期完成的乘加次数乘以核数。也可以增加运算单元，这正是现代 GPU 的思想：SIMT（single instruction multiple thread），让更多线程同时执行运算。下面先介绍 SIMD 数据并行。

### SIMD 数据并行与寄存器加宽

**26:29**

数据并行最简单的想法，是把多个较小的数据打包进一个更宽的数据单元。例如 int4 是 4 位整数，存储时放在一个字节里；一个字节可以放两个 int4，所以处理一个字节时，就可以同时处理两个 int4 数。类似地，可以把 CPU 中执行运算的寄存器变长，让它能存放更多数据。

在 x86 的浮点寄存器中，有 XMM 系列寄存器。把寄存器的位宽加宽，就能一次存放更多数据：64 位可以存两个 32 位 int，128 位可以存四个，256 位可以存八个，512 位可以存十六个。如果让两个这样的寄存器执行加法，在 512 位下就相当于同时对 16 个 int 做加法。这样一条指令就让更多加法同时运行起来。

SIMD 的思想就是：一条向量指令通过多个并行的算术通道执行。例如把 256 位寄存器按 32 位划分，可以得到 8 个 32 位段，每个段就是一个算术通道。

### YMM 向量寄存器与指令集扩展

**28:21**

在 x86 的 YMM 寄存器体系中，一般提供 16 个 256 位的向量寄存器。下面要说明如何用这些寄存器一次完成 8 个 32 位整数的运算，也就是在汇编中怎样调用这些寄存器。

原来的 addq 是 64 位加法，addl 是 32 位加法，没有更宽的操作，因此要操作更大的向量寄存器就必须引入新指令。这些指令扩展在 ISA 中。例如向量加法 VPADDD：V 表示向量指令，P 表示 packed（打包），ADD 表示加法，D 表示 32 位双字。向量乘法也有类似的命名，包含 packed、double word 等标识，并保留 32 位双字结果。具体可以在 ISA 官方文档中查，这里不逐项深究；下面主要介绍几条指令，以及怎样使用向量加载。

### 向量加载、乘法与加法

**30:14**

向量加载采用地址方式：只要指令写清楚，地址后面跟的是 YMM 寄存器，而 YMM 是 256 位，它就会从这个地址取连续的 256 位放入该寄存器。这和前面从地址取数据放到 EDX 或 RDX 是一样的：根据目标是 RDX 还是 EDX，会从地址取 64 位或 32 位再放进去。

向量乘法也可以把内存中的数作为操作数。也就是说，可以让内存中的一个数与 YMM2 相乘，再把结果写到 YMM0。加法也采用类似格式：两个源操作数相加，结果写到后面的目标寄存器。它们都是三操作数指令，比旧 x86 中的两操作数指令更清晰。

### 向量点积的累加形式

**31:37**

在向量实现中，\( x \) 存在内存里，于是让 YMM2 与内存中的这个值相乘，把得到的积存到 YMM0；后面再把这个积累加到累加结果中。

### 从 SIMD 到 SIMT

**35:46**

这是第一个 SIMD 思想。第二个解决思路是用 SIMT 实现线程并行。在 CPU 中，运算通常是从上到下顺序执行的；但 CPU 有多个核，可以让每个核独立完成一部分运算，再把各核结果加起来。这可以看作最简单的 SIMT；严格来说，这并不是 SIMT，因为各核执行的并不是同一条指令，但它确实是在多个线程、多个并行空间中完成运算，然后汇总结果。

### GPU 的核心数量与用途

**36:46**

现在有了一种新硬件，就是 GPU。GPU 的运算核心比 CPU 高几个数量级。以我这台电脑为例，i9-11900H 的运算核心只有 8 个；而 RTX 5090 有 21760 个运算核心。我的电脑可能同时跑 8 个运算，GPU 却能同时跑 21760 个。实际上还不止：如果没记错，每个运算核心里面还有 128 个可以同时跑的线程，所以还要再乘以 128，可以同时跑非常多的运算。

GPU 最初是为图像渲染设计的，因为图像渲染要做大量矩阵乘法。每个像素都有 RGB 三个值，修改图像本质上就是修改这些值，用矩阵完成形变或颜色变化。这与神经网络推理、大模型推理属于同一类运算，所以现在 GPU 变得越来越金贵，因为大模型推理需要它。接下来看 GPU 的架构，也就是它为什么能把运算做得这么快。

### GPU 架构与编程模型

**38:28**

以 RTX 5090 为例，每一个计算单元叫做 SM，它是 GPU 的运算部件。每个 SM 有 128 个运算核心和一块共享内存。显存则是给内部运算单元用的高速存储，它与内存之间的数据交流速度也相差几个数量级。

写 GPU 程序时，需要启动线程。一个顺序执行的程序应该在一个线程里跑，而我们可以让很多个这样的顺序程序同时跑。线程会组成线程块，线程块由程序指定；一般来说，一个线程块里最多有 1024 个线程。一个线程块会被分配给一个 SM。SM 里有 128 个运算核心，会轮流执行线程块里的线程。例如线程块里有 1024 个线程，而一个 SM 有 128 个运算核心，那么就要分 8 批执行。

一次启动的所有线程块组成 grid。SM 还会把每 32 个线程编为一组，同一个 warp 的 32 个线程执行同一条指令。

### Warp 与线程组织

**40:36**

一个 warp 里的 32 个线程共用同一个程序计数器（PC）；GPU 里通常不把它叫 IP，而按 PC 来说，这 32 个线程执行同一条指令。warp 的大小是 32，由硬件决定，程序不能修改。

结合图示来看，一个程序里会写很多可以同时运行的线程代码。一次启动的所有线程组成一个 grid；启动时给每个线程块分配多少线程，就会把总线程划分成若干块。例如每个线程块 256 个线程、总共执行 1024 个线程，就分成 8 个块，每个块分配到一个 GPU 的 SM 上。

### SM、Warp 与多级存储

**41:40**

一个 SM 有 128 个运算核心。warp 是 32 个线程一组，因此 256 个线程组成 8 个 warp；128 个核心可以同时执行 4 个 warp，先执行其中 4 个，其余 warp 等待，等前一批执行完再立刻接上。显存由所有 SM 共用，都可以访问；共享内存只在一个 SM 内部共用，别的 SM 访问不到。主机侧的沟通通过 PCIe 总线进行数据拷贝，速度比显存和 SM 之间的通信慢很多；显存与 SM 之间的通信很快，共享内存更快。计算机中的这种多级结构以后在缓存等部分还会遇到。下面以点乘为例，看如何写 CUDA 程序。

### CUDA kernel 的基本结构

**43:02**

CUDA 程序看起来比前面点乘的写法复杂很多；一旦涉及并行，就要考虑更多事情。

程序以 `__global__` 开头，标记这个函数是一个 kernel，应该在 GPU 上执行。CUDA 程序里经常能看到前面标了 `__global__` 的代码。kernel 里先定义一块共享内存：`shared` 的整型 `cache` 数组。每个线程块共用这块共享内存；一个线程块分配给一个 SM，一个 SM 内部有一块共享内存。因此这里的 `shared int cache` 指的是 SM 内的共享内存，而不是显存。

### 线程编号：threadIdx、blockIdx 与 blockDim

**44:17**

`TID` 表示线程的 ID，`index` 表示线程的总 ID。`threadIdx.x` 是线程在自己所在线程块里的编号，例如块内有 256 个线程，它的 `threadIdx.x` 就是 0 到 255。全局 `index` 由 `blockIdx.x * blockDim.x + threadIdx.x` 计算：`blockIdx.x` 表示当前是第几个 block，`blockDim.x` 表示每个 block 有多少个线程，乘积是当前 block 之前一共有多少线程，再加上块内编号，就得到该线程在整个 grid 中的全局线程编号。`TID` 则只表示它在线程块内的 ID；这几个 ID 需要区分。

### 边界判断与并行乘法

**45:25**

真正计算乘法时，把结果存到 `cache` 里。判断 `index < n`：`index` 是全局 ID，`n` 是总维度；如果全局 ID 超过 `n`，就越界了。总维度不一定能正好划分成若干个大小为 256 的线程块，例如 257 个线程时，最后一个块里只有一个有效线程，其余都是空的。越界线程也必须一起处理，因为它们同时执行；因此用条件判断让越界位置写成 0，正常范围内则计算 `w[index] * x[index]`，把结果写入共享内存 `cache`。这里不写循环，是因为要让计算并行起来。

### 同一 PC 与共享内存中的中间结果

**46:27**

一个线程块里只有一个 PC，所有线程执行同一条指令；不同线程的 `threadIdx`、`blockIdx`、`blockDim` 可能不同。因此执行下来，必须把中间结果存到不同的位置，用 `TID` 在线程块内标识。`cache` 是整个线程块共有的，一个线程块正好 256 个线程，所以直接把结果存到 `TID` 对应的位置。这条指令执行结束，意味着 256 个乘法全部算好；点积要先把对应元素乘起来，再累加。

### 同步：等待所有运算单元完成

**47:26**

有些运算单元可能算得慢，无法保证所有乘法同时完成，电路抖动也可能造成差异。因此需要 `__syncthreads()`：它等待所有运算单元都结束，再继续后面的操作；否则某些单元卡住时，可能读到中间结果。同步之后，已经得到 256 个乘法的结果。

### 用折半方式累加

**47:56**

接下来要把 256 个乘法结果累加起来。如果逐个相加，一个结果依赖前一个结果，比如先算 0+1，再用这个值加 2，就会串行执行，无法发挥 GPU 同时计算很多数据的优势。因此这里的循环采用折半执行：`s` 表示间距，初始为 `blockDim.x / 2`，`blockDim.x` 是 256，所以一开始 `s = 128`。

### 线程块内的折半归约

**48:44**

此时 \(s=128\)。我画一下：这个数组是 cache 数组，这里是 cache 数组的地址。数组一共有 256 个元素，下标从 0 到 255。第一次 \(s\) 初始化为 \(256/2=128\)，相当于把数组分成两份，每份 128 个元素。

接下来判断 `tid < s`，也就是看这个线程落在前半部分还是后半部分。前 128 个线程在数组前半部分，后 128 个线程在数组后半部分。如果线程在前半部分，例如第一个线程，它就执行 `cache[tid] += cache[tid + s]`，把自己位置上的元素和加上间隔 \(s\) 后对应的后半部分元素相加，结果写回前半部分。后面整个 128 个数都这样一一对应相加，得到新的 128 个部分和。

然后调用 `__syncthreads()`，等待这次计算结束。这样一次归约就把 256 个数累加成 128 个数。下一轮间隔继续减半，\(s\) 从 128 变成 64，再继续减半，直到只剩一个数；这个数就是该线程块的累加结果。

最后把结果写入 `block_sum`。`block_sum` 位于显存中，每个线程块对应一个位置。归约结束后，让 `tid == 0` 的线程把 `cache[0]` 写到该线程块对应的 `block_sum[blockIdx.x]`，其他线程不用写。所有线程块计算完成后，`block_sum` 中存放的就是各线程块的和；再把这些值全部加起来，就得到最终结果。

### CUDA 程序的内存分配

**51:17**

接下来讲 CUDA 程序的内存分配问题。这部分比较细节，了解即可。计算机上分为内存和显存。通常写一个局部变量，或者用 `malloc` 分配，或者直接在栈上分配一个变量，它都是分配在主机内存中的。如果要把数据分配到显存上，就需要显式调用 `cudaMalloc`；如果要在共享内存中分配，前面已经讲过，就用 `__shared__` 标识，让变量分配在 SM 的共享内存中。内核中带 `__shared__` 的变量由同一线程块内的线程共享，会被分配到对应的共享内存区域。

### 数据传输、kernel 启动与结果回收

**52:25**

对于要放在显存中的数组，需要显式调用 `cudaMalloc`。例如前面声明的 `dW` 和 `dX` 分别是两个长度为 \(n\) 的 `int` 向量，`d_part` 用来存放结果；`cudaMalloc` 会为它们分配显存，并把相应类型的指针赋回来。要把主机内存中的值放到显存上，就使用 `cudaMemcpy`。例如把 `dW` 对应的 \(n \times \text{sizeof(int)}\) 个字节完整拷贝到显存，`dX` 也做同样的操作。

接下来执行 kernel，也就是前面那个函数。CUDA kernel 的调用语法比较特殊，要用三重尖括号 `<<<...>>>` 指定网格和线程块，例如规定有多少个线程块、每个线程块有多少个线程。这些数量可以由我们自行指定。

前面的 kernel 把各个线程块的和放到了 `block_sum` 中；在这里，`block_sum` 就是 `d_part`，也就是 kernel 的第三个参数。`d_part` 已经由 `cudaMalloc` 分配在显存中。如果后面的累加要在主机内存中完成，就需要把结果拷贝回来：用 `cudaMemcpy` 配合 `cudaMemcpyDeviceToHost`，把 `d_part` 拷贝回主机内存中的 `part`，然后在 CPU 上累加各个线程块的部分和。

当然，这个累加也可以在 GPU 上完成。如果愿意，可以把代码写得更复杂，继续在 GPU 上用折半求和的方式把它算完。

### Softmax 的定义

**02:14**

接下来给大家一个简单的课堂任务：用 GPU 计算 softmax。如果有同学还不了解 softmax，这里先说明一下。

softmax 是一个激活函数、一个激活层。对一个长度为 \(n\) 的数组 \(s\)，其中元素为 \(s_i\)，\(i=0,\dots,n-1\)，softmax 做的事情是：先对每个元素取指数 \(e^{s_i}\)，再把所有指数累加起来作为分母；每个 \(s_i\) 对应的结果就是

\[
\operatorname{softmax}(s_i)=\frac{e^{s_i}}{\sum_{j=0}^{n-1} e^{s_j}}.
\]

这本质上是在做归一化。
