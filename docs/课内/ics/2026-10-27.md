## 计算机系统基础（1）｜第 3 节（09:55）

### 从顺序执行模型出发

**05:07**

同学们，今天开始新的一部分内容。之前已经讲过程序如何在 CPU 中运行，这是核心问题。我们认识了程序运行时 CPU 实际执行的是指令，以及指令在操作什么、数据从哪里来、指令存放在哪里等信息。

今天会进一步深入。之前说 CPU 就是不停取指令、更新 PC：执行完一条指令后取下一条 PC，再执行这条指令，形成执行指令的大循环。今天要看看 CPU 究竟如何一条条完成指令的执行，以及如何把 CPU 设计得更高效。

先看之前见过的一段熟悉代码和一段汇编程序。之前说过，CPU 的执行模式是顺序执行，一条一条往下执行指令；如果遇到 jump 或分支跳转指令，就跳转过去执行。无论如何，这都是基本模型：每次根据当前的 program counter，也就是 PC，取出一条指令，执行完后再重复这个过程。

### 五级流水线

**07:34**

那么，CPU 有没有更高效的执行模式？肯定有。先看一个经典的简化例子，比如以 mini CPU 为例。确实有一些处理器采用五级流水线设计，例如 MIPS。这里看一个简化的例子：每条指令都有五个阶段。之前我们说 CPU 每次执行一条指令，现在要把它拆成五个阶段来看。

### 五级流水线的五个阶段

**08:11**

每条指令都划分为五个阶段，依次是：取指（fetch）、译码（decode）、执行（execute）、访存（memory）和写回（write back）。为什么分阶段，后面再讨论，先看每个阶段做什么。

取指阶段根据当前 PC 从内存中读取一条指令。译码阶段的核心是识别这条指令是否需要操作寄存器、要操作哪些寄存器，并把寄存器的值读出来准备好；虽然叫译码，它同时也完成读寄存器的操作。执行阶段由 CPU 内部的 ALU 完成运算，例如把前面读出的两个寄存器值相加；它也可以计算内存地址，例如 `mov` 这类需要访问内存的指令就在这里完成地址计算。访存阶段拿着这个地址去读内存或写内存；如果是读内存，读出的结果会继续往下传。写回阶段把运算结果或从内存读出的数据写回目标寄存器。

一条指令并不一定五个阶段都有实际工作。例如两个寄存器相加时，访存阶段什么也不用干，只要把结果继续往后传，最后由写回阶段写回即可。但所有指令都统一按这五个阶段来表达，因此这套流程可以描述最复杂的指令。

### 示例：movslq 的五阶段执行

**10:50**

以 x86 中的一条指令 `movslq` 为例。它做的是寄存器之间的传送，同时把 32 位的 long 符号扩展到 64 位的 quad，所以 `s` 表示按符号扩展（sign extension）。假设当前这条指令的地址是 `0x20`，寄存器 EAX 的值是 5。

取指阶段根据当前 PC，也就是 `0x20`，从内存读出这条指令。由于这条指令长度为 3 个字节，随后把 PC 加 3，下一次取指就从新的 PC 取指令。

进入译码阶段，核心是看这条指令是否要操作寄存器、操作哪个寄存器，并把寄存器的值准备好。这里要读的是 EAX，读出它的当前值 5，再把这个值传给下一阶段。

执行阶段完成符号扩展：把 `0x5` 从 32 位扩展到 64 位，数值仍是 `0x5`，只是高位补 0。接着进入访存阶段，但这条指令不需要访存，因此这一阶段没有实际工作，结果继续往下传。

最后是写回阶段。这条指令确实要修改寄存器，目标寄存器在译码阶段就已经确定为 RAX，因此把前面一直传下来的结果写回 RAX。

### 访存阶段的位置与内存操作数

**14:27**

讲完这个流程后，老师问大家有没有觉得奇怪的地方。学生问：访存阶段为什么放在执行阶段之后？老师回答：因为执行阶段做的是计算。对于访存指令，最复杂的操作是先计算地址；地址计算完后，去读内存的值或写内存就可以了。

例如把内存中的一个值加到寄存器里。按这个流程，译码阶段先把寄存器中的值读出来；到了执行阶段，仍然不能直接做加法，因为内存中的值还没有取回来。那么怎么办？在这样一种五级流水线下，不允许直接执行“把内存中的值加到寄存器”这个操作。前面也提到，x86 里确实设计了这样一条指令。

### 指令拆分与 RISC 设计

**16:29**

实际上，它在真正执行的时候，会把一条指令拆成微码（microcode），也就是拆成更细的指令，并不是真的直接对内存中的值做运算。它的做法是先把内存中的值读到寄存器，再把两个寄存器相加，这样就没有问题。

这也是为什么要把一条指令拆分开来的一个原因。如果所有东西都能用一套流水线来设计，那么 CPU 的硬件设计就会很复杂，需要考虑各种情况。所以最后会把它拆成一些比较简单的指令，由这些简单指令去做真正的执行（execute）。因此，这个五阶段的 CPU 设计其实更像 MIPS，它更多采用 RISC 指令集，是一种精简指令集。

在经典指令集里面，会发现它根本没有直接在内存上做加减乘除的操作。好，这是一个非常好的问题。两位同学提的这个问题，还有没有别的问题？

### 取指阶段与指令长度

**17:43**

还有个问题。我问大家一个问题：在取指阶段，我刚才觉得就有点奇怪。取指阶段，CPU 当前有的信息是什么？只有 program counter（PC）。PC 其实是一个值，它是当前要去读的 instruction 的 address，也就是一个地址。那当前 fetch 多长呢？在取指的时候，CPU 怎么知道这边要取三个字节呢？

为什么不是取四个字节？为什么不是取一个字节？是不是由第一个字节来告诉它？我不知道 x86 里面有没有这种指令；有可能，因为不一定能从第一个字节看出它到底多长。

这是一种方法。如果第一个字节能判断，那当然最好，这样只要读一个字节，就知道一共要读多少个字节。如果每条指令的长度都能由第一个字节直接判断，这是一种做法。用终止符？指令里面肯定没有终止符。

还有一种可能，或者一个比较简单的做法，就是所有指令都是定长的，这时候就比较简单。例如 RISC 的这些指令集，所有指令都是四个字节。所以在取指阶段就很简单，每次只需要 fetch 四个字节，PC 也加四，这样也比较确定。

对于变长指令，x86 里面的做法相对复杂一些。它实际上一次 fetch 也会取一段字节，并不是精确地去读。它不是精确地决定我读一个字节还是读四个字节，所以它读取的粒度不是特别确定，可能是 32 或 64 对齐的宽度。然后它在中间去看当前指令到底是什么情况。当然，它还是需要根据前面的编码信息判断整个指令有多长，大概就是这么一个逻辑。

所以它一次性可以读得比三个字节多，多读一点无所谓。解析时发现只有前三个字节属于当前这条指令，那也没问题；它只用前三个字节继续执行就可以了。因此，并不一定第一次就要精确地读出三个字节。

### 五阶段执行与时钟周期

**21:04**

每条 CPU 指令都会经过五个阶段，五个阶段的执行把各种各样的 instruction 都统一成用这五个阶段来表示。

这里有一个概念：时钟周期。我们之前讲过，CPU 里面有一个比较重要的、跟性能相关的参数，叫做赫兹，也就是主频。比如买一个 3.0 GHz 的 CPU，还是买一个 4.0 GHz 的 CPU；它其实就是这个 CPU 在一秒里面有多少个时钟周期。

时钟周期在 CPU 里面是固定的。假设现在是一个固定频率的 CPU，比如 3.0 GHz，就是一秒钟有 3.0G 个时钟周期（CPU cycle）。这也可以作为一个统计时间的量。

### 用 RDTSC 测量 CPU 周期

**22:13**

在 x86 机器里，有一个经典指令 RDTSC，它可以读取当前 CPU 时钟的值。它读的是一个值：在开始的时候读一个值，在结束的时候再读一个值，两个相减，得到的就是一个相对时间。它表示在你记录的、想观测的这段时间里，一共经过了多少个 CPU cycle。

这个时间非常精确，是用 CPU cycle 描述的。什么时候会比较有用？做性能（performance）评测的时候，比如以后写论文或者做一个工作，你去评测它的性能，它会比较有用。尤其是什么时候更有用呢？当你说“为什么我不能用更高层的接口”，比如用 gettimeofday()，用这样的一个系统调用、这样的一个 C 函数去读取、评估时间呢？

那我们现在给大家出一个问题：你现在有一个函数，你写了一个函数，比如这个函数是一个 kernel，也就是一个矩阵相乘。然后你要评测这个 kernel、这个算子写得好不好。你要评测的指标，当然假设功能都是正确的，就是它跑得快不快，执行时间是不是很短。

### 矩阵乘 kernel 的性能评测

**23:25**

这时候你有两个选择：一个是用 gettimeofday() 去测它的时间；另一个是用 RDTSC 去测它经过了多少个 CPU 时钟周期。那什么时候会用这个？或者说这两类方法有什么区别？

大家评测时间的时候，问大家一个题外话：假设你现在有一段程序，对吧？

### 测量函数执行时间

**24:43**

假设程序里写了一段代码，有一大段实现，中间有一个你想测量的函数，比如执行某种计算或完成某个功能。你想知道这个函数、这个实现占用了多长时间，性能怎么样，有什么方法测量？一个简单的方法是在函数调用前记录开始时间，调用后记录结束时间，最后打印结束时间减去开始时间，也就是 \(e-s\)。这就是测量一个函数执行时间的大致写法。

这种写法可能会有什么问题？大家写代码时有没有关心过它到底跑得多快？至少在今天这堂课之后，希望大家记住一件事：两年以后写毕业设计论文、做评测时，要回忆起今天讲的内容。虽然这部分可能只有五分钟，但做 paper、写毕设时，不要连评测中的时间该怎么测都不知道。

### 基线对比与多次测量

**26:23**

大家觉得这样测试有没有问题？什么东西会受 CPU 性能影响？这肯定会受。假设我们实现了同样功能的另一个版本，有一个基线（baseline），也就是做了替换。做毕设时可能要写一个新的算子，而之前别人已经实现过一个算子，这就是已有的基线实现。对性能做最基本的评测，就是拿自己的实现和基线比较。

测试一定会受到机器性能影响，但可以把两个版本跑在同一台机器上评测，计算相对性能，比如相对基线提升了 10% 或 15%，这是可以的。把基线版本和自己的程序跑在同一台机器上，可以规避物理机器对性能的影响。

另一个基本方法是：程序测一次不一定准，可以简单跑五次，取平均，求 average。这是做性能评测的基本思路。但跑五次取平均是否一定合理、一定 OK？五次测量的方差也可能很大。如果五次表现不特别靠谱、方差特别大，就说明测量方法可能不对。

### 计时粒度与 RDTSC

**28:29**

可能的原因之一是函数本身执行时间很短，而计时接口的 granularity（粒度）对不齐。也就是说，计时接口能够观测到的时间粒度有限。比如高层接口只能观测到微秒级，而函数只执行 0.1 微秒、0.2 微秒，这个接口肯定测不出来，或者测出来的结果很乱：可能测出 0，也可能一下测出很大的值。

为什么可能测出很大的值？因为执行过程中可能被抢占，CPU 去干别的事情，测出的时间还包括操作系统调度的时间。RDTSC 可以提供更细的粒度。RDTSC 到什么级别？到 \(10^{-9}\) 秒这个级别。比如 CPU 是 3.0 GHz，一秒钟执行这么多次，每个 cycle 就是这么多分之一秒，约为 \(1/(3\times10^9)\) 秒。如果用 RDTSC 这条指令实现计时，它的精度可能更好，实际测量粒度可以更小。

### 重复执行与 CPU 状态

**30:57**

除此之外，如果函数本身没有其他不可避免的副作用，通常不会只直接测量单次调用，而是让这个函数执行一个 for 循环，比如执行一百次或一千次，从而增大总时间。我们不需要测单次时间，而是让它在计时区间内重复一千次，看总共的时间，再减去计时开销并除以重复次数，这样就可以观测一个比较小的时间段。也就是把函数放在开始和结束之间重复执行一千次。通常这是更进一步的做法。

后面还会讲到，CPU 里其实还有一些别的事情。CPU 的设计其实挺复杂，今天会讲到 CPU 里有一个叫预测执行（speculative execution）的东西。此外，CPU 还有预测机制，还有 cache 高速缓存。它会缓存一些经常执行的指令、经常访问的数据到 CPU 内部，还包括其他信息，比如当前程序执行中的一些预测信息。

### 性能测量中的预热

**32:49**

CPU 需要预测分支是跳转还是不跳转。如果希望更精确地测量性能，通常还会加一个 warm-up 阶段，让程序先热热身，使测量时进入比较稳定的状态。例如，程序要访问的数据已经被缓存到 CPU 内部，就能看到相对稳定、可重复的性能，而不是第一次执行和第十次执行之间出现很大的方差。直接简单平均五次有时问题比较大，数据不够严谨；更简单的做法是把程序重复跑十次，但这十次不记录性能，只用于热身，把当前系统状态弄稳定。这样之后测出来的时间会更科学一些。这些是经验性的数字，属于题外话，下面回到时钟周期。

### 时钟信号与寄存器写入

**34:20**

时钟周期方面，CPU 会一直稳定地发出时钟信号。CPU 内部有些部件被设计成只在时钟上升沿更新数据。以寄存器为例，它有两个信号：一个是时钟信号，一个是 value 信号；只有在收到时钟上升沿时，它才把已经准备好的 value 更新进去。PC 寄存器、flags 等本质上都是寄存器，都会在时钟上升沿被写入。

ALU 这样设计的一个好处是保证同步写入。一条指令有五个阶段。执行过程中，ALU 会算出结果，并产生需要设置的标志，例如是否溢出、结果是否为零；carry flag、sign flag、zero flag 等运算结果标志要写入 flags 寄存器。要写回寄存器的 value 则到最后一个 stage 才写回。五个阶段执行完后，这些 value 都已经准备好，等到这个时钟周期结束、下一个时钟周期的上升沿到来时统一更新。于是下一条指令执行时，看到的是上一条指令更新后的结果，而且是统一、同步的更新。具体为什么在上升沿写入并没有那么重要。

### 五阶段执行流程的统一

**37:03**

CPU 把每条指令都变成统一的五步执行法。任何不太复杂的指令都可以用这五个阶段表示；复杂指令会被拆成比较简单的指令。这样所有指令的执行流程都被统一化，CPU 的硬件和部件设计会更简单、更高效。现在的逻辑是：先取指，再经过后面四个阶段，然后在下一个时钟沿把 value 写入，之后一直重复这个过程。

以算术和逻辑运算为例，比如 add、sub 这类指令，取指阶段读取指令字节，例如读两个字节；decode 阶段读出两个操作数寄存器的值；execute 阶段执行相应计算，并设置相应标志；访存阶段不访存；写回阶段更新目标寄存器。PC 的更新值在取指阶段就已经准备好，并纳入统一的同步更新。接下来看一个具体 case，每个阶段内部都会变成一些要完成的小操作。

### 一条指令的具体执行过程

**39:03**

具体看取指阶段：假设当前 PC 是 0x55，就到 memory 中取出指令，先看 opcode 是什么，从而知道这条指令后面还要读几个字节，再把第二个字节读出来。同时把更新后的 PC value 准备好；但这时还没有写回 PC，因为所有更新都要等这条指令结束时统一进行。

到 decode 阶段，根据前面读出的指令内容，知道要访问哪两个 register，并把它们的值读出来，得到 value a 和 value b。到 execute 阶段，计算需要的结果，并暂时保留这个结果；此时仍然没有写回寄存器，要等指令结束再统一写回。同时，相关的 flags 也会被记录下来。到 write back 阶段，才真正做写回。

### 单周期假设

**40:15**

这里有一个假设：在每一个 CPU 时钟周期里完成一条指令。一条指令花一个时钟周期完成，下一条指令在下一个时钟周期完成，每次都在时钟上升沿更新。听起来一切都很按部就班、非常顺利。时钟频率的赫兹数，在这样一个一条指令一个周期的假设下，就代表一秒钟能执行多少条指令，听起来一切都很好。

### 单周期 CPU 的瓶颈

**40:57**

在单周期实现中，一条指令必须在一个时钟周期内完成。原因是不同阶段之间并不保存中间结果，阶段之间的结果只是组合逻辑中的中间信号；真正被写入寄存器的是在时钟沿到来时更新的状态。因此，必须保证一个周期内一条指令的全部工作完成，并让所有信号在下一个周期开始前更新到目标位置。

这样一来，时钟周期的长度就受最慢、最复杂的那条指令限制。简单指令可能只需要半个周期就能完成，也只能等待。这就是单周期 CPU 的瓶颈：最慢指令决定了时钟周期的长度，也决定了 CPU 主频的上限。这里同样受木桶原理限制。

例如，不同指令依次在一个周期内完成：第三条指令在第三个周期完成。每条指令占一个周期，按顺序执行。

### 五阶段划分与硬件复用

**42:55**

那为什么要把一条指令拆成五个阶段？先看一个更直观的做法，也就是 mini CPU 的软件模拟。它采用解释执行：用一个大的 switch 读取当前指令的 opcode；如果 opcode 是 1，就执行对应的 function 1；如果是 2，就执行 function 2；如果是 3，就执行 function 3。每条指令对应一个功能实现，看到哪条指令就调用哪段实现，这很直观。

但这种做法会让不同指令的功能部件大量重复。例如多条指令都要保存结果，都要读寄存器，很多功能实现是相同的。硬件设计可以复用这些逻辑部件，把每条指令抽象成五个阶段，使所有指令共用相同的部件。这有点像写代码：不会为每个功能把全部代码从头写一遍，而是调用公共的库函数，复用相同的功能。这正是不要为每条指令单独设计一套硬件逻辑的原因。

不过，分成五个阶段后，五个阶段仍然在同一个 CPU、同一个时钟周期内完成；依旧是一条指令执行结束后，再执行下一条指令。这里的五阶段只是在硬件部件上更节省，还没有让 CPU 跑得更快，也没有把时间更充分地利用起来。

### 流水线：食堂打饭与洗车

**45:12**

下一步要解决的问题是：能不能让 CPU 跑得更快，把时间更充分地利用起来？现代 CPU 普遍采用流水线设计。流水线在日常中很常见，例如食堂打饭：先选蔬菜，再选荤菜，最后盛米饭。所有人排成一队，一个人往前走，后面的人跟上来；不是一个人把蔬菜、荤菜、米饭三个阶段全部走完，才去服务下一个人。

指令的五个阶段也是如此。现在的顺序做法是：前一条指令把五个阶段全部走完，后一条指令才进入第一个阶段。如果食堂也这样，所有人都得等最慢的那个人把全部流程走完，瓶颈就在最慢的环节。

流水线的做法是：当前一条指令进入第二个阶段时，下一条指令就进入第一个阶段执行。这样五个阶段的硬件上都有指令在执行。类似自动洗车：前一辆车打完泡沫后进入冲洗阶段，下一辆车就可以进来打泡沫，所有车再依次往前进入下一阶段。因此，整条流水线中可以同时有多辆车，例如同时有三辆车处于不同阶段。

### 顺序执行的周期与吞吐率

**47:36**

刚才说的 CPU 是顺序执行（sequential）的实现：每条指令严格执行完，再去执行下一条指令。假设一条指令中间的计算过程一共需要 300 皮秒（ps），最后写回需要 20 皮秒，那么一条指令一共需要 320 皮秒。时钟周期就被限制在这个长度上，对应的时钟频率约为
\[
\frac{1}{320\times 10^{-12}\ \text{s}}\approx 3.12\times 10^9\ \text{Hz}.
\]
也就是每秒约 3.12 G 次操作。这里的 ops 指 operations per second，即每秒完成的操作数。由于每条指令都要花 320 皮秒，所以可以把这个过程拆开，拆成刚才看到的五个流水线阶段。

### 三阶段拆分与级间保存

**49:01**

现在先用一个抽象的表示：把原来需要 300 皮秒完成的操作拆成 A、B、C 三个部分，每个部分各用 100 皮秒。因为上一阶段的数据要传递给下一阶段，所以中间必须把上一阶段的结果保存下来。原因是同一时刻 A 和 B 中执行的已经不是同一条指令了。用洗车来类比：某个位置是刚进来的新车，前一个位置是更早的车，再前面是最早的车，不同指令处在不同阶段。比如指令 1 先在 A 中执行，执行完后先把结果放到中间保存位置；随后指令 2 进入 A 执行，而指令 1 的结果已经保存在中间。

### 延迟与吞吐率

**49:56**

从单条指令来看，执行时间反而变长了：原来需要 320 皮秒，现在变成 300 加 3 个 20，也就是 360 皮秒，单条指令的延迟变成 360 皮秒。但整个 CPU 流水线的吞吐率提高了，从原来的 3.12 Gops 提高到 8.33 Gops。原因是以前发射一条指令要等 320 皮秒，现在发射下一条只需要等 120 皮秒，因为只要前一条指令经过当前阶段，下一条就可以紧接着发射。流水线并没有降低单条指令的执行时延，而是提高了整体吞吐率。

### 硬件是否变成三倍

**51:14**

这时会自然想到：用三份硬件并行，是不是让硬件变成了三倍？硬件不会变成三倍，只会多一点点，多出来的部分用于临时存储。所谓拆分，并不是把原来指令的五个阶段复制三份，而是把原来的五个阶段拆开，由不同的部件分阶段执行。原先五阶段流水线中的取指、译码、执行、访存、写回都放在一个大框里，总共耗时 300 皮秒；现在的做法是把原来的五个部分拆开，分成三块来执行。硬件并没有增长，不是把硬件复制三份，而是把原来的硬件拆开来分别完成各阶段。

### 流水线时空图

**52:26**

从时空图看，横轴是时间线。没有流水线时，一个操作做完之后，下一个操作才开始；每个时钟周期完成一条指令。采用流水线后，上一条指令还没有完全执行完，只要它执行完当前阶段，下一条指令就可以开始执行。这样气泡或空隙的数量会变少。CPU 真正运转起来后，中间可以同时容纳很多指令；在这个三阶段的例子里，大部分时候有三条指令同时执行，整个 CPU 处于被用满的状态。这也回答了刚才同学的问题。

### 五阶段流水线与空闲部件

**53:30**

五个阶段各由一组独立的硬件负责。每一行表示的是一组硬件；在单周期实现中，一条指令处在某一个阶段时，只有该阶段的硬件在工作。例如一条 mov 指令要经过五个周期，它执行到任何一个阶段时，其他阶段的部件都空闲。执行到访存阶段时，前面三个阶段都空着，为什么不让其他指令来做呢？这正是流水线的基本思想。只需要在每个步骤之间加入级间寄存器保存结果，每一组硬件在下一个 CPU 周期开始时就都可以处理下一条指令。这样，前面分成五个阶段的指令执行就可以同时处理五条指令。

**54:16**

每条指令在某一时刻只占用五个部件中的某一个，也就是只占用其中一个阶段的硬件。因此，在某个时刻，五条指令可以同时在 CPU 中执行。时钟周期由最长的那个阶段决定。

## 计算机系统基础（1）｜第 4 节（10:50）

### 时钟周期与流水线均衡

**00:00**

时钟信号不能以过于微观的方式随时调整，因此需要设定一个固定频率，也就是固定时钟周期。时钟周期必须由最长的阶段决定。例如在这个例子里，每个时钟周期都要按 \(150+20\) 这个最长部分来设置，于是整个设计的吞吐率会受到一定限制。因此，好的流水线设计要尽量把各阶段划分得均衡；只有各阶段尽可能均衡，才能高效实现高吞吐率。

### 通过插入级间寄存器提高吞吐率

**00:44**

下面看一个小例子。假设现在的 CPU 实现共有 A、B、C、D、E、F 六个阶段，并考虑最后再加一个 write back 阶段的情况。问题是：分别插入级间寄存器，插在哪里、插几个，也就是把流水线分成几级，才能使吞吐率最大；要获得潜在的最大吞吐率，最少要分成几级？先考虑只插一个寄存器的情况：应该插在哪里？答案是 C 和 D 之间，因为要让两边尽可能均衡。其实无论插几个，核心逻辑都是保证每个阶段的时间尽可能平均；否则瓶颈会落在更大的阶段上，整个吞吐率就会降低。这个问题可以自己回去看，例如要达到最高吞吐率，最少要分成五级。

### 流水线深度的限制

**02:26**

这里还有一个限制：流水线级数不能无限制增加。看起来级数越深，吞吐率可能越高，但最终会受到一个最基本的开销限制。不同阶段之间要设置级间寄存器，保存中间结果，这是一项固定开销。深度特别深时，真正执行有效工作的时间切片越来越小，图中代表有效工作的蓝色部分越来越小，而代表固定开销的红色部分宽度不变，于是额外开销的占比越来越大，很多时间浪费在保存中间值上，反而得不偿失。因此现代流水线不会只有五级，但也不会做到一百级，通常在十级、二十级这样的深度。设计流水线 CPU 时，把流水线思想用到 CPU 的设计和执行中，CPU 就可以跑得更快。

### 数据冒险

**04:10**

流水线会引入新的问题，第一个叫 data hazard，即数据冲突或数据冒险。看一个例子：有两条指令，第一条做整数乘法，结果写到 ECX；第二条把 ECX 的值作为一个加法操作数，加到 R9D 中。下面看这两条指令在流水线 CPU 中执行时会发生什么。

**05:07**

现在采用的是五级流水线。第一条乘法指令在第一个时钟周期取指，第二个时钟周期译码，第三个时钟周期进入执行阶段，即 execute，开始真正计算乘法。第二条 add 指令也按流水线方式执行：第一条指令离开取指阶段后，它就可以进入取指。因此第一个时钟周期取指还被乘法指令占用，add 指令进不来；到第二个时钟周期，add 指令就可以进入取指阶段，随后进入译码。

当乘法指令执行到第三个时钟周期时，它处于流水线第三级 execute，正在计算这个乘法。假设它算出 \(3 \times 4 = 12\)，也就是 ECX 的值本应被更新为 12。但此时 ECX 寄存器里真正的值仍是之前的 4。原因是乘法指令要到最后写回阶段，才会把算出的 12 写回 ECX；在执行阶段结束时，12 只会先保存到流水线中间的临时寄存器或临时存储中。

对单条指令来说，这没有问题：晚一点写回就晚一点写回。但看下一条 add 指令：在第三个 CPU 时钟周期，它处在流水线的第二个阶段 decode。译码阶段要查看这条指令访问哪些寄存器，并把寄存器的值读出来。此时它发现要读 ECX 和 R9D，于是去读 ECX，但读到的是旧值 4，因为 ECX 的新值 12 还没有被写回。接下来继续执行时，add 指令就会用这个旧值参与运算。

### 数据依赖与写回错误

**08:00**

当两条指令存在数据依赖时，流水线并不一定每次都会出问题；但一旦依赖发生，而前一条指令的结果还没有及时写回，后一条指令就可能读到旧值。这样最后写回的结果就不对了。

### 直接使用新值

**08:28**

如果真按上面的方式计算，就会出现问题。有什么方法可以解决？有同学提出“预测”。老师追问怎么预测，随后指出，这里更准确地说不是预测，而是直接用：CPU 确实知道当前要读 `ECX`，也知道前面有一条指令更新了 `ECX`，只是它的值还没有真正写回。这个判断不需要凭感觉。CPU 知道有一条指令更新了 `ECX` 但尚未写回，同时知道当前又需要读新的 `ECX` 值；如果直接去读，读到的必定是旧值，因此必须想办法读到新值。

### 停顿并插入 bubble

**09:35**

于是设计了一个最简单的办法：先等一等，暂时不要读。比如 `add` 指令在第三个周期本来很着急地想去读 `ECX`，但此时已经知道它还不能读，读到的只会是旧值，于是让这条指令在这里等待，让流水线停顿（stall），后面的指令先不要进入。下一条指令再等待一次，同时在停顿处加入 bubble 操作。

当乘法指令进入下一级时，当前的 `add` 还占着这一级，因此在执行（execute）级插入一个 bubble，相当于什么都不做，也就是一条 `nop` 指令。这样流水线仍能正常运转，但当前这条要读 `ECX` 的 `add` 不会读到旧值。它可以一直等到前面更新 `ECX` 的指令真正写回，中间不再存在尚未落定的中间值；等到所依赖的指令已经写回，`add` 才能继续往下执行。

这时再读 `ECX`，读到的就一定正确。不停顿、继续加 bubble，直到 CPU 确认前一条指令已经真正更新了 `ECX`。这是流水线 CPU 解决这类冲突、这类冒险最基本的一种做法。

### 停顿的代价与数据转发的引入

**12:08**

这种做法有一个很直观的问题：既然已经知道前面那条指令要更新的值是什么，甚至已经算出新值是 12，为什么一定要等到它写回？等待写回并非不行，但会让流水线的很多阶段空转，削弱流水线的优势。

如果一直停下去，乘法指令继续往后做，`add` 指令一直等到写回结束，它的译码（decode）阶段要等到写回之后的周期才真正执行，中间会出现大量 bubble；而且这条指令没有执行时，流水线里其他后续指令也都只能等着。

因此有了新的优化：做数据转发（data forwarding），为流水线增加一条数据通路。

### 数据转发通路

**13:27**

仍然看前面的例子。当乘法指令执行到某个阶段时，它其实已经知道新的 `ECX` 值。此时直接把这个值转发到 `add` 指令的执行（EX）阶段，通过一条数据通路送到该阶段。这样到第四个周期，两条指令都可以同时继续往下做。

乘法指令可以继续做它的访存，与 `add` 无关；它在当前流水级产生的结果作为中间结果（intermediate result）放在流水线寄存器中，再传给 `add` 的下一级。`add` 的执行阶段直接使用转发过来的数据，而不使用从寄存器读出的旧值；它也知道自己刚才没有读出新的 `ECX`，下一次使用转发值即可。这里还会给出一个信号，表明应当采用转发数据。

这样，两条本来存在数据依赖的指令，通过转发就可以解决依赖。整个流水线不需要插入 bubble，也不需要停顿，可以保持满载状态正常向后推进。

### 访存带来的冒险

**14:57**

除了刚才的数据冒险，还有因访存带来的冒险（hazard）。看两条指令：前一条用 `RDI` 和 `R8×4` 计算出一个位置，应该是在访问一个数组，而且大概是一个 `int` 数组；第二条 `mov` 指令把这个内存地址中的值读入 `R10D`；下面一条乘法指令再把 `R10D` 乘上 `ECX`。

再看这两条指令在流水线中的情况：`mov` 指令经过取指、译码、执行，到第四个 CPU 时钟周期进入访存阶段；下面那条乘法指令在第四个 CPU 时钟周期处在流水线的执行（execute）阶段。

### 数据冒险：需要的是访存结果

**16:13**

执行阶段需要用到前面 load 指令要取的那个值。可是前面这条指令在第三阶段执行时，算出来的是地址，而不是该地址中的内容。刚才增加的数据转发可以把执行阶段的结果直接转发过来，但这里转发一个地址没有用；需要的是访存得到的值。因此要等到访存结束，并建立一条从访存阶段到执行阶段的转发。这个转发在当前时序下无法直接做到：前一条指令已经执行到第四个时钟周期，而后面这条指令在第四个时钟周期开始处就需要这个值，再想从访存阶段转发，相当于要求时间倒流，来不及。数据转发只能从前往后，不能从后往前。

所以这种 load-use 数据冒险不能只靠转发解决。回到最简单的方法：等待。访存结果还没出来时，让 EX 阶段无法执行，在流水线中插入一个 bubble；等到访存结束、需要的内容出来后，再转发过去。

### 控制冒险与停顿

**18:16**

数据冒险解决之后，还有控制冒险（control hazard）。CPU 是流水线，每个周期第一阶段都是 fetch；为了让流水线不空，它必须一直取指令。遇到跳转指令时，流水线就困难了。例如比较 EDX 和 EAX，如果 EDX 比 EAX 小，就跳到 L3，否则执行 mov。CPU 取到 jl L3 这条指令后，流水线仍会继续往下走；但当 jl 指令执行到译码阶段时，又要取下一条指令。没有分支时，前一条取完后 PC 加几就能取下一条；现在不是简单的 PC 加几，而要等 jl 执行完，给出 jump 或 not jump 的结果。此时 CPU 不知道下一条是执行 mov 还是跳到 L3，也就不知道该取哪条指令，这就是控制冒险。

解决方法也可以和前面一样：stall。找一种放之四海而皆准的方法，就是一直停、一直等，等前面都做完。这样流水线变成摆设，虽然肯定可行，但程序中有很多分支跳转指令，如果每次都等，性能代价很大。也可以插 bubble，但能不能不等？如果不等待，才有后面的分支预测。

### 分支预测

**21:07**

CPU 设计了一种预测（prediction）机制：看到分支时先猜。分支只有跳和不跳两种选择，就像判断题或选择题；现在有些很流行的轻量模型擅长做这种判断，执行很快，可以用来做决定。CPU 也一样：每次看到 jump 指令，不等待，直接猜跳或不跳，并按照猜的那条路径继续取指令、往下执行。

猜对时结果很好：流水线不需要等，提前执行的指令本来就是应该执行的，能带来性能收益。猜错就比较麻烦：流水线里有一些不应该执行的指令，需要清理流水线，把这些已经进入流水线的指令清除掉；如果它们已经产生影响，也要清掉。

猜对时不用管；例如 jl 指令执行到某个阶段时，已经知道跳或不跳，也就知道猜得对不对，猜对就继续往下走。猜错时，下一阶段要从正确的位置开始取指，因为此时已经知道正确的 PC 在哪里；中间已经在做的指令直接插成 bubble，不再往后推进，中间结果也作废。原因是这些指令根本没有执行到 MEM 阶段和写回（write back）阶段，不会对 memory 和 register 产生影响。

### 分支预测失败的处理与代价

**24:24**

只有访存阶段（MEM）才会真正对内存产生影响，也就是写内存；只有写回阶段（WB）才会真正把结果更新回寄存器。因此，分支预测猜错后，可以直接把流水线中已经在执行的指令作废。它们的中间结果无非存在临时寄存器里，并不重要；插成 bubble 之后，后面也不会再用到。

这就是分支预测。分支预测失败其实没有太大代价：你等着也是等着，与其空着，不如猜一把。猜对了就赚到了；猜错了看起来也没有什么太大影响。但这里也引出一个问题。

### 用 perf 观察分支预测

**25:07**

CPU 到底猜得准不准？CPU 凭什么能猜？它是怎么判断这次跳还是不跳的？这里还有一个例子没加，需要加一个 perf 的例子。

大家回去可以给大模型一个 prompt，大概可以这样写：针对 PPT 第 64 页，帮我写两段代码，然后用 perf 查看当前 CPU 的跳转成功率；两个 case 要分别体现出它猜得很准和猜得不太准的情况。可以看看大模型会生成什么样的程序，它也会告诉你用什么方法，并直接给出 branch prediction 的 miss rate。

那么，它的核心逻辑是什么？

### 预测策略：总是预测跳转

**26:17**

如果让你来做这件事，你会怎么猜？假设你进入 CPU，每次遇到跳转，它都问你往哪跑，你会怎么做？一种直接的做法是永远预测跳转。这也是一种策略：成功率可能比较高，甚至能超过 50%。

想想程序中常见的分支是什么？是不是经常写的循环代码？对于循环，如果一直预测跳转，成功率如何？一个循环如果一共要猜一千次，每次都选跳，就能猜对九百九十九次，因为至少九百九十九次分支是要跳回去的。

### 基于 PC 历史的分支预测

**27:35**

所以 CPU 分支预测器中的做法没有这么简单，但也没有那么复杂。它的基本逻辑是记录当前 PC 对应的分支历史。CPU 并没有高级语言的语义，它只能根据当前 PC 的情况，记录这个 PC 上的分支以前是经常 taken 还是经常 not taken。下一次再遇到同一个 PC 时，就可以根据历史信息判断：如果以前经常 taken，就预测这次也跳转。

硬件内部实现 branch prediction 不能设计得很复杂，否则 instruction fetch 阶段的时间会变长。复杂预测可能更准，但代价是预测耗时增加、硬件部件更复杂、需要记录更多信息。因此一般用很简单的策略来判断。

### 流水线、冒险与减少 bubble

**28:59**

这就是 pipeline 思想在 CPU 中的一个体现：怎样用流水线思想设计更高效的 CPU。流水线又会因为具体问题引入冲突。

由于 data hazard 和 control hazard 的引入，会产生冲突。可以用插 bubble 的方式解决，但插 bubble 又会降低流水线效率，所以还要用其他方法尽可能减少 bubble、提升整体吞吐率。这里减少 bubble 的方法就是 data forwarding 加 branch prediction，分别解决 data hazard 和 control hazard。

现在 CPU 还有什么技术可以进一步提升性能，让 CPU 跑得更快？我们永远希望 CPU 越快越好。

### 乱序执行（OOO）的动机

**30:07**

下面介绍乱序执行，out-of-order，简称 OOO。这是现代 CPU 常用的技术。

它要处理的是这样一种情况：读内存，或者说访存阶段的速度比较慢。通常访存确实比较慢。比如加减法可以在一个 CPU 周期内完成；前面的假设是每一级流水线都能在同一个 cycle 内完成。真实 CPU 肯定更复杂：做加法一个周期可以完成，但访问内存可能没有那么快。

在这种情况下，可能就要执行访存操作。访存时要一直等到写回，后面的指令要等 forwarding 之后才能继续往下走。于是 CPU 里还是会有很多停顿（stall），还是会有很多 bubble。此时有些部件其实是空闲的。

后面有 dependency 的指令都不能执行，只能在那里等着；唯一真正工作的部件是访存阶段。后面的取指、译码等部件其实没在干活，在一些等待周期里，有些硬件是空闲的。那么，有没有办法让这些空闲的部件不要空闲？

### 乱序执行的动机

**32:31**

让这些空闲的部件也充分工作起来。于是 CPU 又设计了一个机制：更后面的指令也可以拿过来执行，不必干等。如果后面的指令与前一条没有依赖关系，就把它拉进来执行；也就是说，可以把更后面的指令提到前面来执行，不用在那里等待。

**33:01**

以刚才那五条指令为例。前面两条指令确实存在依赖关系：要把 r11 从内存中读出来之后，才能去做乘法；而第三条 add 指令又和这个乘法相关，所以前面三条指令确实彼此相关。但后面那些指令和它们其实没有关系——我要加的只是 EX 这个值，为什么也要排在后面一起等？从人的直观理解出发，一条指令接一条指令往下执行比较容易理解，但硬件其实可以干更多的事：让这条指令先执行，而不让它排队。

### 乱序执行（out-of-order execution）

**34:04**

这就是乱序执行的核心思想：只要译码之后的指令，其操作数已经就绪，就完全可以执行。这条指令译码之后要读的寄存器是 EX，它并不依赖前面的指令，直接读进来就可以去做真正的加法、进入 execute 阶段。所以 add 指令真的可以先于本来排在它前面的指令执行，这就是所谓的 out-of-order execution。前面两条指令因为有 data dependency 在等待，而它不管这些，直接往前执行，先把活干完。

### 顺序提交（in-order retirement）

**35:04**

执行完之后，它不能真的直接写回，还要等一等。这段等待时间是指令自己在等——它的计算其实已经完成、已经 OK 了，但要等到前面的指令都经过写回阶段，它才做写回。所以这叫做 out-of-order execution, in-order retirement：指令可以提前把该干的活干完，最大化资源利用率，但逻辑上指令要按顺序往下执行，不能真的把一条指令往前挪，否则语义就不对了，与上层的语义也对不上。真正提交结果时是按顺序的指令退休，只保证最终对外可见的 update 是按序提交的即可。所以在写回处有这样一个等待过程。这样一来，CPU 执行指令的顺序已经不是我们看到的顺序，它可以乱序执行，但最后通过按序提交保证程序结果不变；如果有依赖，这个 dependency 依然会被保护：寄存器更新仍然是前面的指令先更新、后面的指令后更新。这就是三个 O 所代表的含义。

### 超标量（superscalar）

**36:53**

除了这三个 O 之外，还有一个技术叫做 superscalar，中文叫超标量。前面说的五级流水线有五级，每一级的流水线部件可以在物理上再复制一份：把取指部件再复制一份，不就可以同时取两条指令了吗？执行 EX 的部件也可以多复制几份。硬件上有了多份功能部件之后，每个周期开始的时候就可以执行多条指令，而不是像之前的五级流水线那样每个时钟周期只发射一条指令。现在一个时钟周期开始的时候可以有多条指令被发射，同时发射多条指令，所以每个时钟周期可以完成的指令数可以大于 1。这就是超标量的好处。

### 超线程（hyper-threading）

**38:17**

一个线程通常用不满这些超标量的执行部件。所以大家去看 CPU 的配置、看硬件参数的时候，会发现除了核心数之外，还有一个参数叫超线程。比如核心数是 32，超线程可以到 64，也就是一个核上面看起来变成了两个核。这是因为有了超标量的设计之后，这些部件其实有一些冗余，可以让上层软件、让操作系统看起来这个核里面有两个核一样，从而支持更大的并发。这就是所谓的 hyper-threading 技术。

**39:34**

这部分稍微有点扩展，今天的时间已经不够了，就留给大家自己下去看：超线程到底是个什么东西，这里面有一些比较有意思的点。作为扩展知识，就是 superscalar、hyper-threading 和 multicore、multithreading 这几个概念。

### 分支预测与访存依赖

**43:56**

这里提到分支预测猜错的概率只有百分之零点四。预测是否准确，与程序本身的行为有关：如果程序比较好预测，像刚才那个非常简单的例子，就容易预测准确；如果程序完全没有规律，就可能出现 miss，或者需要刻意构造。

这里两条指令之间存在依赖，所以先进行一次访存。访存之后，结果会放到寄存器中；后面只有在这个位置写，才会释放相应内容。这两次访存不会干扰原来的部分，因为这里确实要写回。寄存器的值取决于指令的先后关系；这条指令在后面，所以最后写回也没问题，只要等前面的指令先更新完。

### 并发访存

**45:33**

讨论聚焦于几条指令访问同一地址时会不会互相干扰。老师指出，这些操作与它是否访存没有关系；真正要判断的是它们是否访问同一个地址。流水线各级之间有流水寄存器；访存会写入 memory，从 memory 读出的数据会放到寄存器里。

有同学问：后面的读操作会不会把前面读到的值覆盖掉？这里只有一份，是否会覆盖寄存器中的内容？老师回答，可以假设有多份中间结果；支持多少个并发访存阶段，就可以有多份结果在那里等待，这属于 CPU 内部设计。

### 指令访存与内存更新

**47:07**

老师强调，这个问题确实存在，但这里介绍的是一个硬件设计思想，不必抠具体微架构细节；知道微架构原理、能够自己分析即可。有同学问某条指令是否要拆成两个；老师回答不用，只有带内存操作的指令才会有访存阶段，带立即数的运算不需要。

关于这里的内存是否应该先更新，老师指出内存更新是实际可见的；具体有几种基本做法，接下来从第一种开始说明。

### 流水线中的 store 与地址依赖

**48:48**

如果是 store 阶段的内容，可以把它后续需要的延迟匹配到后面去。这里缓存能够提前进行，是因为它不需要保存。最简单的做法是把相关操作延迟到后面，并识别它是否依赖前面的指令。CPU 设计复杂时，可以判断当前地址是否会影响前面的指令：如果流水线中的指令都不涉及 store，那么就可以直接执行。

**49:31**

具体采用什么方式、细节如何，不必在这里展开；关键是能想到一个可行的方案。这并不需要外部监督：CPU 清楚当前有哪些指令正在执行，也清楚流水线中每条指令的状态。这些信息存在于流水线内部，并随着指令向后传递。

### 内存依赖与保守设计

**50:22**

依赖并不只取决于寄存器，也要看内存是否存在依赖；并不是完全不考虑内存依赖。假设由我们自己设计，可以取一种最保守的方式：把所有内存操作都视为存在依赖。这样，store 不能向前移动，后面只能安排普通计算指令。这一点本身就是一个顶层设计决策。
