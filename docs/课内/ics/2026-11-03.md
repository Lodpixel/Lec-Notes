## 计算机系统基础（1）｜第 3 节（09:55）

### 从 CPU 到缓存

**04:22**

同学们好，我们开始今天的课。上次已经讲完了 CPU。我们讲了 CPU 的五阶段设计，以及它怎样统一指令的执行；也讲了怎样提高 CPU 的执行效率。我们想到了一些方法：用流水线思想提高 CPU 的吞吐率，用超标量（superscalar）方法进一步提高指令吞吐，使同一个周期内可以发射更多指令；还介绍了基于超标量实现超线程（hyper-threading），充分利用 CPU 内部各个空闲部件，提升整个系统的性能。

今天要介绍一个新的主题——cache 缓存。缓存大家应该不陌生，平时使用计算机时经常能看到。大家印象比较深的有哪些？

### 缓存命中与大模型 KV cache

**06:54**

有同学提到缓存命中、缓存未命中。比如调用大模型时，系统会保存 KV cache：如果之前已经问过相同的 prompt，prompt 内容一致，就可以不再重新推理，而是把之前的结果缓存下来，从而更快返回结果，成本也更低；命中缓存时，token 费用也会更低。

今天也会像之前讲 pipeline 一样，用一个经典系统中的 cache 设计，说明设计缓存时需要考虑哪些事情。后面也会结合 cache 的基础设施，看看 cache 是怎样设计的。缓存有软件层面的实现。

### Cache 的通用思想

**08:07**

cache 既有软件实现的，也有硬件实现的，它本身是一个通用的思想。除了大模型推理中会用到 cache，游戏里也会缓存资源：把游戏资源缓存起来之后，打开游戏的速度可以更快。这也是由软件维护的缓存。除此之外，交大之前有一个影视资源站点，大家可能用过“葡萄”。我主要在上面看《冰与火之歌》，每周出一集，不必第一个去下载；通常有人下完之后，后续下载就可以很快，因为有些资源会被缓存到服务器上，大家再去下载时速度就更快。这就是网络中的 cache。

如果每次都从远程机器、离我们很远的机器拉取数据，传输距离很长，中间要经过很多跳，也可能出现网络中断的情况。因此，如果一个资源会被很多人重复使用，就可以先把它拉回交大，缓存到交大的服务器；之后交大同学下载时只要从本地服务器取，速度就快。这些都是 cache 的思路。

### 矩阵求和：按行与按列

**10:09**

先看一个矩阵求和的例子：对一个 \(n \times n\) 的 int 矩阵求和。一个函数按行求和，外层遍历每一行，内层遍历该行中的每个元素并累加；另一个函数按列求和，外层遍历每一列，内层遍历该列中的每个元素并累加。图中颜色越浅表示越早访问，按行求和时最后一个元素最后访问，按列求和则先访问一列再访问下一列。两个函数代码长度几乎一样，操作元素数量都是 \(n^2\)，两层循环的时间复杂度都是 \(O(n^2)\)，读取的数组内容也完全一样。

**11:47**

既然这样，两个函数的运行时间会有差异吗？可以用之前讲过的计时函数实际测量。有同学判断会有差异，并估计大约二十倍；按行求和更快，按列求和更慢。为什么会有这样的差距？接下来看实际测试。

**13:00**

测试方法是：每次调用函数前记录开始时间，结束后记录结束时间，两者相减得到该次运行时间；每个函数跑三次，取最快的一次。代码本身很简单，计时实现通过系统调用获取时间。实际运行结果与前面估计接近：在 Intel x86 机器上，按行和按列约为 0.41 和 7.44；在我这台 Mac M2 的 ARM 处理器上约为 0.37 和 9.98。不同平台会有差距，但倍数仍然明显。

### 从算法复杂度到访存模式

**14:30**

实际测下来，两种写法的差距可以达到数倍，但没有二十到三十倍那么夸张，而且与矩阵规模有关。两个函数的时间复杂度完全一样，都是 \(O(n^2)\)。如果只按算法复杂度推断，它们应当相同；实际差距来自缓存访问模式，也就是数据在内存中的访问顺序。

### 数组的行序存储

**15:21**

\(n \times n\) 数组在内存中按行序存放，每一行的数据相邻，整体是连续的一段。把内存看成按字节寻址的大数组，一个 \(4 \times 4\) 的 int 数组有 16 个元素，在内存中就是第一个到第十六个元素连续排布：先是第 0 行的四个元素，接着第 1 行、第 2 行、第 3 行。按行访问时，每次访问的下一个元素就是内存中相邻的元素。

### 二维数组的访问顺序

**16:25**

每次访问下一个元素，步长就是相邻元素地址之间的差距。如果从 0 地址开始看，这个二维数组按行访问时，偏移量依次是 0、4、8……，因为每个元素是 int，占 4 个字节。

从访问顺序的可视化看，最浅的颜色表示最早访问，最深的颜色表示最后访问。按行访问时，颜色由浅到深逐渐变化，说明时间上相邻的两次访问，其地址也相邻。

按列访问同样访问 16 次，数组元素仍然从 1 到 16 排布，但访问顺序变成 1、5、9、13，先访问 1，再访问 5、9、13。它是跳着访问的。从整个内存布局看，这种访问不连续，颜色的变化也不像按行访问那样规律。

那么这会带来什么区别？为什么跳着访问会比连续访问慢？

### 缓存的作用

**18:18**

真正访问内存时，内存是字节可寻址的：任何一个字节都可以直接访问，访问中间任何一个字节本身没有性能差异。内存给我们的抽象就是一个扁平的大数组，所以访问第 0 个字节和访问第 100 个字节没有区别。

性能差距来自 CPU 和内存之间的另一个部件——缓存。为什么会有缓存？因为写程序时，程序通常具有空间局部性：访问一个内存位置之后，大概率会在相近时间内访问它附近的数据。

### 空间局部性的来源

**19:10**

CPU 因此做了一件事：真正去内存里取一个数据时，不只为这一个数据，而是把相邻的一大块数据一起搬到 CPU 的缓存里。它猜测程序接下来会访问相邻数据，所以下一次访问这些数据时就不必再去内存搬，而可以在刚读入的缓存中找到。

这里的思想很多。先讨论：为什么一个程序会有空间局部性？通常怎么体现？

### 程序中的空间局部性

**20:32**

大家之前可能做过拆炸弹实验，有些同学已经拆过；上课带大家拆炸弹时，我们会看一个程序的执行。程序执行过程中的访存有两种情况。第一种是执行 load、store 这类指令时访问数据。第二种是在做 instruction fetch 时也要访存。取指令时 PC 是怎么更新的？每条指令执行后 PC 都会更新，其特点通常是连续往下执行。假设是 RISC 指令集，并且没有 branch 指令，PC 每次加 4。

所以一段程序代码实际上是一条一条连续往后执行的。执行到一条指令时，通常会继续执行下面的指令，这是大多数情况。也就是说，当程序访问到某个指令所在的位置后，接下来很可能访问与它相邻的下面这些指令。一个函数往下执行，程序通常都是按从上往下的顺序执行，这是第一种情况。

第二种情况是访问数组。例如循环中 i 从 0 到 n，数组元素也是顺序往后访问。因此，无论是对 instruction 的访问，还是对 data 的访问，程序都具有局部性，会访问相邻的数据。

### 缓存行与数组访问

**22:51**

例如要访问 W[0][0] 这个元素时，CPU 第一次读它，初始状态下缓存是空的，所以只能从内存读。从内存读的时候并不是只读这一个元素，而是按一个缓存行的大小，把这一整块数据一起读到缓存里。之后再读 W[0][0] 就可以直接从缓存读。

这样做的好处是：由于存在局部性，程序后面大概率会接着访问 W[0][1]、W[0][2]，于是后面这些数据访问都不需要再去内存里找，直接从缓存读即可。缓存利用空间局部性的特点，减少了对较慢存储的访问。

所以，CPU 和内存之间多了一块缓存。按行加和与按列加和之所以有性能差距，并不是因为访问内存时地址随机化会造成区别，而是因为中间这块缓存起了作用。

### 缓存的访问速度与按块搬运

**24:42**

缓存是 CPU 内部的一个部件，因此真正访问它时会更快。访问缓存与访问内存的时间差大约在十纳秒这个数量级：在现代 CPU 上，缓存访问大约是 1 到 10 纳秒，而内存访问从百纳秒起，二者大约相差一个数量级，这就是性能差距。

数据搬运以数据块为单位，每次访问一个数据块。现代 CPU 通常一次搬 64 字节，甚至 128 字节，这么多数据一次性从内存搬到缓存。因此缓存的一个特点是按块取入：即使内存按字节（byte）寻址，最少可以访问一个 byte、一个字符或一个 char，哪怕只访问一个字节，实际上也会从内存一次性搬一个整块过来。

### 缓存的容量、放置与替换

**25:53**

这就是按块工作的缓存。这样相邻字节会被预取到缓存中。缓存还有一个放置策略。缓存的空间大小也有上限。内存通常有十几 GB、几十 GB，不可能在 CPU 里设计同样大的缓存。现在 CPU 缓存通常为几 MB 到几十 MB，这是桌面级的情况；服务器 CPU 的缓存会更大，通常有几百 MB。但无论多大，缓存行的数量一定有限。

因此有放置策略：从内存把一个数据块搬进来时，究竟放在哪里。有放置策略也意味着有替换策略。例如缓存一共只能放下四个数据块；当取第五个数据块时放不下，就必须驱逐一个，也就是替换掉原来的一个块，这叫作替换策略，决定应该驱逐哪一个块。内存容量远远大于缓存，不可能在 CPU 内部设计一个能缓存所有内存数据的高速缓存。因此就会有缓存命中与缓存不命中。

### 缓存命中与不命中

**27:34**

只要是缓存都会涉及命中和不命中。这和大模型里的缓存命中、不命中不是同一回事，但概念上比较类似。所谓 hit，是 CPU 访问一个内存地址时，数据已经在 CPU 内部的 cache 中，这就是 cache hit；反之，如果这个块不在 cache 中，还必须访问内存，就是 cache miss。

发生 miss 时，还要把这个地址发到内存，让内存把数据取回来；先把整个块取回缓存，再从缓存里取出真正需要的那几个字节，比如要拿 8 个字节，就再访问这 8 个字节。有了这些背景，再看按行访问时 cache hit 和 cache miss 的情况。现在换成一个比较简单的例子。

### 4×4 数组的缓存示例

**28:41**

刚才的数组是 \(4096 \times 4096\)，太大了，画不下；现在画一个 \(4 \times 4\) 的数组，一共只有 16 个元素。假设 CPU 的缓存一共只能放下两个块，即块 0 和块 1；每个块正好能放下四个 int，也就是四个数组元素。

它有一个放置策略：取一个 cache line 回来时，从内存进入缓存可以随机放置，只要找到一个空位放进去即可。缓存满时，替换策略是驱逐最久没有被使用的块。

### 按行访问

**29:37**

现在按行访问，按照行的顺序依次访问。第一次读取时会出现 miss，因为第一次读时缓存里什么也没有，两个块都是空的。CPU 因为要读 \(w_{00}\)，所以从内存把数据搬回来；搬运时按一个 block 进行。这里的 cache line 大小正好是四个 int，所以一次搬四个 int 回来，正好把第一行 \(w_0\) 搬回来。

第一次访问 \(w_{00}\) 是 cache miss；第二次访问 \(w_{01}\) 时，发现 \(w_{01}\) 已经在 cache 里找到了，因为之前已经把整行搬进来了，所以第二次是 cache hit。第三次访问 \(w_{02}\) 时依然是 hit，因为数据还在这里；访问 \(w_{03}\) 时也是 hit。因此，访问第一行这些元素时，只有第一次发生 cache miss，之后三次连续访问都因为空间局部性而命中。这三次命中意味着每次只需要约十纳秒就能访问到数据；否则每次都要花约一百纳秒到内存访问。

按行访问到 \(w_{10}\) 时，又发生 cache miss，因为它不在缓存里。CPU 又去内存找数据，访问 \(w_{10}\)，于是把 \(w_{10}\) 所在的这一行整个搬到 cache line 里；这一次依然是 miss。后面的 \(w_{11}\)、\(w_{12}\)、\(w_{13}\) 又连续三次 hit。因此每次访问一行时，四次读取只有一次 miss，miss rate 很低，为 25%；剩下 75% 都是 cache hit。

### 按列访问

**32:16**

反过来看按列访问的情况。按列访问时，先访问 \(w_{00}\)，再访问 \(w_{10}\)，然后继续向下。访问 \(w_{00}\) 时依然和刚才一样，第一次访问自然发生 cache miss。发生 cache miss 时，缓存仍会按照固定方式把相邻数据取到缓存中，因此它还是缓存了一整行数据。接下来要访问的就是 \(w_{10}\)。

### 按列访问与缓存替换

**32:44**

接着看按列访问。访问 \(w_{00}\) 时第一次自然是 cache miss；之后访问 \(w_{10}\)，cache 里仍没有对应行，所以仍然 miss，于是把 \(w_{10}\) 这一行放入另一个空闲的 cache line。这样 cache 中两个 cache line 都被占用了。下一次按列访问 \(w_{20}\)，它不在已缓存的两行中，仍然 miss。此时要把 \(w_{20}\) 所在行放入 cache，就需要做一次 eviction，因为两个 cache line 都已被占用。按照前面约定的最久未使用策略，被驱逐的是更早由 \(w_{00}\) 装入的那一行；由 \(w_{10}\) 装入的那一行是更近使用的，因此保留。替换之后，再访问 \(w_{30}\) 仍然 miss，又会把相应的行替换掉。继续访问 \(w_{01}\) 时，cache 中当前是另外两行数据，因此仍会继续 miss。

**34:30**

因此，按列访问对这个 cache 的利用非常糟糕。cache 的一个基本假设是会访问连续的数据，所以每次装入的是相邻地址的数据；而按列访问是跳着地址访问的。于是在当前这个例子里，访问所有元素时都会 miss，cache 没有起到作用，每次访存都需要从内存里取数据，自然带来较大的性能差距。访问 cache 和访问内存的延迟大约差十倍：一个在十纳秒量级，一个在百纳秒量级，因此整个程序可能差一个数量级。也就是说，两个程序的时间复杂度看起来都是 \(O(N^2)\)，但实际运行效率仍可能相差一个数量级。通过这个例子，我们看到 CPU 和内存之间确实存在 cache。

### 缓存结构

**35:58**

接下来看 cache 的结构。设计 cache 时要决定：哪些内存数据映射到哪个 cache line。先看一个比较简单的设计，其中常用符号如下：cache 由 \(S\) 个组构成；每个组有 \(E\) 行 cache line；每一行保存一个大小为 \(B\) 字节的块。每一行还包括一个 \(t\) 位的 tag 和一个 1 位的 valid bit。valid bit 表示这一行是空的，还是实际存放了有效数据；tag 用来与内存地址中的相应部分比较。于是 cache 的容量为 \(C = S \times E \times B\)。这里 \(S\) 个组意味着需要用若干位来表示组索引，具体位数由 \(S\) 决定，即 \(\log_2 S\)。

**37:52**

访问内存时，CPU 给出一个内存地址；这个地址对应的数据或块如何搬到 cache 中，需要有映射规则。唯一可以用来做映射的信息就是地址，因此可以认为 cache 做了一个哈希映射，哈希的 key 就是内存地址。CPU 访问内存时，能用来查找 cache line 的唯一信息也就是地址。

### 地址划分

**38:34**

cache 把地址切成三个部分。最低的部分是块内偏移，因为一个 cache line 中有若干字节，例如 8 个字节 \(b_0\) 到 \(b_7\)。若块大小为 8 字节，则块内偏移需要 \(\log_2 8 = 3\) 位。第二部分是组索引，表示这个地址应该放到 cache 的哪个组中；组索引的位数由组数 \(S\) 决定，即 \(\log_2 S\) 位。地址中剩下的部分称为 tag。tag 会与 cache line 中保存的 tag 比较；如果匹配，并且该行的 valid bit 有效，就说明这个 cache line 保存的正是该地址对应的内容。当 \(E>1\) 时，一个组内有多行，具体放到组内哪一行并不由地址中的某一位决定，可以放入空闲行，或按替换策略选择。因此，地址字段由 \(t\) 位 tag、\(s\) 位组索引和 \(b\) 位块内偏移组成。

### 直接映射缓存

**40:33**

缓存有几种不同的设计模式，这与 \(E\) 和 \(S\) 的选择相关。第一种叫直接映射缓存，即每一组里面只有一行。

### 直接映射缓存与地址划分

**40:53**

直接映射缓存中，每组只有一行，即 \(e=1\)。例如当前缓存有 \(s=4\) 个组，每组一行，块大小 \(B=2\) 字节；为便于说明，假设内存地址只有 4 位，实际地址当然不止 4 位。块大小是 2 字节，所以块内偏移需要 1 位；有 4 组，所以组索引需要 2 位；4 位地址中剩下的 1 位就是 tag。因此块 0 和块 4 的组索引都为 00，会映射到同一组；块 1 和块 5 的组索引都为 01，也会映射到同一组。

### 地址 13 的拆分

**42:53**

以地址 13 为例，它的 4 位二进制表示是 1101。按照 tag、组索引、块偏移的顺序拆分：最高位 tag 是 1，中间两位组索引是 10，最后一位块偏移是 1。也就是说，它属于组索引 2，块内偏移为 1，tag 为 1。

### 缓存访问的三个步骤

**43:32**

访问地址 13 对应的字节时，分三步。第一步是组选择：用组索引 10 找到第 2 组。第二步是行匹配：直接映射中每组只有一行，只需检查这一行的有效位是否为 1，以及该行的 tag 是否等于地址中的 tag。这里有效位为 1，tag 也为 1，二者匹配，所以是 cache hit；如果有效位为 0 或 tag 不匹配，就是 cache miss。第三步是取数据：因为块内偏移为 1，所以取该块中偏移为 1 的字节，也就是地址 13 对应的数据。

### 直接映射缓存练习

**45:07**

### 地址切分与组索引的选择

**50:14**

有两个问题。第一个问题是：CPU 在设计 cache 时到底做了什么？它这样切分地址：block size 确定了地址中块偏移有多少位，这一点没有什么可争辩的；最低几位表示在一个 block 内的偏移。中间的 \(s\) 位作为组索引（set index），剩下的高位作为 tag，用于匹配。也可以把这件事理解为把一个地址当成哈希的 key，理论上随便怎么切都可以。于是可以问：如果把高位当作 set index，把中间剩下的位当作 tag，可不可以？

可以，为什么不可以？只要在 cache 里找到一个 cache line 放进去就可以。块偏移只需要负责块内位置，每次不必关心别的块。用这种方式，给任何一个地址都一定能找到对应的 set index，也一定能找到位置放进去。这样放肯定是可以放的，但会不会有不好的地方？下面看看会有什么问题。

### 用中间位作组索引

**52:09**

先用刚才那个简单例子：地址只有 4 位。原来用中间位做 set index 时，从地址 0 到 7 的这些块会被比较均匀地划分到不同的 set。比如地址 0 落在第 0 组；地址 2 中间的 set index 是 \(01_2\)，落到第 1 组；地址 4 中间的两位是 \(10_2\)，落到第 2 组；地址 6 的二进制是 \(0110_2\)，中间的 set index 两位是 \(11_2\)，正好落到第 3 组。因此，用中间两位做 set index 时，连续的内存块会被均匀地划分到不同的 set。若数组正好有 7 个元素，这 7 个连续元素就可以完整地放进 cache。

### 改用高位作组索引

**53:39**

反过来，如果用高两位作为 set index，也完全可以这样设计；给定任何一个地址，一定能找到对应的 set index。但这时会出现什么情况？由于用高位做 set index，连续地址的 tag 部分会比较接近。因为连续地址的变化会先从低位开始：在同一个块内只有 offset 部分不同；跨到下一个块时，变化的是 tag 部分，而 set index 部分不会变。

**54:33**

看具体情况：地址 \(0000_2\) 取最高两位，仍然映射到第 0 组；地址 2 的二进制是 \(0010_2\)，最高两位仍然是 \(00_2\)，所以也放到第 0 组。两者的区别在于，连续的两个 memory block 最终会被映射到同一个 set，这样就会出现问题。

## 计算机系统基础（1）｜第 4 节（10:50）

### 组索引与直接映射的冲突

**00:00**

用中间位作为 set index，会把相邻的数据映射到不同的 cache line，也就是散落到不同的组中，从而提高 cache 的利用率。设计 cache 的一个基本假设是空间局部性：希望相邻数据能够完整地放入较大的 cache 中并得到充分利用。若相邻数据进入同一个组，就很难充分利用空间局部性，相邻数据只能占用 cache 的少数位置，很多 cache 空间用不上。

由此也能看出，set index 使用中间位而不是高位，是为了避免相邻数据挤在同一组。接着看直接映射中的第二个问题：找到一组之后，块 0 和块 4 会进入同一个组。例如地址 8 对应的块 4 会把地址 0 对应的块 0 挤掉，因为块 4 和块 0 的 set index 都是 00，这两个内存块都需要进入 cache 的第 0 组。映射位置发生冲突，两个块只能进来一个。

如果整个访问过程中只访问这两个块，cache 中还有很多空行，仍有另外三行是空的，利用率只有百分之二十五，只有一行在用。这是不希望出现的情况。要提高缓存行的利用率，如果做一个改动，有一种简单方式：采用全相联缓存。

### 全相联缓存的结构与查找

**02:32**

全相联（fully associative）缓存不再分组：只有一个组，所有 cache line 都可以随便放。一个 memory block 可以放进任何一个 cache line，因此块 4 和块 0 可以同时存在于 cache 中。它的优势是所有的空闲行都能被利用：读入一个新块时，只要有任意一行空闲，就不需要做替换。

在全相联缓存中，组数 \(S=1\)，每个组的行数 \(E\) 则变为 \(C/B\)，其中 \(C\) 是整个 cache 的大小，\(B\) 是一个 cache line（block）的大小。因为只有一个组，内存地址不需要组索引；地址中剩下的位都作为 tag。例如块大小为 2，块偏移只需 1 位，剩下的三位都是 tag。查找时也没有组选择过程，直接进行行匹配：把地址中的 tag 与每一行比较，若匹配，再检查有效位是否为 1；若为 1，就是 cache hit。命中后根据块偏移读出相应字节的数据。

全相联缓存的查找仍然是这三步，只是比较 tag 时必须把所有 cache line 都比一遍，因为不知道数据到底在哪一行，每一行都可能存着要访问的数据。找到匹配行后，再检查有效位是否为 1，就可以完成对全相联缓存的查找。

### 全相联的代价与指标比较

**06:07**

全相联缓存的优势是 cache 利用率很高，不会因为两个地址映射到同一个 set 而产生冲突。与直接映射相比，它的问题不在于 CPU 找不到，而在于找起来费劲：每一行都要比较一次 tag。对 CPU 来说，判断两个数是否相等很简单，但同时比较很多行仍是苦力活。直接映射只需要比较一个缓存行，因为 \(E=1\)；全相联则需要比较 \(E=C/B\) 行，这是两者最大的区别。

直接映射可能因为映射冲突产生较多 miss；全相联不会有冲突导致的 miss，只有容量不够、真的放不下时才会发生容量 miss。另一个指标是时延。直观地看，CPU 在 cache 中查找时，比较一行和比较例如 1024 行，显然比较一行的代价更低。

### 延迟与系统设计中的权衡

**08:08**

直接映射的代价更低。无论是硬件设计的复杂度，还是硬件真正执行时所花的时间，只有一行时都更简单，所以直接映射的 cache access latency 会更低，比全相联缓存低。做 CPU 与 cache 的系统设计时，需要比较不同的指标、不同的维度；系统设计中一个经典动作就是 trade-off，也就是平衡不同指标，例如优先吞吐量还是优先延迟。

### 流水线设计中的吞吐量与延迟

**08:54**

上一节学习 CPU pipeline 时，其实也做过权衡：流水线 CPU 设计提升了什么，又牺牲了什么？它提升的是 throughput，也就是单位时间内发射并完成的指令数；牺牲的是每条指令的 latency，单条指令的延迟反而增加了。这是经典的 latency 与 throughput 相互冲突的目标，如何做好平衡，是系统设计中的重要问题。当然，不同系统设计下需要平衡的目标和指标可能不同，但很多时候都要做好这种平衡。

### 组相联缓存

**09:53**

只有一行和只有一个组这两种设计显然都很极端，并不是最好的方案。于是自然的想法是做一个 balance：设计一种既有若干行、又有若干组的 cache。现代 CPU 通常采用的结构就是组相联缓存（set-associative cache），它正是 trade-off 之后得到的设计。设每组的行数为 \(E\)，则 \(E\) 大于 1，肯定不止一行；同时 \(E\) 小于 \(C/B\)，其中 \(C\) 是缓存总容量，\(B\) 是块大小。这样的结构都叫组相联缓存。

内存中的每个块仍然由组索引确定到一个组。确定到某个组之后，这个组里有若干行，不止一行；块可以放在这个组中的任意一行。访问时，只需要比较这个组内各行的 tag，确定目标块到底在不在这个组里。

例如块 0 和块 2：这个例子中 cache 只有两个组，所以组索引只有一位，块 0 和块 2 都被映射到组 0。但因为组 0 有两行，它们并不会冲突，可以同时存在、同时放在组 0 里。

### 组相联缓存的访问过程

**11:35**

下面看组相联缓存访问的三步。仍然读取地址 1001。这个 cache 有两个组，所以 set index 只有一位；每个 cache line 仍然是两个字节，意味着 block size 也占一位，所以小 \(b\) 和小 \(s\) 都是一位，最上面剩下的两位作为 tag。

访问地址 1001 时，先用组索引选择组。组索引取一位，这里是 0，所以找到第 0 个 set。接着做行匹配，看看这个地址的 tag。此例中两行的有效位都为 1，说明两行都 valid；于是同时比较两行的 tag 与目标地址的 tag。目标地址的 tag 是 10，第一行的 tag 与之相等，因此选中这一行。

最后用 block offset 确定访问 cache line 中的哪一个字节。这个 cache line 里存了两个字节，这里偏移为 1，所以访问对应的那个字节。这就是组相联缓存的访问过程。

### 两路组相联缓存的访问练习

**13:15**

再看一个小练习，和之前比较像。在一个两路组相联缓存下，访问序列 0、8、1、9、0、8。这个序列的特点是：地址 0 和地址 8 所在的 memory block 的 set index 相同。地址 0 的 set index 是 0；地址 8 二进制为 1000，它的组索引位也是 0，所以两者的组索引都是 0。不过因为现在是两路组相联缓存，它们可以共存。

访问 0 时自然还是 cache miss。miss 之后，会把包含地址 0 和地址 1 的 memory block 放到 cache line 中，这里放在第 0 行，于是地址 0 和地址 1 所在块的内容被装入。

下面访问 8：它是 cache miss 还是 hit？由于包含 8 和 9 的块还不在缓存中，所以是 miss。miss 之后，会把包含地址 8 和地址 9 的 memory block 放到组 0 的另一行；因为地址 8 的组索引也是 0。这一行的 tag 是 10，放入的是 memory 中的块 m8 和 m9。

然后再访问 1：hit，因为找到包含 0 和 1 的那一行。再访问 9：也是 hit，和前面一样。再访问 0：也是 hit，因为地址 0 依然存在；两条 cache line 同时存在于 set 0 中。最后访问 8：也是 hit。

所以在这个两路组相联缓存下，0、8、1、9、0、8 的访问结果是 miss、miss、hit、hit、hit、hit。

### 组相联中的替换问题

**16:10**

采用组相联缓存设计后，不会像直接映射那样因为地址冲突就产生缺失，两个行可以同时驻留在同一个组中，也能比较有效地利用缓存。这里会引出一个问题：现在一个组有两个缓存行，放两个行时它们可以相安无事；如果访问第三个地址，例如刚才把地址 0 和 8 放进这两行没有问题，现在又访问地址 16，它也会映射到组 0。刚才假设地址只有四位时不可能出现 16，这里只是用来说明还有第三行要进入这个组；这时就需要做替换。三行都想进入组 0，就必须选择替换哪一行。前面讨论的是放置（placement）策略，现在讨论的是驱逐（eviction）策略；它在组相联中存在，在全相联中也存在。

### 替换策略：随机、LRU 与 LFU

**17:53**

例如全相联缓存一共有 512 个行，当 512 个行全部填满后，要访问第 153 个数据块时，替换前 152 个行中的哪一个，就是替换策略要解决的问题。最简单的策略是随机（random），硬件实现很简单，随便选一个，或者轮着来：第一次替换第一个，下一次替换第二个。另一种策略是 LRU（least recently used，最近最少使用），把最久没有被访问的行换掉。还有一种策略是 LFU（least frequently used，最不频繁使用），把最不频繁访问的行换掉。例如在一个时间窗口内，有的行访问了 1000 次，有的行只访问了两次，就把只访问两次的行换掉；即使它最近访问过，但在这个时间片里访问得很少。

### 冷热数据与时间局部性

**18:57**

这就是 frequency，也就是访问频率；LRU 则依据最久没有被访问的时间。这些策略挺直观，本质上是在跟踪 cache line 的 hotness：哪个数据更热，历史上被更频繁访问，或者最近被更频繁访问。最近被访问过的数据，意味着在将来一段时间里依然可能被访问到，所以优先保留它们，把相反的冷数据（cold data）扔掉。这里利用了另一种局部性，叫时间局部性（temporal locality）。前面讲的空间局部性，是从 memory 往缓存拉数据时，一次把相邻数据全部搬进来：访问一个字节，也搬一个 cache line 大小的数据上来，例如 128 个字节。这里则利用程序的时间局部性：刚刚访问过的数据，在接下来一段时间大概率还会被访问，也就是会重复访问相同的数据，或者历史上这段时间里访问比较多的数据，在将来这段时间依然会被访问。替换策略实际上就是假设程序具有时间局部性，然后预测哪个数据是 hot、哪个数据是 cold。

### LRU 示例与实现问题

**20:45**

这里有一个例子：第一次把块 a 放进来，第一次使用是访问 a；第二次把块 b 放进来；下一次再访问 a 时命中；再下一次访问 c 时，就会把 b 替换掉，因为最近访问的是 a，所以替换 b。这就是 LRU 策略。

说起来简单，但怎么实现 LRU？怎么知道一个 cache line 到底什么时候被访问过，怎么记录它的访问时间？可以记录时间戳：现在是 11 点 12 分，就打一个时间戳；下一次挑访问时间最久、时间戳最旧的行替换掉。那又怎么记录 LFU 的频率？是每隔一个纳秒清零一次，还是每隔十个纳秒清零一次？然后统计这段时间内访问了几次。LRU 和 LFU 用软件、用高级语言实现可能没有那么难，但 CPU 里是硬件，硬件怎样表达这样的语义，大家可以作为课后思考。周六是上课的，希望大家周六好好思考。

### 三种映射方式的对比

**22:35**

现在对比三种模型，做个小结。第一种是直接映射。它的特点是 e 等于 1，只有一个条目（entry），每次定位到 set 后只要比较一个 tag，需要比较的缓存行比较少。第二种是全相联，是另一个极端：set 只有一个，所有缓存行都在一个组里，也就是 C/B 个行全在一个组，每次要比较的缓存行特别多，全部都得比一遍；但它的 miss rate 表现比较好。第三种是前面介绍的折中、平衡设计——组相联，也就是中庸之道。组相联中需要比较的缓存行数是 e，冲突相对少一些，但肯定不是最少；因为要比较的行数变少，硬件设计和缓存访问时间比全相联要好，但比不过直接映射，所以它是一个 balance 的设计。

### 按行与按列访问的 miss rate

**36:31**

先看按行访问。访问数组第一个元素 \(w_{00}\) 时一定 miss，因为初始 cache 是空的。发生 miss 后，会一次性把一个完整的 cache line，也就是一个 64 字节的 memory block 装入 cache。这 64 个字节是相邻的，从 \(w_{00}\) 开始，一共包含 16 个 int。也就是说，第一次 miss 实际读入了 \(w_{00}\) 到 \(w_{0,15}\)，接下来的 15 次访问都会 hit。这里相当于预取了连续地址上的数据。

到 \(w_{0,16}\) 时，cache 中匹配不上，又会发生一次 miss，并再次装入接下来的 64 字节，情况和刚才完全一样：一次 miss 后跟着 15 次 hit。整个求和过程中每个元素只访问一次，cache 的路数和组数也足够，不会产生 conflict，所以这个模式一直重复。按行访问的 miss rate 就是 \(1/16\)。

按列访问的 miss rate 是 \(100\%\)。原因和之前讲过的简单例子类似：可以自己把地址算出来，按照前面说的规则看它匹配到哪个 cache 行、哪一路，会发现每次访问都 miss，之前装入的块根本没有被后续访问用上。

### 缓存设计的权衡与系统思想

**39:03**

这节课核心讲了一件事：CPU 的 cache。但更希望大家掌握的是两个思路，而不是记住 cache 要切成几位、几位；地址如何划分，知道有这么回事即可。

第一个思路是系统设计中的 trade-off。缓存设计要权衡的指标包括 miss rate、hit latency 以及硬件复杂度。不同设计就是在这几个指标之间做平衡。实际 CPU 中组数 \(S\)、相联度 \(E\)、块大小 \(B\) 设成多少，都会影响这些指标。比如提高组相联度，可以减少 conflict 带来的 miss；增大块大小 \(B\)，在刚才按行访问的情况下，如果把块大小翻倍，就可以把 miss rate 从 \(1/16\) 降到 \(1/32\)。但代价是：如果搬上来的数据没有被使用，带宽就被白白浪费了。因此 \(B\) 的设计也是取舍。无论是 CPU 设计者还是系统软件设计者，都要理解并做好这种平衡。

第二个思路是，cache 本身就是一种很好的系统设计原则，在计算机系统中大量、广泛存在。比如课件下载到本地，磁盘里也缓存了远端服务器上的文件，这也是一种缓存；再比如 Ollama 装载模型的过程。

### 存储层次与缓存

**41:27**

模型权重先从磁盘加载到内存，再从内存搬到显存；后续请求可以复用第一次加载的模型参数，不必每次都重新从磁盘拉取。把数据从次级存储搬到更高级存储，这个更高级存储通常容量更小、访问速度更快，这就是存储层次。

最早接触的是寄存器：数据从内存搬到寄存器后访问很快，而且可以参与计算。在内存和 CPU 之间之所以还要加入缓存，是因为内存速度与计算速度差距太大。如果所有 load/store 都真的经过内存，CPU 主频做得再高也没用，瓶颈最终会落在内存搬运数据的通路上。硬件缓存可以更快地访问数据，但它有效的前提是程序具有局部性，即存在 hot 的数据和代码；像 column-sum 这类代码完全利用不到缓存，对缓存不友好。

再往外是 SSD 和本地文件，模型权重就存在文件里。把权重拉到内存也是一种缓存。读文件时可以根据特点做预取：一次读一个字节时把一条 cache line 读上来，就是一种预取；读文件也一样，虽然每次只用 read 接口读 4 KB，但可以在搬运时一次搬更大的块，因为读模型权重时大概率会把所有权重都读上来。这些都是 policy 上的设计。

### 分布式存储与各层缓存

**43:50**

单机存储容量有限，容量不够时可以借用远端机器的存储空间，做分布式文件系统，或分布式 key-value store、分布式数据库。把远端数据拿到本地使用时，本地需要有 cache，而本地容量有限。比如有 1 PB 数据，本地只有 1 GB 内存可用作缓存，自然要把最 hot 的数据留在本地，甚至要提前猜一猜接下来会从哪里取数据，做一些预取。这些都是 memory hierarchy 下要考虑的事情。

缓存会发生每一个阶段、每一层。有些必须用硬件实现，因为软件实现无法那么高效；下面一些层则完全可以用软件实现。有了大模型以后，还可以考虑把预取策略做得更好。以前硬件的预取策略都很简单；今年体系结构的一个顶会上有一篇论文做的是 LM prefetch，讨论能否用 LM 指导硬件的预取实现，以及怎样做软硬件协同的硬件缓存。

### 缓存块与教材顺序

### 块大小的取舍

**49:26**

关于块大小：块越大，miss 次数不会更多，但最后仍是一个 trade-off；块大小和软件编程方式有关，需要结合程序的访问模式来看。

### 块大小与预取

**49:41**

按行访问时，块越大，miss rate 确实可以降低；但如果采用前面讲的按列访问，块变大可能也没有用。后面还会讲怎样写出 cache-friendly 的代码。现代 CPU 的块大小可能到 256 字节左右，常见设计是 128 或 256，一个 cache block 大概是 64 字节；现在通常是 64 字节，并且一般会预取。比如预取两个到 128，预取四个就是 256，大体如此，这些也有 trade-off。

### 冲突缺失与地址字段

**50:22**

什么时候会出现冲突缺失（conflict miss）？例如两个地址、两个 memory block 映射到同一个 set，而同一个 set 中能容纳的块数有上限，这时就会发生 conflict。地址通常分成 tag \(t\)、中间的组索引和最后的块偏移量。访问时不是先决定访问哪个组，再比较 tag，最后看偏移吗？为什么不按这个顺序来写地址？先想一下：块偏移一定在最下面，不能随便放。这个顺序很重要；想清楚块偏移为什么不能动，就知道剩下的 set index 和 tag 这两个字段可以互换。

### 组索引为什么放在中间

**52:11**

学生问：这里的地址是不是数组从零开始的那个地址，它不一定是零吧？老师说明，这里讲的是绝对地址；CPU 访问内存时只有一个地址，它不知道这是数组还是别的对象。另一个问题是：为什么用中间位做组索引（set index）？

再以 block size 为 4 个字节为例。地址 0、1、2、3 的块内偏移分别是 0、1、2、3；下一块的真实内存地址是 4、5、6、7，但把它看成一个 cache block 时，块内偏移仍然是 0、1、2、3。也就是说，两个块中对应的地址只有最低两位相同：\(0000\) 和 \(0100\) 的块内偏移都是 0，\(0001\) 和 \(0101\) 的块内偏移都是 1。块大小是多大，最低的多少位就决定块内偏移，所以块内偏移一定由最低的若干位表示。确定块偏移后，这一部分就不动了，剩下的是 set index \(s\) 和 tag \(t\)，这两个可以互换。把 set index 放在中间有好处：相邻的两个 cache block 的 set index 会不同，例如一个是 0，一个是 1，于是它们会被散落到 cache 的不同组中。越相邻的 cache block 被散落到不同组，就越能充分利用 cache。如果相邻的 cache block 全都塞到一个组里，就会发生 conflict。因此用中间位做 set index，剩下的高位就是 tag。
