同学们好，这节课继续介绍剩下的几个 Lab。如果上一节课的环境配置还有问题，可以在过一会儿的 Lab 实践环节处理；遇到什么困难也都可以来问我。这节课先从 Mini CPU 这个 Lab 讲起。这个 Lab 过一段时间就要计分，所以后面会有 deadline。

### 从 printf 看程序如何工作

**07:23**

在这之前有一个前置知识。大家在上这门课之前，很可能已经上过 C++ 和数据结构，可能会写一个最简单的程序：最开始写一个 `std::cout`，输出 `Hello World`；在 C 里面则使用 `printf`。如果在 `printf` 里面打印一行语句，比如程序就是 `printf("Hello World")`，那么这个时候这个程序到底做了什么样的事情？`printf` 到底是怎么输出到屏幕上的？

这个内容在 ICS 后续课程里面也会介绍。但在这里，因为过一会儿要给大家讲解这个框架，所以也稍微提一下。

**08:20**

`printf` 本质上是 libc（C 标准库）中的一个函数。你的程序只是使用了先前开发者已经内置好的函数；`printf` 本身并不在程序里，而在系统某个文件中。运行可执行程序时，程序会到系统中找到这个预置的库并执行相应函数，于是就能使用库中预置的功能。

**09:07**

libc 中的 `printf` 最里面调用 `write` 函数，而 `write` 在汇编中通过一条 `syscall` 指令实现。`syscall` 是特权指令，会把控制流从用户态程序交给操作系统内核。因为要在屏幕上显示一行文字；如果所有程序都能完全操控屏幕，那么现在使用的操作系统上很可能已经满屏都是广告了。因此 `syscall` 要把控制流交给操作系统，由操作系统执行。

### 实验框架中的输出

**09:51**

在实验框架中，例如 `guest hello`，我们使用 `puts` 函数。如果仍然使用 `printf`，执行器中没有系统提供的库，也没有 libc 提供的函数。执行程序时找不到 `printf`；前面学过汇编中调用函数要 `call` 一下，但这里没有这个函数，程序就无法正常运行。因此在框架中通过 `syscall` 直接写一条系统调用指令，也就是把 `syscall` 内置进来，不再使用系统的那一个函数。所以这里打印使用 `puts`、`putint` 等。查看 lab 的 guest 文件夹，会看到里面有很多这种程序。若想自己写一个程序并最终在 mini CPU 中运行，需要注意：不能使用 libc 中的函数，包括 `malloc`、`printf`、`sscanf` 等。

### 直接执行与代为执行

**11:41**

`syscall` 指令如果直接在 CPU 上执行，例如前面的 hello world 程序直接在 CPU 上跑，代码肯定要被加载到计算机或 CPU 中。左边是 `guest hello` 的机器码，可以看到它直接调用了 `syscall`。如果该程序直接在 CPU 上运行，当 IP 指向 `syscall` 时，系统 CPU 发现要执行 `syscall`，就会主动把控制流交给操作系统。但在 mini CPU 框架中模拟执行时，我们会读取 `guest hello` 并代为执行；`syscall` 是特权指令，不能直接模拟。例如要把字符串输出到屏幕，我们只是读到了 `syscall`，它还没有由 CPU 执行。因此在 mini CPU 的机器码中采用代为执行的方式：发现程序调用了 `syscall`，就主动调用 libc 里的 `syscall`，帮它实现这个操作。这里需要特别注意程序到底运行在什么上面。`guest hello` 编译出的二进制可以直接运行，也可以直接在你们现在的操作系统上通过 `./hello` 运行，也可以在 mini CPU 上运行；但直接在机器上运行和在 mini CPU 上运行逻辑不一样。mini CPU 做的是代为执行：它发现那里有 `syscall`，就执行一下 `syscall`，最后把输出送到终端，于是能看到 hello world。

### 内存与寄存器的模拟

**13:54**

关于内存和寄存器：前面讲过指令要对寄存器操作，一些数据存在内存里、存在栈上。mini CPU 中如何模拟内存？直接开一个大数组代表程序的内存。指令、代码、其他数据以及栈都放到这个数组里。大家不用关注这些细节，只需做指令执行操作；例如代码里拿到指针要读数据，直接解析、直接读即可。但仍希望大家了解内存是什么：内存本质上应由操作系统管理，应用应该见不到它；现在由我们主动管理内存，需要理解 guest 程序如何使用它。寄存器同样开一个数组，因为寄存器是 64 位的；用一个大数组表示寄存器，每个寄存器按位置取即可。CPU 上寄存器少，是因为寄存器很金贵，增加寄存器代价很高，需要投入更多钱让电路更复杂。这里的寄存器在内存中，所以可以不必那么局限，可以开很多；如果想探索，开几百个寄存器也可以。

**16:00**

mini CPU 主要做的事情，就是让 CPU 执行程序。CPU 执行程序时，把 PC/IP 指向起始指令，可以理解成指向 `main` 函数；实际上 `main` 之前还有一些别的函数，这里先不管。

### 模拟 CPU 的执行循环

**16:29**

CPU 的 PC 指向 `main` 函数后，程序开始执行。CPU 不断取一条指令、执行这条指令，然后根据这条指令的操作去修改状态：可能给寄存器赋值，可能给内存赋值，也可能从寄存器或内存中取值。执行完后继续往下走，本质上就是程序逻辑顺序向下执行；遇到控制流变化时，再切换到别的控制流。因此，CPU 执行程序本质上就是一个很大的循环。

模拟执行也采用同样的结构。外层是一个 `while` 循环，循环条件是 CPU 还没有停下来，也就是还没有执行到最终停下来的那条指令。后面还有一些指令计数之类的内容，主要是防止代码出现死循环，这里不用管。只要 CPU 还没有停，就继续往下执行。

每轮循环中，首先调用 `x86_begin`，表示开始解析一条指令。然后进入一个很大的 `switch`，判断这条指令到底是什么指令、要执行什么操作。操作执行完后，最后进行一次 `end` 操作。`end` 里面具体做什么这里不用管，它会做一些异常处理，这部分会在后面学习 CPU 异常相关内容时讲到。

### x86 指令格式与解析流程

**18:13**

x86 指令到底怎样读取？这是一个非常复杂的过程，也是这个 lab 比较麻烦、比较难的地方。x86 指令集专门写了一段伪代码，告诉大家怎样解析。上面给出的是 x86 指令的基本格式：首先有一个前缀，然后有一个 REX 字节，然后有一个操作码；这个操作码才是上课讲到的指令操作码。后面还有 ModRM 字节、SIB 字节——大家现在还不知道它们是什么。偏移是进行内存寻址时的偏移，后面还有立即数，也就是 IMM。

读取流程大致如下：首先看前缀，判断是什么前缀并记录下来；然后看有没有 REX 字节；再往后读到操作码。到伪代码中 `OP` 这一步，操作码就读完了。前面的部分是非常复杂的操作，不需要大家处理，前面的 `x86_begin` 会帮大家把 `OP` 解释完成。所以大家只需要知道，在得到操作码之后，要怎样处理这条指令。

如果操作码告诉你说它带有 ModRM，因为 ModRM 可能没有，也可能占一个字节，接下来就去读 ModRM；然后由 ModRM 告诉你有没有 SIB，接下来再读 SIB；后面再读 displacement 和 immediate。这些都由中间的配置决定。

### REX 字节与向后兼容

**20:33**

大家肯定会有疑问：为什么 x86 指令集这么麻烦？因为 x86 是使用最广的指令集，最早的时候就已经在使用。后来电脑越来越复杂，机器一开始可能是 16 位，后来从 16 位变成 32 位，到现在变成 64 位。

以前有很多从 16 位和 32 位程序编译出来的程序，想在 64 位机器上运行，这就很麻烦：指令集要怎样设计，才能保证以前的程序在现在的机器上也能运行？这里举一个例子，不是重点。REX 字节中有一位规定，这条操作使用的是 64 位寄存器还是 32 位寄存器。很容易想到，REX 字节在 64 位机器出现之前应该是没有的；没有 REX 字节时，默认使用 32 位寄存器。所以指令直接从操作码开始，后面这一连串就是以前 32 位机器使用的格式。后来在前面补了一个 REX 字节。如果 REX 字节中某一位规定需要使用 64 位寄存器，就把这条指令改成 64 位的。x86 就是通过这种修修补补的方式，让指令集变得越来越复杂、越来越庞大。

这也是为什么 CSAPP 书上使用的是 CSAPP 作者自己设计的 Y86 指令集，它能让指令变得更简单。但之前很多同学反馈，讲 Y86 指令集没有什么必要，也没有什么实用性。所以今年相当于做一次试点，把指令集改成 x86。但改成 x86 之后，lab 变得很复杂。如果同学们有意见，到时候可以反馈，后面也会持续改进这个 lab。

**23:04**

下面简单看一条指令的字节，也就是一条指令由哪些字节组成。上面这些是从 x86 中随便挑的一些指令。大家肯定看不懂，先不用管，主要先了解怎样对一条指令进行解析。

常规解析流程如下。比如第一条指令 `add`，它把一个内存中的数加到 `r8` 上。这条指令怎样解析？首先由 `x86_begin` 把操作码解析出来。`x86_begin` 会把 `4c` 和 `03` 都解析出来，然后从解析出的数据中可以得到：这是一条 `add` 指令，操作码 `03` 应该是 `add` 的一种形式。从前面解析操作码的过程中，还能得到 REX 字节是 `0x4c`；后面大家会知道这个规则，即 REX 代表什么。同时还会得到一个 `x.size` 等于 8，表示寄存器大小是 8 字节，也就是 64 位寄存器，应该对 `r8` 执行。这里是 `r8`，而不是 `r8d`；`r8d` 是 32 位的，所以这条指令直接对 `r8` 执行。

### 操作码 03 与 ModR/M 字节

**24:33**

这里得到的寄存器是 8 位的。接下来的操作码 `03` 是 `add` 的一种形式；自己实现时，可以查文档或看 README。README 里尽量列出了相关内容，但列得很复杂，中间解析过程比较繁琐、枯燥，最好多和 AI 讨论。可以自己先试着写一两条，剩下的再交给 AI 完成。

操作码 `03` 表示“寄存器加上 r/m”，其中 r/m 是 register or memory，也就是另一个操作数可能是寄存器，也可能是内存。它究竟是哪一种，由接下来的 ModR/M 字节决定。ModR/M 从字面上可以理解为对 register or memory 的修饰。

知道操作码是“寄存器加 r/m”之后，就必然要读取 ModR/M 字节。因此代码接下来调用读取 ModR/M 的函数，完成这一步后，表示当前 x86 指令的 `x` 中一些成员会被赋值。例如这里解码得到 `x.register = 8`，即第一个寄存器使用 8 号寄存器，在 x86 中就是 `r8`；而 `x.rm = -1`，表示另一个操作数不是寄存器，而是内存。

### 内存操作数与 ALU 运算

**26:52**

既然 `x.rm = -1`，就说明它是内存操作数，需要继续往下读。由于是内存操作数，后面必然有 SIB 字节。于是先读出 r/m 的相关信息，再把剩余的内存操作数部分取出来。`RM get` 会根据成员判断当前是寄存器还是内存，并据此取值；这里发现它是一个地址，又因为 `x.rm = -1`，就把该地址处存放的值取出来，放到 `b` 中。接下来调用 x86 ALU 进行运算，这样就把这个加法完成了。

这个过程看起来比较简单，但每一步都是一条 x86 解析规则；只有对规则非常熟悉，才能把整套逻辑自己完整写出来。因此，写这一部分时推荐多和 AI 交流。除了 `interpretation.c` 这一部分，其他部分还是希望大家先尝试用“古法编程”的方式自己完成。

### ModR/M 的作用

**28:28**

接下来介绍 ModR/M 和 SIB 字节各自做了什么。x86 指令中这一环不可或缺，同时也是本次任务的一个 part；介绍完之后，希望大家把这个 part 完成。

ModR/M 首先规定：本次运算的一个操作数是寄存器，另一个操作数是内存还是寄存器。判断要看 mod 字段：如果 mod 是 `11`，就代表 r/m 是寄存器；如果是 `00`、`01`、`10`，就说明另一个操作数在内存中，并且带有一定的偏移。因此需要构建一个非常精密的流程图。至于后面 r/m 等字段分别代表什么，大家自己去看；这里只需要知道，ModR/M 规定了当一个操作数是寄存器时，另一个操作数应该是寄存器还是内存。

如果另一个操作数在内存中，那么 x86 的内存地址会有偏移、基址、变址，再加一个 scale。scale 是常数，可取 1、2、4、8。要构造这个四元组，就需要更多信息，因此存在 SIB 字节。

### SIB 字节

**30:12**

SIB 的名字来自 scale、index、base。它规定 scale 的比例因子，index 是变址寄存器，base 是基址寄存器。scale 占前两位，也就是高的两位；index 表示用哪一个变址寄存器；base 表示基址寄存器，它们都是内存寻址中用到的寄存器，最后得到内存操作数。内存地址由 displacement 偏移、base 基址寄存器、index 变址寄存器乘 scale 相加得到：\[ \text{地址} = \text{displacement} + \text{base} + \text{index} \times \text{scale} \]。SIB 字节后面还可能跟立即数；有时偏移是一个很大的值，会跟在 SIB 字节后面，还需要把这个立即数读出来。

然后就到了 REX 前缀。前面提到 REX 字节做了一些修补，它修补了哪些东西？

### REX 前缀与寄存器扩展

**31:39**

REX 字节的高四位没有任何含义，低四位分别代表不同含义。`REX.W` 表示操作数是不是 64 位：如果为 1，操作数就是 64 位；如果为 0，就是 32 位或更小。`REX.R` 给 ModR/M 中的 register 字段补第 4 位，因为该字段本身只有 3 位。

为什么会有这种情况？还是为了兼容性。在 32 位时代，没有 `r8` 及以后的寄存器，只有前面的 8 个寄存器；那时用 3 位就能表示所有寄存器。引入新寄存器之后，既要能够表达新寄存器，又要兼容旧指令，所以需要 REX 前缀来扩展这些字段。

### REX 扩展位与 ModR/M 解码

**32:51**

前面在 REX 前缀中引入了第四位的概念。REX.R 会给 `reg` 字段的三位补上第四位：R 为 1 时，对应 r8、r9、r10 等扩展寄存器；R 为 0 时，仍使用原来的八个寄存器。REX.X 给 `index` 补最高位，X 为 0 时 index 落在原来的八个寄存器范围内。REX.B 则视情况给 `rm` 或 SIB 中的 `base` 补高位。因此不同字段的扩展方式并不相同，ModR/M 的解析还是比较复杂的。课件下面列了一些例子，可以自己对照理解。

### `modrm_decode` 的入口

**33:55**

接下来要实现的部分，是解析 ModR/M 字节。这里有一个需要大家实现的函数 `modrm_decode`。它的第一个参数 `p` 是一个指向字节的指针，表示当前指令解析到的位置，相当于当前 RIP 所对应的位置。执行完 `x86_begin` 之后，`p` 应当指向操作码的后一位；对照前面的图，这个位置正好是操作码后面的 ModR/M 字节。如果根据操作码判断出当前指令带有 ModR/M 字节，就会进入这个函数，并把 ModR/M 第一个字节的地址传给 `p`。

### 寄存器操作数

**34:53**

进入函数后先读第一个字节，也就是 `p[0]` 处的 ModR/M 字节。读出后判断 `mod` 这两位是不是 11。如果是 11，说明另一个操作数是寄存器。此时把另一个寄存器的编号填好，再把基址、变址等字段都置为 -1，把比例因子 `scale` 置为 1，然后直接返回即可。

### 内存操作数与 SIB

**35:31**

如果 `mod` 不是 11，也就是不等于 3，操作数就必然是内存操作数。对于内存操作数，结构体里的 `rm` 字段不再表示寄存器编号，可以先置为 -1；解码时再根据 r/m 位判断后面的基址、变址如何取，也就是判断当前属于哪种寻址方式。课件这里给了一个流程图，大家需要按照流程图实现 ModR/M 字节的解码过程：后面要判断有没有 SIB 字节；没有 SIB 字节时如何解析，有 SIB 字节时又如何读出基址和变址。

### `modrm_t` 的字段

**36:12**

最后要把读到的信息全部赋给 `modrm_t` 结构体，这个函数的主要任务就完成了。`modrm_t` 中首先有最基本的 `mod`；还有 `reg` 和 `rm`，它们对应前面看到的 ModR/M 字节中的字段。`sub` 也是 `reg` 字段，在某些操作数中用来表示运算类型或操作码扩展。因此 `sub` 和 `reg` 本质上相同，只是 `reg` 还会加上 REX.R 作为第四位，而 `sub` 没有第四位。后面还有 `base`、`index`、`scale`，它们描述内存寻址方式；`rip` 字段表示是否采用相对寻址；`disp_size` 表示偏移量的大小；`disp` 则是后面要读取的偏移值。

### 调用关系与实现要求

**37:24**

这些字段由 `modrm` 这个函数负责填写。`modrm` 内部会调用 `modrm_decode`，把值都填好之后，最终应用到指令 switch 的各个 case 中。例如前面的某个 case 发现需要读 ModR/M，就调用 `modrm`；`modrm` 再调用我们实现的 `modrm_decode`，把各个字段赋好，供后续函数正常使用。因此实现 `modrm_decode` 时，主要就是严格按照这个流程图来写。如果实在不清楚原理，也可以先按照流程图实现；这些内容偏记忆性，原理不必过度深究。这部分先跳过。

### 按流程图走一遍解码

**38:33**

接下来看 ModR/M 这一部分具体怎么做，也就是在 `modrm_decode` 函数中如何遵循刚才的流程图。首先把 `p` 指针指向的第一个字节读出来，记为 `b`。读出之后，按照流程图的第一步，先把 `mod`、`sub`、`reg` 填好：`sub` 就是 `reg` 字段本身；`reg` 还要把 REX.R 作为第四位组合进去，因为 REX.R 代表寄存器编号的第四位。然后把 `base`、`index`、`scale` 等字段设置成默认值，后面需要判断时再改成实际值。

首先判断 `mod` 是不是 11，也就是 `mod` 是不是 3。如果是 3，说明当前是在做寄存器操作；此时把 `rm` 直接赋成寄存器编号，这个编号的第四位由 REX.B 给出。结束之后直接返回当前读了多少个字节，也就是告诉调用者要把指针往后移动多少位。如果 `mod` 不是 11，就说明它是内存操作数，后面再按流程图继续解析 SIB、基址、变址和偏移。

### 解析内存操作数

**40:59**

对于内存操作数，先把 r/m 赋成 -1，再把与内存操作数有关的参数写进来。因为它是内存操作数，还需要读取 SIB 字节：先判断是否存在 SIB 字节，继续读下一位并读取 SIB，让指针 p 自增，再继续读取后面的字段。接着取出 index 和 scale，再取出 base，然后根据相应规范判断应该按什么规则取值。取出来之后，还要另外判断是否为 RIP 相对地址；这里直接给 base 赋值。最后要根据前面得到的信息处理，例如根据 mod 的取值决定后续操作：mod 表示后面偏移量的长度，可能是 0、1 或 4 字节，因此这里还要对 mod 做判断，并给 dsize 赋值。dsize 赋值之后，再读出 displacement，也就是偏移量；四字节偏移使用 memcpy 读取，一字节偏移则读取一字节。最后返回总共读取的字节数，也就是 i 加上 dsize，这样这个函数就完成了。这个函数基本上是一些比较琐碎的底层工作，但希望大家练习字节解析操作，所以还是把这一部分拿出来了。

### `chat_turn` 与 304 字节缓冲区

**21:16**

在一轮对话中，程序会调用 `chat_turn` 函数。每一轮的输入都会记录在某个缓冲区、某个数组里，然后作为输入交给模型推理，最后得到模型要回复的内容。

在 `chat_turn` 函数里，查看二进制码可以看到它肯定会做 `sub` 操作，因为它有一个存放 prompt 的缓冲区。它会先对 `rsp` 做减法，把缓冲区开辟出来，然后往里填字节，这部分字节再作为输入交给后面推理。在这个例子里，缓冲区是 304 个字节，也就是存放 prompt 的数组大小为 304。

### 覆盖返回地址

**22:20**

那么怎样进行一个简单的缓冲区溢出？这里有一个缓冲区，我们往里面写入字节，比如先随意写一些字节，然后向上填充几十个字节。继续填充把整个缓冲区填满。这里为什么用 `0x41`？因为 `0x41` 是大写字母 A，反正都是可以输入的。把它填满之后，如果模型要进行推理，它会把整个缓冲区拿去作为推理输入。

如果继续往上填，越过缓冲区，会看到它先 `push rbp` 保存 RBP；再往上就是保存的返回地址。如果把返回地址覆盖掉，那么 `chat_turn` 函数执行完成、执行 `ret` 时，就会跳到被覆盖的返回地址。这个返回地址现在填到了哪里？填在缓冲区的起始位置。所以当函数返回时，指令指针会直接跑到栈上，开始执行栈上的内容。

### 从危险攻击到实验目标

**23:54**

如果栈上输入的这些值实际上是一些代码，那么 CPU 就会把输入的代码拿来执行。这里可以做非常危险的事情：比如写一个 fork 炸弹把服务器卡死，或者写点别的，直接让服务器删除根目录。因为控制流已经跑到这里，它就可以继续执行，这些都是非常严重的 bug。

但在这次实验里，我们不需要实现那么复杂的攻击。我们假设攻击目标是二进制里的一个函数，叫 `report_pass`。大家只需要让控制流转到这个函数，并且传入正确的参数，就认为这次攻击有效。前面随意输入的这些字节，实际上就是这样的代码。这是什么代码呢？

### Attack 1：无栈随机化与目标地址

### 构造溢出载荷

**29:47**

那么怎样做缓冲区溢出？可以看到前面的字节都是固定的一些字节，随便输入都可以，只要不输入结束符。因为输入会以回车作为结束符，敲了回车，本次输入就结束了。因此前面可以任意选择字符，这里选了大写 A。把缓冲区前面的所有字符全部覆盖之后，再加一个返回地址。这个返回地址就是接下来要执行的那段代码的位置。要找到这个返回地址，需要先找到缓冲区的位置。

### 定位 getbuf 的缓冲区

**30:41**

在 readme 里给出了 `getbuf` 函数。需要看 `gets` 传入的 `buf` 参数是从什么地方来的；在传进来的位置，它会通过 `sub rsp` 的方式开辟这个数组，因此可以找到它的位置。

最简单的是直接搜 `getbuf` 这个函数。可以搜到这个函数所在的位置。这个函数会被很多地方调用，也可以直接尝试搜这个地址，应该可以搜到。可以看到在 `getbuf` 这个函数里面，它每次会调用 `gets`。`gets` 的参数是什么？在这个地方，它通过 `mov %rax, %rdi` 把第一个参数传进去，也就是我们的 buffer。

RAX 是从哪里来的？可以看到它是 `rbp - 0x1c0`；再看上一行，是把 `rsp` 减去 `0x1c0`。所以 RAX 这个地址，或者说 RDI 这一步的地址，就是当前栈的最低点。由此可以得出返回地址在哪里。

### 用 GDB 查看运行时地址

**32:32**

我们怎么知道这个栈在哪里？一个方法是，因为这个栈没有做随机化，地址是固定的，所以可以直接在程序里找；但直接找比较麻烦，因此可以用 GDB 查看这个值在哪里。

可以看到是 `getbuf`，直接用 GDB 执行。和之前讲 Bomb Lab 一样，先打开 ASM 视图，然后看它的汇编。接下来既然要找到这个函数的调用点，就直接在 `getbuf` 这里打断点。执行之后，就直接到了 `getbuf` 函数这里。当前执行位置在这里。既然想知道 RDI，也就是传进去的栈，或者说 buffer 的地址，就往前步进几步。

现在刚好到了 `gets` 这一行，RDI 应该就是 buffer 的地址，直接打印一下。通过 `info registers` 的方式查看。

### 定位 buffer 与返回地址

**34:38**

在调试器中查看寄存器，可以看到 RDI 的值是一个以 `0x7fff` 开头、末尾为 `c7cf70` 的地址；这个地址就是传入的 buffer 的起始位置。函数在这里开辟的空间大小为 `0x1c0`。因此，把 buffer 起始地址与 `0x1c0` 相加，就得到数组结束的位置。

此外，函数入口还执行了 `push rbp`，所以从数组结束位置继续向上还要加 8 个字节，之后才到达返回地址。做这个实验时，填充完数组后要多填充 8 个字节，把保存的 RBP 覆盖掉，接下来才是返回地址。

返回地址可以有多种处理方式，核心是让它返回到一段能够执行我们代码的位置。例如，可以在 buffer 开头插入需要执行的代码，再让返回地址指回 buffer 的起始地址。起始地址就是 RDI，因为 buffer 的地址正是作为参数传进去的；把这个地址写到返回地址处即可。
